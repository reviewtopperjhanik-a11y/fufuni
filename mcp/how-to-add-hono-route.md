## Creating the Route File

All new API features in the Fufuni merchant backend must reside within the `apps/merchant/src/routes/` directory. By convention, the filename should represent the resource in lowercase (e.g., `tags.ts`, `products.ts`).

The framework uses `@hono/zod-openapi` to ensure that every route is not only type-safe but also automatically documented in the `openapi.json` definition. A new route file requires specific imports for environment types, database access, and error handling.

```typescript
// apps/merchant/src/routes/tags.ts
import { OpenAPIHono, createRoute } from '@hono/zod-openapi';
import { z } from 'zod';
import { ApiError, uuid, now, type HonoEnv } from '../types';
import { getDb } from '../db';
import { authMiddleware, adminOnly } from '../middleware/auth';
import {
  TagResponse,
  TagListResponse,
  CreateTagBody,
  ErrorResponse,
} from '../schemas';

// Initialize the public router (unauthenticated)
const publicApp = new OpenAPIHono<HonoEnv>();

// Initialize the admin router (authenticated)
const adminApp = new OpenAPIHono<HonoEnv>();
adminApp.use('*', authMiddleware);

export { publicApp as publicTags, adminApp as adminTags };
```

### Route Design Philosophy
Fufuni enforces a strict separation between public-facing endpoints (accessible via Public API keys `pk_` or unauthenticated) and administrative endpoints (requiring Secret API keys `sk_` or Auth0 JWTs). This is achieved by exporting two separate `OpenAPIHono` instances from every route file.

## Defining OpenAPI Routes

Never define Zod schemas inline within the route handler. All request and response schemas must be imported from `apps/merchant/src/schemas/`. This ensures the OpenAPI documentation remains consistent and schemas can be reused across the frontend and backend.

To define a route, use the `createRoute` function. This metadata object describes the HTTP method, path, tags for documentation, and the structure of requests and responses.

```typescript
const listTagsRoute = createRoute({
  method: 'get',
  path: '/',
  tags: ['Tags'],
  summary: 'List all product tags',
  responses: {
    200: {
      content: { 'application/json': { schema: TagListResponse } },
      description: 'A list of tags used across products',
    },
    500: {
      content: { 'application/json': { schema: ErrorResponse } },
      description: 'Internal server error',
    },
  },
});
```

### Handling the Request
After defining the route metadata, register it on the appropriate app instance using the `.openapi()` method. This method provides a type-safe context `c` where parameters and body content are validated against the schema.

**Verified Fact:** You must never use `c.req.json()` directly. Always use `c.req.valid('json')` or `c.req.valid('param')` to access validated data.

## Database Interaction and Error Handling

Fufuni uses a thin abstraction over Durable Objects SQLite. The `getDb` helper provides a clean interface for executing SQL commands.

- Use `db.query<T>(sql, params)` for `SELECT` statements. It returns an array of results.
- Use `db.run(sql, params)` for mutations like `INSERT`, `UPDATE`, or `DELETE`. It returns an object containing the number of changes.

```typescript
publicApp.openapi(listTagsRoute, async (c) => {
  // Obtain the database helper from the Hono context
  const db = getDb(c.var.db);
  
  try {
    const rows = await db.query<any>(
      `SELECT DISTINCT tag_name FROM product_tags ORDER BY tag_name ASC`
    );
    return c.json({ items: rows }, 200);
  } catch (error) {
    // Standardized error throwing
    throw ApiError.internalServerError(
      error instanceof Error ? error.message : 'Failed to fetch tags'
    );
  }
});
```

### Using ApiError
The `ApiError` class is the standard way to return non-200 responses. Throwing an `ApiError` ensures that the global error handler in `index.ts` catches it and formats a consistent JSON envelope: `{ error: { code, message, details } }`.

| Static Method | Status Code | Use Case |
| :--- | :--- | :--- |
| `ApiError.badRequest(msg)` | 400 | Invalid input data or logic error. |
| `ApiError.unauthorized()` | 401 | Missing or invalid authentication. |
| `ApiError.forbidden()` | 403 | Authenticated but lacks required permissions. |
| `ApiError.notFound(msg)` | 404 | Resource does not exist in the database. |
| `ApiError.conflict(msg)` | 409 | Duplicate handle, SKU, or email. |

## RBAC Guards and Middleware

When building the `adminApp` portion of your route, you must apply Role-Based Access Control (RBAC). Guards are imported from `../middleware/auth` and passed as the `middleware` array in `createRoute`.

### Available Guards
- `adminOnly`: The standard guard. Requires the `admin:store` permission (usually assigned to store managers).
- `superAdminOnly`: Highest level access for system configuration.
- `databaseAdminOnly`: Required for routes that perform direct DB maintenance or raw SQL execution.
- `aiAccessOnly`: Required for interacting with the AI translation or generation features.
- `mailAccessOnly`: Required for manual email triggering or mail server configuration.
- `validJwtAuthOnly`: Ensures a valid Auth0 token is present but does not check for specific admin scopes (useful for customer-specific data).

```typescript
const createTagRoute = createRoute({
  method: 'post',
  path: '/',
  tags: ['Tags'],
  summary: 'Create a new global tag',
  security: [{ bearerAuth: [] }],
  middleware: [adminOnly] as const, // Apply the RBAC guard here
  request: {
    body: {
      content: { 'application/json': { schema: CreateTagBody } },
    },
  },
  responses: {
    201: {
      content: { 'application/json': { schema: TagResponse } },
      description: 'Tag created successfully',
    },
    403: {
      content: { 'application/json': { schema: ErrorResponse } },
      description: 'Forbidden: Admin access required',
    },
  },
});
```

## Registration in index.ts

After creating your route file, you must register the exported apps in `apps/merchant/src/index.ts`. The order of registration is critical because Hono matches routes sequentially.

1. **Public Routes:** Register these **before** any global authentication middleware is applied. Use a specific path prefix like `/v1/my-feature`.
2. **Admin Routes:** Register these in the admin section of the file.

```typescript
// apps/merchant/src/index.ts

// 1. Import your new routes
import { publicTags, adminTags } from './routes/tags';

// ... (CORS and DB setup)

// 2. Register Public Routes (before auth)
app.route('/v1/tags', publicTags);

// 3. (Optional) Register KV Cache
// Only do this for high-traffic public read endpoints.
app.use('/v1/tags', kvCacheMiddleware);

// ... (Auth middleware is usually applied globally to /v1/* elsewhere or inside specific routers)

// 4. Register Admin Routes
app.route('/v1/tags', adminTags);
```

**Verified Fact:** The `kvCacheMiddleware` should be applied to routes that serve public data to increase performance. Mutations on `/v1/categories` and `/v1/products` automatically trigger cache invalidation via `kvInvalidateMiddleware`, but for custom routes, you may need to add them to the invalidation chain in `index.ts`.

## Complete Worked Example: Tags API

This example demonstrates a complete implementation of a "Tags" feature, providing a public list of tags and an admin-only creation endpoint.

```typescript
// apps/merchant/src/routes/tags.ts
import { OpenAPIHono, createRoute } from '@hono/zod-openapi';
import { z } from 'zod';
import { ApiError, uuid, now, type HonoEnv } from '../types';
import { getDb } from '../db';
import { authMiddleware, adminOnly } from '../middleware/auth';
import {
  TagResponse,
  TagListResponse,
  CreateTagBody,
  ErrorResponse,
} from '../schemas';

const publicApp = new OpenAPIHono<HonoEnv>();
const adminApp = new OpenAPIHono<HonoEnv>();

// Admin routes require authentication
adminApp.use('*', authMiddleware);

// --- Public: List Tags ---

const listTagsRoute = createRoute({
  method: 'get',
  path: '/',
  tags: ['Tags'],
  summary: 'List all tags',
  responses: {
    200: {
      content: { 'application/json': { schema: TagListResponse } },
      description: 'List of tags',
    },
  },
});

publicApp.openapi(listTagsRoute, async (c) => {
  const db = getDb(c.var.db);
  try {
    const rows = await db.query<any>(
      `SELECT id, name, slug, color FROM tags ORDER BY name ASC`
    );
    return c.json({ items: rows }, 200);
  } catch (error) {
    throw ApiError.internalServerError('Failed to fetch tags');
  }
});

// --- Admin: Create Tag ---

const createTagRoute = createRoute({
  method: 'post',
  path: '/',
  tags: ['Tags'],
  summary: 'Create a tag (admin)',
  security: [{ bearerAuth: ['admin:store'] }],
  middleware: [adminOnly] as const,
  request: {
    body: {
      content: { 'application/json': { schema: CreateTagBody } },
    },
  },
  responses: {
    201: {
      content: { 'application/json': { schema: TagResponse } },
      description: 'Tag created',
    },
    409: {
      content: { 'application/json': { schema: ErrorResponse } },
      description: 'Tag slug already exists',
    },
  },
});

adminApp.openapi(createTagRoute, async (c) => {
  const { name, slug, color } = c.req.valid('json');
  const db = getDb(c.var.db);

  try {
    // Check for existing slug
    const [existing] = await db.query<{ id: string }>(
      'SELECT id FROM tags WHERE slug = ?',
      [slug]
    );
    
    if (existing) {
      throw ApiError.conflict(`Tag with slug "${slug}" already exists`);
    }

    const id = uuid();
    const timestamp = now();

    await db.run(
      `INSERT INTO tags (id, name, slug, color, created_at, updated_at)
       VALUES (?, ?, ?, ?, ?, ?)`,
      [id, name, slug, color ?? '#000000', timestamp, timestamp]
    );

    const [newTag] = await db.query<any>('SELECT * FROM tags WHERE id = ?', [id]);
    return c.json(newTag, 201);
  } catch (error) {
    if (error instanceof ApiError) throw error;
    throw ApiError.internalServerError('Failed to create tag');
  }
});

export { publicApp as publicTags, adminApp as adminTags };
```

### Implementing Mutations with `db.run`
Note the use of `db.run` in the creation endpoint. Unlike `db.query`, which returns rows, `db.run` returns execution metadata. To return the newly created object to the client, you must perform a subsequent `SELECT` query using the ID generated via the `uuid()` helper. This pattern ensures the client receives the object exactly as it exists in the database (including default values or generated timestamps).
