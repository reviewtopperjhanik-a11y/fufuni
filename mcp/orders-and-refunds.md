## Order Lifecycle and Statuses

In Fufuni, an order progresses through a defined set of statuses that synchronize the backend state with the customer's frontend experience. These statuses are defined in the database migrations and mapped to specific visual cues in the merchant dashboard and customer tracking pages using HeroUI components.

### Core Statuses and Visual Mapping

Fufuni utilizes seven primary statuses. Each status is associated with a specific HeroUI `Chip` color variant to provide immediate visual feedback to administrators and customers.

| Status | Meaning | HeroUI Color |
| :--- | :--- | :--- |
| `pending` | Order created but payment not yet confirmed. | `warning` |
| `paid` | Payment confirmed via Stripe. | `success` |
| `processing` | Merchant is preparing the items for shipment. | `accent` |
| `shipped` | Order has left the warehouse; tracking info usually added. | `accent` |
| `delivered` | Customer has received the package. | `success` |
| `refunded` | Full amount returned to the customer. | `danger` |
| `canceled` | Order voided before fulfillment. | `danger` |

There is also an internal state `partially_refunded` used when an order has had a partial refund issued but remains active or fulfilled.

The following example demonstrates how to create a reusable `OrderStatusBadge` component using React 19 and HeroUI v3, leveraging the `ORDER_STATUS_COLORS` configuration.

      className={className}
      role="status"
      aria-label={`Order status: ${label}`}
    >
      {label}
    </Chip>
  );
};

## The Refund Process

Refunds in Fufuni are strictly "Stripe-first." This means the system never modifies the local database status or balance until the Stripe API confirms the refund was successfully initiated. This ensures that the merchant's financial records in Fufuni always mirror the actual flow of funds in the payment processor.

### Backend Workflow

When a refund is requested via `POST /v1/orders/:orderId/refund`:

1.  **Authorization:** The request is checked for `adminOnly` permissions and a valid Stripe secret key.
2.  **State Validation:** The order must be in a refundable state (`paid`, `processing`, `shipped`, `delivered`, or `partially_refunded`).
3.  **Stripe Interaction:** The `stripe.refunds.create` method is called using the `stripe_payment_intent_id` stored on the order.
4.  **Audit Trail:** A record is inserted into the `refunds` table containing the `stripe_refund_id`, reason, and notes.
5.  **Status Update:** 
    *   If `amount_cents` is less than `total_cents`, the order status becomes `partially_refunded`.
    *   If the refund is for the full amount, the status becomes `refunded`.
6.  **Side Effects:** Full refunds trigger the `order.refunded` webhook and dispatch an automated email to the customer.

### Implementation Logic

The following snippet shows the core logic for processing a refund within the Hono router.

```typescript
// apps/merchant/src/routes/orders.ts (Simplified logic)
import Stripe from 'stripe';
import { ApiError, uuid, now } from '../types';

async function processRefund(c: any, orderId: string, amountCents?: number, reason?: string) {
  const db = c.var.db;
  const stripe = new Stripe(c.get('auth').stripeSecretKey);

  const [order] = await db.query(`SELECT * FROM orders WHERE id = ?`, [orderId]);
  
  try {
    // 1. Trigger Stripe API
    const refund = await stripe.refunds.create({
      payment_intent: order.stripe_payment_intent_id,
      amount: amountCents, // If undefined, Stripe does a full refund
      reason: reason || 'requested_by_customer',
    });

    // 2. Log refund in local DB
    const refundId = uuid();
    await db.run(
      `INSERT INTO refunds (id, order_id, stripe_refund_id, amount_cents, status, created_at)
       VALUES (?, ?, ?, ?, ?, ?)`,
      [refundId, order.id, refund.id, refund.amount, refund.status, now()]
    );

    // 3. Update Order Status
    const isFull = !amountCents || amountCents >= order.total_cents;
    const newStatus = isFull ? 'refunded' : 'partially_refunded';
    
    await db.run(`UPDATE orders SET status = ?, updated_at = ? WHERE id = ?`, 
      [newStatus, now(), orderId]
    );

    return { success: true, stripeId: refund.id };
  } catch (err: any) {
    throw ApiError.stripeError(err.message);
  }
}
```

## Triggering a Refund

To trigger a refund from the Merchant Dashboard, the frontend must send a signed request to the Admin API. Fufuni uses Zod-OpenAPI schemas to validate the input, requiring an optional amount in cents, a reason code, and optional internal notes.

### Refund Reasons

Stripe (and Fufuni) support specific reason codes for refunds:
- `requested_by_customer` (Default)
- `duplicate`
- `fraudulent`

### Frontend Implementation Example

This React component uses HeroUI's `Modal` and `Button` to create a refund interface. It assumes the use of a standard `fetch` or a TanStack Query mutation.

```typescript
// apps/merchant/src/components/orders/refund-modal.tsx
import React, { useState } from "react";
import { Modal, ModalContent, ModalHeader, ModalBody, ModalFooter, Button, Input, Select, SelectItem, Textarea } from "@heroui/react";

interface RefundModalProps {
  isOpen: boolean;
  onClose: () => void;
  order: { id: string; total_cents: number; currency: string };
  onSuccess: () => void;
}

export const RefundModal: React.FC<RefundModalProps> = ({ isOpen, onClose, order, onSuccess }) => {
  const [loading, setLoading] = useState(false);
  const [amount, setAmount] = useState(""); // empty = full refund

  const handleRefund = async () => {
    setLoading(true);
    try {
      const response = await fetch(`/v1/orders/${order.id}/refund`, {
        method: "POST",
        headers: { "Content-Type": "application/json" },
        body: JSON.stringify({
          amount_cents: amount ? Math.round(parseFloat(amount) * 100) : undefined,
          reason: "requested_by_customer",
          notes: "Processed via merchant dashboard"
        }),
      });

      if (!response.ok) throw new Error("Refund failed");
      
      onSuccess();
      onClose();
    } catch (error) {
      console.error(error);
      alert("Error processing refund via Stripe.");
    } finally {
      setLoading(false);
    }
  };

  return (
    <Modal isOpen={isOpen} onClose={onClose}>
      <ModalContent>
        <ModalHeader>Issue Refund</ModalHeader>
        <ModalBody>
          <p className="text-sm text-default-500">
            Total refundable: {(order.total_cents / 100).toFixed(2)} {order.currency}
          </p>
          <Input
            label="Partial Amount (Optional)"
            placeholder="e.g. 10.00"
            value={amount}
            onChange={(e) => setAmount(e.target.value)}
            type="number"
          />
          <Textarea label="Notes" placeholder="Reason for refund..." />
        </ModalBody>
        <ModalFooter>
          <Button variant="flat" onPress={onClose}>Cancel</Button>
          <Button 
            color="danger" 
            isLoading={loading} 
            onPress={handleRefund}
          >
            Confirm {amount ? "Partial" : "Full"} Refund
          </Button>
        </ModalFooter>
      </ModalContent>
    </Modal>
  );
};
```

## Public Order Tracking Security

Fufuni provides two ways for customers to view their order status without requiring a full user account. This is handled by the `publicApp` instance in `orders.ts`.

### 1. Stripe Session Lookup
Used immediately after checkout. The frontend redirects to `/success?session_id=CHECKOUT_SESSION_ID`. The backend provides a `lookupOrderBySession` endpoint.
- **Security:** Stripe Session IDs are long, high-entropy strings (64+ characters) that are effectively unguessable.
- **Exposure:** Returns order details but *never* exposes internal DB IDs or sensitive customer PII like plain emails.

### 2. Signed JWT Tokens
Used for long-term tracking (e.g., from an email link).
- **Security:** When an order is created, Fufuni generates a JWT containing the `orderId`. A hash of this token is stored in the `viewtoken` column of the `orders` table.
- **Verification:** The `getOrderByToken` endpoint verifies the JWT against the `ORDER_TOKEN_SECRET`.
- **Public access:** If the token is invalid, the API returns a generic `404 Not Found` to prevent account enumeration or discovery of valid order IDs.

  }
});
