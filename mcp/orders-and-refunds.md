## Order Lifecycle and Status Machine

Fufuni implements a strict state machine for orders to ensure financial and inventory integrity. The flow typically begins with a `pending` state (during Stripe checkout) and progresses through fulfillment.

```text
       [ Payment Failed ] <────────┐
               │                   │
               ▼                   │
          +---------+        +-----------+
          | pending |------->|  canceled | (Inventory Restored)
          +---------+        +-----------+
               |                   ^
        [ Payment Success ]        │ (Manual or API)
               │                   │
               ▼                   │
          +---------+        +-----------+
          |  paid   |------->|  refunded | (Full or Partial)
          +---------+        +-----------+
               |                   ^
               ▼                   │
          +------------+           │
          | processing |-----------┤
          +------------+           │
               |                   │
               ▼                   │
          +---------+              │
          | shipped |--------------┘
          +---------+
               |
               ▼
          +-----------+
          | delivered |
          +-----------+
```

### Valid Status Transitions
1.  **Paid**: The entry point for confirmed orders. Payment has been verified via Stripe Webhooks or manual test order creation.
2.  **Processing**: The warehouse has acknowledged the order and is preparing for shipment.
3.  **Shipped**: Tracking information (number and URL) is attached. At this stage, a `shipped_at` timestamp is recorded.
4.  **Canceled**: Only available for orders that haven't been shipped. Triggers an automatic inventory restoration.
5.  **Refunded/Partially Refunded**: Financial reversal via Stripe. Can occur at any post-paid step.

## Order Management API Reference

Admin endpoints require a Bearer token with `admin:store` permissions. Public endpoints use scoped tokens (JWT) or Stripe Session IDs.

| Method | Path | Auth | Description |
| :--- | :--- | :--- | :--- |
| `GET` | `/v1/orders` | `admin:store` | List all orders (supports `status`, `email`, and `cursor` pagination). |
| `GET` | `/v1/me/orders` | `customer` | List orders belonging to the authenticated customer. |
| `PATCH` | `/v1/orders/:id/status` | `admin:store` | Update the `status` of an order. |
| `PATCH` | `/v1/orders/:id/cancel` | `admin:store` | Cancel order and restore inventory. |
| `POST` | `/v1/orders/:id/refund` | `admin:store` | Initiate a Stripe refund (partial or full). |
| `GET` | `/v1/orders/:id/invoice` | `admin:store` | Generate a signed, short-lived (1h) URL for the PDF invoice. |
| `GET` | `/v1/orders/lookup` | Public | Look up order status using `stripe_checkout_session_id`. |
| `GET` | `/v1/orders/:id/status` | Public | Look up order status using a signed `viewtoken` (JWT). |

## Updating Order Status

Status updates are performed via the `adminOrders` router. When a status changes to specific values (e.g., `shipped`, `delivered`), the system automatically triggers transactional emails via Mailgun.

```typescript
// Example: Updating an order to 'shipped' with tracking info
import { hc } from 'hono/client';
import type { adminOrders } from '../routes/orders';

const client = hc<typeof adminOrders>('https://api.fufuni.com');

async function shipOrder(orderId: string, trackingNumber: string) {
  const res = await client.v1.orders[':orderId'].$patch({
    param: { orderId },
    json: {
      status: 'shipped',
      tracking_number: trackingNumber,
      tracking_url: `https://track.carrier.com/v1/${trackingNumber}`
    }
  }, {
    headers: { Authorization: 'Bearer sk_live_...' }
  });

  if (res.ok) {
    const order = await res.json();
    console.log(`Order ${order.number} marked as shipped at ${order.tracking.shipped_at}`);
  }
}
```

## Refund Flow and Stripe Integration

Refunds are processed through the `POST /v1/orders/:id/refund` endpoint. Fufuni supports partial refunds by specifying an `amount_cents` in the request body. If no amount is provided, a full refund is issued.

### Refund Side Effects:
1.  **Stripe API**: Calls `stripe.refunds.create` using the `stripe_payment_intent_id` stored on the order.
2.  **Refund Table**: Creates a new record in the `refunds` table for the audit trail.
3.  **Order Update**: If the total refunded amount equals or exceeds the order total, the status is set to `refunded`. Otherwise, it is set to `partially_refunded`.
4.  **Webhooks**: Dispatches an `order.refunded` event to registered webhooks.

```typescript
// Admin refund implementation snippet
adminApp.openapi(refundOrder, async (c) => {
  const { orderId } = c.req.valid('param');
  const { amount_cents, reason } = c.req.valid('json');
  
  const db = getDb(c.var.db);
  const [order] = await db.query<any>(`SELECT * FROM orders WHERE id = ?`, [orderId]);

  const stripe = new Stripe(c.get('auth').stripeSecretKey);
  const refund = await stripe.refunds.create({
    payment_intent: order.stripe_payment_intent_id,
    amount: amount_cents, // undefined = full refund
    reason: reason || 'requested_by_customer',
  });

  // Log refund in DB and update order status
  const isFullRefund = !amount_cents || amount_cents >= order.total_cents;
  const newStatus = isFullRefund ? 'refunded' : 'partially_refunded';
  
  await db.run(`UPDATE orders SET status = ?, updated_at = ? WHERE id = ?`, [newStatus, now(), orderId]);
  
  return c.json({ status: refund.status, amount: refund.amount }, 200);
});
```

## Order Cancellation and Inventory Restoration

When an order is canceled (`PATCH /v1/orders/:id/cancel`), the framework ensures that the stock levels in the `inventory` (or regional `warehouse_inventory`) tables are returned to their pre-purchase state.

### Restoration Logic
The cancellation handler iterates through all `order_items` and increments the `on_hand` count. If the framework is configured with regional warehouses, it restores stock to the specific warehouse that originally fulfilled the item (or uses priority logic if the record is missing).

```sql
-- Conceptual logic for inventory restoration during cancellation
-- 1. Identify items
SELECT sku, qty FROM order_items WHERE order_id = 'order-uuid';

-- 2. Restore inventory (Atomic update)
UPDATE inventory 
SET on_hand = on_hand + ?, 
    updated_at = ? 
WHERE sku = ?;

-- 3. Finalize status
UPDATE orders SET status = 'canceled', updated_at = ? WHERE id = ?;
```

## Order Item Immutability

One of the core architectural principles of Fufuni is the **Immutability of Captured Data**. When an order is placed, the state of the product is "frozen" within the `order_items` table.

### Why Immutability Matters
If a merchant changes the price of a "Blue T-Shirt" from €20 to €25 next week, the historical order from today must still reflect the €20 price for accounting and refund accuracy.

The `order_items` table captures the following at the moment of `paid` status:
- **`unit_price_cents`**: The exact price the customer paid.
- **`tax_rate` / `tax_amount`**: The tax calculation valid at the time of purchase.
- **`currency`**: The currency code (e.g., `USD`, `EUR`) associated with the region.
- **`title`**: The variant title at that specific time (useful if variants are renamed later).

### Table Schema (SQLite)
```sql
CREATE TABLE order_items (
  id TEXT PRIMARY KEY,
  order_id TEXT NOT NULL,
  product_id TEXT,    -- References product (may be null if product deleted)
  variant_id TEXT,    -- References variant
  sku TEXT NOT NULL,
  title TEXT NOT NULL,
  qty INTEGER NOT NULL,
  unit_price_cents INTEGER NOT NULL,
  tax_amount_cents INTEGER DEFAULT 0,
  currency TEXT NOT NULL,
  FOREIGN KEY (order_id) REFERENCES orders(id)
);
```

## Public Order Status Access

Fufuni allows customers to view their order status without creating a full account. This is handled via two distinct methods:

### 1. Stripe Session Lookup
After a successful checkout, Stripe redirects the user back to the storefront. The frontend uses the `session_id` to query the public `/lookup` endpoint. This is secure because Stripe Session IDs are high-entropy, non-guessable strings.

### 2. Signed View Tokens (JWT)
Transactional emails contain tracking links with a signed token.
- **Endpoint**: `GET /v1/orders/:id/status?token={JWT}`
- **Security**: The token is an HMAC-HS256 JWT signed using `ORDER_TOKEN_SECRET`. It contains the `orderId` in the payload. 
- **Verification**: The backend verifies the signature and then compares a hash of the token against the `viewtoken` column in the `orders` table to ensure it hasn't been revoked or regenerated.

```typescript
// Token verification logic in publicOrders app
try {
  // verifyOrderViewToken checks signature and expiration
  await verifyOrderViewToken(token, orderId, c.env.ORDER_TOKEN_SECRET);
  
  const tokenHash = await hashOrderToken(token);
  const [order] = await db.query(
    `SELECT * FROM orders WHERE id = ? AND viewtoken = ?`,
    [orderId, tokenHash]
  );
  
  if (!order) throw ApiError.notFound();
  // ... return limited order details
} catch (e) {
  throw ApiError.unauthorized('Invalid or expired tracking link');
}
```
