## Automation with Deploy Tenant Resources

The `deploy-tenant-resources.ts` script is a idempotent "one-shot" setup utility designed to bootstrap a fresh Auth0 tenant for the Fufuni framework. Instead of manually clicking through the Auth0 Dashboard to create Applications, APIs, and Roles, this script uses the Auth0 Management API to programmatically sync the environment state.

You should run this script:
1.  **Initial Setup:** When first connecting a new Auth0 tenant to a Fufuni project.
2.  **Schema Updates:** When adding new permission scopes or changing OAuth2 callback URLs.
3.  **CI/CD:** As part of a deployment pipeline to ensure the Auth0 configuration matches the codebase.

To execute the deployment, run the following command from the monorepo root:

```bash
# Ensure you have a .env file with Management API credentials
npm run auth0:deploy -- --env-file=.env.local
```

### Core Configuration Targets

The script automates the creation of four critical components:

1.  **SPA Application Client:** Configures a Single Page Application with PKCE (Proof Key for Code Exchange) enabled. It automatically sets `allowed_logout_urls`, `web_origins`, and `callbacks` based on your `STORE_URL`.
2.  **API Resource Server:** Defines the backend API in Auth0. It sets the `AUTH0_AUDIENCE`, configures `RS256` signing, and registers all functional scopes (permissions).
3.  **Social Connections:** Enables default social login providers like Google and GitHub for the SPA client.
4.  **The `authadmin` Role:** Creates a high-privilege role containing `admin:store` and `auth0:admin:api` scopes.

```typescript
// Example of how the script defines the SPA Client configuration
const clientConfig = {
  name: "fufuni-web-client",
  app_type: "spa",
  grant_types: ["authorization_code", "refresh_token"],
  callbacks: ["http://localhost:5173", "https://shop.fufuni.dev"],
  web_origins: ["http://localhost:5173", "https://shop.fufuni.dev"],
  token_endpoint_auth_method: "none", // Required for public clients (SPA)
  oidc_conformant: true,
  is_first_party: true,
};
```

## Environment Variables for Deployment

The deployment script requires specific credentials to communicate with the Auth0 Management API. These are distinct from the variables used by the frontend or the backend at runtime.

| Variable | Description | Source |
| :--- | :--- | :--- |
| `AUTH0_DOMAIN` | Your Auth0 tenant domain (e.g., `fufuni-prod.eu.auth0.com`) | Auth0 Dashboard |
| `AUTH0_TENANT` | The internal name of the tenant used for resource naming | Auth0 Dashboard |
| `AUTH0_MANAGEMENT_API_CLIENT_ID` | Client ID of a "Machine to Machine" application with Management API access | Auth0 Applications |
| `AUTH0_MANAGEMENT_API_CLIENT_SECRET` | Client Secret for the M2M application | Auth0 Applications |
| `AUTH0_AUDIENCE` | The unique identifier for your API (e.g., `https://api.fufuni.com/`) | Logic |
| `STORE_URL` | The base URL of your React frontend | Deployment |

### Example `.env.auth0` Configuration


## Adding a New Permission Scope

The Fufuni framework uses a centralized permission system. To add a new scope (e.g., `delete:products`), follow these four steps:

1.  **Modify the Script:** Add the new scope to the `scopes` array inside the `createOrUpdateResourceServer` call in `deploy-tenant-resources.ts`.
2.  **Sync with Auth0:** Run `npm run auth0:deploy` to push the updated scope list to the Auth0 API.
3.  **Update Role Grants:** If the scope is restricted to admins, ensure it is included in the `authadmin` role configuration within the script or assigned manually in the dashboard.
4.  **Frontend Implementation:** Use the `hasPermission` helper in your React components to guard UI elements.

### Code Example: Adding a Scope

```typescript
// 1. In scripts/auth0/deploy-tenant-resources.ts
const api = await createOrUpdateResourceServer(auth0Domain, token, {
  name: `${tenant}-api`,
  identifier: audience,
  scopes: [
    { value: "read:messages", description: "Read messages" },
    { value: "write:messages", description: "Write messages" },
    { value: "delete:products", description: "Delete store products" }, // NEW SCOPE
  ],
  // ... other config
});

// 4. In a React Component (Frontend)
import { useAuth0 } from "@auth0/auth0-react";
import { hasPermission } from "@/lib/auth-utils";

export function DeleteProductButton() {
  const { user } = useAuth0();
  const canDelete = hasPermission(user, "delete:products");

  if (!canDelete) return null;

  return <button onClick={handleDelete}>Delete Product</button>;
}
```

## The `authadmin` Role and Permissions

The `authadmin` role is the primary administrative role within the Fufuni ecosystem. It acts as a "super-admin" by aggregating two critical permission sets:

*   **`admin:store`**: Grants access to all administrative endpoints in the Fufuni backend (e.g., managing orders, modifying stock).
*   **`auth0:admin:api`**: Specifically allows the user to trigger actions that interact with the Auth0 Management API via the backend proxy.

### Assigning Roles to Users

While the script creates the role, you must assign it to users. This is typically done via the Auth0 Dashboard or a backend management route:

```typescript
// Example: Manual role assignment logic using the Management API
async function assignAdminRole(userId: string, roleId: string) {
  const response = await fetch(`https://${process.env.AUTH0_DOMAIN}/api/v2/users/${userId}/roles`, {
    method: "POST",
    headers: {
      Authorization: `Bearer ${mgmtToken}`,
      "Content-Type": "application/json",
    },
    body: JSON.stringify({
      roles: [roleId], // The ID of the 'authadmin' role
    }),
  });
  return response.ok;
}
```

## Management API Client vs. SPA Client

It is vital to distinguish between the two types of Auth0 Clients used in the framework.

### Management API Client (`M2M`)
*   **Used by:** `deploy-tenant-resources.ts` and the Fufuni backend.
*   **Authentication:** `client_id` + `client_secret`.
*   **Purpose:** Backend-to-backend operations. It has high privileges to read/write users, roles, and settings.
*   **Security:** The secret must NEVER be exposed to the frontend.

### SPA Client (`Public`)
*   **Used by:** The Vite/React frontend application.
*   **Authentication:** PKCE (Authorization Code Flow). No client secret is used.
*   **Purpose:** User login and obtaining an Access Token to call the Fufuni API.
*   **Security:** Relies on `Allowed Origins` and `Allowed Callback URLs` to prevent unauthorized redirects.

```typescript
// Frontend configuration (SPA Client)
export const auth0Config = {
  domain: import.meta.env.VITE_AUTH0_DOMAIN,
  clientId: import.meta.env.VITE_AUTH0_CLIENT_ID, // Use the SPA ID here
  authorizationParams: {
    redirect_uri: window.location.origin,
    audience: import.meta.env.VITE_AUTH0_AUDIENCE,
  },
};
```

## The Login Post-Action

The deployment script installs a custom Auth0 Action (stored in `scripts/auth0/auth0-code/add-userinfo-to-access-jwt.js`). By default, Auth0 Access Tokens do not contain user-friendly permission lists in a format easily consumable by the frontend.

### Why it is needed

Standard Auth0 tokens include scopes in a space-separated string within the `scope` claim. However, to support complex UI guards and RBAC (Role-Based Access Control) in React, Fufuni enriches the ID Token with a custom claim containing the user's full permissions array.

This enrichment ensures that `import.meta.env.PERMISSIONS` (or the equivalent state in the React Auth provider) accurately reflects the user's capabilities without requiring additional API calls.

### The Action Script

```javascript
/**
 * Handler that will be called during the execution of a PostLogin flow.
 */
exports.onExecutePostLogin = async (event, api) => {
  const namespace = 'https://fufuni.dev';
  if (event.authorization && event.authorization.roles) {
    // Add roles and permissions to the ID Token for the frontend
    api.idToken.setCustomClaim(`${namespace}/roles`, event.authorization.roles);
    
    // We also map permissions directly into the ID token for easy access
    // This allows hasPermission("admin:store") to work instantly
    const permissions = event.authorization.permissions || [];
    api.idToken.setCustomClaim(`${namespace}/permissions`, permissions);
  }
};
```

When the frontend receives the ID Token after a successful login, the `useAuth0` hook parses this custom claim, allowing the `hasPermission` utility to verify access locally before the user even makes a network request to a protected endpoint.

## Troubleshooting Common Issues

### 401 Unauthorized during deployment
This usually means your `AUTH0_MANAGEMENT_API_CLIENT_SECRET` is incorrect or the M2M application in Auth0 does not have the "Management API" authorized with the required "Read/Write Clients" and "Read/Write Resource Servers" scopes.

### 403 Forbidden on API calls
Ensure the `AUTH0_AUDIENCE` in your `.env` file matches exactly the "Identifier" field in the Auth0 API section. A trailing slash difference (e.g., `https://api.com` vs `https://api.com/`) will cause signature verification to fail.

### Permissions not showing in Frontend
If you have assigned a role to a user but the frontend does not see the new permissions:
1.  Check the "Actions" > "Flows" > "Login" in Auth0 Dashboard to ensure the `Add Userinfo to jwt` action is actually deployed and dragged into the pipeline.
2.  Log out and log back in to refresh the ID Token.

```bash
# Verify your local environment before running deployment
cat .env | grep AUTH0
```
