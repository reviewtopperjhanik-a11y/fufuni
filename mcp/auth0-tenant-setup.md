## Auth0 Tenant Setup and Configuration

The `deploy-tenant-resources.ts` script is a critical "one-shot" utility designed to automate the provisioning of a Fufuni tenant within the Auth0 ecosystem. Instead of manually clicking through the Auth0 Dashboard, this script ensures that every environment (development, staging, production) is configured identically. You should run this script when setting up a new Auth0 tenant or when updates to the infrastructure (like new permission scopes or login actions) are required.

To execute the deployment, run the following command from the monorepo root:

```bash
# Execute the deployment for a specific environment file
npm run auth0:deploy -- --env-file=.env.local
```

The script performs the following operations:
1.  **SPA Client Configuration**: Sets up a Single Page Application client with PKCE (Proof Key for Code Exchange) enabled.
2.  **API Resource Server**: Creates or updates an API resource server (defined by `AUTH0_AUDIENCE`) and attaches the necessary OAuth2 scopes.
3.  **Social Connections**: Automatically enables common social login providers (Google, GitHub, Apple) for the created SPA client.
4.  **Security Roles**: Configures the `authadmin` role which serves as the primary administrative persona for the Fufuni dashboard.

### Example: Basic Script Execution
Before running the script, ensure your `.env` file contains the Management API credentials. The script will guide you through missing variables via interactive prompts if necessary.

```typescript
// scripts/auth0/deploy-tenant-resources.ts snippet

const token = await getValidMgmtToken(
  auth0Domain,

console.log(`Success: Configured SPA Client ${client.client_id}`);
```

## Required Environment Variables

The deployment script requires specific variables to authenticate against the Auth0 Management API and to define the target architecture. These must be present in the file passed to the `--env-file` argument.

| Variable | Description |
| :--- | :--- |
| `AUTH0_DOMAIN` | Your Auth0 tenant domain (e.g., `tenant.eu.auth0.com`). |
| `AUTH0_TENANT` | The internal slug/name of the tenant. |
| `AUTH0_MANAGEMENT_API_CLIENT_ID` | Client ID of the "Auth0 Management API" Test Application. |
| `AUTH0_MANAGEMENT_API_CLIENT_SECRET` | Client Secret of the "Auth0 Management API" Test Application. |
| `AUTH0_AUDIENCE` | The unique identifier for your API (e.g., `https://api.fufuni.com/`). |
| `STORE_URL` | The base URL of your frontend (used for callbacks and logout). |

## Adding a New Permission Scope

In Fufuni, permissions are centralized in the Auth0 Resource Server configuration. To add a new scope (e.g., `manage:inventory`), follow these four specific steps to ensure the scope is propagated from the backend to the frontend guards.

1.  **Modify the Script**: Open `scripts/auth0/deploy-tenant-resources.ts` and add the new scope to the `createOrUpdateResourceServer` call.
2.  **Run Deployment**: Execute `npm run auth0:deploy` to push the new scope configuration to the Auth0 API.
3.  **Update Role Grants**: If the permission is meant for administrators, go to the Auth0 Dashboard > User Management > Roles > `authadmin` and add the new scope to the API permissions.
4.  **Implement Frontend Guard**: Use the `hasPermission` utility in your React components to protect UI elements.

### Example: Adding the 'manage:inventory' Scope
```typescript
// 1. Inside deploy-tenant-resources.ts
const api = await createOrUpdateResourceServer(auth0Domain, token, {
  name: `${tenant}-api`,
  identifier: audience,
  scopes: [
    { value: "read:messages", description: "Read messages" },
    { value: "write:messages", description: "Write messages" },
    { value: "manage:inventory", description: "Full access to inventory" }, // New scope
  ],
  // ... other settings
});

// 4. In a React 19 Component (frontend)
import { useAuth } from "@/hooks/use-auth";

export function InventoryPanel() {
  const { hasPermission } = useAuth();

  if (!hasPermission("manage:inventory")) {
    return <p>Access Denied: Inventory Management Required</p>;
  }

  return <div>Inventory Dashboard</div>;
}
```

## The authadmin Role

The `authadmin` role is the root administrative entity in the Fufuni framework. It aggregates permissions that allow a user to manage both the business data and the authentication infrastructure itself.

-   **`admin:store`**: Grants full access to e-commerce resources (orders, products, customers) within the SQLite/Durable Object backend.
-   **`auth0:admin:api`**: Grants the user the ability to interact with the Fufuni backend's Management API proxy, allowing for user management and role assignment directly from the store dashboard.

### Assigning the Role
While the deploy script *creates* the role, it does not assign it to users automatically. You must assign it manually via the Auth0 Dashboard or via the backend API:

```typescript
// Backend logic to assign the authadmin role via Management API
async function assignAdminRole(userId: string) {
  const roles = await getRolesByName("authadmin");
  const roleId = roles[0].id;
  
  await auth0Request(domain, token, `users/${userId}/roles`, {
    method: "POST",
    body: JSON.stringify({ roles: [roleId] }),
  });
}
```

## Management API Client vs. SPA Client

It is vital to distinguish between these two clients to avoid security vulnerabilities like leaking secrets to the frontend.

### Management API Client (`AUTH0_MANAGEMENT_CLIENT_ID`)
-   **Type**: Machine-to-Machine (M2M).
-   **Usage**: Used by the `deploy-tenant-resources.ts` script and the Hono backend.
-   **Capability**: Can create users, delete clients, and change tenant settings.
-   **Security**: Contains a `client_secret`. **NEVER** expose this variable to the Vite/React frontend.

### SPA Client (`AUTH0_CLIENT_ID`)
-   **Type**: Single Page Application.
-   **Usage**: Used by React 19 + HeroUI frontend.
-   **Capability**: Handles user login, logout, and token acquisition via PKCE.
-   **Security**: Does not use a secret. It relies on strictly enforced "Allowed Web Origins" and "Allowed Callback URLs" configured by the deploy script.

## The Login Post-Action

Standard OAuth2/OIDC flows often put user permissions inside the Access Token (JWT), but not the ID Token. To simplify frontend logic and avoid complex decoding, the Fufuni deploy script installs a custom Auth0 Action.

This script runs after a user successfully logs in and enriches the user's `idToken` with a custom claim containing their permissions array. This is what allows `import.meta.env.PERMISSIONS` logic to function correctly in the browser.

### Example: Post-Login Action Code
This code is stored in `scripts/auth0/auth0-code/add-userinfo-to-access-jwt.js` and is automatically uploaded by the deploy script.

```javascript
/**
 * Handler that adds permissions to the tokens.
 */
exports.onExecutePostLogin = async (event, api) => {
  const namespace = 'https://fufuni.com';
  
  // Extract permissions from the event context
  const permissions = event.authorization?.permissions || [];

  // Add permissions to the ID Token for frontend visibility
  api.idToken.setCustomClaim(`${namespace}/permissions`, permissions);
  
  // Add permissions to the Access Token for backend verification
  api.accessToken.setCustomClaim(`${namespace}/permissions`, permissions);
};
```

By injecting these permissions directly into the tokens, the Fufuni frontend can perform synchronous permission checks without needing to query a separate `/userinfo` endpoint after every page load, significantly improving the user experience and interface responsiveness.
