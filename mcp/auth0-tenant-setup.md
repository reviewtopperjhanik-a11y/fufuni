# Auth0 Tenant Setup & Permissions

## 1. Deploy Script Overview
`scripts/auth0/deploy-tenant-resources.ts` provisions **all** Auth0 resources needed by Fufuni in a single run:

| Resource | Purpose |
|----------|---------|
| **SPA Application** | Front‑end OAuth client (grant types: `authorization_code`, `refresh_token`) |
| **API Resource Server** | The backend API (`https://api.<domain>/`) with scopes |
| **Permission Scopes** | `admin:store`, `auth0:admin:api`, `ai:api`, `mail:api`, `database:admin` |
| **Post‑Login Action** | Injects `user_metadata` into the JWT |
| **M2M Client** | Short‑lived Management API client for backend calls |

### Running the script

```bash

# 2️⃣ Run the deployment
npx tsx scripts/auth0/deploy-tenant-resources.ts -- --env-file=.env.fufuni
```

- `--env-file` is **required**.

## 2. Auth0 Permissions & Scopes

| Permission (scope) | Grants |
|---------------------|--------|
| `admin:store` | Full CRUD access to store resources (products, inventory, orders). |
| `auth0:admin:api` | Proxy access to the Auth0 Management API (`https://api.auth0.com/`). Used by the admin panel. |
| `ai:api` | Calls to the AI / NLP features exposed by the backend. |
| `mail:api` | Access to the email sending API. |
| `database:admin` | Direct database operations (e.g. read/write to SQLite via the Durable Object). |

> These permissions are defined as **custom scopes** on the Auth0 API Resource Server.  
> Each scope is represented in JWT as `scope: "<space‑separated list>"`.

### Example JWT payload fragment

```json
{
  "sub": "auth0|123456",
  "aud": "https://api.fufuni.com",
  "scope": "admin:store ai:api",
  "user_metadata": { "wishlist": [...], "theme": "dark" }
}
```

## 3. Post‑Login Action – JWT Injection

| Item | What it is | Why it matters |
|------|------------|----------------|
| `user_metadata` | Custom claim added to the access token | Provides the front‑end wishlist, theme, and other per‑user data without extra API round‑trips. |
| Action name | `Add Userinfo to jwt` (configurable) | Ensures the claim is always present after authentication. |

### Action code snippet (simplified)

```typescript
exports.onExecutePostLogin = async (event, api) => {
  // Grab user metadata
  const metadata = event.user.user_metadata ?? {};

  // Add it as a custom claim under the API audience
  const aud = "https://api.fufuni.com";
  api.idToken.setCustomClaim(aud, metadata);

  // Optional: also put it in the access token
  api.accessToken.setCustomClaim(aud, metadata);
};
```

> The action runs **after** the user authenticates, so the token is ready when the front‑end receives it.

## 4. M2M Token Caching

| Item | Value |
|------|-------|
| Purpose | Avoid hitting the per‑month M2M token quota when the backend proxies to the Auth0 Management API. |
| KV Key | `auth0_management_token` |
| TTL | ~23 hours (default TTL used by the script) |

### Why 23 hours?
Auth0 enforces a *monthly* token quota for machine‑to‑machine clients. By caching a token for ~23 h, the script guarantees that the backend can perform frequent Management API calls without exhausting the quota.

```ts
// Example KV read/write (pseudo‑code)
const token = await kv.get<string>('auth0_management_token');
if (!token || isExpired(token)) {
  const newToken = await fetchM2MToken();
  await kv.put('auth0_management_token', newToken, { expirationTtl: 23 * 3600 });
}
```

1. **Define the permission in the deploy script**  
   ```ts

   const newScope = {
     name: "custom:api:feature",
     description: "Access to the new custom API feature",
   };
   // Append to the array of scopes you create on the Resource Server
   ```

2. **Re‑run the deployment**  
   ```bash
   npx tsx scripts/auth0/deploy-tenant-resources.ts -- --env-file=.env.fufuni
   ```

3. **Add a backend RBAC guard**  
   ```ts
   // src/server/routes/api.ts
   router.use(
     "/api/custom",
     requirePermission("custom:api:feature") // middleware
   );
   ```

4. **Guard the frontend**  
   ```tsx
   // src/app/pages/CustomFeature.tsx
   <AuthenticationGuardWithPermission permission="custom:api:feature">
     <CustomFeatureComponent />
   </AuthenticationGuardWithPermission>
   ```

5. **Update the UI (if needed)** – e.g., add a menu item that only shows when the user has the new permission.

6. **Test**  
   - Log in as a user with `custom:api:feature` granted.  
   - Verify the feature is accessible.  
   - Log in as a user without the permission and ensure access is denied.
