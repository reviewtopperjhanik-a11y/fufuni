## Auth0 Resource Provisioning

Fufuni uses a centralized deployment script to ensure that the Auth0 tenant is configured identically across development, staging, and production environments. The script `scripts/auth0/deploy-tenant-resources.ts` automates the creation of the Single Page Application (SPA), the Resource Server (API), permission scopes, and the Post-Login Action.

### Running the Deployment Script

The script requires an environment file containing your Auth0 Management API credentials. You must first create a "Machine-to-Machine" (M2M) application in the Auth0 Dashboard with access to the "Auth0 Management API" to obtain these credentials.

```bash
# 1. Create your environment file (e.g., .env.auth0)
# Required vars: AUTH0_DOMAIN, AUTH0_TENANT, AUTH0_MANAGEMENT_API_CLIENT_ID, 
# AUTH0_MANAGEMENT_API_CLIENT_SECRET, AUTH0_AUDIENCE, STORE_URL

# 2. Run the deployment script
npx tsx scripts/auth0/deploy-tenant-resources.ts -- --env-file=.env.auth0
```

### Resources Provisioned
- **SPA Client**: Configured with `authorization_code` and `refresh_token` flows. It automatically sets up allowed callback URLs and logout URLs based on your `STORE_URL`.
- **Resource Server (API)**: Registers your API audience and defines the standard OAuth2 scopes used by the framework.
- **Social Connections**: Automatically enables GitHub, Google, Microsoft, and Apple connections for the created application.
- **Post-Login Action**: Deploys a Node.js script to the Auth0 runtime that modifies the issued Access Token.

## Permissions and Scopes Reference

Fufuni uses RBAC (Role-Based Access Control) enforced via Auth0 scopes. These scopes are requested by the frontend and validated by the backend Hono middleware.

| Permission / Scope | Default Role | Description |
|:---|:---|:---|
| `admin:store` | Admin | General access to store management (Products, Orders, Settings). |
| `auth0:admin:api` | Auth Admin | Access to the Management API proxy. Required for the `/admin/users-and-permissions` page. |
| `ai:api` | AI Admin | Permission to invoke AI-powered features (Image generation, product descriptions). |
| `mail:api` | Mail Admin | Permission to trigger transactional emails and view logs. |
| `admin:database` | DB Admin | Access to direct SQLite/D1 query execution via the admin console. |

## Post-Login Action and JWT Injection

Fufuni utilizes an Auth0 Post-Login Action to inject `user_metadata` directly into the Access Token as custom claims. This eliminates the need for the backend to perform extra database lookups or API calls to Auth0 to retrieve user preferences or metadata like wishlists.

### Why use Custom Claims?
Standard JWTs contain limited information (sub, aud, exp). By injecting `user_metadata`, the Fufuni backend can immediately identify the user's interface preferences or local state without an additional round-trip.

### Action Implementation
The action code is located at `scripts/auth0/auth0-code/add-userinfo-to-access-jwt.js`.

```javascript
/**
 * Handler that will be called during the execution of a PostLogin flow.
 */
exports.onExecutePostLogin = async (event, api) => {
  const namespace = 'https://fufuni.com/';
  
  // Inject metadata into the Access Token
  if (event.user.user_metadata) {
    api.accessToken.setCustomClaim(`${namespace}user_metadata`, event.user.user_metadata);
  }

  // Also ensure email is present in the token for convenience
  api.accessToken.setCustomClaim(`${namespace}email`, event.user.email);
};
```

## M2M Management Token Caching

The Fufuni backend frequently interacts with the Auth0 Management API (e.g., to list users or update roles). To avoid hitting the strict rate limits and monthly quotas of Auth0 M2M tokens, Fufuni caches the Management API access token in Cloudflare KV.

### Implementation Details
- **KV Key**: `auth0_management_token`
- **TTL (Time To Live)**: ~23 hours (82800 seconds). Auth0 tokens typically last 24 hours; we refresh slightly before expiration.
- **Storage**: The token is stored as a plain string in the KV namespace bound to the Worker.

```typescript
// Logical representation of the token retrieval in the backend
async function getManagementToken(env: Env): Promise<string> {
  const cached = await env.KV.get("auth0_management_token");
  if (cached) return cached;

  const response = await fetch(`https://${env.AUTH0_DOMAIN}/oauth/token`, {
    method: "POST",
    headers: { "content-type": "application/json" },
    body: JSON.stringify({
      client_id: env.AUTH0_MANAGEMENT_CLIENT_ID,
      client_secret: env.AUTH0_MANAGEMENT_CLIENT_SECRET,
      audience: `https://${env.AUTH0_DOMAIN}/api/v2/`,
      grant_type: "client_credentials",
    }),
  });

  const data = await response.json();
  // Cache for 23 hours
  await env.KV.put("auth0_management_token", data.access_token, { expirationTtl: 82800 });
  return data.access_token;
}
```

## Users and Permissions Management

The Framework provides a built-in UI for managing user roles and permissions located at `/admin/users-and-permissions`. 

### Security Architecture
1. **Frontend**: The `UsersAndPermissionsPage` component renders the list of users. It requires the `auth0:admin:api` permission.
2. **Backend Proxy**: Instead of calling Auth0 directly (which would expose the Management Token), the browser calls a Fufuni backend endpoint (e.g., `/api/admin/auth0/users`).
3. **Validation**: The backend verifies the caller has the `auth0:admin:api` scope in their JWT.
4. **Execution**: The backend retrieves the cached M2M token and performs the request to the Auth0 Management API on behalf of the user.

### Frontend Guard Example
Using the HeroUI-integrated guard to protect the management view:

```tsx
import { AuthenticationGuardWithPermission } from "@/components/auth/guard";

export default function UsersAndPermissionsPage() {
  return (
    <AuthenticationGuardWithPermission permission="auth0:admin:api">
      <div className="p-6">
        <h2 className="text-2xl font-bold">User Management</h2>
        {/* User list and Role assignment logic */}
      </div>
    </AuthenticationGuardWithPermission>
  );
}
```

## Step-by-Step: Adding a New Permission

When adding a new feature (e.g., a "Reports" module), follow these steps to integrate a new permission into the Fufuni ecosystem.

### 1. Update the Deployment Script
Add the new scope to the `scopes` array in `scripts/auth0/deploy-tenant-resources.ts`.

```typescript
// Inside deployResources function
const api = await createOrUpdateResourceServer(auth0Domain, token, {
  // ... existing config
  scopes: [
    ...existingScopes,
    { value: "read:reports", description: "View financial reports" },
  ],
});
```

### 2. Provision the Tenant
Run the script to update the Resource Server in Auth0.

```bash
npx tsx scripts/auth0/deploy-tenant-resources.ts -- --env-file=.env.local
```

### 3. Implement Backend RBAC Guard
Use the Zod-OpenAPI middleware to enforce the scope on your new route.

```typescript
import { createRoute } from "@hono/zod-openapi";
import { authMiddleware } from "@/middleware/auth";

const getReportsRoute = createRoute({
  method: 'get',
  path: '/api/reports',
  middleware: [authMiddleware(['read:reports'])] as const,
  responses: {
    200: { description: 'Report data' },
    403: { description: 'Forbidden' }
  },
});
```

### 4. Implement Frontend Guarding
Wrap the navigation link or the page content with the permission guard.

```tsx
import { usePermissions } from "@/hooks/use-permissions";

function Sidebar() {
  const { hasPermission } = usePermissions();

  return (
    <nav>
      {hasPermission("read:reports") && (
        <a href="/admin/reports">Financial Reports</a>
      )}
    </nav>
  );
}
```

### 5. Assign to User
Go to the `/admin/users-and-permissions` page in your running application, locate your user, and assign the role associated with the `read:reports` scope (or create a new role in the Auth0 dashboard and assign it). You will need to log out and log back in for the new scope to appear in your local JWT.
