## Auth0 Tenant Orchestration

The Fufuni framework uses a centralized orchestration script to ensure that Auth0 tenants are configured consistently across development, staging, and production environments. Instead of manually clicking through the Auth0 Dashboard, we treat our identity configuration as code.

The script located at `scripts/auth0/deploy-tenant-resources.ts` is a one-shot setup tool. You should run it when initializing a new environment or when permission scopes and application settings change.

```bash
# From the monorepo root, run the deployment script for a specific environment
npm run auth0:deploy -- --env-file=.env.production

# To see detailed setup instructions for the initial Management API keys
npx tsx scripts/auth0/deploy-tenant-resources.ts -- --detailed-help
```

The script performs the following idempotent operations:
1.  **SPA Client Configuration**: Sets up the Single Page Application client with PKCE, authorized callbacks, and logout URLs.
2.  **API Resource Server**: Defines the API (Audience), sets the signing algorithm to RS256, and registers all functional scopes.
3.  **Social Connections**: Automatically enables Google, GitHub, and other providers for the created client.
4.  **RBAC Roles**: Ensures the `authadmin` role exists with the necessary administrative scopes.
5.  **Post-Login Actions**: Deploys Node.js code to the Auth0 pipeline to inject permissions into tokens.

## Required Environment Variables

Before running the deployment script, you must provide a set of bootstrap variables. These allow the script to authenticate with the Auth0 Management API and identify your specific tenant.

| Variable | Description | Source |
| :--- | :--- | :--- |
| `AUTH0_DOMAIN` | Your Auth0 tenant domain (e.g., `fufuni-dev.eu.auth0.com`) | Auth0 Dashboard |
| `AUTH0_TENANT` | The short name/slug of your tenant | Auth0 Dashboard |
| `AUTH0_MANAGEMENT_API_CLIENT_ID` | Client ID of a "Machine to Machine" app with Management API access | Auth0 APIs -> Management API -> Test |
| `AUTH0_MANAGEMENT_API_CLIENT_SECRET` | Client Secret for the Management API client | Auth0 APIs -> Management API -> Test |
| `AUTH0_AUDIENCE` | The unique identifier for your API (e.g., `https://api.fufuni.com/`) | User Defined |
| `STORE_URL` | The base URL of your frontend application | Developer Environment |

### Example `.env.auth0` Bootstrap File

```env
AUTH0_DOMAIN=fufuni-shop.eu.auth0.com
AUTH0_TENANT=fufuni-shop
AUTH0_MANAGEMENT_API_CLIENT_ID=m2m_client_id_from_auth0
AUTH0_MANAGEMENT_API_CLIENT_SECRET=m2m_secret_from_auth0
AUTH0_AUDIENCE=https://api.fufuni.com/
STORE_URL=http://localhost:5173
```

## Adding New Permission Scopes

Adding a new permission to the Fufuni ecosystem requires a coordinated update across the identity provider and the codebase. Follow these four steps to register and use a new scope:

### Step 1: Update the Deployment Script
Modify the `scopes` array within `deploy-tenant-resources.ts` to include your new permission.

```typescript
// scripts/auth0/deploy-tenant-resources.ts

const api = await createOrUpdateResourceServer(auth0Domain, token, {
  name: `${tenant}-api`,
  identifier: audience,
  scopes: [
    { value: "read:messages", description: "Read messages" },
    { value: "write:messages", description: "Write messages" },
    // NEW SCOPE ADDED HERE:
    { value: "manage:inventory", description: "Full access to product stock levels" },
  ],
  signing_alg: "RS256",
  // ... other config
});
```

### Step 2: Push Configuration to Auth0
Run the deployment script to update the Resource Server in Auth0.

```bash
npm run auth0:deploy -- --env-file=.env
```

### Step 3: Update Role Grants
If the permission is restricted to administrators, go to the Auth0 Dashboard -> User Management -> Roles -> `authadmin` -> Permissions and add the new scope from your API. Alternatively, update the script's role-creation logic to include the new scope automatically.

### Step 4: Implement Frontend Guards
Use the `hasPermission` utility in your React components to protect UI elements.

```tsx
import { useAuth } from "@/hooks/use-auth";

export function InventoryPanel() {
  const { hasPermission } = useAuth();

  if (!hasPermission("manage:inventory")) {
    return <p>Access Denied: You require manage:inventory scopes.</p>;
  }

  return (
    <div>
      <h3>Stock Management</h3>
      {/* Inventory controls */}
    </div>
  );
}
```

## The `authadmin` Role

Fufuni defines a default administrative role named `authadmin`. This role is the "Super User" of the system. It is designed to bridge the gap between application-level logic and identity-provider management.

### Granted Scopes
1.  `admin:store`: Grants full access to the Fufuni backend API (e.g., creating products, viewing orders, modifying site settings).
2.  `auth0:admin:api`: A custom scope used by the backend to determine if the user is allowed to call the Management API proxy (e.g., to invite new users or change user roles via the Fufuni dashboard).

### Assignment
Assigning this role is currently a manual process in the Auth0 Dashboard for security reasons:
1.  Navigate to **User Management** -> **Users**.
2.  Select the Target User.
3.  Click the **Roles** tab.
4.  Click **Assign Roles** and select `authadmin`.

## Management API Client vs. SPA Client

It is critical to distinguish between the two types of Auth0 clients used in the Fufuni framework. Using the wrong credentials will result in 401 Unauthorized or 403 Forbidden errors.

### Management API Client (M2M)
*   **Type**: Machine-to-Machine.
*   **Usage**: Used by `deploy-tenant-resources.ts` and the Backend Proxy.
*   **Permissions**: Highly privileged; can create clients, delete users, and change tenant settings.
*   **Env Var**: `AUTH0_MANAGEMENT_API_CLIENT_ID`.

### SPA Client (Frontend)
*   **Type**: Single Page Application.
*   **Usage**: Used by the React 19 frontend via the Auth0 SPA SDK.
*   **Permissions**: Limited; can only authenticate users via PKCE. It cannot perform management tasks.
*   **Env Var**: `AUTH0_CLIENT_ID`.

```typescript
// backend/src/config.ts
// The backend needs to know BOTH to verify user tokens (Audience) 
// and to perform admin tasks (Management Secret).

export const authConfig = {
  domain: process.env.AUTH0_DOMAIN,
  audience: process.env.AUTH0_AUDIENCE,
  managementId: process.env.AUTH0_MANAGEMENT_API_CLIENT_ID,
  managementSecret: process.env.AUTH0_MANAGEMENT_API_CLIENT_SECRET,
};
```

## Login Post-Action and Permission Injection

By default, Auth0 Access Tokens contain scopes, but ID Tokens do not. Fufuni requires user permissions to be available in the frontend to handle UI state without constant API calls. 

The deployment script installs a custom **Login Post-Action**. This script runs every time a user logs in. It fetches the user's roles and permissions from the Auth0 context and injects them into the `https://fufuni.com/permissions` claim in the issued tokens.

### The Action Script
The script at `scripts/auth0/auth0-code/add-userinfo-to-access-jwt.js` is automatically uploaded by the deployer.

```javascript
/**
 * Handler that will be called during the execution of a PostLogin flow.
 */
exports.onExecutePostLogin = async (event, api) => {
  const namespace = 'https://fufuni.com';
  if (event.authorization && event.authorization.permissions) {
    // Add permissions to both ID Token (for frontend) and Access Token (for API)
    api.idToken.setCustomClaim(`${namespace}/permissions`, event.authorization.permissions);
    api.accessToken.setCustomClaim(`${namespace}/permissions`, event.authorization.permissions);
  }
};
```

### Why this is needed
Without this action, your React frontend would know *who* the user is, but it would not know *what* they can do. By enriching the token, Fufuni can initialize the `useAuth` hook with a local copy of permissions:

```typescript
// frontend/src/hooks/use-auth.ts
export const useAuth = () => {
  const { user } = useAuth0();
  
  // The permission claim is mapped from the JWT injected by the Auth0 Action
  const permissions: string[] = user?.["https://fufuni.com/permissions"] || [];

  const hasPermission = (scope: string) => permissions.includes(scope);

  return { user, permissions, hasPermission };
};
```

This synchronization ensures that the `import.meta.env.PERMISSIONS` logic used in frontend guards always stays in sync with the real scopes defined in the Auth0 Resource Server.
