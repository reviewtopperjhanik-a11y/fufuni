## User Preferences and Wishlist Architecture

In Fufuni, user-specific settings are bifurcated based on their relational complexity and performance requirements. Lightweight preferences, such as the product wishlist, theme selections, or UI toggles, are stored directly within Auth0's `user_metadata`. This strategy avoids the overhead of maintaining a dedicated SQLite table for simple key-value pairs and ensures that user preferences are available immediately upon authentication via the JWT (JSON Web Token) payload.

### The user_metadata Strategy
By storing preferences in Auth0, the Fufuni backend leverages the Auth0 Management API to persist data. When a user logs in, the Fufuni Auth0 Action injects the `user_metadata` into the access token. The frontend then decodes this token locally using `jose`.

**Advantages:**
1.  **Zero-Latency Read:** Preferences are read from the JWT already in memory. No additional API calls are needed to display the "Favorited" state of a product.
2.  **State Synchronization:** Since the token is the single source of truth, refreshing the token automatically synchronizes all components.
3.  **Reduced DB Load:** SQLite is reserved for transactional data (orders, inventory, carts) rather than transient UI states.

### Multi-tenant Namespacing
Fufuni is designed for multi-tenancy. Multiple store instances might share the same Auth0 tenant. To prevent data collisions, all `user_metadata` is namespaced using the `STORE_URL`.

```typescript
// Example of the JWT payload structure (decoded)
{
  "sub": "auth0|12345",
  "extra_user_info/user_metadata": {
    "https://mystore.fufuni.com": {
      "wishlist": ["prod_01J2", "prod_09K3"],
      "newsletter_opt_in": true,
      "theme": "dark"
    },
    "https://other-store.io": {
      "wishlist": ["prod_ZZZ9"]
    }
  }
}
```

The utility function `getStoreMetadata` (used within `useWishlist`) safely extracts the object corresponding to the current environment's `STORE_URL`.

## The `useWishlist` Hook

The `useWishlist` hook is the primary interface for managing product favorites. It provides a reactive state derived from the JWT and handles the mutation flow through the Fufuni backend.

### Hook API and Implementation
The hook uses `useTokenUserData`—a low-level utility that subscribes to a specific custom event and parses the current token.

```typescript
import { useWishlist } from "@/hooks/use-wishlist";
import { Button } from "@heroui/react";
import { HeartIcon } from "@/components/icons";

export const WishlistButton = ({ productId }: { productId: string }) => {
  const { isFavorite, toggle, isLoading } = useWishlist();
  const active = isFavorite(productId);

  return (
    <Button
      isIconOnly
      variant={active ? "solid" : "flat"}
      color={active ? "danger" : "default"}
      isLoading={isLoading}
      onPress={() => toggle(productId)}
      aria-label="Toggle Wishlist"
    >
      <HeartIcon fill={active ? "currentColor" : "none"} />
    </Button>
  );
};
```

### The Mutation Flow
When `toggle(productId)` is called, the following sequence occurs:
1.  **Optimistic Check:** The hook determines if the item should be added or removed based on the current local state.
2.  **API Call:** A request is sent to the Fufuni backend (`POST` or `DELETE` to `/v1/me/wishlist`).
3.  **Token Refresh:** Crucially, the hook calls `refreshToken()`. This forces the frontend to fetch a new JWT from the Auth0 proxy. This new token contains the updated `user_metadata`.
4.  **Event Dispatch:** A `fufuni:wishlist-updated` custom event is dispatched with the new data, signaling all other components using the hook to update their local state immediately.

## Event-Driven Reactivity

Fufuni avoids heavy global contexts (like Redux or deep React Context providers) for preferences. Instead, it uses the DOM's `CustomEvent` system for high-performance, cross-component updates.

### Handling `WISHLIST_UPDATED_EVENT`
The constant `WISHLIST_UPDATED_EVENT` (defined as `fufuni:wishlist-updated`) acts as the synchronization backbone.

```typescript
// How to manually listen for wishlist updates in a non-hook component
useEffect(() => {
  const handleUpdate = (event: CustomEvent<string[]>) => {
    const newWishlist = event.detail;
    console.log("Wishlist updated across tabs/components:", newWishlist);
  };

  window.addEventListener("fufuni:wishlist-updated" as any, handleUpdate);
  return () => window.removeEventListener("fufuni:wishlist-updated" as any, handleUpdate);
}, []);
```

Because `useTokenUserData` listens to this event internally, any call to `setWishlist` in one instance of `useWishlist` will trigger a re-render in every other component using the hook throughout the application.

## Saved Carts vs. Wishlist

It is vital to distinguish between the **Wishlist** and **Saved Carts**. While they appear similar to the user, their technical implementation is completely different.

### Comparison Table

| Feature | Wishlist | Saved Carts |
| :--- | :--- | :--- |
| **Storage Location** | Auth0 `user_metadata` | SQLite `saved_carts` Table |
| **Data Type** | Array of IDs (strings) | Relational Rows (FK to Carts/Products) |
| **Persistence** | Global (Auth0) | Store Database (Local) |
| **Sync Method** | JWT Refresh + CustomEvent | API Re-fetch (TanStack Query) |
| **Best For** | Simple "Like" flags | Complex cart snapshots, price tracking |

### Saved Carts Schema
Saved carts are stored in the SQLite database because they need to maintain relationships with specific cart items and configurations that might change over time.

```sql
-- apps/server/src/db/schema.sql

CREATE TABLE saved_carts (
    id TEXT PRIMARY KEY,
    user_id TEXT NOT NULL,
    cart_id TEXT NOT NULL,
    name TEXT NOT NULL,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (cart_id) REFERENCES carts(id) ON DELETE CASCADE
);

CREATE INDEX idx_saved_carts_user ON saved_carts(user_id);
```

## Step-by-Step: Adding a New Preference Field

If you need to add a new preference (e.g., `preferred_currency`), follow these steps to ensure full integration with the Fufuni framework.

### 1. Update the Metadata Extraction
Modify your extraction logic to include the new field. Since `user_metadata` is unstructured in Auth0, you must handle the parsing safely.

```typescript
// apps/client/src/lib/store-metadata.ts

export interface StoreMetadata {
  wishlist: string[];
  preferred_currency?: string; // New field
}

export function getStoreMetadata(userMetadata: any, storeUrl: string): StoreMetadata {
  return userMetadata?.[storeUrl] || { wishlist: [] };
}
```

### 2. Create a Custom Hook
Wrap the logic in a hook that uses `useTokenUserData` and provides a mutation function.

```typescript
// apps/client/src/hooks/use-currency-preference.ts

export function useCurrencyPreference() {
  const auth = useAuth();
  const { refreshToken } = useTokenRefresh();
  const apiBase = getApiBase();

  const parseCurrency = (token: string | null) => {
    const payload = decodeJwt(token ?? "") as any;
    const meta = getStoreMetadata(payload["extra_user_info/user_metadata"], STORE_URL);
    return meta.preferred_currency || "USD";
  };

  const { data: currency, setData } = useTokenUserData(parseCurrency, "fufuni:currency-updated");

  const setCurrency = async (newCurrency: string) => {
    await auth.patchJson(`${apiBase}/v1/me/preferences`, { 
      preferred_currency: newCurrency 
    });
    
    const newToken = await refreshToken();
    setData(parseCurrency(newToken));
    
    window.dispatchEvent(new CustomEvent("fufuni:currency-updated"));
  };

  return { currency, setCurrency };
}
```

### 3. Implement the Backend Patch
Ensure the `PATCH /v1/me/preferences` endpoint in the Hono server accepts the new field and merges it correctly into the existing Auth0 metadata.

```typescript
// apps/server/src/routes/me/preferences.ts

// Inside the handler:

const updatedStoreMeta = {

  [storeUrl]: updatedStoreMeta

```
