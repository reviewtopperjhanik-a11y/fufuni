## Multi-tier Authentication Architecture

Fufuni employs a unified authentication strategy that bridges Auth0-managed identities with internal API keys and OAuth tokens. While user identities and permissions are managed exclusively within Auth0, the backend `authMiddleware` acts as a polymorphic gateway to validate three distinct token formats.

### Accepted Token Types

1.  **Auth0 JWT**: A standard three-part Bearer token (`header.payload.signature`). Verified against the tenant's JWKS. Must contain a specific permission (defaulting to `admin:store`) to grant admin access.
2.  **Admin API Key**: Tokens prefixed with `sk_` (e.g., `sk_4f...`). These are stored as SHA-256 hashes in the `api_keys` table within the Durable Object's SQLite database.
3.  **OAuth Token**: A 64-character lowercase hexadecimal string. These are scoped tokens typically used for third-party integrations, looked up in the `oauth_tokens` table.

### AuthRole Mapping

The `AuthRole` type defines the internal privilege levels. The middleware maps incoming tokens to one or more of these roles based on database entries or Auth0 permission claims.

```typescript
// apps/merchant/src/types.ts
export type AuthRole = 
  | 'public'          // Unauthenticated or public-key requests
  | 'admin'           // Auth0 'admin:store' OR sk_ API key
  | 'oauth'           // 64-char hex token with specific scopes
  | 'authadmin'      // Auth0 'auth0:admin:api' (Superadmin)
  | 'databaseadmin'  // Auth0 'admin:database'
  | 'aiadmin'        // Auth0 'ai:api'
  | 'mail'           // Auth0 'mail:api'
  | 'customer';      // Valid Auth0 JWT with no admin permissions
```

## Backend Guard Matrix

Fufuni uses Hono middleware factories to enforce Role-Based Access Control (RBAC). These guards should be applied after `authMiddleware`.

| Guard | Required Role | Auth0 Permission | Typical Use Case |
| :--- | :--- | :--- | :--- |
| `adminOnly` | `admin` | `admin:store` | Managing products, categories, and orders. |
| `superAdminOnly` | `authadmin` | `auth0:admin:api` | Managing Auth0 users and Management API tokens. |
| `databaseAdminOnly` | `databaseadmin` | `admin:database` | Direct SQL execution or database backups. |
| `aiAccessOnly` | `aiadmin` | `ai:api` | Configuring LLM parameters for translations. |
| `mailAccessOnly` | `mail` | `mail:api` | Sending transactional emails or configuring Mailgun. |
| `validJwtAuthOnly` | Any valid JWT | N/A | General user profile access without specific RBAC. |

### Example: Protecting Admin Routes

Standard admin protection requires both the authentication layer and the specific role guard.

```typescript
import { Hono } from 'hono';
import { authMiddleware, adminOnly } from '../middleware/auth';
import { type HonoEnv } from '../types';

const products = new Hono<HonoEnv>();

// Apply auth to all routes in this router
products.use('*', authMiddleware);

// Protect sensitive write operations
products.post('/', adminOnly, async (c) => {
  const auth = c.get('auth');
  console.log(`User ${auth.sub} is creating a product`);
  // Implementation...
  return c.json({ success: true });
});

export default products;
```

## Customer Authentication Patterns

For customer-facing storefront features (like `/v1/me/orders`), use `customerAuthMiddleware`. Unlike the standard admin middleware, it does not look for API keys or specific RBAC permissions; it strictly validates Auth0 JWTs and extracts identity claims.

```typescript
import { Hono } from 'hono';
import { customerAuthMiddleware } from '../middleware/customer-auth';
import { type HonoEnv } from '../types';

const customerApi = new Hono<HonoEnv>();

customerApi.use('*', customerAuthMiddleware);

customerApi.get('/me/profile', async (c) => {
  const auth = c.get('auth');
  
  // auth.sub contains the Auth0 user ID (e.g. 'auth0|123')
  // auth.email is extracted from the JWT claims
  return c.json({
    id: auth.sub,
    email: auth.email,
    metadata: auth.user_metadata
  });
});
```

## OAuth Scoped Access

When using hexadecimal OAuth tokens, permissions are managed via scopes rather than roles. The `requireScope` factory ensures that the token used in the request carries all necessary permissions.

```typescript
import { Hono } from 'hono';
import { authMiddleware, requireScope } from '../middleware/auth';

const externalApi = new Hono();

externalApi.get('/stats', 
  authMiddleware, 
  requireScope('reports:read', 'analytics:view'), 
  async (c) => {
    return c.json({ orders: 150 });
  }
);
```

## Frontend Security Patterns

The React 19 frontend uses a combination of Higher-Order Components (HOCs) and hooks to manage visibility and access.

### Route Protection with AuthenticationGuard

The `AuthenticationGuard` component wraps page-level components. If a user is not logged in, it triggers a redirect to the Auth0 login page.

```tsx
import { AuthenticationGuard } from '@/components/auth/authentication-guard';
import { DashboardPage } from '@/pages/admin/Dashboard';

// In your router configuration
const routes = [
  {
    path: '/admin',
    element: <AuthenticationGuard component={DashboardPage} />
  }
];
```

### Conditional UI with Permissions

To hide specific UI elements (like a "Delete" button) based on the user's Auth0 permissions, use `AuthenticationGuardWithPermission`.

```tsx
import { AuthenticationGuardWithPermission } from '@/components/auth/permission-guard';
import { Button } from '@heroui/react';

export const ProductActions = () => {
  return (
    <div>
      <Button color="primary">Edit Product</Button>
      
      <AuthenticationGuardWithPermission 
        permission="admin:database" 
        fallback={<p>You do not have permission to delete items.</p>}
      >
        <Button color="danger">Delete Product</Button>
      </AuthenticationGuardWithPermission>
    </div>
  );
};
```

### Programmatic Checks with Hooks

Fufuni distinguishes between login state and permission state through two separate hooks:

1.  **`useAuth()`**: Provides synchronous state about the login session.
2.  **`useSecuredApi()`**: Provides the `hasPermission(perm)` helper to check for specific Auth0 claims asynchronously.

```tsx
import { useAuth } from '@/hooks/useAuth';
import { useSecuredApi } from '@/hooks/useSecuredApi';
import { useEffect, useState } from 'react';

export const AdminToolbar = () => {
  const { isAuthenticated } = useAuth();
  const { hasPermission } = useSecuredApi();
  const [canAccessSettings, setCanAccessSettings] = useState(false);

  useEffect(() => {
    if (isAuthenticated) {
      hasPermission('admin:store').then(setCanAccessSettings);
    }
  }, [isAuthenticated, hasPermission]);

  if (!isAuthenticated) return null;

  return (
    <nav>
      {canAccessSettings && <a href="/settings">Store Settings</a>}
    </nav>
  );
};
```

## Administrative User Management

Fufuni provides a `UsersAndPermissionsPage` (`/admin/users-and-permissions`) which allows authorized admins to manage permissions without logging into the Auth0 Dashboard. This page utilizes the backend `/v1/__auth0/token` endpoint to interact with the Auth0 Management API via the worker.

### Login vs. Redirection

The framework provides two primary entry points for authentication:
- **`LoginLogoutLink`**: A contextual component that switches between "Login" and "Logout" based on state. Ideal for headers.
- **`LoginButton`**: A standalone component to trigger the Auth0 flow.

Users should be redirected to Auth0 automatically only when attempting to access a protected route wrapped in `AuthenticationGuard`. For public storefront pages, use `LoginLogoutLink` to allow optional sign-in.
