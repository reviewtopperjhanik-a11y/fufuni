## Authentication Architecture

Fufuni employs a multi-tiered authentication system designed for Cloudflare Workers. While **Auth0** serves as the primary Identity Provider (IdP) for human users (admins and customers), the framework also supports machine-to-machine (M2M) communication via API keys and scoped OAuth tokens. 

Role-Based Access Control (RBAC) is managed exclusively within the Auth0 dashboard for users. The backend middleware translates Auth0 permissions into internal `AuthRole` values, which are then used to gate specific Hono routes.

## Token Types and Role Assignment

The `authMiddleware` is the central entry point for authenticated requests. It identifies and validates three distinct token formats:

| Token Type | Format | Validation Mechanism | Assigned Role |
| :--- | :--- | :--- | :--- |
| **Auth0 JWT** | 3-part Bearer Token | Verified against Auth0 JWKS (Domain/Audience) | `admin`, `authadmin`, `databaseadmin`, `aiadmin`, `mail`, or `customer` |
| **Admin API Key** | `sk_...` prefix | SHA-256 hash lookup in the `api_keys` table | Defined in the database row (usually `admin`) |
| **OAuth Token** | 64-char hex string | SHA-256 hash lookup in `oauth_tokens` joined with `customers` | `oauth` |

### Role Resolution Logic

When a JWT is provided, roles are derived from the `permissions` claim. A single user can possess multiple roles simultaneously (represented as an array in `c.var.auth.role`).

```typescript
// Example of how roles are mapped from Auth0 permissions in authMiddleware
const roles: AuthRole[] = [];

// ADMIN_STORE_PERMISSION defaults to 'admin:store'
if (perms.includes(c.env.ADMIN_STORE_PERMISSION || 'admin:store')) {
  roles.push('admin');
}

// ADMIN_AUTH0_PERMISSION defaults to 'auth0:admin:api'
if (perms.includes(c.env.ADMIN_AUTH0_PERMISSION || 'auth0:admin:api')) {
  roles.push('authadmin');
}
```

## Backend RBAC Guards

Fufuni provides specialized middleware factories to enforce granular access control. These guards check the `AuthContext` populated by the initial `authMiddleware`.

| Middleware | Required Role | Required Auth0 Permission | Use Case |
| :--- | :--- | :--- | :--- |
| `adminOnly` | `admin` | `admin:store` | Standard dashboard management (Products, Orders). |
| `superAdminOnly` | `authadmin` | `auth0:admin:api` | Management API access and user permission editing. |
| `databaseAdminOnly`| `databaseadmin`| `admin:database` | Direct SQL execution or migration triggers. |
| `aiAccessOnly` | `aiadmin` | `ai:api` | Configuring LLM providers and translation settings. |
| `mailAccessOnly` | `mail` | `mail:api` | Sending transactional emails or checking logs. |
| `validJwtAuthOnly` | Any | None (Valid JWT only) | General authenticated routes without specific perms. |

### Protecting Admin Routes

To secure a route, you must first apply `authMiddleware` to initialize the context, followed by the specific RBAC guard.

```typescript
import { Hono } from 'hono';
import { authMiddleware, adminOnly } from './middleware/auth';
import { type HonoEnv } from './types';

const app = new Hono<HonoEnv>();

// Protect all routes in this router
app.use('/v1/products/*', authMiddleware);
app.use('/v1/products/*', adminOnly);

app.post('/v1/products', async (c) => {
  const auth = c.get('auth');
  console.log(`Product created by: ${auth.role}`);
  return c.json({ success: true });
});
```

## Management API and Superadmins

The `superAdminOnly` guard protects sensitive infrastructure operations, most notably the `/v1/__auth0/token` endpoint. This endpoint returns a cached **Auth0 Management API Token**.

Caching is critical here to stay within Auth0's Machine-to-Machine (M2M) token issuance quotas. The frontend uses this token to communicate with Auth0 via the `UsersAndPermissionsPage` for managing other users' access levels without leaving the storefront dashboard.

```typescript
import { Hono } from 'hono';
import { authMiddleware, superAdminOnly } from './middleware/auth';

const auth0Internal = new Hono<HonoEnv>();

/**
 * Returns an Auth0 Management API token.
 * Only accessible to users with 'auth0:admin:api' permission.
 */
auth0Internal.get('/token', authMiddleware, superAdminOnly, async (c) => {
  // Logic to fetch from KV cache or request new token from Auth0
  const token = await getManagementToken(c.env);
  return c.json({ access_token: token });
});
```

## Customer Authentication

The `customerAuthMiddleware` is tailored for the storefront (client-facing) API, specifically for routes under `/v1/me/*`. Unlike the standard auth middleware, it:
1. Rejects API keys (`sk_`, `pk_`)—it **only** accepts JWTs.
2. Does not require specific admin permissions.
3. Sets the role to `customer`.
4. Extracts identity claims like `sub` (Auth0 ID), `email`, and `user_metadata`.

```typescript
import { Hono } from 'hono';
import { customerAuthMiddleware } from './middleware/customer-auth';

const me = new Hono<HonoEnv>();

// Apply customer auth to the entire sub-router
me.use('*', customerAuthMiddleware);

me.get('/profile', async (c) => {
  const auth = c.get('auth');
  const sub = auth.sub; // e.g., 'auth0|64abc...'
  
  const db = getDb(c.var.db);
  const customer = await db.query(
    'SELECT * FROM customers WHERE auth0_sub = ?',
    [sub]
  );
  
  return c.json(customer[0]);
});
```

## OAuth Scopes for Third-Party Apps

When an external application uses a 64-character hex token, the role is set to `oauth`. These tokens are scoped. The `requireScope` middleware ensures the token possesses the necessary permissions for the specific action.

```typescript
import { authMiddleware, requireScope } from './middleware/auth';

// Ensure the OAuth token has 'orders:read' scope
app.get('/v1/external/orders', 
  authMiddleware, 
  requireScope('orders:read'), 
  async (c) => {
    return c.json({ orders: [] });
  }
);
```

## Frontend Guards and Permissions

Fufuni uses React 19 and a specialized Auth provider to manage security on the client side. 

### AuthenticationGuard vs. AuthenticationGuardWithPermission

1.  **`AuthenticationGuard`**: Used in the router level. If the user is not logged in, it triggers a redirect to the Auth0 login page.
2.  **`AuthenticationGuardWithPermission`**: Used for conditional UI rendering. It checks for a specific permission string and can show an optional "forbidden" fallback or simply hide the children.

```tsx
import { AuthenticationGuard, AuthenticationGuardWithPermission } from '@/components/auth-guard';
import { ProductsTable } from '@/components/products-table';

// 1. Page-level protection (Redirects to login if unauthenticated)
export const AdminProductsPage = () => (
  <AuthenticationGuard component={ProductsTable} />
);

// 2. Feature-level protection (Hides UI if permission missing)
export const DeleteProductButton = ({ id }: { id: string }) => (
  <AuthenticationGuardWithPermission 
    permission="admin:store" 
    fallback={<p>View Only Mode</p>}
  >
    <Button color="danger" onPress={() => deleteProduct(id)}>
      Delete Product
    </Button>
  </AuthenticationGuardWithPermission>
);
```

### Async Permission Checks

While `isAuthenticated` from `useAuth()` provides a synchronous boolean for login status, checking permissions is often asynchronous as it involves parsing the access token claims. `useSecuredApi()` provides the `hasPermission` helper.

```tsx
import { useSecuredApi } from '@/hooks/use-secured-api';
import { useEffect, useState } from 'react';

export const SettingsPanel = () => {
  const { hasPermission } = useSecuredApi();
  const [canEdit, setCanEdit] = useState(false);

  useEffect(() => {
    // hasPermission is an async check against the JWT claims
    hasPermission('admin:store').then(setCanEdit);
  }, [hasPermission]);

  if (!canEdit) return null;

  return <div>Sensitive Settings</div>;
};
```

## User and Permission Management

The `UsersAndPermissionsPage` (`/admin/users-and-permissions`) provides a high-level UI for managing Auth0 identities. It leverages the framework's ability to proxy Management API requests. 

This page allows admins to:
- Invite new users.
- Toggle permissions like `admin:store` or `ai:api`.
- Block/Unblock users.

Admins should use this internal page rather than the Auth0 Dashboard for day-to-day operations to ensure they remain within the context of the merchant's store environment.
