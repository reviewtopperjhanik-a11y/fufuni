## Purpose and Architecture

Fufuni provides an embedded OAuth2 server to facilitate secure, programmatic access to the Merchant API. While Auth0 remains the primary identity provider for the Merchant Dashboard (UI-based authentication), the embedded OAuth2 server is designed for two specific use cases:

1.  **Machine-to-Machine (M2M):** Enabling external services, scripts, or backend integrations to perform operations on behalf of the store (e.g., syncing inventory from a PIM).
2.  **Platform Integration:** Allowing third-party applications (AI agents, mobile apps) to act on behalf of a customer via the Authorization Code flow with PKCE (Proof Key for Code Exchange).

This dual-layer approach ensures that while human administrators use robust SSO, programmatic access remains lightweight, high-performance (running entirely on Cloudflare Workers), and under the merchant's direct control.

### Core Differences

| Feature | Auth0 (Dashboard) | Embedded OAuth2 (API) |
| :--- | :--- | :--- |
| **Primary User** | Store Admin / Staff | API Clients / Integrations |
| **Auth Method** | Browser-based Login | Client Credentials / Auth Code |
| **Token Type** | RS256 JWT (Auth0 Tenant) | HS256 JWT (Local Secret) |
| **Storage** | External | SQLite (Durable Objects) |

## Client Registration

OAuth clients are managed through the administrative API. Creating a client generates a `client_id` and a `client_secret`. 

**Critical Security Note:** The `client_secret` is hashed using `bcrypt` (or `hashKey` utility) before being stored in the `oauth_clients` table. It is returned **only once** in plaintext during the creation response. If lost, the secret must be regenerated.

### Creating an OAuth Client

To register a new integration, use the admin endpoint. You must specify the allowed scopes and a name for the client.

```typescript
// Example: Internal script to register a new M2M client
async function registerSyncClient(adminToken: string) {
  const response = await fetch('https://api.fufuni.store/v1/oauth/clients', {
    method: 'POST',
    headers: {
      'Authorization': `Bearer ${adminToken}`,
      'Content-Type': 'application/json'
    },
    body: JSON.stringify({
      name: 'Inventory Sync Bot',
      scopes: ['read:products', 'write:products', 'read:orders']
    })
  });

  const data = await response.json();
  console.log('Client ID:', data.client_id);
  console.log('Client Secret:', data.client_secret); // Store this safely!
}
```

### Database Schema Reference

The `oauth_clients` table tracks the credentials and permissions:

```sql
CREATE TABLE oauth_clients (
  id TEXT PRIMARY KEY,
  client_id TEXT UNIQUE NOT NULL,
  client_secret_hash TEXT, -- Stored as bcrypt hash
  name TEXT NOT NULL,
  redirect_uris TEXT, -- JSON array for Auth Code flow
  scopes TEXT, -- JSON array of allowed scopes
  created_at TEXT NOT NULL
);
```

## Token Request (Client Credentials Grant)

For server-to-server integrations, the `client_credentials` grant type is used. The client exchanges its ID and secret for a short-lived JWT access token.

### Requesting a Token via CURL

```bash
curl -X POST https://api.fufuni.store/v1/oauth/token \
  -H "Content-Type: application/json" \
  -d '{
    "grant_type": "client_credentials",
    "client_id": "cli_987654321",
    "client_secret": "your_secret_here",
    "scope": "read:products write:products"
  }'
```

### Successful Response

The server returns a signed JWT. By default, tokens are valid for 3600 seconds (1 hour).

```json
{
  "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "scope": "read:products write:products"
}
```

## Scope System and Restriction

Scopes in Fufuni control granular access to API resources. When a client requests a token, the server validates that the requested scopes are a subset of the scopes assigned to the `oauth_client` record during registration.

### Available Scopes

| Scope | Permission |
| :--- | :--- |
| `read:products` | View product listings and details |
| `write:products` | Create, update, or delete products |
| `read:orders` | View order history and status |
| `write:orders` | Update order status or tracking info |
| `read:customers` | Access customer profiles and addresses |
| `openid` / `profile` | Used specifically for Customer Auth Code flows |

### Implementation Logic

The token endpoint performs a set intersection check:

```typescript
// Simplified scope validation in oauth.ts
const requestedScopes = body.scope?.split(' ') || [];
const allowedScopes = JSON.parse(client.scopes);

const hasValidScopes = requestedScopes.every(s => allowedScopes.includes(s));
if (!hasValidScopes) {
  throw ApiError.invalidRequest('Requested scopes exceed client permissions');
}
```

## Token Structure and Security

Fufuni uses signed JWTs (JSON Web Tokens) for the embedded server. Unlike the Auth0 tokens which use RSA (RS256), the embedded server uses HMAC with SHA-256 (HS256) for performance and simplicity within the Cloudflare Worker environment.

### JWT Claims

The token payload contains the following standard claims:

```json
{
  "sub": "cli_987654321", // Client ID
  "iss": "https://api.fufuni.store",
  "iat": 1715432000,
  "exp": 1715435600,
  "scopes": ["read:products", "write:products"],
  "cid": "cust_12345" // Optional: Present only if acting on behalf of a customer
}
```

### Required Configuration

To enable JWT signing, the following secret must be set in your `wrangler.toml` or via the Cloudflare Dashboard:

```bash
# Add the signing secret to your environment
npx wrangler secret put OAUTH_JWT_SECRET
```

## Token Verification and Middleware

The framework provides an `oauthMiddleware` to protect routes. This middleware is distinct from the `customerAuthMiddleware` used for frontend sessions.

### Using the Middleware

Routes in Fufuni are designed to be "Auth-Agnostic," meaning they can accept either an Auth0 token or an Embedded OAuth token by chaining middlewares or using a unified validator.

```typescript
import { Hono } from 'hono';
import { oauthMiddleware } from '../middleware/oauth';
import { getDb } from '../db';

const products = new Hono<HonoEnv>();

// This route accepts OAuth2 Bearer tokens
products.get('/', oauthMiddleware('read:products'), async (c) => {
  const db = getDb(c.var.db);
  const products = await db.query('SELECT * FROM products');
  return c.json(products);
});

export { products };
```

### Internal Verification Logic

The middleware performs three checks:
1.  **Signature:** Validates the HS256 signature against `OAUTH_JWT_SECRET`.
2.  **Expiration:** Checks the `exp` claim against the current time.
3.  **Scope Requirement:** Ensures the token contains the specific scope required for the route.

```typescript
// snippet of middleware logic
export const oauthMiddleware = (requiredScope: string) => {
  return async (c: Context, next: Next) => {
    const authHeader = c.req.header('Authorization');
    if (!authHeader?.startsWith('Bearer ')) throw ApiError.unauthorized();

    const token = authHeader.split(' ')[1];
    const secret = c.env.OAUTH_JWT_SECRET;

    try {
      const payload = await verifyJwt(token, secret); // HS256 verification
      if (!payload.scopes.includes(requiredScope)) {
        throw ApiError.forbidden('Insufficient scope');
      }
      c.set('oauth_payload', payload);
      await next();
    } catch (e) {
      throw ApiError.unauthorized('Invalid token');
    }
  };
};
```

## Customer Authorization (PKCE Flow)

While M2M uses client secrets, Fufuni also supports the **Authorization Code Flow with PKCE** for public clients or integrations acting on behalf of a user.

### The Authorization URL

Clients redirect customers to the `/oauth/authorize` endpoint:

```text
GET /v1/oauth/authorize?
  response_type=code&
  client_id=my_mobile_app&
  redirect_uri=https://app.example.com/callback&
  scope=openid%20profile%20ucp:scopes:order&
  code_challenge=E9Melho2V8KQG3_D64mHMpCO1Dyb0Zf150P806uMEY&
  code_challenge_method=S256
```

### Login and Verification

1.  **Identity Verification:** The merchant server displays a login page (handled in `oauth.ts`).
2.  **Magic Link:** Fufuni sends a magic link to the customer's email (In dev mode, this link is shown in the console or a temporary UI page).
3.  **Code Issuance:** Once the link is clicked, the customer is redirected back to the `redirect_uri` with an authorization code.
4.  **Token Exchange:** The client exchanges the `code` and the `code_verifier` (PKCE) for a JWT using the `/v1/oauth/token` endpoint with `grant_type: "authorization_code"`.

### Example Token Exchange (Auth Code)

```typescript
// Client-side exchange after receiving 'code'
const tokenResponse = await fetch('https://api.fufuni.store/v1/oauth/token', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({
    grant_type: 'authorization_code',
    code: 'auth_code_from_url',
    redirect_uri: 'https://app.example.com/callback',
    client_id: 'my_mobile_app',
    code_verifier: 'original_pkce_verifier'
  })
});
```

This ensures that third-party applications never see the customer's email or magic tokens, adhering to the Unified Commerce Platform (UCP) compliance standards.
