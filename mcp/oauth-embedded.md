## Purpose and Architecture

Fufuni utilizes a dual-authentication strategy. While **Auth0** is the primary provider for customer-facing authentication (web login, profile management), the **Embedded OAuth2 Server** provides a lightweight, internal solution for Machine-to-Machine (M2M) communication and third-party platform integrations.

This embedded server allows the merchant to issue API keys (client IDs and secrets) to external services, AI agents, or ERP systems that need to interact with the Fufuni store programmatically without a browser-based session.

### Key Differences
| Feature | Auth0 (External) | Fufuni Embedded OAuth2 |
| :--- | :--- | :--- |
| **Primary Target** | Human Customers | AI Agents, Backend Services, Admin Tools |
| **Grant Types** | Authorization Code + PKCE | Client Credentials, Authorization Code |
| **Storage** | External Cloud | Internal SQLite (Durable Objects) |
| **Signing Key** | RSA (JWKS) | HMAC SHA-256 (`OAUTH_JWT_SECRET`) |

```typescript
// Example: Checking for OAuth context in a Hono route
import { Hono } from 'hono';
import { type HonoEnv } from '../types';

const app = new Hono<HonoEnv>();

app.get('/v1/internal/sync', async (c) => {
  // If authorized via oauthMiddleware, c.var.oauth contains the client info
  const oauth = c.get('oauthPayload');
  
  if (oauth) {
    return c.json({ 
      message: "Authorized via Embedded OAuth2",
      clientId: oauth.cid,
      scopes: oauth.sco 
    });
  }
  
  return c.json({ error: "Unauthorized" }, 401);
});
```

## Client Registration and Management

Clients must be registered in the `oauth_clients` table before they can request tokens. This is handled via admin-only endpoints. When a client is created, a `client_secret` is generated, hashed using `bcrypt` (or a secure equivalent like `PBKDF2` depending on the environment configuration), and stored.

**Important:** The raw `client_secret` is returned to the user **exactly once** during the creation response. It is never stored in plaintext and cannot be recovered.

### Creating a New OAuth Client

```typescript
// Admin Route: POST /v1/oauth/clients
// This example demonstrates how a client is persisted to the SQLite DB
import { uuid, now } from '../types';
import { hashKey } from '../middleware/auth'; // Uses bcrypt or SHA-256 hashing

async function createClient(db: any, name: string, scopes: string[]) {
  const clientId = `client_${uuid().split('-')[0]}`;
  const rawSecret = `fufuni_sk_${uuid().replace(/-/g, '')}`;
  const hashedSecret = await hashKey(rawSecret);

  await db.run(
    `INSERT INTO oauth_clients (id, client_id, client_secret_hash, name, scopes, created_at)
     VALUES (?, ?, ?, ?, ?, ?)`,
    [uuid(), clientId, hashedSecret, name, JSON.stringify(scopes), now()]
  );

  return {
    client_id: clientId,
    client_secret: rawSecret, // RETURNED ONLY ONCE
    scopes: scopes
  };
}
```

### Database Schema Reference

The SQLite table (managed by the Merchant Durable Object) typically follows this structure:

## Token Generation (Client Credentials Grant)

The `POST /v1/oauth/token` endpoint is the workhorse for machine-to-machine integration. It validates the `client_id` and `client_secret` and returns a signed JWT.

### Request/Response Example

A service identifies itself by sending its credentials in the request body (or via Basic Auth).

**Request (curl):**
```bash
curl -X POST https://api.yourstore.com/v1/oauth/token \
  -H "Content-Type: application/json" \
  -d '{
    "grant_type": "client_credentials",
    "client_id": "client_8f2a1b",
    "client_secret": "fufuni_sk_...",
    "scope": "read:products read:orders"
  }'
```

**Successful Response:**
```json
{
  "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "scope": "read:products read:orders"
}
```

### Implementation Logic

```typescript
// oauth.ts - Token Endpoint Implementation Snippet
oauth.post('/token', async (c) => {
  const body = await c.req.json();
  const { grant_type, client_id, client_secret, scope } = body;

  if (grant_type !== 'client_credentials') {
    throw ApiError.invalidRequest('Only client_credentials grant is supported for M2M');
  }

  const db = getDb(c.var.db);
  const [client] = await db.query(
    `SELECT * FROM oauth_clients WHERE client_id = ?`,
    [client_id]
  );

  // Validate secret (simplified comparison, use verifyHash in production)
  const isValid = await verifyHash(client_secret, client.client_secret_hash);
  if (!client || !isValid) {
    throw ApiError.unauthorized('Invalid client credentials');
  }

  // Validate Scopes: Requested scopes must be a subset of granted scopes
  const grantedScopes = JSON.parse(client.scopes);
  const requestedScopes = scope ? scope.split(' ') : grantedScopes;
  const hasValidScopes = requestedScopes.every((s: string) => grantedScopes.includes(s));

  if (!hasValidScopes) {
    throw ApiError.invalidRequest('Invalid scopes requested');
  }

  // Generate JWT using the OAUTH_JWT_SECRET
  const token = await generateJwt(
    { 
      sub: client.id, 
      cid: client.client_id, 
      sco: requestedScopes 
    },
    c.env.OAUTH_JWT_SECRET
  );

  return c.json({
    access_token: token,
    token_type: 'Bearer',
    expires_in: 3600,
    scope: requestedScopes.join(' ')
  });
});
```

## Scope-Based Authorization

The embedded server uses a specific list of granular scopes to control access to merchant resources. Unlike Auth0 customer tokens which usually have a `customer` scope, OAuth tokens are tailored for specific tasks.

### Available Scopes

- `read:products`: Allows viewing catalog, variants, and inventory.
- `write:products`: Allows creating, updating, or deleting products.
- `read:orders`: Allows viewing order history and fulfillment status.
- `write:orders`: Allows updating fulfillment status or processing refunds.
- `read:customers`: Allows viewing customer profiles (PII).

### Scope Enforcement in Routes

The `oauthMiddleware` populates the context with the granted scopes, which can then be checked at the route level.

```typescript
import { createMiddleware } from 'hono/factory';

export const requireScope = (required: string) => {
  return createMiddleware<HonoEnv>(async (c, next) => {
    const payload = c.get('oauthPayload');
    
    if (!payload || !payload.sco.includes(required)) {
      throw ApiError.forbidden(`Missing required scope: ${required}`);
    }
    
    await next();
  });
};

// Usage in a router
const productApi = new Hono<HonoEnv>();
productApi.delete('/:id', requireScope('write:products'), async (c) => {
  // Logic to delete product
});
```

## JWT Token Structure and Security

Tokens generated by the Fufuni OAuth2 server are **HS256 (HMAC with SHA-256)** signed JWTs. This differs from Auth0 which typically uses RS256. HS256 is chosen here for performance and simplicity within the Cloudflare Workers environment.

### JWT Claims
- `iss`: The origin URL of the merchant store.
- `sub`: The internal UUID of the OAuth client.
- `cid`: The public `client_id`.
- `sco`: An array of authorized scopes.
- `iat`: Issued at timestamp.
- `exp`: Expiration timestamp (default +3600 seconds).

### Security Requirements

The system **requires** the `OAUTH_JWT_SECRET` variable to be set in the Cloudflare environment. Without this secret, the token generation will fail.

```bash
# Set the signing secret in the Cloudflare environment
wrangler secret put OAUTH_JWT_SECRET
```

**Warning:** If this secret is changed, all currently active OAuth tokens will be immediately invalidated as their signatures will no longer match the new secret.

## Middleware and Route Protection

The `oauthMiddleware` is responsible for extracting the Bearer token from the `Authorization` header, verifying the signature against `OAUTH_JWT_SECRET`, and checking the expiration.

Fufuni routes are designed to be "Auth-Agnostic" where possible, meaning they can accept either an Auth0 token (from a customer) or an OAuth token (from a service).

### Implementation of the Middleware

```typescript
import { jwt } from 'hono/jwt';

export const oauthMiddleware = createMiddleware<HonoEnv>(async (c, next) => {
  const authHeader = c.req.header('Authorization');
  
  if (!authHeader?.startsWith('Bearer ')) {
    return await next();
  }

  const token = authHeader.split(' ')[1];
  
  try {
    // Verify using internal secret
    const payload = await jwt.verify(token, c.env.OAUTH_JWT_SECRET, 'HS256');
    
    // Attach payload to context for downstream use
    c.set('oauthPayload', payload as any);
    c.set('isMachineAccount', true);
    
  } catch (e) {
    // If it's not a valid internal token, we let it pass.
    // The customerAuthMiddleware might still pick it up if it's an Auth0 token.
    console.debug('Token is not a valid internal OAuth token');
  }

  await next();
});
```

### Combined Auth Strategy

In the main application entry point, both middlewares are often used in sequence to allow flexible access:

```typescript
const app = new Hono<HonoEnv>();

// Register both - they populate context variables if they find valid tokens
app.use('*', oauthMiddleware);
app.use('*', customerAuthMiddleware);

app.get('/v1/orders/:id', async (c) => {
  const customer = c.get('customer');
  const oauth = c.get('oauthPayload');

  // Logic: either the customer who owns the order OR an OAuth client with read:orders
  if (customer || (oauth && oauth.sco.includes('read:orders'))) {
    // Fetch and return order
  }

  throw ApiError.unauthorized();
});
```

## Required Wrangler Secret: OAUTH_JWT_SECRET

To ensure the security of the embedded OAuth server, the `OAUTH_JWT_SECRET` must be a high-entropy string (at least 32 characters). This secret is shared across all Durable Object instances for a specific merchant deployment, ensuring that a token issued by the OAuth router can be verified by any middleware instance within the same environment.

```typescript
// Accessing the secret in a Cloudflare Worker
export interface Bindings {
  OAUTH_JWT_SECRET: string;
  // ... other bindings
}

// In a route
const secret = c.env.OAUTH_JWT_SECRET;
if (!secret) {
  throw new Error("Configuration Error: OAUTH_JWT_SECRET is missing");
}
```

This secret should be rotated periodically using `wrangler secret put`. Note that rotation is "hard"—it does not support multiple valid secrets simultaneously; once updated, only the new secret is valid for verification.
