## Embedded OAuth Server

The merchant service ships with a self-contained OAuth 2.1 authorization server that lives **inside the same Cloudflare Worker** as the rest of the shop.  
It is **not** a proxy to Auth0; it uses its own SQLite tables (`oauth_clients`, `oauth_authorizations`, `oauth_tokens`) and issues **short-lived access tokens** that are **only valid for the Fufuni REST API exposed by that worker**.  
Auth0 is still used for **first-party** dashboard or checkout logins (those tokens never leave the browser), while the embedded server is meant for **third-party platforms** (mobile apps, AI agents, drop-shipping tools) that need to act **on behalf of a customer**.

Key differences at a glance:

| Aspect | Auth0 (first-party) | Embedded OAuth (third-party) |
|---|---|---|
| Audience | `https://fufuni.app` | `https://{{worker_subdomain}}.fufuni.workers.dev` |
| Token issuer | `https://auth.fufuni.app` | same as `audience` |
| Scopes | full RBAC | subset listed in `VALID_SCOPES` |
| Token storage | http-only cookie | `Authorization: Bearer` header |
| Token lifetime | 24 h (session) | 1 h (access) / 30 d (refresh) |
| User creation | manual / invite | auto-provisioned on first OAuth login |

### Authorization-Code Flow for Third Parties

The flow is standard OAuth 2.1 + PKCE (no client secret required).  
Platforms register on first use (row is inserted automatically) and must remember the `client_id` they started with.

#### 1. Discovery
```typescript
// GET /.well-known/oauth-authorization-server
const res = await fetch('https://shop-abc.fufuni.workers.dev/.well-known/oauth-authorization-server');
const meta = await res.json();

console.log(meta.authorization_endpoint); // "/oauth/authorize"
console.log(meta.scopes_supported);
// ["openid","profile","checkout","orders.read","orders.write", …]
```

#### 2. Authorization request
```typescript
// TypeScript (consumer side)
const verifier = generateVerifier();        // 43-char random
const challenge = await sha256base64url(verifier);

const authUrl = new URL(meta.authorization_endpoint);
authUrl.searchParams.set('client_id',    'com.example.app');
authUrl.searchParams.set('redirect_uri', 'com.example.app:/oauth/callback');
authUrl.searchParams.set('response_type','code');
authUrl.searchParams.set('scope',        'orders.read checkout');
authUrl.searchParams.set('state',        'xyz');          // optional
authUrl.searchParams.set('code_challenge', challenge);
authUrl.searchParams.set('code_challenge_method','S256');

// Redirect user
window.location.href = authUrl.toString();
```

The merchant renders a **magic-link page** (no e-mail service yet).  
When the customer clicks the link the endpoint `/oauth/verify` is hit and the browser is redirected back to the platform with `?code=XXX&state=xyz`.

#### 3. Token exchange
```typescript
const tokenRes = await fetch(meta.token_endpoint, {
  method : 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({
    grant_type   : 'authorization_code',
    client_id    : 'com.example.app',
    code         : url.searchParams.get('code'),
    redirect_uri : 'com.example.app:/oauth/callback',
    code_verifier: verifier,
  }),
});
const { access_token, refresh_token, expires_in, scope } = await tokenRes.json();
```

#### 4. Calling the shop API
```typescript
const api = axios.create({
  baseURL: 'https://shop-abc.fufuni.workers.dev/api',
  headers: { Authorization: `Bearer ${access_token}` },
});

const { data } = await api.get('/orders'); // only orders the customer owns
```

#### 5. Refreshing
```typescript
const { data } = await axios.post(meta.token_endpoint, {
  grant_type   : 'refresh_token',
  client_id    : 'com.example.app',
  refresh_token: storedRefreshToken,
});
// new access_token, same refresh_token
```

### Scope Limitations

The embedded server **whitelists** scopes in `VALID_SCOPES`.  
Anything not in that array is rejected with `invalid_request`.

| Scope | Meaning | Equivalent Auth0 permission |
|---|---|---|
| `openid` | include `sub` in id-token | — |
| `profile` | `name`, `email`, `picture` claims | — |
| `checkout` | create/checkout session | `checkout:write` |
| `orders.read` | list/read own orders | `order:read` |
| `orders.write` | cancel order | `order:write` |
| `addresses.read` | own addresses | `address:read` |
| `addresses.write` | add/update address | `address:write` |
| `ucp:scopes:checkout_session` | Universal-Checkout-Protocol scope | — |
| `ucp:scopes:order` | UCP order scope | — |
| `ucp:scopes:identity` | UCP identity scope | — |

Scopes **never** grant cross-customer access; every SQL query is filtered by the customer linked to the token.  
Merchant-level or admin scopes (`store:write`, `analytics`, `sk_*`) are **unavailable** through this server—those require an Auth0 token issued to a **first-party** dashboard user.

### Quick Start for Platform Developers

```bash
# 1. Pick a client_id (reverse-domain)
export CLIENT_ID=com.example.shipbot

# 2. Start the flow (PKCE)
npx @fufuni/oauth-cli \
  --issuer https://shop-abc.fufuni.workers.dev \
  --client-id $CLIENT_ID \
  --scope "orders.read checkout"

# 3. Store the returned refresh_token securely
# 4. Use it from your worker
```

The CLI opens the magic-link page, waits for the redirect, and prints the tokens—no manual copy-paste needed during development.
