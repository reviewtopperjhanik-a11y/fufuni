## Internal vs External Authentication

Fufuni utilizes two distinct authentication layers to balance administrative security with third-party interoperability. It is critical for developers to distinguish between the **Auth0 Identity Provider** and the **Embedded OAuth Server**.

### Auth0 (Administrative Access)
Auth0 is used exclusively for the Fufuni Merchant Dashboard. It handles B2B authentication for store owners and staff. When a merchant logs into `dashboard.fufuni.com`, they are using Auth0. This layer provides full access to the merchant's private API keys (`sk_`) and global configuration.

### Embedded OAuth (Third-Party Access)
The Embedded OAuth Server (located in `apps/merchant/src/routes/oauth.ts`) is a custom implementation running on Cloudflare Durable Objects. It allows external platforms—such as AI agents, mobile apps, or partner marketplaces—to act on behalf of a **Customer**, not the Merchant.

| Feature | Auth0 Instance | Embedded OAuth Server |
| :--- | :--- | :--- |
| **Target User** | Merchant / Admin | Store Customer / AI Agent |
| **Storage** | External (Auth0 Cloud) | Internal (SQLite Durable Object) |
| **Trust Level** | High (Full Admin) | Limited (Scoped access) |
| **Security Mechanism** | OIDC / JWT | OAuth 2.0 + PKCE (Proof Key for Code Exchange) |
| **Primary Use** | Dashboard Login | 3rd-party Checkouts & Order History |

## The Authorization Code Flow with PKCE

The Fufuni OAuth server implements the **Authorization Code Flow with PKCE** (RFC 7636). This is the gold standard for secure authentication in environments where client secrets cannot be safely stored (like SPAs or mobile apps) and for Universal Commerce Platform (UCP) compliance.

### 1. Discovery
Third-party apps first query the discovery endpoint to locate the authorization and token endpoints.

```typescript
// GET /oauth/.well-known/oauth-authorization-server
oauth.get('/.well-known/oauth-authorization-server', async (c) => {
  const baseUrl = new URL(c.req.url).origin;
  
  return c.json({
    issuer: baseUrl,
    authorization_endpoint: `${baseUrl}/oauth/authorize`,
    token_endpoint: `${baseUrl}/oauth/token`,
    revocation_endpoint: `${baseUrl}/oauth/revoke`,
    response_types_supported: ['code'],
    grant_types_supported: ['authorization_code', 'refresh_token'],
    code_challenge_methods_supported: ['S256'],
    token_endpoint_auth_methods_supported: ['none'], // PKCE removes the need for client_secret
    scopes_supported: [
      'openid', 'profile', 'ucp:scopes:checkout_session', 'checkout'
    ],
  });
});
```

### 2. Authorization and Login
When a user clicks "Connect to Fufuni" in a 3rd-party app, they are redirected to `/oauth/authorize`. The framework validates the request and renders a server-side login page.

Currently, Fufuni uses a **Magic Link** system for customer authentication. Instead of a password, customers enter their email, receive a link, and verify their identity.

```typescript
// Logic within POST /oauth/authorize
oauth.post('/authorize', async (c) => {
  const { auth_id, email } = await c.req.parseBody();
  const db = getDb(c.var.db);

  // 1. Generate a secure magic token
  const magicToken = generateSecret();
  const magicTokenHash = await hashKey(magicToken);
  
  // 2. Store the pending authorization
  await db.run(
    `UPDATE oauth_authorizations 
     SET customer_email = ?, magic_token_hash = ?, magic_expires_at = ? 
     WHERE id = ?`,
    [email.toLowerCase(), magicTokenHash, getExpiry(15), auth_id]
  );

  // 3. Dev Mode: Show link on screen (Production: Send via Resend/SendGrid)
  const magicLink = `${new URL(c.req.url).origin}/oauth/verify?token=${magicToken}&auth=${auth_id}`;
  return c.html(generateMagicLinkSentPage(email, magicLink));
});
```

### 3. Token Exchange
After the user clicks the magic link, they are redirected back to the third-party `redirect_uri` with a `code`. The third-party app then exchanges this code for an `access_token` by providing the `code_verifier`.

```typescript
// Logic within POST /oauth/token for grant_type: authorization_code
async function handleAuthorizationCodeGrant(c: any, body: Record<string, string>) {
  const { code, code_verifier, client_id } = body;
  const db = getDb(c.var.db);
  const codeHash = await hashKey(code);

  const [auth] = await db.query<any>(
    `SELECT * FROM oauth_authorizations WHERE code_hash = ? AND status = 'authorized'`,
    [codeHash]
  );

  // PKCE Validation: Verify the code_verifier matches the code_challenge
  const expectedChallenge = await generateCodeChallenge(code_verifier);
  if (expectedChallenge !== auth.code_challenge) {
    throw ApiError.invalidRequest('Invalid code_verifier (PKCE mismatch)');
  }

  // Issue tokens
  const accessToken = generateSecret();
  const refreshToken = generateSecret();
  
  await db.run(
    `INSERT INTO oauth_tokens (id, client_id, access_token_hash, refresh_token_hash, scope)
     VALUES (?, ?, ?, ?, ?)`,
    [uuid(), client_id, await hashKey(accessToken), await hashKey(refreshToken), auth.scope]
  );

  return c.json({
    access_token: accessToken,
    refresh_token: refreshToken,
    token_type: 'Bearer',
    expires_in: 3600
  });
}
```

## Scope Limitation and Security

Unlike internal API keys which have omnipotent access to the merchant's data, the Embedded OAuth server strictly limits what third-party applications can see or do. Scopes are validated during the initial `/authorize` request.

### Supported Scopes
The Fufuni framework restricts third-party apps to a subset of permissions related to customer activity:

*   `openid` / `profile`: Identity and email access.
*   `checkout`: Permission to create orders.
*   `orders.read`: Permission to view the customer's personal order history.
*   `ucp:scopes:checkout_session`: Compliance scope for UCP agents.

### Security Persistence (SQLite Schema)
The OAuth server state is persisted in the same Durable Object as the merchant's store data, but in specific tables. This ensures that even if one store's OAuth database is compromised, other stores in the Fufuni network remain unaffected.

```sql
-- Schema for OAuth operations (managed in apps/merchant/src/db.ts)

CREATE TABLE IF NOT EXISTS oauth_clients (
  id TEXT PRIMARY KEY,
  client_id TEXT UNIQUE NOT NULL,
  name TEXT NOT NULL,
  redirect_uris TEXT NOT NULL, -- JSON array
  created_at TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS oauth_authorizations (
  id TEXT PRIMARY KEY,
  client_id TEXT NOT NULL,
  customer_email TEXT,
  scope TEXT NOT NULL,
  code_challenge TEXT NOT NULL,
  code_hash TEXT,
  status TEXT DEFAULT 'pending', -- pending, authorized, used
  expires_at TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS oauth_tokens (
  id TEXT PRIMARY KEY,
  client_id TEXT NOT NULL,
  customer_id TEXT NOT NULL,
  access_token_hash TEXT UNIQUE NOT NULL,
  refresh_token_hash TEXT UNIQUE NOT NULL,
  scope TEXT NOT NULL,
  access_expires_at TEXT NOT NULL,
  refresh_expires_at TEXT NOT NULL
);
```

## Implementation Best Practices

### Automatic Client Registration
In the current Fufuni iteration, the server supports "Auto-Registration." If a client requests authorization and their `client_id` does not exist, the server creates a entry based on the hostname of the `redirect_uri`. This facilitates rapid prototyping with AI agents.

```typescript
// Inside GET /authorize
let [client] = await db.query<any>(
  `SELECT * FROM oauth_clients WHERE client_id = ?`,
  [clientId]
);

if (!client) {
  const domain = new URL(redirectUri).hostname;
  await db.run(
    `INSERT INTO oauth_clients (id, client_id, name, redirect_uris, created_at)
     VALUES (?, ?, ?, ?, ?)`,
    [uuid(), clientId, domain, JSON.stringify([redirectUri]), now()]
  );
}
```

### Hash Verification
Tokens (Access, Refresh, Magic, and Authorization Codes) must **NEVER** be stored in plain text. Fufuni uses the `hashKey` helper (utilizing SHA-256 via Web Crypto API) before saving to the SQLite database.

```typescript
// Correct way to verify a token from a request
const providedToken = c.req.query('token');
const tokenHash = await hashKey(providedToken);

const [auth] = await db.query(
  `SELECT * FROM oauth_authorizations WHERE magic_token_hash = ?`,
  [tokenHash]
);
```

### Token Revocation
The `/revoke` endpoint allows clients to invalidate their own tokens. This is essential for security hygiene when a user disconnects an app.

```typescript
oauth.post('/revoke', async (c) => {
  const body = await c.req.parseBody();
  const token = body['token'] as string;
  
  if (!token) return c.json({ revoked: true });
  
  const tokenHash = await hashKey(token);
  
  // Delete both access and refresh tokens associated with this hash
  await db.run(
    `DELETE FROM oauth_tokens WHERE access_token_hash = ? OR refresh_token_hash = ?`,
    [tokenHash, tokenHash]
  );
  
  return c.json({ revoked: true });
});
```
