## LocalizedContent Type Definition and Storage

In Fufuni, multi-language content is managed through a specific pattern known as `LocalizedText` (implemented as `LocalizedDesc` in the codebase). This pattern allows a single database column to store content for multiple regions while maintaining backward compatibility with legacy plain-text data.

The data is stored in the SQLite database as a `TEXT` column containing a JSON-serialized object. The keys of this object are BCP 47 locale strings (e.g., `en-US`, `fr-FR`), and the values are the localized strings.

```typescript
/**
 * LocalizedText (LocalizedDesc) structure.
 * Keys are locale codes, values are the actual content (HTML or Plain Text).
 */
export type LocalizedText = Record<string, string>;

// Database representation (JSON string)
// '{"en-US": "Blue Shirt", "fr-FR": "Chemise Bleue"}'

// Legacy representation (Plain text - auto-migrated on first edit)
// 'Blue Shirt'
```

When the framework encounters a plain string in a field that expects `LocalizedText`, it treats it as legacy data. The system automatically migrates this to the JSON format once an administrator edits the field in a specific locale, usually preserving the original text in the `en-US` key as a fallback.

## The getLocalizedText Logic and Fallback Chain

Retrieving text requires a "best-effort" resolution logic. If a requested locale (e.g., `es-ES`) is missing from the JSON object, the system traverses a predefined fallback chain to ensure the user never sees an empty string.

### Fallback Chain Definition
The order of preference for fallbacks is strictly defined to ensure consistency across the application:
1. `en-US` (American English)
2. `fr-FR` (French)
3. `es-ES` (Spanish)
4. `zh-CN` (Simplified Chinese)
5. `ar-SA` (Arabic)
6. `he-IL` (Hebrew)

### Implementation Example
The function `getLocalizedText` (internally mapped to `resolveDescription` or `resolveTitle`) implements this traversal.

```typescript
import { resolveTitle, resolveDescription } from "@/utils/description";

const rawDbValue = '{"en-US": "Pro Skateboard", "fr-FR": "Skate Pro"}';

// 1. Exact match
const titleFr = resolveTitle(rawDbValue, "fr-FR"); // "Skate Pro"

// 2. Fallback to en-US (if es-ES is missing)
const titleEs = resolveTitle(rawDbValue, "es-ES"); // "Pro Skateboard"

// 3. Handling legacy plain text
const legacyValue = "Old Skateboard";
const resolved = resolveTitle(legacyValue, "fr-FR"); // "Old Skateboard" (legacy compatibility)
```

## renderDescription vs stripHtml

Fufuni distinguishes between rich-text content (Descriptions) and plain-text content (Titles, Tax names, Vendors). 

### renderDescription()
When displaying product descriptions, we expect HTML. The `renderDescription` pattern (utilizing `resolveDescription`) prepares the string for injection into the DOM. Since the backend sanitizes content, the frontend uses `dangerouslySetInnerHTML`.

```tsx
import { resolveDescription } from "@/utils/description";

interface DescriptionProps {
  content: string;
  locale: string;
}

export const ProductDescription = ({ content, locale }: DescriptionProps) => {
  const htmlContent = resolveDescription(content, locale);

  return (
    <div 
      className="prose dark:prose-invert max-w-none"
      dangerouslySetInnerHTML={{ __html: htmlContent }} 
    />
  );
};
```

### stripHtml()
For contexts where HTML is forbidden—such as `<title>` tags, meta descriptions for SEO, or PDF invoice generation—the `stripHtml` utility is used to sanitize the resolved localized string.

```typescript
import { resolveTitle, stripHtml } from "@/utils/description";

const rawTitle = '{"en-US": "<strong>Sale</strong> Cap"}';
const locale = "en-US";

// Resolve and then strip tags
const cleanTitle = stripHtml(resolveTitle(rawTitle, locale)); 
// Output: "Sale Cap"
```

### Title Guards
The helper `resolveTitle` automatically applies `stripHtml` to its output. This prevents administrators from accidentally injecting HTML into plain-text fields like product names or tax categories.

## useLocalizedTextInput Hook

The `useLocalizedTextInput` hook is the standard Fufuni pattern for building multi-lingual forms in the admin dashboard. It synchronizes a controlled HeroUI input component with the complex `LocalizedText` JSON structure.

### Hook Parameters
- `value`: The raw string from the DB (JSON or plain text).
- `onChange`: Callback to update the parent state.
- `selectedLocale`: The currently active tab/language in the UI.
- `parseFn`/`mergeFn`/`getFn`: Utility functions from `description.ts` that define how this specific field behaves (e.g., Title vs. Handle).

### Usage in an Admin Form
The following example demonstrates a multi-tab title input with AI translation support.

```tsx
import { Tabs, Tab, Input, Button } from "@heroui/react";
import { useLocalizedTextInput } from "@/hooks/use-localized-text-input";
import { parseTitle, mergeTitleLocale, getTitleForLocale } from "@/utils/description";
import { SparklesIcon } from "@heroicons/react/24/solid";

export const LocalizedTitleInput = ({ value, onChange, locales }: any) => {
  const [activeTab, setActiveTab] = React.useState("en-US");

  const {
    inputValue,
    handleInputChange,
    handleAiTranslate,
    isTranslating,
    canUseAi,
    isRTL
  } = useLocalizedTextInput({
    value,
    onChange,
    selectedLocale: activeTab,
    parseFn: parseTitle,
    mergeFn: mergeTitleLocale,
    getFn: getTitleForLocale,
  });

  return (
    <div className="flex flex-col gap-4">
      <Tabs 
        selectedKey={activeTab} 
        onSelectionChange={(key) => setActiveTab(key as string)}
      >
        {locales.map((lang: any) => (
          <Tab key={lang.code} title={lang.name} />
        ))}
      </Tabs>

      <div className="relative">
        <Input
          label="Product Title"
          value={inputValue}
          onValueChange={handleInputChange}
          dir={isRTL ? "rtl" : "ltr"}
          endContent={
            canUseAi && (
              <Button
                isIconOnly
                size="sm"
                variant="light"
                isLoading={isTranslating}
                onClick={handleAiTranslate}
              >
                <SparklesIcon className="w-4 h-4 text-primary" />
              </Button>
            )
          }
        />
      </div>
    </div>
  );
};
```

## Rich-Text HTML Storage in Localized Fields

While titles and tags are plain text, the `description` field in the `products` table stores localized rich-text. The backend utilizes a TipTap-based editor (on the client) which generates HTML strings. These strings are stored inside the `LocalizedText` JSON.

### Storage Example
```json
{
  "en-US": "<h1>Quality Cotton</h1><p>Breathable fabric.</p>",
  "fr-FR": "<h1>Coton de Qualité</h1><p>Tissu respirant.</p>"
}
```

### Processing Logic
When editing rich text, the `getEditorContent` helper is used. Unlike `resolveDescription`, which might return a fallback, `getEditorContent` is designed to show the administrator exactly what exists for that locale, or provide the fallback as a starting point for translation if the field is currently empty.

```typescript
import { getEditorContent, mergeLocale } from "@/utils/description";

// When switching to 'fr-FR' in the editor:
const contentToEdit = getEditorContent(rawDbString, "fr-FR");

// When saving:
const updatedJson = mergeLocale(rawDbString, "fr-FR", editor.getHTML());
```

## Adding Support for a New Locale

To add a new locale to an existing admin form, follow these steps:

### 1. Update the i18n Configuration
Ensure the new locale is defined in `apps/client/src/i18n/index.ts` so the `availableLanguages` array includes it.

```typescript
// apps/client/src/i18n/index.ts
export const availableLanguages = [
  { code: "en-US", name: "English", nativeName: "English", isRTL: false },
  { code: "fr-FR", name: "French", nativeName: "Français", isRTL: false },
  { code: "ja-JP", name: "Japanese", nativeName: "日本語", isRTL: false }, // NEW
];
```

### 2. Update the UI Component
The `useLocalizedTextInput` hook doesn't limit the locales; it responds to the `selectedLocale` passed to it. If your form uses a Tabs layout, ensure the tabs iterate over the updated language list.

```tsx
// Inside your Product Editor component
import { availableLanguages } from "@/i18n";

const ProductEditor = ({ product, updateProduct }) => {
  return (
    <LocalizedTitleInput 
      value={product.title} 
      onChange={(val) => updateProduct({ title: val })}
      locales={availableLanguages} // The component now renders Japanese automatically
    />
  );
};
```

### 3. Database Migration (Optional)
Existing records do not need a migration. The first time an admin switches to the Japanese tab and types a title, `mergeTitleLocale` will detect the JSON structure and add the `ja-JP` key to the existing object. If the field was previously a plain string, it will convert it to JSON, placing the legacy text in `en-US` and the new text in `ja-JP`.

```typescript
// Migration logic inside mergeTitleLocale automatically handles this:
const result = mergeTitleLocale("Legacy Title", "ja-JP", "日本語のタイトル");
// Result: '{"en-US": "Legacy Title", "ja-JP": "日本語のタイトル"}'
```
