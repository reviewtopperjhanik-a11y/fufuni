## Data Model and Schema

Fufuni manages inventory at the intersection of product variants and physical locations. While legacy systems might track a single global count, the framework utilizes a multi-warehouse architecture where stock is localized.

### SQLite Schema

The core state resides in the `inventory` and `warehouses` tables. The `inventory` table tracks both physical stock (`on_hand`) and temporary holds (`reserved`) for every variant at every location.

```sql
-- Core warehouse definition
CREATE TABLE warehouses (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  address TEXT,
  is_default INTEGER DEFAULT 0, -- 1 if this is the default warehouse for new stock
  priority INTEGER DEFAULT 0,    -- Used for allocation logic
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);

-- Inventory mapping (Variant <-> Warehouse)
CREATE TABLE inventory (
  variant_id TEXT NOT NULL,
  warehouse_id TEXT NOT NULL,
  on_hand INTEGER DEFAULT 0,   -- Physical items in the building
  reserved INTEGER DEFAULT 0,  -- Items in carts or pending payment
  updated_at INTEGER NOT NULL,
  PRIMARY KEY (variant_id, warehouse_id),
  FOREIGN KEY (variant_id) REFERENCES variants(id),
  FOREIGN KEY (warehouse_id) REFERENCES warehouses(id)
);

-- Audit log for stock movements
CREATE TABLE inventory_logs (
  id TEXT PRIMARY KEY,
  variant_id TEXT NOT NULL,
  warehouse_id TEXT NOT NULL,
  delta INTEGER NOT NULL,
  reason TEXT,
  created_at INTEGER NOT NULL
);
```

## Transaction Safety in Durable Objects

Fufuni leverages Cloudflare Durable Objects (DO) to guarantee consistency. Because a DO is a single-threaded execution environment for a specific "partition" (like a merchant's store), we avoid the complex race conditions typical in distributed databases.

Every inventory mutation—reservation, release, or deduction—must occur within a DO request. This ensures that two customers attempting to buy the last item will be processed sequentially. If `reserveStock` is called by User A, the SQLite row is locked during the update; User B's request will see the updated `reserved` count immediately after.

```typescript
// Example of an atomic adjustment within a Hono route using DO storage
app.post('/v1/inventory/adjust', async (c) => {
  const { variantId, warehouseId, delta, reason } = await c.req.json();
  const db = getDb(c.var.db);

  // We wrap logic in a standard transaction, but the DO itself 
  // provides the primary serialization of these requests.
  const result = await db.run(
    `UPDATE inventory 
     SET on_hand = on_hand + ?, updated_at = ? 
     WHERE variant_id = ? AND warehouse_id = ? 
     AND (on_hand + ?) >= 0`,
    [delta, Date.now(), variantId, warehouseId, delta]
  );

  if (result.changes === 0) {
    throw ApiError.invalidRequest("Insufficient stock or invalid variant/warehouse mapping");
  }

  return c.json({ success: true });
});
```

## Inventory Utility Functions (`lib/inventory.ts`)

The framework provides a standard library to interact with stock levels. These functions abstract the multi-warehouse complexity from the business logic.

### 1. `getStockLevel(db, variantId)`
Calculates total availability across all warehouses. Availability is defined as `on_hand - reserved`.

```typescript
export async function getStockLevel(db: Database, variantId: string): Promise<number> {
  const result = await db.query<{ available: number }>(
    `SELECT SUM(on_hand - reserved) as available 
     FROM inventory 
     WHERE variant_id = ?`,
    [variantId]
  );
  return result[0]?.available ?? 0;
}
```

### 2. `reserveStock(db, variantId, qty)`
Increments the `reserved` column. This is typically called when a customer adds an item to a checkout session. It prioritizes the warehouse with the highest available stock.

```typescript
export async function reserveStock(db: Database, variantId: string, qty: number): Promise<void> {
  const timestamp = Date.now();
  
  // Find the warehouse with the most stock to fulfill this reservation
  const result = await db.run(
    `UPDATE inventory
     SET reserved = reserved + ?, updated_at = ?
     WHERE variant_id = ?
       AND warehouse_id = (
         SELECT warehouse_id FROM inventory
         WHERE variant_id = ?
         ORDER BY (on_hand - reserved) DESC
         LIMIT 1
       )
       AND (on_hand - reserved) >= ?`,
    [qty, timestamp, variantId, variantId, qty]
  );

  if (result.changes === 0) {
    throw new Error(`Insufficient inventory for variant: ${variantId}`);
  }
}
```

### 3. `releaseStock(db, variantId, qty)`
Decrements the `reserved` column without touching `on_hand`. Use this when a checkout expires or a cart is cleared.

```typescript
export async function releaseStock(db: Database, variantId: string, qty: number): Promise<void> {
  await db.run(
    `UPDATE inventory 
     SET reserved = MAX(reserved - ?, 0), updated_at = ?
     WHERE variant_id = ?`,
    [qty, Date.now(), variantId]
  );
}
```

### 4. `deductStock(db, variantId, qty)`
The final step after payment. It reduces both `on_hand` and `reserved` counts simultaneously.

```typescript
export async function deductStock(db: Database, variantId: string, qty: number): Promise<void> {
  await db.run(
    `UPDATE inventory 
     SET on_hand = MAX(on_hand - ?, 0), 
         reserved = MAX(reserved - ?, 0),
         updated_at = ?
     WHERE variant_id = ? AND reserved >= ?`,
    [qty, qty, Date.now(), variantId, qty]
  );
}
```

## Checkout Lifecycle

The inventory state transitions through several phases during a customer's purchase journey:

1.  **Validation (Cart/Checkout Start):** The system calls `getStockLevel`. If stock is sufficient, `reserveStock` is called. The items are now "soft-locked."
2.  **Payment Processing:** While the customer is on the Stripe hosted page, the items remain reserved.
3.  **Completion (Post-Payment):** Upon receiving a `checkout.session.completed` webhook, the system calls `deductStock`.
4.  **Failure/Expiry:** If the customer abandons the checkout or payment fails, `releaseStock` is called to return the units to the "available" pool.

## Low-Stock Webhooks

To prevent stockouts, Fufuni includes an automated notification system. After any `deductStock` operation, the system evaluates the remaining available quantity against a configured threshold (default is 10).

### Event Trigger
If `available < threshold`, a `low_stock` event is dispatched via the Webhook subsystem.

```typescript
// Internal logic triggered after deductStock
async function checkLowStock(db: Database, variantId: string) {
  const available = await getStockLevel(db, variantId);
  const threshold = 10; 

  if (available <= threshold) {
    await dispatchWebhook('low_stock', {
      variant_id: variantId,
      current_stock: available,
      threshold: threshold,
      timestamp: Date.now()
    });
  }
}
```

## Multi-warehouse Aggregation

The framework supports intelligent stock routing. When a product is created, Fufuni looks for the warehouse marked `is_default: 1` and creates the initial `inventory` record there with a quantity of 0.

When querying stock for the storefront, the backend sums the `on_hand` and `reserved` values across all warehouses associated with that variant. This allows a merchant to have stock in London and New York, and the website will show the combined availability to the user.

```sql
-- Aggregation query used by the storefront
SELECT 
    v.id as variant_id,
    SUM(i.on_hand) as total_physical,
    SUM(i.reserved) as total_reserved,
    (SUM(i.on_hand) - SUM(i.reserved)) as total_available
FROM variants v
JOIN inventory i ON v.id = i.variant_id
WHERE v.id = 'var_999'
GROUP BY v.id;
```
