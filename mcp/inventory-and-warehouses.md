## Multi-Warehouse Architecture

Fufuni utilizes a hybrid inventory system designed to support both single-location merchants and complex multi-warehouse operations. The source of truth for stock levels is the `warehouse_inventory` table. Every physical movement—whether an arrival of new stock, a manual adjustment, or a sale—is recorded in `warehouse_inventory_logs` to provide a full audit trail.

To maintain backward compatibility with legacy checkout engines and high-level dashboard views, the framework synchronizes aggregated totals into a legacy `inventory` table. 

### Data Structure and Aggregation

The system distinguishes between three primary metrics:
1.  **On Hand**: The total physical units currently present in a warehouse.
2.  **Reserved**: Units allocated to pending orders/carts but not yet shipped.
3.  **Available**: Calculated as `on_hand - reserved`. This is the figure shown to customers.

The following example demonstrates how to retrieve aggregated inventory across all warehouses for a specific SKU using the `Database` utility:

```typescript
import type { Database } from '../db';

/**
 * Retrieves aggregated inventory status for a SKU across all locations.
 */
async function getGlobalSkuStatus(db: Database, sku: string) {
  const query = `
    SELECT 
      sku,
      SUM(on_hand) as total_on_hand,
      SUM(reserved) as total_reserved,
      (SUM(on_hand) - SUM(reserved)) as total_available
    FROM warehouse_inventory
    WHERE sku = ?
    GROUP BY sku
  `;
  
  const [result] = await db.query<any>(query, [sku]);
  
  if (!result) {
    return { sku, on_hand: 0, reserved: 0, available: 0 };
  }

  return {
    sku: result.sku,
    on_hand: result.total_on_hand,
    reserved: result.total_reserved,
    available: result.total_available
  };
}
```

### Warehouse Selection Logic

When reserving inventory for an order, Fufuni employs a "Highest Availability" strategy. The system identifies the warehouse with the most available stock for that specific SKU and places the reservation there. This prevents single-warehouse depletion when other locations have surplus.

## Reservation and Commitment Lifecycle

Inventory in Fufuni follows a strict lifecycle to prevent overselling while ensuring that stock is not "lost" due to abandoned carts or failed payments.

### 1. Reservation (Order Creation)
When a customer adds an item to their cart or initiates checkout, `reserveInventory` is called. This increments the `reserved` column but leaves `on_hand` untouched. 

### 2. Commitment (Payment Success)
Once the Stripe webhook confirms payment, `commitSale` is triggered. This decrements both `on_hand` and `reserved` simultaneously.

### 3. Release (Expiration/Failure)
If a payment fails or a cart session expires, `releaseReservation` decrements the `reserved` count, making the stock available to other customers again.

Here is how these functions are typically orchestrated within a service or middleware:

```typescript
import { reserveInventory, commitSale, releaseReservation } from '../lib/inventory';
import { getDb } from '../db';
import type { Database } from '../db';

/**
 * Example of the inventory lifecycle during a checkout process.
 */
export async function processOrderInventory(db: Database, sku: string, qty: number) {
  try {
    // Step 1: Reserve the stock immediately when order is placed
    // This throws if insufficient stock is available.
    await reserveInventory(db, sku, qty);
    console.log(`Reserved ${qty} units for SKU: ${sku}`);

    // ... Payment logic occurs here ...
    const paymentSuccessful = true; 

    if (paymentSuccessful) {
      // Step 2: Confirm the sale and deduct physical stock
      await commitSale(db, sku, qty);
    } else {
      // Step 3: Payment failed, put the stock back
      await releaseReservation(db, sku, qty);
    }
  } catch (error) {
    // Handle insufficient inventory or DB errors
    console.error("Inventory operation failed", error);
    throw error;
  }
}
```

## Inventory Logging and Auditing

Every modification to the `warehouse_inventory` must be accompanied by an entry in `warehouse_inventory_logs`. This table records the `delta` (change in quantity) and a `reason` string (e.g., "restock", "damage", "return", "manual_adjustment").

### Manual Stock Adjustment

When an administrator manually adjusts stock through the Merchant Dashboard, the `adjustWarehouseInventory` route handles the update and the logging in a single atomic flow.

```typescript
import { uuid, now } from '../types';
import type { Database } from '../db';

/**
 * Adjusts inventory at a specific warehouse and logs the change.
 */
async function manualStockAdjustment(
  db: Database, 
  sku: string, 
  warehouseId: string, 
  delta: number, 
  reason: string
) {
  const timestamp = now();
  
  // 1. Update the physical stock
  await db.run(
    `UPDATE warehouse_inventory 
     SET on_hand = on_hand + ?, updated_at = ? 
     WHERE sku = ? AND warehouse_id = ?`,
    [delta, timestamp, sku, warehouseId]
  );

  // 2. Create the audit log
  await db.run(
    `INSERT INTO warehouse_inventory_logs (id, sku, warehouse_id, delta, reason, created_at) 
     VALUES (?, ?, ?, ?, ?, ?)`,
    [uuid(), sku, warehouseId, delta, reason, timestamp]
  );

  // 3. Sync to legacy table (Crucial for framework consistency)
  await db.run(
    `UPDATE inventory
     SET on_hand = (SELECT SUM(on_hand) FROM warehouse_inventory WHERE sku = ?),
         updated_at = ?
     WHERE sku = ?`,
    [sku, timestamp, sku]
  );
}
```

## Handling Insufficient Stock

Preventing overselling is a critical requirement. While the `lib/inventory.ts` utility performs internal checks, the **Hono handler** is responsible for validating stock levels and throwing the appropriate `ApiError.insufficientInventory()`.

### Handler-Level Validation

Before attempting any reservation, the handler should verify the available quantity. This allows the API to return a clean 400 Bad Request error to the frontend before any database locks or complex transactions begin.

```typescript
import { OpenAPIHono, createRoute } from '@hono/zod-openapi';
import { getAvailableQty, reserveInventory } from '../lib/inventory';
import { ApiError, type HonoEnv } from '../types';
import { getDb } from '../db';

const app = new OpenAPIHono<HonoEnv>();

// Example route for adding to cart with strict inventory check
app.post('/cart/add', async (c) => {
  const { sku, quantity } = await c.req.json();
  const db = getDb(c.var.db);

  // 1. Check availability
  const available = await getAvailableQty(db, sku);
  
  if (available < quantity) {
    // Verified Fact: The handler must throw the error, not the lib directly.
    throw ApiError.insufficientInventory(sku);
  }

  // 2. Proceed with reservation
  await reserveInventory(db, sku, quantity);

  return c.json({ success: true, message: "Item reserved in cart" });
});
```

### Low Stock Webhooks

The framework includes a utility `checkLowInventory` which is called after every inventory adjustment. If the `available` quantity drops below a configured threshold (default is 10 units), the system triggers a webhook to notify the merchant via email or Slack.

```typescript
// Inside a Hono route handler after adjustment:
import { checkLowInventory } from '../lib/webhooks';

// ... update logic ...

const available = level.on_hand - level.reserved;

// Fire-and-forget background task to check thresholds
c.executionCtx.waitUntil(
  checkLowInventory(c.var.db, c.executionCtx, sku, available)
);
```

## Regional Inventory Mapping

Fufuni supports grouping warehouses into **Regions**. This is useful for storefronts that only ship to specific geographic areas from specific hubs.

The `getRegionalInventory` route allows the frontend to query stock restricted to a specific region, which is essential for accurate "Estimated Delivery" calculations and region-specific availability.

```typescript
/**
 * Query pattern for regional aggregation
 */
async function getStockByRegion(db: Database, sku: string, regionId: string) {
  return await db.query<any>(
    `SELECT 
       SUM(wi.on_hand) as regional_on_hand,
       SUM(wi.reserved) as regional_reserved
     FROM warehouse_inventory wi
     JOIN region_warehouses rw ON wi.warehouse_id = rw.warehouse_id
     WHERE wi.sku = ? AND rw.region_id = ?`,
    [sku, regionId]
  );
}
```

This ensures that even if a product is in stock globally, a customer in the "Europe" region will see it as "Out of Stock" if the European warehouses are empty.
