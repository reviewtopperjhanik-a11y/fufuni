## Evolution of Fufuni Migrations

Fufuni leverages Cloudflare Durable Objects (DO) with embedded SQLite. Unlike traditional architectures where a single central database is migrated via a CI/CD pipeline, Fufuni's database is decentralized. Every merchant has their own unique Durable Object instance containing its own SQLite file. 

This architectural choice necessitates a "self-healing" migration strategy. When a Durable Object wakes up, it must inspect its own internal state, determine its current schema version, and apply necessary transformations. As of the current development cycle, the framework has evolved through 33 distinct schema iterations. Any developer introducing a change to the database structure must target version **034** and follow a non-negotiable three-step protocol to ensure that both existing merchants (legacy data) and new merchants (fresh data) remain in sync.

### Why three steps?
1.  **Deltas for Existing Data:** Existing merchant DOs already have tables. We cannot simply overwrite their files. We must apply `ALTER TABLE` or `CREATE TABLE` commands sequentially.
2.  **Golden Image for New Data:** When a new merchant signs up, it is inefficient to run 34 separate SQL migration scripts. Instead, we maintain a `SCHEMA` constant that represents the "latest state." This allows new DOs to boot up instantly with the correct structure.
3.  **Historical Integrity:** The `.sql` files in the migrations folder serve as the source of truth for version control, audit trails, and providing context to AI coding assistants (LLMs) that need to understand the data model.

## The Strict 3-Step Migration Protocol

When adding a feature that requires a database change—for example, adding a `loyalty_points` column to a `customers` table—you must perform these three operations in a single pull request.

### Step 1: Modifying ensureInitialized() in apps/merchant/src/do.ts

The `ensureInitialized()` method is the runtime engine of our migrations. It uses the `PRAGMA user_version` feature of SQLite to track which migration was last applied to that specific DO.

```typescript
// apps/merchant/src/do.ts

async ensureInitialized() {
  // Get current version from SQLite PRAGMA
  const currentVersionResult = this.storage.sql.exec("PRAGMA user_version;").one();
  let currentVersion = Number(currentVersionResult?.user_version || 0);

  // ... previous migrations 001 to 033 ...

  // NEW MIGRATION: 034
  if (currentVersion < 34) {
    console.log("Applying migration 034: Add loyalty_points to customers");
    try {
      // Use this.storage.sql.exec for DDL statements
      this.storage.sql.exec(`
        ALTER TABLE customers ADD COLUMN loyalty_points INTEGER DEFAULT 0;
        PRAGMA user_version = 34;
      `);
      currentVersion = 34;
    } catch (e) {
      console.error("Migration 034 failed:", e);
      throw e; // Crash the DO to prevent data corruption
    }
  }
}
```

### Step 2: Modifying the SCHEMA Constant

The `SCHEMA` constant is used by the `initializeNewDatabase()` logic (or similar) when a DO detects it has no existing tables. This constant must always reflect the absolute current state of the database.

### Step 3: Creating the .sql Migration File

You must create a physical file in the migrations directory. This file is not executed by the production code at runtime, but it is required for developer tooling, local environment seeding, and documentation.

```sql

-- Author: Senior Developer
```

## Automatic Execution Mechanism

The Fufuni framework ensures that migrations run automatically without manual intervention or external "migration runner" tools. This is achieved by hooking into the Durable Object's lifecycle.

### The Lifecycle Hook

Inside the `MerchantDO` class (extending `DurableObject`), the `ensureInitialized` method is called within the `fetch` handler or the `constructor`. To minimize latency on every request, we typically wrap it in a "once-per-instantiation" promise.

```typescript
// apps/merchant/src/do.ts
import { DurableObject } from "cloudflare:workers";

export class MerchantDO extends DurableObject {
  private initializationPromise: Promise<void> | null = null;

  constructor(state: DurableObjectState, env: Env) {
    super(state, env);
  }

  /**
   * The fetch handler is the entry point for all requests to this DO.
   * We ensure the DB is migrated before processing any logic.
   */
  async fetch(request: Request): Promise<Response> {
    // Lazy initialization pattern
    if (!this.initializationPromise) {
      this.initializationPromise = this.ensureInitialized();
    }
    
    await this.initializationPromise;

    // Proceed with Hono router or custom logic
    return this.router.fetch(request);
  }

  async ensureInitialized() {
    const version = this.storage.sql.exec("PRAGMA user_version").one().user_version;
    
    // If version is 0, it's a fresh DB
    if (version === 0) {
      console.log("Initializing fresh database...");
      this.storage.sql.exec(SCHEMA);
      this.storage.sql.exec("PRAGMA user_version = 34"); // Set directly to latest
      return;
    }

    // Apply incremental updates if not fresh
    // (The logic from Step 1 goes here)
  }
}
```

### Handling Schema Conflicts

Because SQLite in Durable Objects is strictly typed when using specific configurations, or dynamic when using others, you must be careful with `ALTER TABLE`. 

1.  **Adding Columns:** Always provide a `DEFAULT` value if the column is `NOT NULL`.
2.  **Dropping Columns:** SQLite does not support `ALTER TABLE DROP COLUMN` in older versions. While Cloudflare's SQLite is modern, the safest way to "drop" is often to ignore the column in your Zod schemas and DTOs.
3.  **Renaming Tables:** If renaming, you must use a transaction to ensure data integrity.

### Transactional Safety

When applying migrations, use `this.storage.transaction()` to ensure that if a migration fails halfway through, the database version isn't incremented and the changes are rolled back.

```typescript
// Example of a transactional migration block within ensureInitialized
if (currentVersion < 34) {
  this.storage.transaction(() => {
    this.storage.sql.exec("ALTER TABLE customers ADD COLUMN loyalty_points INTEGER DEFAULT 0;");
    this.storage.sql.exec("PRAGMA user_version = 34;");
  });
  currentVersion = 34;
}
```

## Local Verification Checklist

Before submitting a PR with migration **034**, perform these checks:

### 1. Fresh Install Check
Wipe your local Miniflare/Wrangler state:
```bash
# Delete local DO storage
rm -rf .wrangler/state/v3/durable_objects/
```
Run the app. Verify that the `customers` table has the `loyalty_points` column immediately upon the first request.

### 2. Upgrade Check
1. Revert your `do.ts` changes temporarily to version 033.
2. Seed some data into the `customers` table.
3. Re-apply migration 034 code.
4. Run the app. Verify that existing customers now have the `loyalty_points` column with the default value of `0` and that no data was lost.

### 3. File Inventory
Ensure the following files exist and match:
- [ ] `apps/merchant/src/do.ts`: `ensureInitialized()` contains the `if (version < 34)` block.
- [ ] `apps/merchant/src/do.ts`: `SCHEMA` constant includes the new column/table.
- [ ] `apps/merchant/migrations/034_your_feature_name.sql`: Contains the raw SQL.

This 3-step process is the backbone of Fufuni's database reliability. Failure to update the `SCHEMA` constant will result in broken new installations, while failure to update `ensureInitialized` will break existing production merchant accounts.
