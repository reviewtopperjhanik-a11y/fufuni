## Database Migration Architecture

In the Fufuni framework, each Merchant (store) runs inside a dedicated Cloudflare Durable Object (DO) powered by SQLite. Unlike traditional centralized databases where a single migration script updates one global instance, Fufuni manages thousands of isolated database instances. When the codebase is updated, every existing Durable Object must safely transition its schema the next time it wakes up, while simultaneously ensuring that newly created Durable Objects start with the most current schema immediately.

As of the current version, the system tracks migrations up to version **033**. Any new schema change must increment this version (e.g., **034**) and follow the synchronized 3-step update process to prevent data loss or schema drift between old and new merchant instances.

### The Lifecycle of a Migration

When a Durable Object is instantiated, the `constructor` or the first request triggers a call to `ensureInitialized()`. This method checks the `PRAGMA user_version` of the local SQLite file. If the version is lower than the current application version, the system executes the missing delta scripts sequentially until the database is up to date.

## The Strict 3-Step Migration Process

To maintain consistency between the code-level schema definitions and the actual database state, every developer MUST perform these three steps in a single PR. Skipping any step will result in either broken new installs or legacy instances that fail to update.

### 1. Update ensureInitialized() in apps/merchant/src/do.ts

The `ensureInitialized` method is the runtime engine for migrations. It detects the current version of the existing SQLite database and applies the necessary SQL commands to evolve it.

```typescript
// apps/merchant/src/do.ts

async ensureInitialized() {
  // 1. Get current version
  let version = this.db.prepare("PRAGMA user_version").get<{ user_version: number }>()?.user_version ?? 0;

  // ... (existing migrations 001 to 033)

  // Example: Adding Migration 034 to add a 'priority' column to the 'tasks' table
  if (version < 34) {
    console.log("Migrating to version 034: Adding task priority...");
    this.db.exec(`
      ALTER TABLE tasks ADD COLUMN priority INTEGER DEFAULT 0;
      PRAGMA user_version = 34;
    `);
    version = 34;
  }
}
```

**Key Requirement:** Always increment `PRAGMA user_version` at the end of the `exec` block. This ensures that the migration doesn't run again on the next reboot.

### 2. Update the SCHEMA Constant in apps/merchant/src/do.ts

The `SCHEMA` constant is the "Source of Truth" for new database instances. When a new merchant signs up, their Durable Object is empty. Instead of running 34 migrations sequentially, the DO simply executes the full `SCHEMA` string to create the latest structure in one go.

```typescript
// apps/merchant/src/do.ts

const SCHEMA = `
CREATE TABLE IF NOT EXISTS settings (
  key TEXT PRIMARY KEY,
  value TEXT
);

CREATE TABLE IF NOT EXISTS tasks (
  id TEXT PRIMARY KEY,
  title TEXT NOT NULL,
  content TEXT,
  priority INTEGER DEFAULT 0, -- Added in 034
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

-- IMPORTANT: New databases must also set their user_version to the latest
PRAGMA user_version = 34;
`;
```

**Why this is mandatory:** If you only update `ensureInitialized()`, new merchants will have a schema that is 34 versions behind, and the system will immediately try to run 34 migrations on the first request, which is inefficient and prone to errors if the migrations assume existing data that doesn't exist yet.

### 3. Create a .sql File in apps/merchant/migrations/

Fufuni maintains a historical audit log of every change. These files are used for version control diffs, local development tooling, and giving LLM context windows a clear view of how the database evolved.

Create a file named `034_add_task_priority.sql`:

```sql
-- apps/merchant/migrations/034_add_task_priority.sql

-- Migration: 034
-- Description: Adds a priority column to the tasks table for better sorting.

ALTER TABLE tasks ADD COLUMN priority INTEGER DEFAULT 0;

-- Note: We do not include PRAGMA user_version here as this file is 
-- for documentation and external tooling, not direct DO execution.
```

## Automating Startup and Initialization

The Durable Object's `fetch` method is the entry point for all requests. To ensure the database is ready before any business logic runs, we use a "lazy initialization" pattern or a "check-once" pattern in the DO class.

### Implementation in the Merchant DO

The following example shows how the DO class manages its SQLite connection and ensures migrations run before the Hono router handles the request.

```typescript
// apps/merchant/src/do.ts
import { DurableObject } from "cloudflare:workers";
import { ConfigSqliteDatabase } from "fufuni-sqlite-wrapper"; // Hypothetical wrapper

export class MerchantDO extends DurableObject {
  private db: any; // SQLite instance
  private initialized: boolean = false;

  constructor(state: DurableObjectState, env: Env) {
    super(state, env);
    // Initialize SQLite storage
    this.db = state.storage.sql;
  }

  async ensureInitialized() {
    if (this.initialized) return;

    // Check version
    let version = this.db.prepare("PRAGMA user_version").get().user_version;

    if (version === 0) {
      // New Database: Apply full schema
      this.db.exec(SCHEMA);
    } else {
      // Existing Database: Apply Deltas
      if (version < 34) {
        this.db.exec(`
          ALTER TABLE tasks ADD COLUMN priority INTEGER DEFAULT 0;
          PRAGMA user_version = 34;
        `);
      }
      // Add future migrations here (35, 36...)
    }

    this.initialized = true;
  }

  async fetch(request: Request) {
    // Every request triggers the migration check
    await this.ensureInitialized();
    
    // Pass control to the Hono app/router
    return app.fetch(request, this.env, this.state);
  }
}
```

## Migration Best Practices

### Destructive Changes
SQLite's `ALTER TABLE` is limited. You cannot drop columns or rename them directly in older SQLite versions without recreating the table. When a migration requires a complex change, use the temporary table pattern:

```sql
-- Pattern for complex migrations (e.g., Migration 035)
BEGIN TRANSACTION;
CREATE TABLE tasks_new (
  id TEXT PRIMARY KEY,
  title TEXT NOT NULL,
  priority_level INTEGER DEFAULT 0 -- Renamed from 'priority'
);
INSERT INTO tasks_new(id, title, priority_level)
SELECT id, title, priority FROM tasks;
DROP TABLE tasks;
ALTER TABLE tasks_new RENAME TO tasks;
PRAGMA user_version = 35;
COMMIT;
```

In `do.ts`, this would be wrapped in a `this.db.exec()` block.

### Idempotency
Migrations must be idempotent where possible. Use `IF NOT EXISTS` for table creations and check for column existence if your SQLite environment supports it, although the `user_version` check is the primary defense against double-execution.

### SQLite Pragma Settings
Fufuni enables specific pragmas for performance within Durable Objects. Migrations should not interfere with these settings unless specifically intended.

```sql
-- Standard Fufuni SQLite Pragmas
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
PRAGMA foreign_keys = ON;
```

## Troubleshooting Migrations

### Version Mismatch
If a Durable Object fails to start, check the logs in the Cloudflare Dashboard. The most common error is a syntax error in the `ensureInitialized()` SQL block. If a migration fails halfway through, the `user_version` won't be updated, and the DO will attempt the same migration on the next request.

### Manual Reset (Development Only)
During local development with `wrangler`, if your local database state becomes corrupted due to failed migrations, you can clear the local state:

```bash
# Clear local Durable Object state
npx wrangler dev --persist-to ./path/to/clean/dir
# OR manually delete the .wrangler/state directory
rm -rf .wrangler/state/v3/durable_objects/
```

### Production Data Safety
Never use `DROP TABLE` in a migration unless you are absolutely certain the data is no longer needed or has been successfully migrated to a new structure. Always prefer `ALTER TABLE ... ADD COLUMN` for backwards compatibility.
