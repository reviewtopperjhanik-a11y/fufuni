## Database Migration Architecture

In the Fufuni framework, migrations are managed through a dual-process system. While SQL files are maintained in the `apps/merchant/migrations/` directory for historical tracking and local development testing, the **absolute source of truth** for the production schema is the `ensureInitialized()` method within the `MerchantDO` class in `do.ts`.

This approach ensures that every Durable Object instance automatically validates and upgrades its internal SQLite schema upon instantiation, preventing version mismatch between the application logic and the underlying data store.

### Implementing a New Migration

When adding a feature that requires schema changes, you must follow these two steps:
1. Create a numbered SQL file (e.g., `035-add-loyalty-points.sql`) in the migrations folder.
2. Add the equivalent logic to the `ensureInitialized()` method in `do.ts` using `IF NOT EXISTS` or `ALTER TABLE ... ADD COLUMN` guards.

```typescript
// Example of implementing Migration 035 in do.ts
async ensureInitialized() {
  const sql = this.storage.sql;
  
  // 1. Initial baseline (Truncated for example)
  sql.exec(`CREATE TABLE IF NOT EXISTS products (...)`);

  // ... (Previous migrations 001 through 034)

  // 2. New Migration: Loyalty Points
  // We use TRY-CATCH or PRAGMA table_info to safely add columns
  try {
    sql.exec(`ALTER TABLE customers ADD COLUMN loyalty_points INTEGER DEFAULT 0`);
  } catch (e) {
    // Column already exists, ignore
  }

  // 3. New Table with triggers
  sql.exec(`
    CREATE TABLE IF NOT EXISTS loyalty_logs (
      id TEXT PRIMARY KEY,
      customer_id TEXT NOT NULL REFERENCES customers(id),
      delta INTEGER NOT NULL,
      reason TEXT,
      created_at TEXT DEFAULT (datetime('now'))
    );
  `);
}
```

### Product Feedback
The `product_reviews` table (Migration 028) stores customer ratings. It uses a status-based moderation system.

```sql
-- Querying approved reviews for a specific product
SELECT author_name, rating, body, created_at 
FROM product_reviews 
WHERE product_id = ? AND status = 'approved' 
ORDER BY created_at DESC;
```

FROM shipping_rates sr
JOIN region_shipping_rates rsr ON sr.id = rsr.shipping_rate_id

## Performance and Optimization

Migration 005 and 025 introduced performance indexes tailored for e-commerce query patterns, such as "Active Carts" or "Low Stock" alerts.

### Critical Performance Indexes
- `idx_orders_store_status_created`: Used for the Admin Dashboard order list.
- `idx_inventory_low_stock`: A partial index (`WHERE on_hand - reserved <= 10`) for inventory alerts.
- `idx_products_handle`: A partial index for SEO slug resolution.
- `idx_orders_viewtoken`: Unique index for anonymous order tracking via secure links (Migration 016).

### Covering Indexes for Frontend
Covering indexes include the actual data in the index leaf nodes, allowing SQLite to return results without a secondary table lookup.

```sql
-- From Migration 005: Optimizing the product list API
CREATE INDEX IF NOT EXISTS idx_products_list_covering 
ON products(store_id, status, id, title, created_at);
```
