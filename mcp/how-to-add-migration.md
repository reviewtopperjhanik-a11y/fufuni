## When to Use Database Migrations

In the Fufuni framework, schema changes are never "one-off" manual executions. Because every merchant instance runs in its own **Durable Object (DO)** with a private SQLite database, schema evolution must be automated and idempotent.

You must create a migration whenever you:
- Create a new table.
- Add a column to an existing table.
- Create or modify an index.
- Seed mandatory default data (like system-level settings).

Every change requires a **triple-entry update**:
1. A new `.sql` file in `apps/merchant/migrations/`.
2. A new entry in the `migrations` array inside the `ensureInitialized()` method of `do.ts`.
3. An update to the `SCHEMA` constant in `do.ts` to ensure fresh DO instances start with the latest schema.

## Step-by-Step Migration Process

### 1. Create the SQL Migration File
Create a new file in `apps/merchant/migrations/` using the zero-padded 3-digit naming convention. If the last migration was `034`, your new file must be `035-description.sql`.

```sql
-- apps/merchant/migrations/035-product-tags.sql
-- Description: Adds a dedicated tags table for better product organization

CREATE TABLE IF NOT EXISTS product_tags (
  id         TEXT PRIMARY KEY,
  name       TEXT NOT NULL UNIQUE,
  slug       TEXT NOT NULL UNIQUE,
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE IF NOT EXISTS product_tag_map (
  product_id TEXT NOT NULL REFERENCES products(id) ON DELETE CASCADE,
  tag_id     TEXT NOT NULL REFERENCES product_tags(id) ON DELETE CASCADE,
  PRIMARY KEY (product_id, tag_id)
);

CREATE INDEX IF NOT EXISTS idx_tag_map_product ON product_tag_map(product_id);
CREATE INDEX IF NOT EXISTS idx_tag_map_tag ON product_tag_map(tag_id);
```

### 2. Update the ensureInitialized() Logic
The `MerchantDO` uses an internal `migrations` table to track applied changes. You must append your new migration to the `migrations` array inside `do.ts`. Note that `this.sql.exec()` is synchronous in Durable Objects.

```typescript
// Inside apps/merchant/src/do.ts -> MerchantDO -> ensureInitialized()

const migrations: Array<{ name: string; sql: string }> = [
  // ... existing migrations (001 to 034) ...
  {
    name: '035_product_tags_feature',
    sql: `
      CREATE TABLE IF NOT EXISTS product_tags (
        id         TEXT PRIMARY KEY,
        name       TEXT NOT NULL UNIQUE,
        slug       TEXT NOT NULL UNIQUE,
        created_at TEXT NOT NULL DEFAULT (datetime('now'))
      );
      CREATE TABLE IF NOT EXISTS product_tag_map (
        product_id TEXT NOT NULL REFERENCES products(id) ON DELETE CASCADE,
        tag_id     TEXT NOT NULL REFERENCES product_tags(id) ON DELETE CASCADE,
        PRIMARY KEY (product_id, tag_id)
      );
      CREATE INDEX IF NOT EXISTS idx_tag_map_product ON product_tag_map(product_id);
      CREATE INDEX IF NOT EXISTS idx_tag_map_tag ON product_tag_map(tag_id);
    `,
  },
];
```

### 3. Synchronize the SCHEMA Constant
The `SCHEMA` constant is the "Bootstrap Schema." When a brand-new merchant is created, the code first executes everything in `SCHEMA`. To avoid re-running dozens of migration blocks on the first boot, the `SCHEMA` constant should always reflect the final desired state of the database.

```typescript
// Inside apps/merchant/src/do.ts

const SCHEMA = `
-- ... existing tables ...

CREATE TABLE IF NOT EXISTS product_tags (
  id         TEXT PRIMARY KEY,
  name       TEXT NOT NULL UNIQUE,
  slug       TEXT NOT NULL UNIQUE,
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE IF NOT EXISTS product_tag_map (
  product_id TEXT NOT NULL REFERENCES products(id) ON DELETE CASCADE,
  tag_id     TEXT NOT NULL REFERENCES product_tags(id) ON DELETE CASCADE,
  PRIMARY KEY (product_id, tag_id)
);

-- ... existing indexes ...
CREATE INDEX IF NOT EXISTS idx_tag_map_product ON product_tag_map(product_id);
CREATE INDEX IF NOT EXISTS idx_tag_map_tag ON product_tag_map(tag_id);
`;
```

## Worked Example: Adding a "Internal Notes" Feature

Suppose we want to add an `internal_notes` column to the `orders` table and a new `order_logs` table to track administrative changes.

### Step A: The SQL File
Create `apps/merchant/migrations/036-order-internal-tracking.sql`:

```sql
-- Migration 036: Order tracking enrichment
ALTER TABLE orders ADD COLUMN internal_notes TEXT;

CREATE TABLE IF NOT EXISTS order_logs (
  id         TEXT PRIMARY KEY,
  order_id   TEXT NOT NULL REFERENCES orders(id) ON DELETE CASCADE,
  staff_id   TEXT,
  action     TEXT NOT NULL,
  details    TEXT,
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE INDEX IF NOT EXISTS idx_order_logs_order ON order_logs(order_id);
```

### Step B: The DO Migration Array
Add the entry to the `migrations` list in `do.ts`. Ensure the `name` property is unique and descriptive.

```typescript
// apps/merchant/src/do.ts

// ... inside ensureInitialized()
{
  name: '036_order_internal_tracking',
  sql: `
    ALTER TABLE orders ADD COLUMN internal_notes TEXT;
    CREATE TABLE IF NOT EXISTS order_logs (
      id         TEXT PRIMARY KEY,
      order_id   TEXT NOT NULL REFERENCES orders(id) ON DELETE CASCADE,
      staff_id   TEXT,
      action     TEXT NOT NULL,
      details    TEXT,
      created_at TEXT NOT NULL DEFAULT (datetime('now'))
    );
    CREATE INDEX IF NOT EXISTS idx_order_logs_order ON order_logs(order_id);
  `,
},
```

## Data Type Standards

When writing migrations, you must adhere to the following SQLite type conventions used in Fufuni:

| Data Type | SQL Type | Notes |
| :--- | :--- | :--- |
| **UUIDs / IDs** | `TEXT` | Generated via `crypto.randomUUID()` in TS. |
| **Booleans** | `INTEGER` | Use `0` for false, `1` for true. Use `DEFAULT 0`. |
| **Currency/Money** | `INTEGER` | Always store as **cents** (e.g., $10.00 is `1000`). |
| **Dates/Times** | `TEXT` | Always store as ISO 8601 strings. Use `datetime('now')`. |
| **JSON Objects** | `TEXT` | Use for unstructured metadata or configuration. |
| **Decimals/Rates** | `REAL` | Use for tax percentages or average ratings. |

## Common Pitfalls and Rules

### Idempotency is Mandatory
Always use `CREATE TABLE IF NOT EXISTS` and `CREATE INDEX IF NOT EXISTS`. Durable Objects might restart during an initialization phase. If your migration is partially applied, it must be safe to run again.

### Alter Table Restrictions
SQLite's `ALTER TABLE` is limited. You cannot add a `UNIQUE` constraint or a `FOREIGN KEY` constraint directly within an `ALTER TABLE ADD COLUMN` statement. 
**The Workaround:** 
1. Add the column as a plain `TEXT` or `INTEGER`.
2. Create a `UNIQUE INDEX` in the next statement to enforce uniqueness.

```sql
-- Correct way to add a unique handle
ALTER TABLE products ADD COLUMN handle TEXT;
CREATE UNIQUE INDEX IF NOT EXISTS idx_products_handle ON products(handle) WHERE handle IS NOT NULL;
```

### Migration Naming
The `name` in the `migrations` array MUST match the filename stem. If your file is `034-something.sql`, the name in the code should ideally be `034_something` or `034-something`. This allows developers to quickly correlate the code logic with the version history.

### The Migration Table
Never manually delete rows from the `migrations` table in a production Durable Object. If a migration fails because a column already exists (perhaps added manually during debugging), the catch block in `ensureInitialized()` will attempt to mark it as applied anyway to prevent the DO from getting stuck in a crash loop.

```typescript
try {
  this.sql.exec(migration.sql);
  this.sql.exec('INSERT INTO migrations (name) VALUES (?)', migration.name);
} catch (e) {
  // If migration fails (e.g., column already exists), mark as applied
  try {
    this.sql.exec('INSERT INTO migrations (name) VALUES (?)', migration.name);
  } catch { /* Already recorded */ }
}
```

### Synchronous Nature
Remember that `this.sql.exec` is synchronous. Do not use `await` inside the loop that iterates through the `migrations` array. Standard `Promise` logic is only required when performing cryptographic operations (like `hashKey`) or fetching external resources.
