## When to use a Migration

In the Fufuni framework, the database schema for each merchant resides within a Cloudflare Durable Object (DO) using SQLite. Because Durable Objects are long-lived and persist state, you cannot simply update a SQL string and expect existing merchant databases to change.

You must use a migration whenever you:
- Add a new table.
- Add a column to an existing table.
- Add an index to improve query performance.
- Rename a table or column (though this is discouraged).
- Add constraints (like `CHECK` or `UNIQUE`).

Fufuni uses a **Triple-Entry Schema Strategy**. Every change must be reflected in:
1. A standalone `.sql` file in `apps/merchant/migrations/`.
2. A migration block in the `migrations` array within `do.ts`.
3. The `SCHEMA` constant in `do.ts` (so new DO instances start with the latest schema).

### Migration Comparison

| Scenario | Update `SCHEMA`? | Add Migration Block? | Create `.sql` File? |
| :--- | :--- | :--- | :--- |
| **New Framework Install** | Yes (Initial setup) | No | Yes |
| **Adding a Feature** | Yes (For new shops) | Yes (For existing shops) | Yes |
| **Fixing a typo in comments** | Yes | No | No |

## Step-by-Step Implementation

Follow these steps to add a migration. For this guide, we assume the next migration number is **035**.

### 1. Create the SQL Migration File
Create a new file in `apps/merchant/migrations/035-your-feature.sql`. This file is used for external tooling (like Cloudflare D1 local development) and documentation.

```sql
-- apps/merchant/migrations/035-product-tags.sql
-- Migration 035: Adding product tags for categorization
-- Target: SQLite (Cloudflare Durable Objects)

CREATE TABLE IF NOT EXISTS product_tags (
  id         TEXT PRIMARY KEY,
  name       TEXT NOT NULL UNIQUE,
  color_hex  TEXT DEFAULT '#000000',
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE IF NOT EXISTS product_tag_links (
  product_id TEXT NOT NULL REFERENCES products(id) ON DELETE CASCADE,
  tag_id     TEXT NOT NULL REFERENCES product_tags(id) ON DELETE CASCADE,
  PRIMARY KEY (product_id, tag_id)
);

CREATE INDEX IF NOT EXISTS idx_product_tag_links_tag ON product_tag_links(tag_id);
```

### 2. Update the Migration Array in `do.ts`
Navigate to the `ensureInitialized()` method in `apps/merchant/src/do.ts`. Find the `migrations` array and append your new migration object. The `name` property **must match the filename stem exactly** (excluding the extension).

```typescript
// Inside MerchantDO class in do.ts

private ensureInitialized(): void {
  // ... existing initialization logic ...

  const migrations: Array<{ name: string; sql: string }> = [
    // ... existing migrations (001 through 034) ...
    {
      name: '035-product-tags',
      sql: `
        CREATE TABLE IF NOT EXISTS product_tags (
          id         TEXT PRIMARY KEY,
          name       TEXT NOT NULL UNIQUE,
          color_hex  TEXT DEFAULT '#000000',
          created_at TEXT NOT NULL DEFAULT (datetime('now'))
        );
        CREATE TABLE IF NOT EXISTS product_tag_links (
          product_id TEXT NOT NULL REFERENCES products(id) ON DELETE CASCADE,
          tag_id     TEXT NOT NULL REFERENCES product_tags(id) ON DELETE CASCADE,
          PRIMARY KEY (product_id, tag_id)
        );
        CREATE INDEX IF NOT EXISTS idx_product_tag_links_tag ON product_tag_links(tag_id);
      `,
    },
  ];

  for (const migration of migrations) {
    if (!appliedMigrations.has(migration.name)) {
      try {
        // Durable Object SQL exec is SYNCHRONOUS
        this.sql.exec(migration.sql);
        this.sql.exec('INSERT INTO migrations (name) VALUES (?)', migration.name);
      } catch (e) {
        // Fallback: mark as applied to prevent loops if SQL fails due to existing columns
        this.sql.exec('INSERT OR IGNORE INTO migrations (name) VALUES (?)', migration.name);
      }
    }
  }
}
```

### 3. Update the `SCHEMA` Constant
Finally, update the `SCHEMA` string at the top of `do.ts`. This ensures that any *new* Durable Object created after your code is deployed starts with the tags table already in place.

```typescript
// apps/merchant/src/do.ts

const SCHEMA = `
-- ... existing tables ...

CREATE TABLE IF NOT EXISTS product_tags (
  id         TEXT PRIMARY KEY,
  name       TEXT NOT NULL UNIQUE,
  color_hex  TEXT DEFAULT '#000000',
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE IF NOT EXISTS product_tag_links (
  product_id TEXT NOT NULL REFERENCES products(id) ON DELETE CASCADE,
  tag_id     TEXT NOT NULL REFERENCES product_tags(id) ON DELETE CASCADE,
  PRIMARY KEY (product_id, tag_id)
);

CREATE INDEX IF NOT EXISTS idx_product_tag_links_tag ON product_tag_links(tag_id);
`;
```

## Migration Syntax and Data Types

SQLite in Cloudflare Durable Objects is strict but has specific behaviors. When writing your migration SQL, adhere to the following conventions:

### Recommended Data Types
| Usage | SQLite Affinity | Example |
| :--- | :--- | :--- |
| Primary Keys (UUIDs) | `TEXT` | `id TEXT PRIMARY KEY` |
| Monetary Values | `INTEGER` | `price_cents INTEGER` |
| Dates/Timestamps | `TEXT` | `created_at TEXT DEFAULT (datetime('now'))` |
| Booleans | `INTEGER` | `is_active INTEGER DEFAULT 1` (0 or 1) |
| Percentages/Ratings | `REAL` | `average_rating REAL DEFAULT 0.0` |
| JSON Blobs | `TEXT` | `metadata TEXT` (use `JSON.stringify`/`JSON.parse`) |

### Adding Columns to Existing Tables
SQLite's `ALTER TABLE` is limited. You cannot add a `UNIQUE` constraint or a `NOT NULL` constraint without a default value in an `ALTER` statement.

**Incorrect:**
```sql
ALTER TABLE products ADD COLUMN internal_code TEXT UNIQUE; -- Will likely fail
```

**Correct (Fufuni Pattern):**
```sql
ALTER TABLE products ADD COLUMN internal_code TEXT;
CREATE UNIQUE INDEX IF NOT EXISTS idx_products_internal_code ON products(internal_code) WHERE internal_code IS NOT NULL;
```

## Idempotency and Safety

The `ensureInitialized()` method runs every time a Durable Object is "woken up" or a `fetch` is received for the first time in that instance's lifecycle. Idempotency is critical.

### The `migrations` Table
Fufuni maintains a `migrations` table inside each DO.
```sql
CREATE TABLE IF NOT EXISTS migrations (
  name TEXT PRIMARY KEY,
  applied_at TEXT NOT NULL DEFAULT (datetime('now'))
);
```
The framework checks this table before running any entry in the `migrations` array. If the `name` (e.g., `035-product-tags`) exists in the table, the SQL is skipped.

### Using `IF NOT EXISTS`
Even with the `migrations` table, you should always use `IF NOT EXISTS` for tables and indexes. This provides a second layer of safety if a migration was partially applied or if the `SCHEMA` constant and migrations overlap.

```typescript
// Example of a safe, idempotent column addition logic inside do.ts
try {
  const tableInfo = this.sql.exec("PRAGMA table_info(products)").toArray() as Array<{ name: string }>;
  const hasInternalCode = tableInfo.some((c) => c.name === 'internal_code');
  if (!hasInternalCode) {
    this.sql.exec('ALTER TABLE products ADD COLUMN internal_code TEXT');
  }
} catch (e) {
  console.error("Manual schema check failed", e);
}
```

## Common Pitfalls

1.  **Asynchronous Confusion**: `ensureInitialized()` is synchronous. Do **not** use `await` inside the migration loop. Durable Object SQLite execution is blocking and immediate.
2.  **Naming Mismatch**: If you name your file `035-add-tags.sql` but put `name: 'add-tags'` in the migration array, the local D1 tools and the production DO will drift. **Always keep them identical.**
3.  **Retroactive Modification**: Never change the SQL string of a migration that has already been deployed (e.g., `030-store-themes`). If you need to fix a mistake in migration 030, create migration `037-fix-themes`.
4.  **Complex ALTERs**: SQLite does not support `DROP COLUMN` or `RENAME COLUMN` in older versions. While Cloudflare DO uses a modern SQLite, it is safest to stick to `ADD COLUMN`. If you must restructure a table, you usually need to create a new table, copy data, and drop the old one.
5.  **ForeignKey Constraints**: Remember that `PRAGMA foreign_keys = ON;` must be active. When adding tables with foreign keys, ensure the referenced table (e.g., `products`) already exists earlier in the `SCHEMA` or in a previous migration.
