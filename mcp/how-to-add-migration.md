# How to Add a Database Migration

When you need to change the persistent schema of a Durable Object, you must record that change in three places:

| Place | What you add | Why it matters |
|-------|--------------|----------------|
| **`apps/merchant/do.ts` – `SCHEMA` constant** | Full DDL with `CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS` etc. | Initial creation of a brand‑new Durable Object (no migration history yet). |
| **`apps/merchant/do.ts` – `ensureInitialized()` migration block** | A synchronous `this.sql.exec()` that runs the same DDL and writes a row to the `migrations` table. | Updates an existing Durable Object that has already been initialized. |
| **`apps/merchant/migrations/NNN-description.sql`** | Same DDL, but in a separate file for tooling and version control. | Enables Cloudflare Wrangler or local scripts to apply migrations manually, e.g. when running `wrangler d1 execute`. |

> **Rule of thumb** – *Edit `SCHEMA` only for the very first creation of the object (e.g. during a local test or when you wipe the database). All subsequent schema changes must go through the migration pattern.*

---

## 1. When to Use a Migration

| Scenario | Do you use a migration? | Why |
|----------|-------------------------|-----|
| Adding a new table, column, or index | **Yes** | The table/column may already exist on production; migrations are idempotent and tracked. |
| Modifying an existing column type or constraint | **Yes** | You must `ALTER TABLE` or drop/recreate the column; migrations guarantee the change runs only once. |
| Changing the default value of a column | **Yes** | Requires an `ALTER TABLE` or `UPDATE` statement; migrations record the change. |
| Removing a table or column | **Yes** | You must run a `DROP TABLE`/`DROP COLUMN` and record it. |
| Updating a data‑migration script (e.g. seeding new data) | **Yes** | These are separate migrations that may be run once. |
| Minor code refactor that does **not** touch the database | **No** | No schema change, so no migration needed. |

## 2. Exact Steps to Add a Migration

### a. Create the SQL file

1. Find the current highest migration number (currently **033**).  
2. Increment and zero‑pad to three digits: `034`.  
3. Create the file `apps/merchant/migrations/034-add-tags.sql`.  
4. Write the DDL with `IF NOT EXISTS` and any necessary `CREATE INDEX` or `TRIGGER` blocks.

```sql
-- Migration 034: Add a simple tags table
PRAGMA foreign_keys = ON;

CREATE TABLE IF NOT EXISTS tags (
  id          TEXT PRIMARY KEY,
  name        TEXT NOT NULL UNIQUE,
  description TEXT,
  created_at  TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at  TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE INDEX IF NOT EXISTS idx_tags_name
  ON tags (name);
```

> **Tip** – Keep the file short: just the DDL, not data migration logic.

### b. Add the migration block in `ensureInitialized()` (inside `do.ts`)

```ts
// Inside ensureInitialized()
{
  // 034-add-tags.sql
  const sql = `
    PRAGMA foreign_keys = ON;

    CREATE TABLE IF NOT EXISTS tags (
      id          TEXT PRIMARY KEY,
      name        TEXT NOT NULL UNIQUE,
      description TEXT,
      created_at  TEXT NOT NULL DEFAULT (datetime('now')),
      updated_at  TEXT NOT NULL DEFAULT (datetime('now'))
    );

    CREATE INDEX IF NOT EXISTS idx_tags_name
      ON tags (name);
  `;
  // Run the migration only if it hasn't been applied yet
  const applied = this.sql.exec(`SELECT 1 FROM migrations WHERE name='034-add-tags'`);
  if (!applied.rows?.length) {
    this.sql.exec(sql);
    this.sql.exec(`INSERT INTO migrations (name) VALUES ('034-add-tags')`);
  }
}
```

**Key points**

- Use the exact migration name (`034-add-tags`) that matches the file stem.  
- Keep the block synchronous (`this.sql.exec()`).  
- Wrap the `INSERT` in the same transaction (Durable Objects run each `exec` atomically).  
- The `SELECT 1` guard ensures the migration is idempotent.

### c. Add the full DDL to the `SCHEMA` constant

Append the same DDL to `SCHEMA` (or create a new `CREATE TABLE` block if you prefer to keep the sections organized).

> **Why** – This ensures that a brand‑new Durable Object, with no migration history, starts with the new table.

## 4. Common Pitfalls

| Pitfall | How to avoid it |
|---------|-----------------|
| **Wrong migration name** | The migration table stores the *file stem* (`NNN-description`). Use exactly that string in the `INSERT` and the `SELECT` guard. |
| **Missing `IF NOT EXISTS`** | Forgetting it can make migrations fail when re‑applying. Always prefix `CREATE TABLE`, `CREATE INDEX`, and `CREATE TRIGGER` with `IF NOT EXISTS`. |
| **Running async code in `ensureInitialized()`** | Durable Object SQL is synchronous. Use `this.sql.exec()`; do **not** `await db.run()` or any promise. |
| **Adding the same DDL to both `SCHEMA` and the migration** | This is required; otherwise a freshly created DO will miss the table. |
| **Wrong column types** | Stick to SQLite conventions: `TEXT` for UUIDs/dates, `INTEGER` for booleans/cents, `REAL` for percentages/ratings. |
| **Not tracking the migration** | Forgetting the `INSERT INTO migrations` line means the same migration will run on every initialization. |
| **Using `DROP TABLE` in a migration without a guard** | Since `DROP TABLE` is irreversible, wrap it in an `IF EXISTS` guard or ensure it's idempotent. |
| **Hard‑coding dates or UUIDs** | Use `datetime('now')` and `TEXT` columns for IDs; avoid `INTEGER` auto‑increments unless you need them. |
| **Skipping the `PRAGMA foreign_keys = ON;`** | Without it, foreign‑key constraints are ignored. Include it in every migration that references other tables. |
