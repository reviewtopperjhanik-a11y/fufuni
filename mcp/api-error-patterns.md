## API Error Handling Reference

In the Fufuni framework, error handling is standardized using the `ApiError` class. This class ensures that every error returned by the backend follows a consistent JSON structure, allowing the frontend to predictably handle failures, display toast notifications, or render validation messages.

The `ApiError` class extends the native JavaScript `Error` but adds a machine-readable `code`, an HTTP `statusCode`, and an optional `details` object for metadata (such as validation errors or affected SKUs).

### ApiError Static Helpers Table

The following static methods are available on the `ApiError` class to maintain consistency across the codebase:

| Method | HTTP Status | Code | Use Case |
| :--- | :--- | :--- | :--- |
| `invalidRequest` | 400 | `invalid_request` | Schema validation failures or missing parameters. |
| `badRequest` | 400 | `bad_request` | Generic client-side errors. |
| `unauthorized` | 401 | `unauthorized` | Missing or invalid authentication (Auth0/API Key). |
| `forbidden` | 403 | `forbidden` | Authenticated user lacks required permissions. |
| `notFound` | 404 | `not_found` | Resource (Product, Order, SKU) does not exist. |
| `conflict` | 409 | `conflict` | State mismatch (e.g., duplicate unique field). |
| `insufficientInventory` | 409 | `insufficient_inventory` | Attempting to purchase more than available stock. |
| `internalServerError` | 500 | `internal_server_error` | Unexpected runtime crashes or DB failures. |
| `stripeError` | 502 | `stripe_error` | Failures during external communication with Stripe. |

## Backend: Throwing Structured Errors

When writing Hono route handlers, you should never return raw JSON for errors. Instead, `throw` an instance of `ApiError`. Fufuni’s global error handler (configured in the Hono app instance) catches these exceptions and converts them into a standardized response.

### Implementation in Route Handlers

This example demonstrates how to use various `ApiError` methods within a product update logic.

```typescript
// apps/merchant/src/routes/products.ts
import { Hono } from 'hono';
import { ApiError, type HonoEnv } from '../types';

const app = new Hono<HonoEnv>();

app.patch('/:id', async (c) => {
  const { id } = c.req.param();
  const db = c.get('db');
  const body = await c.req.json();

  // 1. Check existence
  const product = await db.query('SELECT id FROM products WHERE id = ?', [id]);
  if (product.length === 0) {
    throw ApiError.notFound(`Product with ID ${id} not found`);
  }

  // 2. Validate business logic
  if (body.price < 0) {
    throw ApiError.invalidRequest('Price cannot be negative', { 
      field: 'price', 
      value: body.price 
    });
  }

  // 3. Handle specific inventory constraints
  if (body.stock_change) {
    const currentStock = 5; // Simplified for example
    if (currentStock + body.stock_change < 0) {
      throw ApiError.insufficientInventory(id);
    }
  }

  // ... proceed with update
  return c.json({ success: true });
});
```

### Global Hono Error Handler

The framework uses a central `app.onError` hook to transform these errors. This ensures the client always receives a JSON object with the shape `{ error: { code, message, details } }`.

```typescript
// apps/merchant/src/index.ts
import { Hono } from 'hono';
import { ApiError } from './types';

const app = new Hono();

app.onError((err, c) => {
  if (err instanceof ApiError) {
    return c.json({
      error: {
        code: err.code,
        message: err.message,
        details: err.details
      }
    }, err.statusCode as any);
  }

  // Fallback for non-ApiError exceptions
  console.error(err);
  return c.json({
    error: {
      code: 'internal_server_error',
      message: err.message || 'An unexpected error occurred'
    }
  }, 500);
});
```

## Advanced Error Scenarios

### Conflict and Inventory Errors
The `conflict` error (409) is specifically used when the request is syntactically correct but violates business state rules. The most common specialized version is `insufficientInventory`.


## Frontend: Handling API Errors

Fufuni provides a `useSecuredApi()` hook in the React frontend. This hook handles authentication headers automatically. When a request returns a non-2xx status code, the standard practice is to catch the error and extract the JSON message for UI feedback.

### Processing Errors in Components

Using React 19 and HeroUI v3 components, errors are typically displayed using toast notifications or inline alert messages.

```typescript
// apps/merchant-ui/src/components/ProductForm.tsx
import React, { useState } from 'react';
import { Button, Input, addToast } from '@heroui/react';
import { useSecuredApi } from '../hooks/useSecuredApi';

export const ProductForm = () => {
  const api = useSecuredApi();
  const [loading, setLoading] = useState(false);

  const handleSubmit = async (formData: any) => {
    setLoading(true);
    try {
      const res = await api.post('/v1/products', formData);
      
      if (!res.ok) {
        // Parse the ApiError format
        const errorData = await res.json();
        throw new Error(errorData.error?.message || 'Failed to create product');
      }

      addToast({ title: 'Success', color: 'success' });
    } catch (err: any) {
      // Display the structured error message to the user
      addToast({
        title: 'Error',
        description: err.message,
        color: 'danger'
      });
    } finally {
      setLoading(false);
    }
  };

  return (
    <form onSubmit={(e) => { e.preventDefault(); handleSubmit({ name: 'New Product' }); }}>
      <Button isLoading={loading} type="submit">Create Product</Button>
    </form>
  );
};
```

### Handling Validation Details (400 Bad Request)

If the backend throws `ApiError.invalidRequest` with a `details` object, the frontend can use that data to highlight specific form fields.


## Customizing the ApiError Class

If you need to add new error types (e.g., `payment_required` for 402 errors), update the `ApiError` class in `apps/merchant/src/types.ts`.

```typescript
// apps/merchant/src/types.ts addition
export class ApiError extends Error {
  // ... existing methods

  /**
   * Used for features requiring a paid subscription.
   */
  static paymentRequired(message = 'Subscription required') {
    return new ApiError('payment_required', 402, message);
  }
}
```

By strictly adhering to this `ApiError` pattern, the Fufuni framework maintains a robust contract between the Durable Object SQLite backend and the Vite-powered frontend, ensuring that developers can debug issues efficiently by looking at the machine-readable `code` and the human-readable `message`.
