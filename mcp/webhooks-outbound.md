## Webhook Security and Signature Verification

Fufuni secures all outbound webhook notifications using a standard HMAC-SHA256 signature. This allows the receiving server to verify that the request originated from your Fufuni instance and that the payload has not been tampered with. Each webhook is assigned a unique secret, prefixed with `whsec_`, which consists of 32 random bytes encoded as a 64-character hex string.

When Fufuni dispatches an event, it includes the following headers:

- `X-Fufuni-Signature`: The HMAC-SHA256 hex digest of the raw JSON request body.
- `X-Fufuni-Timestamp`: The Unix timestamp (in seconds) when the delivery was initiated.
- `X-Fufuni-Delivery-Id`: A unique UUID for the specific delivery attempt.
- `User-Agent`: Always set to `Fufuni-Webhook/1.0`.

### Implementing a Verification Receiver

To verify a webhook, you must compute the HMAC-SHA256 of the raw body using your webhook secret and compare it to the signature header.

```typescript
import crypto from 'node:crypto';

/**
 * Example of a Node.js/Express-style receiver verifying a Fufuni webhook.
 */
export async function verifyFufuniWebhook(
  rawBody: string,
  signature: string,
  secret: string
): Promise<boolean> {
  // 1. Create the HMAC-SHA256 generator with your 'whsec_...' secret
  const hmac = crypto.createHmac('sha256', secret);
  
  // 2. Update with the raw string payload
  hmac.update(rawBody);
  
  // 3. Generate the hex digest
  const expectedSignature = hmac.digest('hex');

  // 4. Use timingSafeEqual to prevent timing attacks
  return crypto.timingSafeEqual(
    Buffer.from(signature, 'hex'),
    Buffer.from(expectedSignature, 'hex')
  );
}
```

## Dispatching Events and Fan-out

The Fufuni backend uses a fan-out pattern to notify all active subscribers interested in a specific event. The core logic resides in `apps/merchant/src/lib/webhooks.ts`. When an event occurs (e.g., a payment is confirmed), the code calls `dispatchWebhooks`.

### Supported Event Types

The framework supports specific event strings and wildcards:
- `order.created`, `order.updated`, `order.shipped`, `order.refunded`
- `inventory.low` (Triggered when available stock falls $\le 5$)
- `order.*` (Subscribes to all order-related events)
- `*` (Subscribes to all events)

### Triggering a Dispatch

When writing a new service or route, you trigger the webhook system by passing the Durable Object stub and the Worker's `ExecutionContext`.

```typescript

 */
export async function handleRefund(

  ctx: ExecutionContext, 
  orderId: string,

  // Business logic for refund...
```

The system filters webhooks by `status = 'active'`, checks the `events` JSON array in the database for matches, creates a record in `webhook_deliveries` with `status = 'pending'`, and immediately schedules the first attempt via `ctx.waitUntil`.

## Delivery Lifecycle and Retry Logic

Fufuni implements a reliable delivery mechanism using a dedicated `webhook_deliveries` table in the SQLite (Durable Objects) database. This table tracks every attempt, response code, and response body (up to 1000 characters).

### Exponential Backoff

If a delivery fails, Fufuni retries up to `MAX_ATTEMPTS = 3`. The retry logic uses an exponential backoff formula: $2^{attempt} \times 1000$ milliseconds.

- **Retry conditions**: Retries occur if there is a network error, a `5xx` server error, or a `429` rate limit response.
- **Immediate Failure**: If the receiver returns a `4xx` error (excluding 429), the delivery is marked as `failed` immediately, as these typically indicate a configuration or payload error that retries won't fix.

### Database Schema for Tracking

```sql
CREATE TABLE webhook_deliveries (
  id TEXT PRIMARY KEY,
  webhook_id TEXT NOT NULL,
  event_type TEXT NOT NULL,
  payload TEXT NOT NULL,         -- Full JSON envelope
  status TEXT DEFAULT 'pending', -- 'pending', 'success', 'failed'
  attempts INTEGER DEFAULT 0,
  response_code INTEGER,
  response_body TEXT,
  created_at TEXT NOT NULL,
  last_attempt_at TEXT,
  FOREIGN KEY (webhook_id) REFERENCES webhooks(id)
);
```

### Manual and Background Retries

While the initial attempts happen via `ctx.waitUntil`, Fufuni also provides a `retryFailedDeliveries` utility. This can be bound to a Cloudflare Cron Trigger to re-attempt deliveries that are in a `failed` state but have not yet reached `MAX_ATTEMPTS` within the last 24 hours.

```typescript
// apps/merchant/src/lib/webhooks.ts

export async function retryFailedDeliveries(stub: DOStub, ctx: ExecutionContext): Promise<number> {
  const db = getDb(stub);

  const failed = await db.query<{
    id: string;
    webhook_id: string;
    payload: string;
    attempts: number;
  }>(
    `SELECT wd.id, wd.webhook_id, wd.payload, wd.attempts
     FROM webhook_deliveries wd
     JOIN webhooks w ON w.id = wd.webhook_id
     WHERE wd.status = 'failed' 
       AND wd.attempts < 3
       AND w.status = 'active'
       AND wd.created_at > datetime('now', '-24 hours')
     LIMIT 50`
  );

  // ... Logic to trigger deliverWebhook for each record
  return failed.length;
}
```

## Admin Interface Integration

The Fufuni Admin UI provides a full management suite for webhooks. Located at `/admin/webhooks`, it allows merchants to register endpoints, select events, and monitor the health of their integrations.

### API Routes for Management

The management endpoints are built using `hono/zod-openapi` and require `admin:store` or legacy secret key authentication.

| Method | Path | Description |
| :--- | :--- | :--- |
| `GET` | `/v1/webhooks` | List all configured webhooks |
| `POST` | `/v1/webhooks` | Create a new webhook (returns the `whsec_` secret) |
| `GET` | `/v1/webhooks/{id}` | Get details and last 20 deliveries |
| `PATCH` | `/v1/webhooks/{id}` | Update URL, events, or status |
| `POST` | `/v1/webhooks/{id}/rotate-secret` | Generate a new signing secret |
| `POST` | `/v1/webhooks/{id}/deliveries/{dId}/retry` | Manually trigger a retry for a specific delivery |

### Creating a Webhook via React

The frontend uses `HeroUI` modals and `react-query` to manage the creation workflow. When a webhook is created, the secret is displayed only once.

```typescript
import { useMutation } from "@tanstack/react-query";
import { useSecuredApi } from "@/authentication";

export function CreateWebhookButton() {
  const { postJson } = useSecuredApi();

  const mutation = useMutation({
    mutationFn: (data: { url: string; events: string[] }) =>
      postJson('/v1/webhooks', data),
    onSuccess: (result) => {
      // The 'result.secret' contains the 'whsec_...' value
      console.log("Save this secret:", result.secret);
    }
  });

  const handleCreate = () => {
    mutation.mutate({
      url: "https://api.example.com/webhooks",
      events: ["order.created", "inventory.low"]
    });
  };

  return (
    <button onClick={handleCreate} disabled={mutation.isPending}>
      Add Webhook
    </button>
  );
}
```

### Low Inventory Threshold

A specific feature of the Fufuni outbound system is the `checkLowInventory` helper. This is called whenever an order is placed or inventory is manually adjusted. If the `available` quantity (on-hand minus reserved) is $\le 5$, an `inventory.low` event is dispatched. This threshold is hardcoded in the framework as `LOW_INVENTORY_THRESHOLD = 5`.
