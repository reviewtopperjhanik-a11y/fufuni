## Webhook Architecture and Schema

Fufuni implements an asynchronous fan-out pattern for outbound webhooks. When a significant event occurs (like an order being paid or inventory dropping), the system identifies all active webhooks subscribed to that event and schedules deliveries. This ensures that the primary request (e.g., the Stripe webhook processing) is not blocked by slow or failing third-party endpoints.

The system relies on two primary SQLite tables within the Durable Object:
1.  `webhooks`: Stores the endpoint URL, the signing secret (`whsec_...`), and the list of subscribed event patterns (supporting wildcards like `order.*`).
2.  `webhook_deliveries`: Tracks individual delivery attempts, response codes, and serialized payloads for audit and retry purposes.

```typescript

  response_code: number | null;
  response_body: string | null;
  created_at: string;
  last_attempt_at: string | null;
}
```

### Supported Event Types
The system supports specific events and wildcard matching. The `inventory.low` event is specifically triggered when the available quantity of a SKU is $\le 5$.

| Event Pattern | Description |
| :--- | :--- |
| `order.created` | Triggered when a new order is successfully paid. |
| `order.updated` | Triggered on status changes (e.g., from paid to shipped). |
| `order.shipped` | Triggered when an order is fulfilled. |
| `inventory.low` | Triggered when stock drops to 5 or fewer units. |
| `order.*` | Matches any event starting with "order.". |
| `*` | Matches all events dispatched by the system. |

## Security and Signature Verification

Every outbound request is signed using a secret unique to each webhook. This allows the receiving server to verify that the request originated from Fufuni and that the body has not been tampered with.

The signature is a `HMAC-SHA256` hash of the raw JSON request body, using the webhook secret as the key. The secret is always a 64-character hex string prefixed with `whsec_`.

### Delivery Headers
The following headers are included in every POST request to the subscriber:
- `X-Fufuni-Signature`: The hex-encoded HMAC-SHA256 signature.
- `X-Fufuni-Timestamp`: The Unix timestamp (seconds) when the signature was generated.
- `X-Fufuni-Delivery-Id`: A unique UUID for this specific delivery attempt.
- `User-Agent`: Always `Fufuni-Webhook/1.0`.

## Dispatching Events

To trigger a webhook from the backend, use the `dispatchWebhooks` function. This function handles the fan-out logic, checking which webhooks are active and matching the event pattern before inserting records into `webhook_deliveries`.

It uses `ctx.waitUntil` to ensure the delivery process continues even after the current HTTP response is sent to the client (or to Stripe).

## Delivery and Retry Mechanism

Fufuni implements a reliable delivery system with exponential backoff.

1.  **Initial Attempt**: Occurs immediately upon dispatch via `ctx.waitUntil`.
2.  **Retry Policy**: If the delivery fails, it is retried up to `MAX_ATTEMPTS = 3`.
3.  **Backoff Schedule**: The delay between retries is calculated as $2^{attempt} \times 1000$ milliseconds.
    - Attempt 1: 2 seconds
    - Attempt 2: 4 seconds
    - Attempt 3: 8 seconds
4.  **Failure Criteria**: 
    - The system retries on network errors, `5xx` Server Errors, and `429` Too Many Requests.
    - It **stops** and marks the delivery as `failed` if the recipient returns a `4xx` error (excluding 429), as these usually indicate a client-side configuration error (e.g., 404 Not Found or 401 Unauthorized).

### Automated Cron Retries
While the immediate `waitUntil` handles transient failures, a background cron job (scheduled in `wrangler.toml`) should call `retryFailedDeliveries` to pick up any records stuck in a `failed` state from the last 24 hours that haven't exhausted their attempts.

## Admin UI Management

The Merchant Dashboard provides a full interface for managing outbound webhooks at `/admin/webhooks`. 

### Features for Developers:
- **Registration**: Add endpoint URLs and select event subscriptions.
- **Secret Rotation**: Regenerate the `whsec_` key immediately if a compromise is suspected. This will cause subsequent deliveries to use the new signature.
- **Log Inspection**: View the 20 most recent deliveries for any webhook, including the HTTP response code and the number of attempts made.
- **Manual Retry**: Force a retry of a failed delivery directly from the UI, which resets the attempt counter and sets the status back to `pending`.

### Wildcard Logic Implementation
When `dispatchWebhooks` runs, it parses the stored JSON array of events and performs the following matches:
- Exact match: `order.created === order.created`
- Global wildcard: `*` matches everything.
- Namespace wildcard: `order.*` matches any event starting with `order.`.

```typescript
const isSubscribed = subscribedEvents.some((e) => {
  if (e === '*') return true;
  if (e === eventType) return true;
  if (e.endsWith('.*')) {
    const prefix = e.slice(0, -2);
    return eventType.startsWith(prefix + '.');
  }
  return false;
});
```
