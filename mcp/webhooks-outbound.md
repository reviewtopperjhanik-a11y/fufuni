## Outbound vs. Inbound Webhooks

Fufuni distinguishes between **Inbound** and **Outbound** webhooks to ensure a clear flow of data between the e-commerce core and external services.

*   **Inbound Webhooks:** These are handled at `/v1/webhooks/stripe`. They receive notifications from external providers (like Stripe) to trigger internal Fufuni state changes, such as marking an order as paid or updating inventory after a checkout session completes.
*   **Outbound Webhooks:** These are managed via the Merchant Admin API and allow Fufuni to notify your own external systems (ERPs, custom dashboards, or marketing tools) when domain events occur.

### Outbound Webhook Registration

To receive notifications, an administrator must register an endpoint. This is done through the `webhooks-outbound.ts` router using a `POST` request. Each registered webhook receives a unique signing secret (prefixed with `whsec_`) used for security.

```typescript
// Example of registering a new outbound webhook via the Merchant API
// POST /v1/webhooks/

const registerWebhook = async (apiBase: string, token: string) => {
  const response = await fetch(`${apiBase}/v1/webhooks`, {
    method: 'POST',
    headers: {
      'Authorization': `Bearer ${token}`,
      'Content-Type': 'application/json',
    },
    body: JSON.stringify({
      url: 'https://api.my-service.com/fufuni-receiver',
      events: ['order.created', 'order.shipped', 'inventory.low'],
    }),
  });

  const data = await response.json();
  console.log('Webhook Secret:', data.secret); // Save this for signature verification!
  return data;
};
```

## Supported Event Names and Triggers

Fufuni supports a variety of events that trigger outbound notifications. You can subscribe to specific events or use wildcards.

### Event Types

| Event Name | Trigger Point |
| :--- | :--- |
| `order.created` | Emitted when a checkout session is successfully completed and an order record is persisted. |
| `order.paid` | Emitted when payment is confirmed (often simultaneous with created). |
| `order.shipped` | Emitted when an admin updates the order status to "shipped". |
| `order.cancelled` | Emitted when an order is cancelled or refunded. |
| `inventory.low` | Emitted when a SKU's available quantity drops below the defined threshold (default: 5). |
| `order.*` | A wildcard that matches any event starting with "order.". |
| `*` | A global wildcard that matches every event emitted by the system. |

### Internal Dispatch Example

In the backend, events are dispatched using the `dispatchWebhooks` utility from `lib/webhooks.ts`. This utility automatically filters for active subscribers.

```typescript
import { dispatchWebhooks } from '../lib/webhooks';

// Example trigger inside an order update route
async function markOrderShipped(c: Context) {
  const db = getDb(c.var.db);
  const orderId = c.req.param('id');

  await db.run(`UPDATE orders SET status = 'shipped' WHERE id = ?`, [orderId]);

  // Dispatching the outbound webhook asynchronously
  c.executionCtx.waitUntil(
    dispatchWebhooks(c.var.db, c.executionCtx, 'order.shipped', {
      order_id: orderId,
      shipped_at: new Date().toISOString(),
    })
  );

  return c.json({ success: true });
}
```

## Delivery Mechanics and Retry Schedule

Fufuni uses a robust, non-blocking delivery system powered by Cloudflare Workers' `waitUntil`. This ensures that customer-facing requests are not slowed down by external API latency.

### Retry Logic

If a delivery fails (defined as a non-2xx response or a network timeout), Fufuni implements an exponential back-off strategy.

1.  **Maximum Attempts:** 3.
2.  **Failure Criteria:** Any status code $\ge 400$ (excluding 429) or request timeout.
3.  **Back-off Intervals:**
    *   **Attempt 1:** Immediate.
    *   **Attempt 2:** 1 second after failure.
    *   **Attempt 3:** 4 seconds after failure.
    *   **Attempt 4:** 16 seconds after failure.

### Database Logging

Every attempt is logged in the `webhook_deliveries` table. This allows admins to audit failures directly from the dashboard.

```sql
-- Querying recent failures for a specific webhook
SELECT 
    id, 
    event_type, 
    status, 
    attempts, 
    response_code, 
    last_attempt_at 
FROM webhook_deliveries 
WHERE webhook_id = 'wh_123' 
AND status = 'failed'
ORDER BY created_at DESC;
```

## HMAC-SHA256 Signature Verification

To ensure that a webhook payload actually came from your Fufuni instance and has not been tampered with, you **must** verify the signature provided in the headers.

### Required Headers

*   `X-Fufuni-Signature`: The HMAC-SHA256 hex digest of the raw JSON body.
*   `X-Fufuni-Timestamp`: The Unix timestamp (seconds) when the signature was generated.
*   `X-Fufuni-Delivery-Id`: A unique UUID for the delivery attempt.

### Consumer Verification (Node.js/TypeScript)

Use the following pattern in your receiving service to validate the payload.

```typescript
import { createHmac, timingSafeEqual } from 'node:crypto';

/**
 * Verifies the Fufuni signature
 * @param body Raw request body string
 * @param signature Value from X-Fufuni-Signature header
 * @param secret Your webhook secret (whsec_...)
 */
function verifyFufuniSignature(body: string, signature: string, secret: string): boolean {
  const hmac = createHmac('sha256', secret);
  const computedSignature = hmac.update(body).digest('hex');

  // Use timingSafeEqual to prevent timing attacks
  return timingSafeEqual(
    Buffer.from(signature, 'hex'),
    Buffer.from(computedSignature, 'hex')
  );
}

// Usage in an Express/Hono route
app.post('/webhook', async (req, res) => {
  const signature = req.headers['x-fufuni-signature'] as string;
  const rawBody = JSON.stringify(req.body); // Ensure you use the raw buffer/string
  
  if (!verifyFufuniSignature(rawBody, signature, process.env.FUFUNI_SECRET!)) {
    return res.status(401).send('Invalid signature');
  }

  // Proceed with processing
  const { type, data } = req.body;
  console.log(`Received event: ${type}`, data);
  res.status(200).send('OK');
});
```

## Manual Resend and Management

If an external system was down and the maximum retries were exhausted, administrators can manually trigger a retry via the Admin Dashboard or the API.

### Retrying a Specific Delivery

The `POST /v1/webhooks/{id}/deliveries/{deliveryId}/retry` endpoint resets the attempt counter and immediately schedules a new delivery.

```typescript
// Admin implementation for retrying a failed delivery
adminApp.openapi(retryDeliveryRoute, async (c) => {
  const { id, deliveryId } = c.req.valid('param');
  const db = getDb(c.var.db);

  const [webhook] = await db.query<any>(`SELECT * FROM webhooks WHERE id = ?`, [id]);
  const [delivery] = await db.query<any>(
    `SELECT * FROM webhook_deliveries WHERE id = ? AND webhook_id = ?`,
    [deliveryId, id]
  );

  if (!delivery) throw ApiError.notFound('Delivery not found');

  // Reset status to pending for the logs
  await db.run(
    `UPDATE webhook_deliveries SET status = 'pending', attempts = 0 WHERE id = ?`, 
    [deliveryId]
  );

  // Trigger immediate async delivery
  c.executionCtx.waitUntil(retryDelivery(c.var.db, webhook, delivery));

  return c.json({ status: 'pending', message: 'Delivery retry triggered' });
});
```

### Rotating Secrets

If a secret is compromised, it should be rotated immediately. Rotating a secret invalidates the old one immediately; any deliveries currently in flight with the old secret will fail verification on the consumer side.

```typescript
// Rotating a secret via the API
const rotateSecret = async (webhookId: string, token: string) => {
  const res = await fetch(`/v1/webhooks/${webhookId}/rotate-secret`, {
    method: 'POST',
    headers: { 'Authorization': `Bearer ${token}` }
  });
  const { secret } = await res.json();
  return secret; // New 'whsec_...' string
};
```

## Delivery Log Structure

The webhook delivery detail API (`GET /v1/webhooks/{id}/deliveries/{deliveryId}`) provides a full trace of the HTTP interaction, which is essential for debugging payload mismatches or remote server errors.

### Schema: WebhookDeliveryResponse

```typescript
interface WebhookDeliveryResponse {
  id: string;             // Delivery UUID
  event_type: string;     // e.g., 'order.created'
  payload: object;        // The actual JSON sent
  status: 'success' | 'failed' | 'pending';
  attempts: number;       // Current attempt count (1-3)
  response_code: number;  // HTTP status from consumer (e.g., 200, 500)
  response_body: string;  // First 1000 characters of remote response
  created_at: string;     // ISO timestamp of first attempt
  last_attempt_at: string; // ISO timestamp of most recent attempt
}
```

This structure is rendered in the `WebhooksPage` component (`apps/client/src/pages/admin/webhooks.tsx`), providing a visual timeline of all interactions with the configured endpoint.
