## Outbound Webhooks vs. Inbound Webhooks

In the Fufuni ecosystem, it is critical to distinguish between **Inbound** and **Outbound** webhooks. They serve different purposes and are handled by different logic paths within the framework.

*   **Inbound Webhooks:** These are HTTP requests sent *to* Fufuni by external services. The most common example is the **Stripe Webhook** (`POST /v1/webhooks/stripe`), which notifies Fufuni that a payment was successful so the framework can convert a Cart into an Order.
*   **Outbound Webhooks:** These are HTTP requests sent *from* Fufuni's Durable Objects to external URLs configured by the merchant. They notify third-party systems (like ERPs, custom shipping dashboards, or Slack bots) about internal domain events.

### Inbound Stripe Webhook Example
The following snippet demonstrates how Fufuni handles an incoming event from Stripe to trigger order creation:

```typescript
// apps/merchant/src/routes/webhooks.ts
webhooks.post('/stripe', async (c) => {
  const signature = c.req.header('stripe-signature');
  const body = await c.req.text();
  const db = getDb(c.var.db);

  // Inbound logic: Verify Stripe signature and process payment
  const event = await stripe.webhooks.constructEventAsync(
    body, 
    signature!, 
    c.env.STRIPE_WEBHOOK_SECRET
  );

  if (event.type === 'checkout.session.completed') {
    // Logic to finalize order in the SQLite DO
    await handleOrderCreation(db, event.data.object);
  }
  return c.json({ ok: true });
});
```

## Outbound Endpoint Registration

Outbound webhooks are managed via the Merchant Admin API. To start receiving notifications, an external system must register an endpoint URL and subscribe to specific event patterns.

### Registration Payload
When registering via `POST /v1/webhooks/outbound`, the following fields are required:

| Field | Type | Description |
| :--- | :--- | :--- |
| `url` | `string` | The target HTTP(S) URL to receive the POST request. |
| `events` | `string[]` | An array of event names or patterns (e.g., `order.*`). |

### Example: Creating a Webhook Subscription
The following TypeScript code demonstrates how to register a new outbound webhook using the standard Merchant API structure:

```typescript
// Example registration request using the Fufuni Admin API
const registerWebhook = async (adminToken: string) => {
  const response = await fetch('https://api.fufuni.store/v1/webhooks/outbound', {
    method: 'POST',
    headers: {
      'Authorization': `Bearer ${adminToken}`,
      'Content-Type': 'application/json'
    },
    body: JSON.stringify({
      url: 'https://my-erp-system.com/webhooks/fufuni',
      events: ['order.created', 'inventory.low']
    })
  });

  const result = await response.json();
  // IMPORTANT: Save the returned 'secret' to verify signatures later
  console.log('Webhook Secret:', result.secret); 
  return result;
};
```

## Supported Events and Trigger Points

Fufuni dispatches outbound webhooks when specific state transitions occur within the Durable Object. Subscriptions support wildcards (e.g., `order.*`) to capture all related events.

### Core Event List
*   **`order.created`**: Triggered immediately after a successful Stripe checkout and conversion from a cart.
*   **`order.paid`**: Triggered when a payment intent is successfully captured.
*   **`order.shipped`**: Dispatched when an admin updates the order status to `shipped`.
*   **`order.cancelled`**: Triggered upon order cancellation.
*   **`product.created` / `product.updated` / `product.deleted`**: Triggered when the product catalog is modified.
*   **`inventory.low`**: A specialized event triggered when `on_hand - reserved` quantity falls below the `LOW_INVENTORY_THRESHOLD` (default: 5).

### Event Dispatcher Implementation
The `dispatchWebhooks` function handles the "fan-out" logic, finding all active webhooks that match the event type.

```typescript
// apps/merchant/src/lib/webhooks.ts
export async function dispatchWebhooks(
  stub: DOStub,
  ctx: ExecutionContext,
  eventType: WebhookEventType,
  data: Record<string, unknown>
): Promise<void> {
  const db = getDb(stub);
  const webhooks = await db.query<any>(
    `SELECT id, url, events, secret FROM webhooks WHERE status = 'active'`
  );

  for (const webhook of webhooks) {
    const subscribedEvents = JSON.parse(webhook.events);
    if (isSubscribed(subscribedEvents, eventType)) {
      const deliveryId = uuid();
      // Record the intent to deliver
      await db.run(
        `INSERT INTO webhook_deliveries (id, webhook_id, event_type, payload, status, created_at)
         VALUES (?, ?, ?, ?, 'pending', ?)`,
        [deliveryId, webhook.id, eventType, JSON.stringify(data), now()]
      );

      // Execute delivery asynchronously without blocking the main request
      ctx.waitUntil(deliverWebhook(stub, webhook.id, webhook.url, webhook.secret, deliveryId, data));
    }
  }
}
```

## Delivery Mechanics and Retry Schedule

Fufuni uses an asynchronous delivery model powered by Cloudflare Workers' `ExecutionContext.waitUntil`. This ensures that store operations (like checkout) remain fast even if the webhook recipient is slow or temporarily offline.

### Retry Schedule
If a delivery fails (non-2xx response or network error), Fufuni follows an exponential back-off schedule:

1.  **First Failure:** Retry after 1 second.
2.  **Second Failure:** Retry after 4 seconds.
3.  **Third Failure:** Retry after 16 seconds.

After 3 failed attempts, the delivery status is marked as `failed` in the database.

### Implementation of Exponential Back-off
```typescript
// Inside deliverWebhook function
for (let attempt = 1; attempt <= MAX_ATTEMPTS; attempt++) {
  try {
    const response = await fetch(url, {
      method: 'POST',
      headers: { /* ... headers ... */ },
      body: JSON.stringify(payload),
    });

    if (response.ok) {
      await updateDeliveryStatus(db, deliveryId, 'success', response.status);
      return;
    }
  } catch (err) {
    // Log error for next attempt
  }

  if (attempt < MAX_ATTEMPTS) {
    // Exponential back-off: 1s, 4s, 16s...
    await new Promise((r) => setTimeout(r, Math.pow(2, attempt) * 1000));
  }
}
```

## Security: HMAC-SHA256 Signatures

Every outbound request includes security headers to prevent spoofing. The payload is signed using the `secret` generated during webhook registration.

### Headers Sent to Consumer
*   **`X-Fufuni-Signature`**: The HMAC-SHA256 hex digest of the raw JSON body.
*   **`X-Fufuni-Timestamp`**: The Unix timestamp of the delivery attempt.
*   **`X-Fufuni-Delivery-Id`**: The unique ID of this specific delivery attempt.

### Signature Computation (Backend)
```typescript
async function signPayload(payload: string, secret: string): Promise<string> {
  const encoder = new TextEncoder();
  const key = await crypto.subtle.importKey(
    'raw',
    encoder.encode(secret),
    { name: 'HMAC', hash: 'SHA-256' },
    false,
    ['sign']
  );
  const signature = await crypto.subtle.sign('HMAC', key, encoder.encode(payload));
  return Array.from(new Uint8Array(signature))
    .map((b) => b.toString(16).padStart(2, '0'))
    .join('');
}
```

## Consumer Signature Verification

When receiving a webhook from Fufuni, your server **must** verify the signature before processing any data. This ensures the request originated from your Fufuni instance and that the payload hasn't been tampered with.

### Node.js Verification Example
This example uses the native `node:crypto` module to verify the signature.

```typescript
import { createHmac, timingSafeEqual } from 'node:crypto';

/**
 * Verifies a Fufuni webhook signature.
 * @param body - The raw request body as a string.
 * @param signature - The value from X-Fufuni-Signature header.
 * @param secret - Your whsec_... secret key.
 */
function verifyFufuniSignature(body: string, signature: string, secret: string): boolean {
  const hmac = createHmac('sha256', secret);
  const computed = hmac.update(body).digest('hex');
  
  // Use timingSafeEqual to prevent timing attacks
  return timingSafeEqual(
    Buffer.from(computed),
    Buffer.from(signature)
  );
}
```

## Delivery Logs and Monitoring

All delivery attempts are persisted in the `webhook_deliveries` table. This log is essential for debugging failed integrations and auditing data flow.

### Querying Delivery History
The admin API provides an endpoint to retrieve the last 20 deliveries for a specific webhook:
`GET /v1/webhooks/outbound/{id}`

**Returned Fields:**
*   `id`: The unique delivery attempt ID.
*   `event_type`: The name of the event (e.g., `order.created`).
*   `status`: `success`, `failed`, or `pending`.
*   `attempts`: Number of tries performed so far.
*   `response_code`: The HTTP status code returned by the consumer's server.
*   `response_body`: The first 1000 characters of the consumer's response (useful for debugging 500 errors).
*   `created_at`: Original event timestamp.

### SQL Schema for Delivery Logs
```sql
CREATE TABLE webhook_deliveries (
  id TEXT PRIMARY KEY,
  webhook_id TEXT NOT NULL,
  event_type TEXT NOT NULL,
  payload TEXT NOT NULL, -- Full JSON context
  status TEXT DEFAULT 'pending', -- 'success', 'failed'
  attempts INTEGER DEFAULT 0,
  response_code INTEGER,
  response_body TEXT,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  last_attempt_at DATETIME,
  FOREIGN KEY (webhook_id) REFERENCES webhooks(id)
);
```

## Manual Resend

In cases where a consumer's server was down for an extended period (exceeding the 16-second final retry), admins can manually trigger a resend of a failed delivery.

### Manual Retry Endpoint
`POST /v1/webhooks/outbound/{id}/deliveries/{deliveryId}/retry`

This endpoint resets the `attempts` counter to 0 and sets the status to `pending`, immediately triggering a new `deliverWebhook` call via `ctx.waitUntil`.

### When to Use Manual Resend
*   **Server Outages:** If your receiving endpoint was down for several hours.
*   **Logic Errors:** After deploying a fix to your webhook handler and needing to re-process failed events.
*   **Testing:** To verify your verification logic without having to place a new test order.

```typescript
// apps/merchant/src/routes/webhooks-outbound.ts
adminApp.openapi(retryDeliveryRoute, async (c) => {
  const { id, deliveryId } = c.req.valid('param');
  const db = getDb(c.var.db);

  const [webhook] = await db.query<any>(`SELECT * FROM webhooks WHERE id = ?`, [id]);
  const [delivery] = await db.query<any>(
    `SELECT * FROM webhook_deliveries WHERE id = ? AND webhook_id = ?`,
    [deliveryId, id]
  );

  // Trigger immediate retry
  c.executionCtx.waitUntil(retryDelivery(c.var.db, webhook, delivery));

  return c.json({ status: 'pending', message: 'Delivery retry triggered' }, 200);
});
```
