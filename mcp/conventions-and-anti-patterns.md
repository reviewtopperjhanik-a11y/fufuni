### Database Queries and Migrations

Fufuni uses raw SQL for performance and predictability within Durable Objects. Drizzle ORM is explicitly forbidden to avoid bundle bloat and unexpected query behavior in the DO environment.

**Anti-Pattern:** Modifying an old migration or using an ORM to manage state.

```typescript
// ❌ WRONG: Modifying an existing migration object in do.ts
// This will NEVER run on existing instances.
const migrations = [
  { name: "init", sql: "CREATE TABLE products..." } // DO NOT TOUCH THIS
];
```

**Correct Approach:** Append a new migration object to the `ensureInitialized()` sequence in `do.ts` and create a corresponding `.sql` file for version control.

```typescript
// ✅ CORRECT: migrations in apps/merchant/src/do.ts
async function ensureInitialized(db: SqliteDatabase) {
  const migrations = [
    { name: "001_init", sql: SCHEMA },
    { 
      name: "002_add_discount_code", 
      sql: "ALTER TABLE orders ADD COLUMN discount_code TEXT;" 
    }
  ];

  for (const m of migrations) {
    const exists = db.query("SELECT name FROM migrations WHERE name = ?").get(m.name);
    if (!exists) {
      db.run(m.sql);
      db.run("INSERT INTO migrations (name) VALUES (?)", m.name);
    }
  }
}

// Data access using getDb helper
```

## Pricing and Multi-Region Logic

Fufuni supports global commerce where a single product variant may have different prices in different regions (e.g., USD for North America, EUR for Europe).

**Anti-Pattern:** Querying the `price` column directly from the `variants` table. This ignores regional overrides and currency logic.

```typescript
// ❌ WRONG: Direct variant price access

```

**Correct Approach:** Always join with `variant_prices` and filter by the active `region_id`.

```typescript
// ✅ CORRECT: Regional price selection

  SELECT 
    v.*, 
    vp.amount as current_price,
    vp.currency_code
  FROM variants v
  JOIN variant_prices vp ON v.id = vp.variant_id
  WHERE v.id = ? AND vp.region_id = ?
`;
const priceData = db.query(sql).get(variantId, regionId);
```

### Stripe Webhooks and Refunds

Integrity of financial data is paramount. Never manually adjust order totals or status in the database if a corresponding Stripe action is required.

**Anti-Pattern:** Refunding an order by simply updating the database status.

```typescript
// ❌ WRONG: DB-only refund
db.run("UPDATE orders SET status = 'refunded' WHERE id = ?", orderId);
```

**Correct Approach:** Initiate the refund via the Stripe API. The webhook handler or the subsequent lines in the controller will then update the local database once the financial transaction is acknowledged.

```typescript
// ✅ CORRECT: Stripe-first refund
app.post("/v1/orders/:id/refund", async (c) => {
  const id = c.req.param("id");
  const order = await getOrderFromDb(id);
  
  // 1. Call Stripe
  const refund = await stripe.refunds.create({
    payment_intent: order.stripe_payment_intent_id,
  });

  // 2. Update DB only after successful API call
  if (refund.status === 'succeeded') {
    db.run("UPDATE orders SET status = 'refunded' WHERE id = ?", id);
  }
  return c.json({ success: true });
});
```
