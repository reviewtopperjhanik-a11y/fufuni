## Architecture of User Metadata in Fufuni

In the Fufuni framework, we minimize database round-trips for user preferences (like wishlists, themes, or saved carts) by leveraging the Auth0 JWT. Instead of querying the backend every time a component needs to know if an item is in a wishlist, we inject `user_metadata` directly into the Access Token.

This injection happens via an Auth0 post-login Action. The metadata is placed under a specific namespace: `extra_user_info/user_metadata`. This allows the frontend to read user state instantly upon decoding the JWT, using the `jose` library, without making additional network requests to the `/userinfo` endpoint.

### JWT Structure and Decoding

When a user authenticates, the resulting Access Token contains a payload similar to this:

```json
{
  "iss": "https://auth.fufuni.com/",
  "sub": "auth0|123456",
  "extra_user_info/user_metadata": {
    "https___shop_fufuni_com": {
      "wishlist": ["prod_1", "prod_2"],
      "theme": "dark"
    }
  },
  "iat": 1710000000,
  "exp": 1710003600
}
```

To read this client-side, we use `decodeJwt`:

```typescript
import { decodeJwt } from "jose";

interface MetadataPayload {
  "extra_user_info/user_metadata"?: Record<string, any>;
}

export const getMetadataFromToken = (token: string | null): any => {
  if (!token) return null;
  try {
    const payload = decodeJwt(token) as MetadataPayload;
    return payload["extra_user_info/user_metadata"] || {};
  } catch (error) {
    console.error("Failed to decode JWT for metadata", error);
    return null;
  }
};
```

## Multi-Store Scoping and Normalization

Fufuni is designed for multi-tenancy. A single Auth0 tenant might serve multiple store instances (e.g., `shop.brand-a.com` and `shop.brand-b.com`). To prevent data collisions between stores, all `user_metadata` is scoped under a key derived from the store's URL.

### The Normalization Logic

Auth0 imposes strict character limits on metadata keys. Specifically, dots (`.`), colons (`:`), and slashes (`/`) are forbidden. We use `normalizeStoreUrl` to transform a standard URL into a valid Auth0 key.

```typescript
/**
 * Normalizes store URL: "https://store.example.com/" -> "https___store_example_com"
 */
export const normalizeStoreUrl = (storeUrl?: string): string | undefined => {
  if (!storeUrl) return undefined;
  const normalized = storeUrl
    .replace(/\/$/, "") // Remove trailing slash
    .replace(/[:.\/]/g, "_"); // Replace forbidden characters with underscores

  return normalized || undefined;
};

/**
 * Extracts store-specific data, falling back to root for legacy support.
 */
export const getStoreMetadata = (userMetadata: any, storeUrl?: string): any => {
  if (!userMetadata || typeof userMetadata !== "object") return undefined;

  const normalizedUrl = normalizeStoreUrl(storeUrl);

  if (
    normalizedUrl &&
    userMetadata[normalizedUrl] &&
    typeof userMetadata[normalizedUrl] === "object"
  ) {
    return userMetadata[normalizedUrl];
  }

  return userMetadata;
};
```

## The useTokenUserData Hook

To manage this data reactively in React 19, Fufuni provides the `useTokenUserData<T>` hook. This hook solves three problems:
1. **Initial Hydration**: Reading from the token on mount.
2. **Auth Lifecycle**: Updating data when a user logs in or out.
3. **Cross-Component Sync**: Updating multiple UI elements (e.g., a header badge and a product button) when a mutation occurs.

### Implementation Pattern

```typescript
import { useTokenUserData } from "@/hooks/use-token-user-data";
import { getMetadataFromToken } from "@/lib/jwt-utils";
import { getStoreMetadata } from "@/lib/store-metadata";

const STORE_URL = import.meta.env.VITE_STORE_URL;
const WISHLIST_SYNC_EVENT = "fufuni:wishlist-sync";

export function useWishlist() {
  const selector = (token: string | null) => {
    const fullMetadata = getMetadataFromToken(token);
    const storeMetadata = getStoreMetadata(fullMetadata, STORE_URL);
    return (storeMetadata?.wishlist as string[]) || [];
  };

  const { data, isLoading, setData } = useTokenUserData<string[]>(
    selector,
    WISHLIST_SYNC_EVENT
  );

  return { wishlist: data, isLoading, setWishlist: setData };
}
```

## Cross-Component Reactivity

When a user clicks "Add to Wishlist", we perform a mutation. However, the JWT in the user's browser does not update immediately—it only refreshes when the `auth.getAccessToken()` call triggers a silent refresh or when the token expires.

To ensure the UI is "Optimistically Reactive" across the whole app, we use `CustomEvent`.

### The Sync Flow
1. **Mutation**: Component A calls the backend API `PATCH /v1/me/wishlist`.
2. **Local Update**: Component A calculates the new wishlist state.
3. **Dispatch**: Component A dispatches a `CustomEvent` with the new state.
4. **Broadcast**: All other components using `useTokenUserData` listen for this event and update their local React state immediately via `setData`.

```typescript
// Inside a ProductCard component
const handleToggleWishlist = async () => {
  const newWishlist = isFavorite 
    ? wishlist.filter(id => id !== productId)
    : [...wishlist, productId];

  // 1. Update Backend
  await apiClient.patch("/v1/me/preferences", { 
    wishlist: newWishlist 
  });

  // 2. Broadcast to all other components
  window.dispatchEvent(
    new CustomEvent(WISHLIST_SYNC_EVENT, { detail: newWishlist })
  );
};
```

## Step-by-Step: Adding a New Preference Field

Suppose you want to add a `preferredCurrency` setting for users. Follow these steps to implement it end-to-end.

### Step 1: Define Constants and Types
Create a dedicated hook file for the preference.

```typescript
// apps/client/src/hooks/use-currency-preference.ts
export const CURRENCY_SYNC_EVENT = "fufuni:currency-sync";
export type CurrencyCode = "USD" | "EUR" | "GBP";
```

### Step 2: Implement the Hook
Use the `useTokenUserData` hook with a specific selector.

```typescript
import { useTokenUserData } from "./use-token-user-data";
import { getMetadataFromToken } from "@/lib/jwt-utils";
import { getStoreMetadata, normalizeStoreUrl } from "@/lib/store-metadata";

export function useCurrencyPreference() {
  const selector = (token: string | null): CurrencyCode => {
    const raw = getMetadataFromToken(token);
    const storeData = getStoreMetadata(raw, import.meta.env.VITE_STORE_URL);
    return (storeData?.preferredCurrency as CurrencyCode) || "USD";
  };

  return useTokenUserData<CurrencyCode>(selector, CURRENCY_SYNC_EVENT);
}
```

### Step 3: Persistence via Backend API
The backend `PATCH /v1/me/preferences` endpoint (implemented in Hono) handles merging the data into the Auth0 management API.

```typescript
// Example of how the frontend triggers the update
const { data: current, setData } = useCurrencyPreference();

const updateCurrency = async (newCurrency: CurrencyCode) => {
  // Update local state and notify other components immediately
  window.dispatchEvent(new CustomEvent(CURRENCY_SYNC_EVENT, { detail: newCurrency }));
  
  // Persist to Auth0 via Fufuni Backend
  await fetch("/api/v1/me/preferences", {
    method: "PATCH",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ preferredCurrency: newCurrency })
  });
};
```

### Step 4: Backend Scoping (Hono/Cloudflare Worker)
On the backend, ensure you use the same `normalizeStoreUrl` logic before sending data to Auth0.

```typescript
// apps/backend/src/routes/me.ts
app.patch("/preferences", async (c) => {
  const body = await c.req.json();
  const storeUrl = c.env.STORE_URL;
  const normalizedKey = normalizeStoreUrl(storeUrl);
  
  const userId = c.get("jwtPayload").sub;
  
  // We nest the update under the normalized key
  await auth0Management.updateUserMetadata(userId, {
    [normalizedKey]: body
  });
  
  return c.json({ success: true });
});
```

### Summary of Data Flow
| Action | Component | Mechanism |
| :--- | :--- | :--- |
| **Read** | `useTokenUserData` | `decodeJwt(token)` |
| **Write** | Mutation Helper | `PATCH /v1/me/preferences` |
| **Sync** | `window` | `CustomEvent` |
| **Refresh** | Auth0 Action | Merged into JWT on next token issuance |

This pattern ensures that user metadata is **globally available**, **store-isolated**, and **eventually consistent** without taxing the SQLite Durable Objects for simple UI preferences.
