## JWT User Metadata Architecture

Fufuni leverages Auth0 `user_metadata` to store lightweight, per-user preferences and state such as wishlists, theme settings, and saved carts. Unlike traditional architectures that require a database lookup for every preference check, Fufuni injects this metadata directly into the JWT Access Token via an Auth0 post-login Action.

### Metadata Injection and Namespace

To avoid collisions with standard OIDC claims, all Fufuni-specific metadata is nested under a custom namespace. The verified namespace for this data is `extra_user_info/user_metadata`. 

When a user authenticates, the resulting JWT contains a payload structured like this:

```json
{
  "iss": "https://auth.fufuni.com/",
  "sub": "auth0|12345",
  "extra_user_info/user_metadata": {
    "https___shop_example_com": {
      "wishlist": ["prod_1", "prod_2"],
      "theme": "dark"
    },
    "global_preference": "en-US"
  },
  "iat": 1715600000,
  "exp": 1715686400
}
```

## Multi-Store Scoping and Normalization

Fufuni is designed for multi-tenancy. A single Auth0 tenant might serve multiple Fufuni store instances. To prevent data leakage or overwrites between stores, metadata is scoped using a normalized version of the store's base URL.

### Character Restrictions

Auth0 metadata keys do not allow dots (`.`), colons (`:`), or slashes (`/`). The framework provides a `normalizeStoreUrl` helper to convert standard URLs into safe metadata keys. Both the frontend and backend must use this identical logic to ensure consistency.

```typescript
/**
 * apps/client/src/lib/store-metadata.ts
 */

export const normalizeStoreUrl = (storeUrl?: string): string | undefined => {
  if (!storeUrl) return undefined;
  const normalized = storeUrl
    .replace(/\/$/, "") // Remove trailing slash
    .replace(/[:.\/]/g, "_"); // Replace dots, colons, and slashes with underscores

  return normalized || undefined;
};

/**
 * Example Usage:
 * const key = normalizeStoreUrl("https://store.fufuni.com/");
 * // Result: "https___store_fufuni_com"
 */
```

### Retrieving Scoped Metadata

The `getStoreMetadata` helper attempts to find data specific to the current store. If no store-specific key is found, it falls back to the root metadata object for backward compatibility or global settings.

```typescript
export const getStoreMetadata = (userMetadata: any, storeUrl?: string): any => {
  if (!userMetadata || typeof userMetadata !== "object") return undefined;

  const normalizedUrl = normalizeStoreUrl(storeUrl);

  if (
    normalizedUrl &&
    userMetadata[normalizedUrl] &&
    typeof userMetadata[normalizedUrl] === "object"
  ) {
    return userMetadata[normalizedUrl];
  }

  return userMetadata;
};
```

## Reading Metadata Client-Side

Because the metadata is embedded in the JWT, the frontend does not need to perform an additional API request to fetch user preferences. Using the `jose` library, the client can decode the token instantly.

```typescript
import { decodeJwt } from "jose";

interface CustomClaims {
  "extra_user_info/user_metadata"?: Record<string, any>;
}

export function getMetadataFromToken(token: string | null): any {
  if (!token) return null;
  try {
    const payload = decodeJwt(token) as CustomClaims;
    return payload["extra_user_info/user_metadata"] || {};
  } catch (e) {
    console.error("Failed to decode JWT", e);
    return null;
  }
}
```

## The useTokenUserData Hook

The `useTokenUserData<T>` hook is the central mechanism for consuming user metadata in React components. It manages the loading state from the Auth0 token and provides a synchronization layer for cross-component updates.

### Hook Implementation

The hook uses a `parseFromToken` selector function to extract the specific piece of data (e.g., the wishlist array) and an `eventName` to listen for manual updates triggered by other components.

```typescript
import { useState, useEffect } from "react";
import { useAuth } from "@/authentication";

export function useTokenUserData<T>(
  parseFromToken: (token: string | null) => T,
  eventName: string,
): {
  data: T;
  isLoading: boolean;
  isError: boolean;
  setData: (value: T) => void;
} {
  const auth = useAuth();
  const [data, setData] = useState<T>(() => parseFromToken(null));
  const [isLoading, setIsLoading] = useState<boolean>(auth.isAuthenticated);
  const [isError, setIsError] = useState<boolean>(false);

  useEffect(() => {
    let isMounted = true;
    const load = async () => {
      if (!auth.isAuthenticated) {
        if (isMounted) { setData(parseFromToken(null)); setIsLoading(false); }
        return;
      }
      try {
        const token = await auth.getAccessToken();
        if (isMounted) { setData(parseFromToken(token)); setIsLoading(false); }
      } catch {
        if (isMounted) { setIsError(true); setIsLoading(false); }
      }
    };
    load();
    return () => { isMounted = false; };
  }, [auth.isAuthenticated, auth.getAccessToken]);

  useEffect(() => {
    const handleSync = (e: Event) => {
      setData((e as CustomEvent<T>).detail);
    };
    window.addEventListener(eventName, handleSync);
    return () => window.removeEventListener(eventName, handleSync);
  }, [eventName]);

  return { data, isLoading, isError, setData };
}
```

## Cross-Component Reactivity

When a user modifies a preference (e.g., adds an item to their wishlist), the change follows a specific lifecycle to ensure the UI remains reactive across the entire application without a full page reload.

1.  **Mutation**: The component calls a Fufuni backend endpoint (e.g., `PATCH /v1/me/wishlist`).
2.  **Persistence**: The backend updates the Auth0 `user_metadata` via the Auth0 Management API.
3.  **Local Sync**: The initiating component dispatches a `CustomEvent` with the new value.
4.  **UI Update**: All active `useTokenUserData` hooks listening for that `eventName` update their local state immediately.
5.  **Token Refresh**: Since the JWT still contains the *old* data, a background call to `getAccessTokenSilently({ cacheMode: 'force-network' })` is often triggered to ensure the next token contains the updated claims.

### Example: Dispatching a Sync Event

```typescript
const WISHLIST_CHANGED_EVENT = "fufuni:wishlist:changed";

const updateWishlist = async (newItems: string[]) => {
  // 1. API Call
  await api.patch("/v1/me/wishlist", { items: newItems });
  
  // 2. Immediate UI Sync
  window.dispatchEvent(new CustomEvent(WISHLIST_CHANGED_EVENT, { 
    detail: newItems 
  }));
};
```

## Step-by-Step: Adding a New Preference Field

To add a new per-user field (e.g., `layoutDensity`), follow these steps:

### 1. Define the Selector

Create a helper function to extract your new field from the JWT.

```typescript
// apps/client/src/hooks/use-layout-density.ts
import { getMetadataFromToken } from "@/lib/jwt-utils";
import { getStoreMetadata } from "@/lib/store-metadata";

const EVENT_NAME = "fufuni:layout:density";
const STORE_URL = import.meta.env.VITE_STORE_URL;

export const useLayoutDensity = () => {
  return useTokenUserData<string>((token) => {
    const metadata = getMetadataFromToken(token);
    const storeData = getStoreMetadata(metadata, STORE_URL);
    return storeData?.layoutDensity ?? "comfortable"; // Default value
  }, EVENT_NAME);
};
```

### 2. Implement the Backend Update

The Fufuni backend should handle the storage of this field in Auth0.

```typescript
// apps/server/src/routes/me.ts
import { normalizeStoreUrl } from "../lib/store-metadata";

app.patch("/v1/me/preferences", async (c) => {
  const { layoutDensity } = await c.req.json();
  const user = c.get("user"); // Authenticated user from middleware
  const storeKey = normalizeStoreUrl(process.env.STORE_URL);

  // Update Auth0 Management API
  await auth0.updateUserMetadata(user.id, {
    [storeKey]: {
      layoutDensity
    }
  });

  return c.json({ success: true });
});
```

### 3. Update the UI and Sync

Call the API and trigger the event so other components (like a Sidebar and a Settings Page) update simultaneously.

```typescript
const SettingsToggle = () => {
  const { data: density, setData } = useLayoutDensity();

  const toggleDensity = async () => {
    const next = density === "comfortable" ? "compact" : "comfortable";
    
    // Optimistic update + Event Sync
    window.dispatchEvent(new CustomEvent("fufuni:layout:density", { detail: next }));
    
    // Persist to backend
    await api.patch("/v1/me/preferences", { layoutDensity: next });
  };

  return <Button onClick={toggleDensity}>Current: {density}</Button>;
};
```

### 4. Verification

After the `PATCH` request, the next time `auth.getAccessToken()` is called (either via natural expiration or a forced refresh), the `extra_user_info/user_metadata` claim in the JWT will reflect the new `layoutDensity` value. The `useTokenUserData` hook handles this transition gracefully by re-running the `load()` effect when the authentication state or token provider changes.
