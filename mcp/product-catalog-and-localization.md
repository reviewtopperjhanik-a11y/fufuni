## Product Catalog & Multilingual Content

The Fufuni catalog engine is designed for high-performance international e-commerce. It leverages SQLite's JSON capabilities within Cloudflare Durable Objects to manage localized content without the overhead of complex join tables for every translation. All text-heavy fields are stored as localized objects, and the system distinguishes between administrative management and public storefront access.

### Product and Variant Data Models

The catalog is split into two primary entities: **Products** (the logical grouping) and **Variants** (the specific SKU, size, or color).

#### Product Model
A product acts as a container for metadata and one or more variants. Key fields include:
- `id`: A UUID v4.
- `handle`: A unique, URL-safe slug (e.g., `classic-cotton-tshirt`). **Requirement:** Must be generated from the `en-US` title and match `/^[a-z0-9-]+$/`.
- `title_json`: A JSON object of localized strings.
- `description_json`: A JSON object of localized HTML/Markdown.
- `status`: One of `active`, `draft`, or `archived`.

#### Variant Model
Variants hold the physical and inventory-specific data:
- `sku`: The Stock Keeping Unit identifier.
- `price_cents` / `currency`: Display-only pricing stored in the main table.
- `weight_g`: Integer weight in grams.
- `dims_cm`: JSON object containing package dimensions.

### Multilingual Field Patterns

Fufuni strictly enforces a JSON-based localization pattern for `title`, `description`, `vendor`, and `tags`. This prevents "column bloat" and simplifies adding new languages.

#### Correct vs. Incorrect Storage

| Field | Correct Pattern (JSON) | Wrong Pattern (String) |
| :--- | :--- | :--- |
| **Title** | `{"en-US": "Red Hat", "fr-FR": "Chapeau Rouge"}` | `"Red Hat"` |
| **Tags** | `{"en-US": "summer,cotton", "fr-FR": "été,coton"}` | `"summer, cotton"` |

#### Handling Multilingual Fields in Code

When interacting with the database via `getDb()`, remember that SQLite returns these fields as strings. You must parse them before sending them to the client.

```typescript
// Logic for parsing localized fields from SQLite
export function getLocalizedValue(jsonStr: string, locale: string, fallback = 'en-US'): string {
  try {
    const data = JSON.parse(jsonStr);
    return data[locale] || data[fallback] || Object.values(data)[0] as string || "";
  } catch {
    return "";
  }
}
```

### Product Pricing & Currency

While the `variants` table contains a `price_cents` column, this is strictly for **display and fallback purposes**. 

**Source of Truth:** For checkout, tax calculation, and multi-region storefronts, the system queries the `variant_prices` table. This allows a single variant to have different prices in `USD`, `EUR`, and `GBP` without relying on real-time exchange rates.

```sql
-- Schema for the source-of-truth pricing
CREATE TABLE variant_prices (
    id TEXT PRIMARY KEY,
    variant_id TEXT NOT NULL,
    currency TEXT NOT NULL, -- e.g., 'USD'
    amount_cents INTEGER NOT NULL,
    compare_at_amount_cents INTEGER,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (variant_id) REFERENCES variants(id)
);
```

### Product Search and Filtering

Fufuni uses full-text `LIKE` queries for search. This is optimized for the SQLite engine running inside Durable Objects. The search covers the `handle` and the JSON-stringified versions of title, vendor, and tags.

- **Params:**

### Product Status Lifecycle

Every product and variant follows a simple state machine:

1.  **Draft:** Initial state. Visible in the Merchant dashboard but hidden from the public API.
2.  **Active:** Visible in the public catalog and available for purchase.
3.  **Archived:** Soft-deleted. Hidden from the public API and active merchant views, but retained for historical order reference.

**Note:** The `publicCatalog` router automatically filters for `status = 'active'`. The `adminCatalog` (Merchant API) returns all statuses but requires `adminOnly` middleware.

In this example, we will add a new localized `color_name_json` field to the Product entity to allow for better filtering on the frontend.

#### 3. Backend Route Implementation
Ensure the data is correctly stringified when saving to SQLite.

```typescript
// apps/merchant/src/routes/catalog.ts
adminApp.openapi(updateProduct, async (c) => {
  const { id } = c.req.valid('param');
  const body = c.req.valid('json');
  const db = getDb(c.env);

  const updateParts: string[] = [];
  const params: any[] = [];

  if (body.color_name_json) {
    updateParts.push('color_name_json = ?');
    params.push(JSON.stringify(body.color_name_json));
  }
  
  params.push(id);
  await db.prepare(`UPDATE products SET ${updateParts.join(', ')} WHERE id = ?`)
    .run(...params);

  return c.json({ success: true }, 200);
});
```

### Key Constraints Summary
- **Primary Key:** Always UUID v4 for products and variants.
- **Slug Generation:** Handles are generated once at creation. If the `en-US` title changes later, the handle should *not* change automatically to prevent broken SEO links, unless explicitly requested.
- **SQLite JSON:** Use `JSON_EXTRACT` in SQL for advanced filtering if simple `LIKE` is insufficient, but be aware of performance on large datasets within Durable Objects.
- **Security:** Always use the `authMiddleware` and `adminOnly` decorators for any route that modifies the catalog.
