## Order View Tokens (OVT) Architecture

In the Fufuni framework, customers are not required to create an Auth0 account to complete a purchase. This "Guest Checkout" workflow creates a challenge: how can a customer track their order status or view their invoice without a persistent session? Order View Tokens (OVT) solve this by providing a cryptographically signed, time-limited proof of access.

An OVT is a JSON Web Token (JWT) signed using the HMAC-HS256 algorithm. It encapsulates the Order ID and an expiration timestamp. When a guest visits a tracking URL, the frontend extracts this token and sends it to the backend. The backend validates that the token was signed by the merchant's secret and specifically references the requested Order ID.

### Key Benefits
- **Zero-friction access**: Customers click a link in their email and immediately see their order status.
- **Security by Design**: Even if an attacker guesses an Order ID, they cannot view the details without the corresponding signed token.
- **Stateless Verification**: The backend does not need to look up a session table; it only needs the environment secret to verify the token's integrity.
- **Deterministic Generation**: Using the same secret and order ID results in the same token (given a fixed issuance time), allowing the system to re-send confirmation emails without generating new database entries.

## Token Generation: `generateOrderViewToken()`

The generation process uses the `jose` library, which is natively supported by Cloudflare Workers. The token includes an `oid` (Order ID) claim. By default, tokens are valid for 30 days (`TOKEN_TTL_SECONDS`), ensuring the customer can check the status from fulfillment through delivery.

### Implementation Example

The following example demonstrates how to generate a token during the checkout completion phase.

```typescript
import { generateOrderViewToken } from '@/lib/order-token';

interface CheckoutContext {
  orderId: string;
  env: {
    ORDER_VIEW_TOKEN_SECRET: string;
  };
}

async function finalizeOrder(ctx: CheckoutContext) {
  // Generate the raw JWT token
  // This token will be sent to the customer via email
  const rawToken = await generateOrderViewToken(
    ctx.orderId, 
    ctx.env.ORDER_VIEW_TOKEN_SECRET
  );

  const trackingUrl = `https://fufuni.store/order/${ctx.orderId}?token=${rawToken}`;
  
  console.log(`Generated tracking link: ${trackingUrl}`);
  return { rawToken, trackingUrl };
}
```

### Determinism and Resending
A unique feature of the Fufuni OVT implementation is the ability to make generation deterministic. By passing a specific `issuedAt` date (like the order's `created_at` timestamp), you can reproduce the exact same token string multiple times. This prevents URL churn if a customer requests multiple copies of their confirmation email.

```typescript
// Deterministic generation using the order's creation date
const token = await generateOrderViewToken(order.id, secret, {
  issuedAt: new Date(order.createdAt),
  ttlSeconds: 60 * 60 * 24 * 30 // 30 days
});
```

## Database Security: `hashOrderToken()`

Following security best practices, Fufuni never stores the raw JWT "secret" string in the database. If a database export were leaked, raw tokens could be used to impersonate guests until the 30-day expiration passes. 

Instead, we store a SHA-256 hash of the token. When a guest presents a token, we hash the incoming string and compare it to the value in the `order_view_token` column of the `orders` table.

### Hashing Mechanism

```typescript
import { hashOrderToken } from '@/lib/order-token';

async function saveOrderToDb(orderId: string, rawToken: string, db: D1Database) {
  // We hash the token before storage
  const hashedToken = await hashOrderToken(rawToken);

  await db.prepare(
    "UPDATE orders SET order_view_token = ? WHERE id = ?"
  )
    .bind(hashedToken, orderId)
    .run();
}
```

This approach ensures that even with read-access to the database, an attacker cannot derive the original token required to view order details via the API.

## Token Verification: `verifyOrderViewToken()`

Verification is the most critical step. It happens within the Hono API routes. The function `verifyOrderViewToken` performs three distinct checks:
1.  **Signature Check**: Validates that the token was signed using the `ORDER_VIEW_TOKEN_SECRET`.
2.  **Expiration Check**: Validates that the current time is before the `exp` claim in the JWT.
3.  **Cross-Check**: Critically, it compares the `oid` claim inside the token with the `orderId` provided in the request path. This prevents a "Token Substitution" attack where a token for Order A is used to try and view Order B.

### Backend Route Example

```typescript
import { Hono } from 'hono';
import { verifyOrderViewToken } from '@/lib/order-token';

const app = new Hono<{ Bindings: { ORDER_VIEW_TOKEN_SECRET: string } }>();

app.get('/v1/orders/:id', async (c) => {
  const orderId = c.req.param('id');
  const token = c.req.query('token');
  const secret = c.env.ORDER_VIEW_TOKEN_SECRET;

  if (!token) {
    return c.json({ error: 'Unauthorized: No token provided' }, 401);
  }

  try {
    // 1. Verify JWT integrity and match with path parameter
    const payload = await verifyOrderViewToken(token, orderId, secret);
    
    // 2. Fetch order from Durable Object / SQLite
    // Since verification passed, we know the user is authorized to see THIS orderId
    const orderData = await c.get('orderRepo').findById(payload.oid);
    
    return c.json(orderData);
  } catch (err) {
    return c.json({ error: 'Invalid or expired token' }, 403);
  }
});
```

## Full Lifecycle Flow

The integration of Order View Tokens spans the entire lifecycle of an order, from the initial confirmation to the final delivery tracking.

### 1. Order Creation (Backend)
When the checkout is finalized in the Durable Object:
- An Order ID is generated.
- `generateOrderViewToken(orderId, secret)` is called.
- The raw token is passed to the email worker.
- `hashOrderToken(token)` is called and the result is saved in the `orders` table.

### 2. Email Delivery
The customer receives an email containing a link:
`https://merchant.fufuni.com/order/ORD-123-456?token=eyJhbGciOiJIUzI1NiI...`

### 3. Frontend Hydration (React 19)
When the guest clicks the link, the React application captures the query parameter using `URLSearchParams`.

```typescript
// apps/merchant/src/pages/OrderView.tsx
import { useSearchParams, useParams } from 'react-router-dom';
import { useQuery } from '@tanstack/react-query';

export function OrderView() {
  const { orderNumber } = useParams();
  const [searchParams] = useSearchParams();
  const token = searchParams.get('token');

  const { data, isLoading } = useQuery({
    queryKey: ['order', orderNumber, token],
    queryFn: async () => {
      const res = await fetch(`/api/v1/orders/${orderNumber}?token=${token}`);
      if (!res.ok) throw new Error('Unauthorized');
      return res.json();
    },
    enabled: !!token && !!orderNumber
  });

  if (isLoading) return <p>Loading order...</p>;
  // Render order details using HeroUI components...
}
```

### 4. API Validation (Hono)
The backend receives the request, runs `verifyOrderViewToken`, and returns the sensitive order data (shipping address, items, status) only if the token is valid.

## Configuration: The `ORDER_VIEW_TOKEN_SECRET`

The security of this entire system relies on the secrecy of the `ORDER_VIEW_TOKEN_SECRET`. If this secret is compromised, an attacker can generate valid tokens for any order in the database.

### Setting the Secret in Production
Use the Wrangler CLI to set the secret in your Cloudflare Workers environment. This ensures the secret is encrypted at rest and never committed to version control.

```bash
# For the production environment
npx wrangler secrets put ORDER_VIEW_TOKEN_SECRET

# For the preview/development environment
npx wrangler secrets put ORDER_VIEW_TOKEN_SECRET --env preview
```

### Setting the Secret Locally
For local development, add the secret to your `.dev.vars` file in the root of the backend project.

```env
# .dev.vars
ORDER_VIEW_TOKEN_SECRET=your_local_high_entropy_random_string_here
```

### Requirements for the Secret
- **Entropy**: Use a long, random string (e.g., a 64-character hex string).
- **Consistency**: The secret must be identical across all instances of the worker that handle order generation and order verification.
- **Rotation**: If the secret is rotated, all tokens issued with the old secret will immediately become invalid. Customers will need to request a new tracking link or log in via Auth0 to see their orders.
