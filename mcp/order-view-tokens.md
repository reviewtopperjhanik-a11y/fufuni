## Purpose and Overview

Order View Tokens are signed JWT (JSON Web Tokens) that grant temporary, unauthenticated read-only access to a specific order's details. In the Fufuni framework, these tokens solve the "guest checkout" problem: allowing a customer to view their invoice or order status from an email link without requiring them to create an account or log in to the merchant dashboard.

These tokens are strictly scoped to a single `orderId` and are designed to be short-lived. Per Fufuni security standards, these tokens have a **1-hour TTL (Time To Live)**. This window is sufficient for a customer to click a link in a confirmation email, view the invoice, and save it as a PDF.

### Key Characteristics
- **Authentication-less:** No headers like `Authorization: Bearer <JWT>` are required for the viewing endpoint.
- **Single-Purpose:** The token only allows access to `GET /v1/orders/view/:token`. It cannot be used for modifying orders or accessing other customer data.
- **HMAC-Signed:** Tokens are signed using `HS256` with a merchant-specific `ORDER_TOKEN_SECRET`.

## Order Token Utilities

The core logic resides in `apps/merchant/src/lib/order-token.ts`. It uses the Web Crypto API via the `jose` library, ensuring compatibility with Cloudflare Workers.

### Token Generation and Verification

The primary functions used by the backend are `generateOrderViewToken` and `verifyOrderViewToken`.

```typescript
import { generateOrderViewToken, verifyOrderViewToken } from './lib/order-token';

// Example: Generating a token during an email dispatch process
const secret = env.ORDER_TOKEN_SECRET;
const orderId = "ord_123abc";

// Generates a signed JWT valid for 1 hour (3600 seconds)
const token = await generateOrderViewToken(orderId, secret, {
  ttlSeconds: 3600 
});

console.log(`Generated Token: ${token}`);

// Example: Verifying the token in a public route
try {
  const payload = await verifyOrderViewToken(token, orderId, secret);
  console.log(`Verified Order ID: ${payload.oid}`);
} catch (err) {
  console.error("Invalid or expired token", err);
}
```

## Backend Implementation

The backend exposes two specific endpoints to handle the generation and consumption of these tokens.

### 1. Generating the View URL (Authenticated)

This route is used by the merchant dashboard or the automated email service. It requires standard admin authentication.

```typescript
// apps/merchant/src/index.ts (Hono Router)
import { generateOrderViewToken } from './lib/order-token';

app.get('/v1/orders/:id/invoice', async (c) => {
  const orderId = c.req.param('id');
  const secret = c.env.ORDER_TOKEN_SECRET;
  const baseUrl = c.env.FRONTEND_URL; // e.g., https://shop.fufuni.com

  // Verify the requester has permission to view this order first
  const order = await c.var.db.orders.getById(orderId);
  if (!order) return c.json({ error: 'Not found' }, 404);

  const token = await generateOrderViewToken(orderId, secret, { ttlSeconds: 3600 });
  
  // Return the public URL that the frontend will handle
  const viewUrl = `${baseUrl}/order-view?token=${token}&oid=${orderId}`;
  
  return c.json({ viewUrl });
});
```

### 2. Public Invoice Retrieval (Unauthenticated)

This route is public. It does not use the standard `auth` middleware. It relies entirely on the validity of the token passed in the URL.

```typescript
// apps/merchant/src/index.ts
import { verifyOrderViewToken } from './lib/order-token';

app.get('/v1/orders/view/:token', async (c) => {
  const token = c.req.param('token');
  const orderId = c.req.query('oid'); // Cross-check with query param
  const secret = c.env.ORDER_TOKEN_SECRET;

  if (!orderId) {
    return c.json({ error: 'Missing order reference' }, 400);
  }

  try {
    // verifyOrderViewToken throws if expired or tampered
    await verifyOrderViewToken(token, orderId, secret);
    
    // Fetch full order details including items and shipping
    const orderDetails = await c.var.db.orders.getFullDetails(orderId);
    
    return c.json(orderDetails);
  } catch (e) {
    return c.json({ error: 'Unauthorized or expired link' }, 401);
  }
});
```

## Frontend Integration

The frontend uses React 19 and HeroUI v3 to render the invoice. The `OrderViewPage` component is responsible for parsing the URL, fetching the data, and displaying the invoice.

```typescript
// apps/storefront/src/pages/OrderView.tsx
import { useEffect, useState } from 'react';
import { useSearchParams } from 'react-router-dom';
import { Spinner, Card, CardBody } from '@heroui/react';

export default function OrderViewPage() {
  const [searchParams] = useSearchParams();
  const [order, setOrder] = useState<any>(null);
  const [error, setError] = useState<string | null>(null);

  const token = searchParams.get('token');
  const orderId = searchParams.get('oid');

  useEffect(() => {
    if (!token || !orderId) {
      setError("Invalid access link.");
      return;
    }

    fetch(`/api/v1/orders/view/${token}?oid=${orderId}`)
      .then(res => {
        if (!res.ok) throw new Error("Link expired or invalid");
        return res.json();
      })
      .then(data => setOrder(data))
      .catch(err => setError(err.message));
  }, [token, orderId]);

  if (error) return <div className="p-10 text-danger">{error}</div>;
  if (!order) return <Spinner label="Loading Invoice..." className="m-20" />;

  return (
    <Card className="max-w-4xl mx-auto my-10">
      <CardBody>
        <h2 className="text-2xl font-bold">Invoice for {order.id}</h2>
        <p>Status: {order.status}</p>
        {/* Render invoice items, totals, and shipping details here */}
      </CardBody>
    </Card>
  );
}
```

## Security Considerations

Because Order View Tokens bypass traditional login, they must be handled with strict security protocols.

### 1. Short TTL (Time To Live)
The framework strictly enforces a **1-hour expiration**. 
- **Why:** The token grants access to Sensitive Personal Information (PII), including the customer's full name, shipping address, and the last 4 digits of their payment card. 
- **Constraint:** Do not increase this TTL. If a customer needs access after the link expires, they should request a new email or log in to their account.

### 2. Secret Management
The `ORDER_TOKEN_SECRET` is the root of trust. If this secret is leaked, an attacker can forge tokens for any `orderId`.
- **Wrangler Setup:**
  ```bash
  # Add the secret to your Cloudflare Worker environment
  npx wrangler secret put ORDER_TOKEN_SECRET
  ```
- **Rotation:** If you rotate this secret, all existing order view links in customer inboxes will immediately become invalid.

### 3. Token Scoping
The `verifyOrderViewToken` function requires the `orderId` as a secondary parameter. This prevents "Token Substitution" attacks where a valid token for Order A is used to attempt to view Order B. The payload inside the JWT (`oid`) must match the requested resource.

### 4. Single-Use Concept
While technically valid for multiple requests within that hour, the frontend implementation is designed to consume the token once to generate a view. The framework does not implement a server-side revocation list for these tokens; they are considered "Stateless Public Accessors."

### 5. Data Exposure Minimization
The `GET /v1/orders/view/:token` endpoint should return only the data necessary for an invoice. Avoid returning internal merchant notes, fraud risk scores, or full payment gateway responses in the public payload.

```typescript
// Good Practice: Filter the public response
const publicOrder = {
  id: order.id,
  total: order.total,
  items: order.items.map(i => ({ name: i.name, qty: i.qty, price: i.price })),
  shippingAddress: order.shippingAddress,
  maskedCard: `**** **** **** ${order.paymentLast4}`
};
```
