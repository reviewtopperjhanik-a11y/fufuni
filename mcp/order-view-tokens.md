## Order View Token Architecture

Order View Tokens (OVT) provide a secure mechanism for guest users to access their order status and history without requiring a full Auth0 account. In a headless e-commerce environment, forcing registration during checkout increases friction. Fufuni utilizes OVTs to bridge the gap between checkout and delivery tracking.

The architecture relies on JSON Web Tokens (JWT) using the HS256 (HMAC with SHA-256) algorithm. These tokens are signed by the backend using a private secret and contain the internal Order UUID as a claim.

### Security Model
1.  **Read-Only Access**: OVTs grant access strictly to a specific order resource. They cannot be used to modify order state or access other customer data.
2.  **Time-Bound**: Tokens have a default TTL of 30 days, matching the typical lifecycle of a retail order.
3.  **Cryptographic Binding**: The token is bound to a specific `orderId`. Even if a valid token is intercepted, it cannot be reused to query a different order ID because the backend cross-checks the token's internal `oid` claim against the requested resource ID.
4.  **Database Privacy**: Fufuni follows the "Secret Hashing" principle. We store a SHA-256 hash of the generated token in the database rather than the raw token. This prevents an attacker with database-read access from impersonating customers.

```typescript
// Example: The internal OVT payload structure
interface OrderTokenPayload {
  oid: string; // The Order UUID
  iat: number; // Issued at timestamp
  exp: number; // Expiration timestamp
}
```

## Token Generation: generateOrderViewToken()

Generating a token occurs during the finalization of the checkout process or when a user requests a new "Track My Order" link. The function `generateOrderViewToken` utilizes the `jose` library, which is natively supported by Cloudflare Workers.

### Deterministic Generation
By default, JWTs generate a new "issued at" (`iat`) timestamp every time they are called. However, Fufuni supports deterministic generation by passing a specific `issuedAt` date in the `OrderViewTokenOptions`. This is useful when re-sending a confirmation email; we can regenerate the exact same token hash without needing to store the raw token string in the database.

```typescript
import { generateOrderViewToken } from '@/lib/order-token';

async function handleNewOrder(orderId: string, secret: string) {
  // Generate a token valid for 30 days
  const token = await generateOrderViewToken(orderId, secret, {
    // Optional: set specific iat to make it deterministic
    issuedAt: new Date('2026-01-01T00:00:00Z') 
  });
  
  console.log(`Generated Token: ${token}`);
  return token;
}
```

### Signature and TTL
The function automatically handles the transformation of the string secret into a `CryptoKey` using a SHA-256 hash. This ensures that even short or weak environment variables are expanded into a robust key for the HMAC-HS256 algorithm. The default TTL is set to 2,592,000 seconds (30 days).

## Database Storage with hashOrderToken()

Fufuni mandates that raw tokens should never be stored in plain text. If the database is compromised, an attacker could use raw tokens to view order details for thousands of customers. Instead, we use `hashOrderToken()` to create a one-way fingerprint of the token.

### Implementation Logic
The `hashOrderToken` function uses the Web Crypto API `crypto.subtle.digest` to perform a SHA-256 hash of the raw JWT string. The resulting hex string is what gets saved to the `order_view_token` column in the SQLite (Durable Object) database.

```typescript
import { hashOrderToken } from '@/lib/order-token';

/**
 * Persisting a token during order creation
 */
async function saveOrderToDb(orderId: string, rawToken: string, db: any) {
  const hashedToken = await hashOrderToken(rawToken);
  
  await db.prepare(`
    UPDATE orders 
    SET order_view_token = ? 
    WHERE id = ?
  `).bind(hashedToken, orderId).run();
}
```

### SQL Schema Context
The `orders` table in the Fufuni SQLite schema includes a specific column for this hash:

```sql

CREATE TABLE IF NOT EXISTS orders (
```

## Token Verification: verifyOrderViewToken()

Verification is the gatekeeper for the `GET /v1/orders/:id` endpoint. When a guest clicks a link like `fufuni.com/order/FF-123?token=ey...`, the frontend sends the raw token in the `Authorization` header or as a query parameter.

The `verifyOrderViewToken` function performs three critical checks:
1.  **Integrity**: It verifies that the JWT signature matches the `ORDER_TOKEN_SECRET`.
2.  **Expiration**: It checks the `exp` claim against the current time.
3.  **Cross-Check**: It ensures that the `oid` (Order ID) encoded inside the token matches the `:id` parameter requested in the URL. This prevents "Token Substitution" attacks.

```typescript
import { verifyOrderViewToken } from '@/lib/order-token';

// In a Hono middleware or route handler
app.get('/v1/orders/:id', async (c) => {
  const orderId = c.req.param('id');
  const token = c.req.query('token');
  const secret = c.env.ORDER_VIEW_TOKEN_SECRET;

  if (!token) {
    return c.json({ error: 'Unauthorized' }, 401);
  }

  try {
    const payload = await verifyOrderViewToken(token, orderId, secret);
    // Payload contains { oid: '...' }
    // Proceed to fetch order details from DB
  } catch (err) {
    return c.json({ error: 'Invalid or expired token' }, 403);
  }
});
```

## End-to-End Flow Implementation

The following flow demonstrates how a guest customer interacts with the OVT system from checkout to order tracking.

### 1. Order Creation (Backend)
When the checkout succeeds, the system generates the token, hashes it, and stores the hash.

```typescript
// Step 1: Generate
const rawToken = await generateOrderViewToken(newOrder.id, env.ORDER_TOKEN_SECRET);

// Step 2: Hash and Store
const hashed = await hashOrderToken(rawToken);
await store.updateOrderToken(newOrder.id, hashed);

// Step 3: Send Email (Pseudo-code)
await emailProvider.send({
  to: customerEmail,
  template: 'order_confirmation',
  vars: {
    trackingUrl: `https://shop.fufuni.com/order/${newOrder.orderNumber}?token=${rawToken}`
  }
});
```

### 2. Guest Visit (Frontend)
The React 19 frontend captures the token from the URL using `useSearchParams` and includes it in the API request.

```tsx
// apps/merchant/src/pages/OrderTracking.tsx
import { useSearchParams, useParams } from 'react-router-dom';
import { useEffect, useState } from 'react';

export function OrderTrackingPage() {
  const { orderNumber } = useParams();
  const [searchParams] = useSearchParams();
  const token = searchParams.get('token');
  const [order, setOrder] = useState(null);

  useEffect(() => {
    async function fetchOrder() {
      // The frontend calls the backend with the raw token
      const res = await fetch(`/api/v1/orders/by-number/${orderNumber}?token=${token}`);
      if (res.ok) {
        const data = await res.json();
        setOrder(data);
      }
    }
    if (token && orderNumber) fetchOrder();
  }, [token, orderNumber]);

  if (!token) return <div>Access Denied: Missing Token</div>;
  
  return (
    <div className="p-4">
      <h1 className="text-2xl font-bold">Order {orderNumber}</h1>
      {order ? <OrderDetails data={order} /> : <p>Loading...</p>}
    </div>
  );
}
```

### 3. Verification (Backend Middleware)
The backend confirms the token is valid before returning sensitive data like shipping addresses.

```typescript
// apps/merchant/src/routes/orders.ts
import { verifyOrderViewToken } from '../lib/order-token';

const orderRouter = new Hono<{ Bindings: Bindings }>();

orderRouter.get('/by-number/:orderNumber', async (c) => {
  const orderNumber = c.req.param('orderNumber');
  const token = c.req.query('token');
  
  // 1. Fetch order from DB by human-readable number
  const order = await c.var.db.getOrderByNumber(orderNumber);
  if (!order) return c.notFound();

  // 2. Verify token against the internal UUID
  try {
    await verifyOrderViewToken(token!, order.id, c.env.ORDER_VIEW_TOKEN_SECRET);
  } catch (e) {
    return c.json({ error: 'Invalid Token' }, 403);
  }

  return c.json(order);
});
```

## Environment Configuration

The `ORDER_VIEW_TOKEN_SECRET` is the root of trust for all guest access. If this secret is leaked, anyone can generate valid tokens for any order ID. If it is changed, all existing order tracking links in customer emails will immediately become invalid.

### Local Development
Add the secret to your `.dev.vars` file (used by Wrangler for local development):

```bash
# .dev.vars
ORDER_VIEW_TOKEN_SECRET="a-very-long-random-string-for-local-dev"
```

### Production Deployment
Use the Wrangler CLI to set the secret in the Cloudflare environment. This ensures the secret is encrypted and not stored in plaintext within the repository or CI logs.

```bash
# Set production secret
npx wrangler secret put ORDER_VIEW_TOKEN_SECRET

# When prompted, paste a secure 32+ character string
```
