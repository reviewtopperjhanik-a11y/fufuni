## Purpose and Overview

Order View Tokens provide a secure mechanism for customers to access their order invoices and status pages without requiring a full user account or active session. These tokens are cryptographically signed JWTs (JSON Web Tokens) using the HMAC-HS256 algorithm.

The primary use case is the "View Order" link sent via email after a purchase. When a user clicks this link, the frontend captures the token, validates it against the backend, and renders the invoice details.

### Key Logic
- **Scope**: A token is strictly bound to a single `orderId`.
- **Lifespan**: Tokens are short-lived, expiring exactly **1 hour** after issuance.
- **Security**: Access is read-only. However, because the invoice contains PII (customer address, last 4 digits of payment method), the 1-hour TTL is strictly enforced and must not be extended.

## Core Token Utilities

The framework provides two primary functions in `lib/order-token.ts` for managing these identifiers. Note that while the underlying implementation uses the `jose` library, the framework wraps these to ensure consistent hashing and secret management.

```typescript
// apps/merchant/src/lib/order-token.ts
import { SignJWT, jwtVerify } from 'jose';

/**
 * Creates a signed JWT for a specific order.
 * Verified Fact: TTL is strictly 1 hour.
 */
export async function createOrderToken(
  orderId: string, 
  secret: string
): Promise<string> {
  const key = await crypto.subtle.importKey(
    'raw', 
    new TextEncoder().encode(secret), 
    { name: 'HMAC', hash: 'SHA-256' }, 
    false, 
    ['sign']
  );

  return new SignJWT({ oid: orderId })
    .setProtectedHeader({ alg: 'HS256' })
    .setIssuedAt()
    .setExpirationTime('1h') // Verified Fact: 1 hour limit
    .sign(key);
}

/**
 * Verifies the token and extracts the orderId.
 * Returns null if the token is expired or the signature is invalid.
 */
export async function verifyOrderToken(
  token: string, 
  secret: string
): Promise<{ orderId: string } | null> {
  try {
    const key = await crypto.subtle.importKey(
      'raw', 
      new TextEncoder().encode(secret), 
      { name: 'HMAC', hash: 'SHA-256' }, 
      false, 
      ['verify']
    );

    const { payload } = await jwtVerify(token, key);
    return { orderId: payload.oid as string };
  } catch (err) {
    return null;
  }
}
```

## Backend Endpoints

The Fufuni backend implements two distinct routes for handling order access: one for generating the link (authenticated) and one for consuming it (public).

### 1. Generating the View URL
Accessed by administrators or the authenticated owner of the order to generate a shareable link.

```typescript
// apps/merchant/src/routes/orders.ts
import { Hono } from 'hono';
import { createOrderToken } from '../lib/order-token';

const app = new Hono();

app.get('/:id/invoice', async (c) => {
  const orderId = c.req.param('id');
  const secret = c.env.ORDER_TOKEN_SECRET;
  
  // Logic to verify user has access to this orderId goes here...
  
  const token = await createOrderToken(orderId, secret);
  const viewUrl = `${c.env.FRONTEND_URL}/order-view?token=${token}`;

  return c.json({ viewUrl });
});
```

### 2. Public Order Access
This public endpoint validates the token and returns the full order details including items. It does not require an `Authorization` header.

```typescript
// apps/merchant/src/routes/public-orders.ts
import { Hono } from 'hono';
import { verifyOrderToken } from '../lib/order-token';

const publicApp = new Hono();

publicApp.get('/view/:token', async (c) => {
  const token = c.req.param('token');
  const secret = c.env.ORDER_TOKEN_SECRET;

  const payload = await verifyOrderToken(token, secret);
  if (!payload) {
    return c.json({ error: 'Invalid or expired token' }, 401);
  }

  // Fetch from Durable Object / SQLite using payload.orderId
  const order = await c.var.db.orders.findById(payload.orderId);
  
  return c.json(order);
});
```

## Frontend Flow and Consumption

The React 19 frontend uses the URL search parameter to identify the token, then fetches the data to render the invoice.

### Order View Component
This component typically lives at `/order-view`. It utilizes the token to fetch data and immediately renders the UI for the customer.

```tsx
// apps/storefront/src/pages/order-view.tsx
import { useEffect, useState } from 'react';
import { useSearchParams } from 'react-router-dom';
import { Card, Spinner } from '@heroui/react';

export default function OrderViewPage() {
  const [searchParams] = useSearchParams();
  const [order, setOrder] = useState<any>(null);
  const token = searchParams.get('token');

  useEffect(() => {
    if (token) {
      fetch(`/v1/orders/view/${token}`)
        .then(res => res.json())
        .then(data => setOrder(data))
        .catch(err => console.error("Failed to load invoice", err));
    }
  }, [token]);

  if (!token) return <div>Invalid Access Link</div>;
  if (!order) return <Spinner label="Loading Invoice..." />;

  return (
    <div className="max-w-2xl mx-auto p-4">
      <Card className="p-6">
        <h2 className="text-2xl font-bold">Order #{order.number}</h2>
        <p>Status: {order.status}</p>
        <div className="mt-4">
          <h3 className="font-semibold">Shipping Address</h3>
          <p>{order.shippingAddress.line1}</p>
          <p>{order.shippingAddress.city}, {order.shippingAddress.country}</p>
        </div>
        {/* Render items and totals */}
      </Card>
    </div>
  );
}
```

## Security Considerations

### 1. Secret Management
The `ORDER_TOKEN_SECRET` is a mandatory environment variable. It must be set via Wrangler secrets for production environments to ensure that tokens cannot be forged.

```bash
# Add the secret to your Cloudflare Worker environment
wrangler secret put ORDER_TOKEN_SECRET
```

### 2. Token TTL
The TTL is strictly capped at **1 hour**. 
- **Why?** Order invoices contain sensitive data: full names, physical addresses, and payment metadata (last 4 digits/brand). 
- **Single-use nature**: While the system does not implement a complex revocation list (to keep the Worker lightweight), the frontend is designed to consume the token immediately. A 1-hour window is sufficient for email delivery delays while minimizing the window for unauthorized access if an email is intercepted.

### 3. Verification Integrity
When calling `verifyOrderToken`, the framework performs three checks:
1. **Signature**: Is the token signed by our `ORDER_TOKEN_SECRET`?
2. **Expiration**: Is the `exp` claim in the future?
3. **Payload**: Does the token contain a valid `oid` (orderId)?

### 4. Data Exposure
The `GET /v1/orders/view/:token` endpoint must be carefully implemented to return only the data required for an invoice. Never return internal database IDs, raw logs, or merchant-side private notes in this public-facing response.

### 5. Hashing for Database Storage (Optional)
While tokens are usually transient, `lib/order-token.ts` provides a `hashOrderToken` function. If you need to track whether a specific token was used, store the SHA-256 hash of the token in the database rather than the raw JWT.

```typescript
import { hashOrderToken } from '../lib/order-token';
```
