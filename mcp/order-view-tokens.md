## Purpose of Order View Tokens

Order View Tokens provide a secure mechanism for unauthenticated users (such as customers receiving an automated email) to access a specific order's invoice and status page without logging into the Fufuni merchant dashboard. 

In the Fufuni ecosystem, standard order management is protected by session-based or API-key authentication. However, a customer needs to view their receipt or tracking status via a direct link. These tokens are signed HMAC-HS256 JWTs that grant scoped, read-only access to a single resource: the order invoice.

### Key Logic Flow
1.  **Merchant/System Action**: An administrator or an automated trigger calls the authenticated invoice endpoint.
2.  **Token Generation**: The backend generates a JWT containing the `orderId` in its payload, signed with `ORDER_TOKEN_SECRET`.
3.  **Public URL**: The backend returns a URL containing this token (e.g., `https://shop.fufuni.com/order-view?token=...`).
4.  **Customer Access**: The customer clicks the link. The frontend extracts the token and calls the public API.
5.  **Verification**: The backend verifies the signature and TTL. If valid, it returns the order data for rendering.

## Core Utilities in `order-token.ts`

The framework uses the `jose` library, which is native-compatible with Cloudflare Workers' `crypto` global. This ensures high-performance signing without external heavy dependencies like `jsonwebtoken`.

### Token Generation and Verification

The `generateOrderViewToken` function creates the signed payload. While the source code might defaults to 30 days, **Fufuni production standards require a strict 1-hour TTL** for invoice tokens to minimize exposure risk.

```typescript
import { generateOrderViewToken, verifyOrderViewToken } from './lib/order-token';

// Example: Generating a token within a Hono route
const ORDER_TOKEN_SECRET = c.env.ORDER_TOKEN_SECRET;
const orderId = "ord_7721-abc-123";

// Generate a token valid for 1 hour (3600 seconds)
const token = await generateOrderViewToken(orderId, ORDER_TOKEN_SECRET, {
  ttlSeconds: 3600 
});

console.log(`Generated JWT: ${token}`);

// Example: Verifying the token
try {
  const payload = await verifyOrderViewToken(token, orderId, ORDER_TOKEN_SECRET);
  console.log(`Verified access for Order ID: ${payload.oid}`);
} catch (err) {
  console.error("Invalid or expired token");
}
```

## Backend API Endpoints

The framework implements two specific routes to handle the lifecycle of an order view.

### 1. Authenticated Link Generation
**Endpoint**: `GET /v1/orders/:id/invoice`
**Auth**: Required (Admin or Order Owner)

This endpoint returns the public-facing URL that the customer will use. It does not return the invoice data directly, but rather the capability to view it.

```typescript
import { Hono } from 'hono';
import { generateOrderViewToken } from '../lib/order-token';

const app = new Hono<{ Bindings: { ORDER_TOKEN_SECRET: string } }>();

app.get('/v1/orders/:id/invoice', async (c) => {
  const orderId = c.req.param('id');
  const secret = c.env.ORDER_TOKEN_SECRET;

  // 1. Verify user has permission to manage this order
  // const user = c.get('user');
  // ... check permissions ...

  // 2. Generate the 1-hour token
  const token = await generateOrderViewToken(orderId, secret, {
    ttlSeconds: 3600
  });

  // 3. Construct the frontend URL
  const viewUrl = `https://checkout.fufuni.com/order-view?token=${token}&oid=${orderId}`;

  return c.json({
    viewUrl,
    expiresAt: new Date(Date.now() + 3600 * 1000).toISOString()
  });
});
```

### 2. Public Data Retrieval
**Endpoint**: `GET /v1/orders/view/:token`
**Auth**: Public (Token-based)

This is the endpoint called by the frontend `/order-view` page. It consumes the token and returns the full order details.

```typescript
import { Hono } from 'hono';
import { verifyOrderViewToken } from '../lib/order-token';

const publicApp = new Hono<{ Bindings: { ORDER_TOKEN_SECRET: string, DB: D1Database } }>();

publicApp.get('/v1/orders/view/:token', async (c) => {
  const token = c.req.param('token');
  const orderId = c.req.query('oid'); // Cross-check ID
  const secret = c.env.ORDER_TOKEN_SECRET;

  if (!orderId) return c.json({ error: "Missing order ID" }, 400);

  try {
    // Verify JWT integrity, expiration, and that oid matches the token payload
    await verifyOrderViewToken(token, orderId, secret);

    // Fetch order from SQLite (Durable Object or D1)
    // const order = await db.query.orders.findFirst({ where: eq(orders.id, orderId) });
    const order = { id: orderId, status: 'paid', total: 59.99, items: [] }; // Mock

    return c.json(order);
  } catch (e) {
    return c.json({ error: "Unauthorized or expired link" }, 401);
  }
});
```

## Frontend Flow and Consumption

The frontend implementation uses React 19 and HeroUI v3. The page responsible for rendering the invoice must handle the extraction of parameters from the URL.

### The Order View Page
The logic resides in a dedicated route, typically `/order-view`. It uses `useSearchParams` to grab the token and performs a fetch to the public backend endpoint.

```typescript
import React, { useEffect, useState } from 'react';
import { useSearchParams } from 'react-router-dom';
import { Spinner, Card, CardBody } from '@heroui/react';

export const OrderViewPage = () => {
  const [searchParams] = useSearchParams();
  const [order, setOrder] = useState<any>(null);
  const [error, setError] = useState<string | null>(null);

  const token = searchParams.get('token');
  const oid = searchParams.get('oid');

  useEffect(() => {
    if (!token || !oid) {
      setError("Invalid access link.");
      return;
    }

    async function loadOrder() {
      const resp = await fetch(`/api/v1/orders/view/${token}?oid=${oid}`);
      if (!resp.ok) {
        setError("This link has expired or is invalid.");
        return;
      }
      const data = await resp.json();
      setOrder(data);
    }

    loadOrder();
  }, [token, oid]);

  if (error) return <div className="p-10 text-danger">{error}</div>;
  if (!order) return <Spinner className="m-20" size="lg" />;

  return (
    <div className="max-w-4xl mx-auto p-6">
      <Card>
        <CardBody>
          <h2 className="text-2xl font-bold">Invoice for #{order.id}</h2>
          <p>Status: {order.status}</p>
          {/* Render PDF components or Invoice tables here */}
        </CardBody>
      </Card>
    </div>
  );
};
```

## Security Considerations

Implementing unauthenticated access requires strict adherence to security protocols to prevent data harvesting.

### 1. Mandatory 1-Hour TTL
While the utility allows custom TTLs, Fufuni framework policy dictates that Order View Tokens **must not exceed 1 hour**. These tokens grant access to sensitive PII (Personally Identifiable Information) including:
*   Customer full name and shipping address.
*   The last 4 digits of the payment card.
*   The items purchased and total spend.

A short TTL ensures that even if an email is forwarded or a link is left in a browser history on a public computer, the window of vulnerability is limited.

### 2. Token Cross-Checking
When calling `verifyOrderViewToken`, the `orderId` must be passed separately from the URL path or query string. The utility checks if the `oid` inside the JWT payload matches the requested `orderId`. This prevents "Token Substitution" attacks where a valid token for Order A is used to try and view Order B.

### 3. Required Wrangler Secrets
The signing process depends on a high-entropy secret. This must be configured in your Cloudflare environment.

**Development (`.dev.vars`):**
```bash
ORDER_TOKEN_SECRET="dev-secret-keep-it-long-and-secure-123456"
```

**Production:**
```bash
npx wrangler secret put ORDER_TOKEN_SECRET
```

### 4. Single-Use Context
The framework treats these tokens as conceptually single-use. While they are technically valid until the 1-hour expiration, the frontend flow is designed to generate the PDF/View immediately and discard the state. No server-side revocation list is maintained (to keep the Workers' edge-side verification stateless and fast). If a customer needs access again after an hour, they must request a new link via the "Resend Invoice" feature in the merchant dashboard.
