## Cloudflare Worker Patterns

### 1. Accessing Bindings in a Route Handler

Bindings are accessed through the `c.env` object. For example:

```typescript
export default {
  async fetch(request: Request, c: ExecutionContext): Response {
    const merchant = c.env.MERCHANT;
    const images = c.env.IMAGES;
    const kvCache = c.env.KV_CACHE;

    // Use the bindings as needed
  }
}
```

### 2. The Durable Object Pattern

We use a single Durable Object (DO) instance for our Merchant DO.

#### Getting the Stub

To get the stub, you need to use the `c.env.MERCHANT` object:

```typescript
const merchantStub = await c.env.MERCHANT.get(c.request.url.pathname);
```

#### Calling query() and run()

You can call `query()` to perform read-only operations:

```typescript
const response = await merchantStub.query(c.request);
```

To perform read-write operations, use `run()`:

```typescript
const response = await merchantStub.run(c.request);
```

### 3. KV Cache

The KV cache is implemented using the `kvCacheMiddleware` (located in `apps/merchant/src/middleware/kv-cache.ts`).

#### How kv-cache Middleware Works

The middleware checks if the request is a GET request and if the cache key exists in KV. If it does, it returns the cached response.

The cache key is generated as `cache:<full-url>`, including query parameters.

#### Invalidate Cache Manually

To invalidate the cache manually, you can use the `kvInvalidateMiddleware`. This middleware purges all cache keys that match a certain prefix.

### 4. R2

Product images are stored and served using R2.

### 5. Secrets

Secrets must be stored in Wrangler secrets or the `.env` file.

#### Mailgun Secrets List

The following Mailgun secrets are required:

* `MAILGUN_API_KEY`
* `MAILGUN_DOMAIN`
* `MAILGUN_BASE_URL` (default: https://api.mailgun.net)
* `MAILGUN_USER` (sender address)

### 6. Adding a New Binding

To add a new binding, follow these steps:

1. Update `wrangler.jsonc` with the new binding:

```json
{
  "bindings": [
    {
      "name": "NEW_BINDING",
      "type": "R2Bucket"
    }
  ]
}
```

2. Update `worker-configuration.d.ts` with the new binding type:

```typescript
interface Env {
  NEW_BINDING: R2Bucket;
}
```

3. Update the `Env` type with the new binding:

```typescript
interface Env extends Cloudflare.Env {
  NEW_BINDING: R2Bucket;
}
```

### 7. CI/CD

Environment variables are mapped to GitHub secrets.

#### How create-env-artifact.yaml Works

The `create-env-artifact.yaml` workflow generates an encrypted `.env` and `wrangler.jsonc` artifact consumed by CI deploy jobs.

To expose a new variable to the frontend via `vite.config.ts` define block:

1. Add the new variable to the `.env` file.
2. Add the new variable to the `define` block in `apps/client/vite.config.ts`:

```javascript
define: {
  'import.meta.env': {
    NEW_VARIABLE: process.env.NEW_VARIABLE,
  },
},
```

The `import.meta.env` object in the frontend will have the new variable.

### .env and GitHub Secrets

Every `.env` variable has a 1:1 equivalent GitHub secret (same name). When you add a new env variable, also add it to `.github/workflows/create-env-artifact.yaml` so CI can pass it to the Worker build. 

The `generate-wrangler-jsonc.py` script generates `wrangler.jsonc` from `.env` and base `wrangler.jsonc`. It also generates `secrets.json` for `wrangler secret bulk` command.

The `create-env-artifact.yaml` generates an encrypted `.env` + `wrangler.jsonc` artifact consumed by CI deploy jobs. Without adding a new variable there, it will be absent from CI deployments.

### Frontend Env Vars

Frontend env vars are NOT VITE_ prefixed. They are injected via `vite.config.ts` define block as `import.meta.env.VARIABLE_NAME`.

To expose a new variable to the browser: add it to the define block in `apps/client/vite.config.ts`.

The `import.meta.env.PERMISSIONS` is a string[] derived at build time from all *_PERMISSION .env keys (scopesArray in `vite.config.ts`). This drives navbar permission filtering without hardcoding permission strings.

The Mailgun is used for transactional emails. Required backend env vars (Wrangler secrets): `MAILGUN_API_KEY`, `MAILGUN_DOMAIN`, `MAILGUN_BASE_URL` (default: https://api.mailgun.net), `MAILGUN_USER` (sender address). Email sending is silently skipped if `MAILGUN_API_KEY` is absent.

The `kvCacheMiddleware` (apps/merchant/src/middleware/kv-cache.ts) serves GET responses from KV before hitting the Durable Object. Cache key = cache:<full-url> including query params.

The KV cache TTL is configurable via three env vars (also GitHub Secrets): `KV_CACHE_SEARCH_TTL_SECONDS` (default 300s, search results), `KV_CACHE_REVIEWS_TTL_SECONDS` (default 600s, product reviews), `KV_CACHE_DEFAULT_TTL_SECONDS` (default 3600s, all other catalog/category routes).

The `kvCacheMiddleware` bypasses the cache for non-GET methods and for Authorization headers other than Bearer pk_* (admin JWTs and sk_ keys always hit the Durable Object directly).

The `kvInvalidateMiddleware` purges all cache:*/v1/products and cache:*/v1/categories keys after any successful POST/PATCH/DELETE. Invalidation is prefix-based and paginates through kv.list().

The `deploy-cloudflare-worker.yaml` runs automatically on push to main (apps/merchant/** changed). It decrypts the env artifact, runs wrangler secret bulk from secrets.json, then deploys. Requires `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` GitHub Secrets.

The `npm run dev:env` is the recommended full-stack dev command (run from monorepo root). It starts both workspaces in parallel via Turborepo: the Merchant Worker (copies root .env to apps/merchant/.dev.vars then runs wrangler dev on localhost:8787) and the Client Vite SPA (sources root .env then runs vite on localhost:5173). Pass --base=/path to auto-adjust `STORE_URL` and `CORS_ORIGIN` for subpath testing.

The `npm run stripe:listen` is a SEPARATE command (not included in dev:env). It requires the Stripe CLI to be installed globally. It reads `STRIPE_SECRET_KEY` from .env and runs: stripe listen --load-from-webhooks-api --forward-to http://localhost:8787. Must be run in a second terminal alongside dev:env.

The `npm run build:env` builds all workspaces sourcing .env (used by CI). `npm run build:client:env` builds only the client SPA. Both resolve env vars at build time via the `vite.config.ts` define block.
