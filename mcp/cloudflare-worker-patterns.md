## Accessing Bindings in Route Handlers

In the Fufuni framework, backend routes are built using Hono. All Cloudflare bindings (Durable Objects, R2 Buckets, KV Namespaces, and Environment Variables) are available through the Hono context object `c.env`. These bindings are strictly typed based on the `worker-configuration.d.ts` file.

### Binding Usage Example

When writing a route handler, you access the bindings directly from the environment. For example, to check a cache or interact with the Merchant database, use the following pattern:

```typescript
import { Hono } from 'hono';
import { env } from 'hono/adapter';

const app = new Hono<{ Bindings: Env }>();

app.get('/v1/catalog', async (c) => {
  // Accessing KV Cache
  const cachedData = await c.env.KV_CACHE.get('cache:catalog_list', 'json');
  if (cachedData) return c.json(cachedData);

  // Accessing the Durable Object (Merchant Database)
  const id = c.env.MERCHANT.idFromName('global');
  const stub = c.env.MERCHANT.get(id);
  
  // Standard DO RPC call
  const products = await stub.getProducts();

  // Accessing R2 for metadata
  const imageMetadata = await c.env.IMAGES.head('products/hero.jpg');

  return c.json({ products, hasHero: !!imageMetadata });
});
```

## The Durable Object Singleton Pattern

Fufuni utilizes a **Single Durable Object Instance** pattern to manage the merchant's state and SQLite database. Instead of spawning multiple DOs, we use a fixed name (usually `"global"`) to ensure all requests for a specific merchant hit the same stateful instance. This provides strong consistency for inventory and order management.

### Calling the DO Stub

We typically interact with the DO using high-level RPC methods defined in the `MerchantDO` class. The two primary methods for raw operations (if exposed) are usually encapsulated logic methods, but the pattern for retrieval is consistent.

```typescript
/**
 * Pattern for retrieving the Global Merchant Stub
 */
export const getMerchantStub = (env: Env) => {
  // Fufuni uses a singleton DO named 'global' for the SQLite store
  const id = env.MERCHANT.idFromName('global');
  return env.MERCHANT.get(id);
};

// Inside a Hono route:
app.post('/v1/orders', async (c) => {
  const stub = getMerchantStub(c.env);
  const body = await c.req.json();
  
  // Executing logic inside the DO
  const order = await stub.createOrder(body);
  return c.json(order, 201);
});
```

## KV Caching and Invalidation

The `kvCacheMiddleware` significantly reduces latency by serving `GET` requests directly from Cloudflare's KV store, bypassing the Durable Object execution entirely. 

### Configuration Variables
Cache behavior is controlled by three specific environment variables (and corresponding GitHub Secrets):
- `KV_CACHE_SEARCH_TTL_SECONDS`: Default 300s.
- `KV_CACHE_REVIEWS_TTL_SECONDS`: Default 600s.
- `KV_CACHE_DEFAULT_TTL_SECONDS`: Default 3600s (Catalog, Categories).

### Manual Invalidation
The framework uses `kvInvalidateMiddleware`. After any successful mutation (`POST`, `PATCH`, `DELETE`), the middleware purges cache keys using a prefix-based scan.

```typescript
// Manual Invalidation Logic Pattern
async function purgeProductCache(env: Env) {
  const prefix = "cache:*/v1/products";
  let cursor: string | undefined;

  do {
    const list = await env.KV_CACHE.list({ prefix, cursor });
    for (const key of list.keys) {
      await env.KV_CACHE.delete(key.name);
    }
    cursor = list.cursor;
  } while (cursor);
}
```

## R2 Image Management

Product images are stored in the `IMAGES` R2 bucket. The framework avoids public R2 buckets for better security, instead serving images through a Worker route that performs authorization or utilizes Cloudflare's Image Transformation service via the `IMAGES_URL` variable.

### Storing and Serving Patterns

```typescript
app.put('/v1/images/:name', async (c) => {
  const name = c.req.param('name');
  const blob = await c.req.blob();

  // Upload to R2
  await c.env.IMAGES.put(`products/${name}`, blob, {
    httpMetadata: { contentType: blob.type }
  });

  return c.json({ success: true });
});

app.get('/img/:name', async (c) => {
  const name = c.req.param('name');
  const object = await c.env.IMAGES.get(`products/${name}`);
  
  if (!object) return c.notFound();

  const headers = new Headers();
  object.writeHttpMetadata(headers);
  headers.set('etag', object.httpEtag);

  return new Response(object.body, { headers });
});
```

## Secrets and Configuration

Fufuni distinguishes between public `vars` and private `secrets`. While `vars` are defined in `wrangler.jsonc`, sensitive data like API keys must be handled as Worker Secrets.

### Secret Management Rules
1.  **Mailgun List**: To enable transactional emails, the following secrets must be set: `MAILGUN_API_KEY`, `MAILGUN_DOMAIN`, `MAILGUN_USER` (sender), and `MAILGUN_BASE_URL` (usually `https://api.mailgun.net`).
2.  **.env vs Secrets**: The `.env` file is used for local development and CI/CD artifact building. The `generate-wrangler-jsonc.py` script converts these into a `secrets.json` which is then pushed to Cloudflare in bulk.

### Required Backend Secrets Table
| Secret | Description |
| :--- | :--- |
| `STRIPE_SECRET_KEY` | Used for payment processing within the DO. |
| `AUTH0_CLIENT_SECRET` | Used for verifying management API tokens. |
| `MERCHANT_SK` | Private key for internal data signing. |
| `CRYPTOKEN` | Key used for encrypting CI/CD artifacts. |

## Adding a New Binding

To add a new binding (e.g., a new R2 bucket or KV namespace), follow this strict workflow to maintain type safety:

1.  **Update `wrangler.jsonc`**: Add the binding entry.
2.  **Generate Types**: Run `npx wrangler types` to update `worker-configuration.d.ts`.
3.  **Update Global `Env`**: Ensure your Hono instance and utility functions use the updated `Env` interface.

```bash
# Example: Adding a new KV for sessions
# 1. Modify wrangler.jsonc manually or via script
# 2. Run type generation
npx wrangler types
```

```typescript
// 3. Verify in your code
export interface Env {
  // ... existing bindings
  SESSIONS: KVNamespace; // This should now appear in worker-configuration.d.ts
}
```

## CI/CD Pipeline and Variable Mapping

The Fufuni CI/CD pipeline (GitHub Actions) ensures that environment variables are synchronized between the repository and the deployed Worker.

### 1:1 Secret Mapping
Every variable in your local `.env` must have a corresponding GitHub Secret with the exact same name. The `create-env-artifact.yaml` workflow iterates through these to build the deployment environment.

### Exposing Variables to the Frontend
Frontend variables are injected at build time. Unlike standard Vite apps, Fufuni does **not** use the `VITE_` prefix. Instead, it uses the `define` block in `vite.config.ts`.

```typescript
// apps/client/vite.config.ts snippet
export default defineConfig({
  define: {
    'import.meta.env.API_BASE_URL': JSON.stringify(process.env.API_BASE_URL),
    'import.meta.env.STORE_NAME': JSON.stringify(process.env.STORE_NAME),
    // Exposing permissions dynamically
    'import.meta.env.PERMISSIONS': JSON.stringify(getScopesArrayFromEnv(process.env)),
  }
});
```

### CI Deployment Steps
1.  `create-env-artifact.yaml`: Sinks GitHub Secrets into a `.env` file, runs the Python generator to create `wrangler.jsonc` and `secrets.json`, then encrypts the bundle.
2.  `deploy-cloudflare-worker.yaml`: Decrypts the bundle, runs `npx wrangler secret bulk < secrets.json` to update Cloudflare, and executes `wrangler deploy`.
3.  `pages.yaml`: Builds the React SPA, injecting the variables defined in the `.env` file into the static JS assets.
