## Accessing Bindings in Route Handlers

In the Fufuni framework, backend logic is powered by Hono. Bindings defined in `wrangler.jsonc` are automatically available on the context object (`c.env`). These bindings include the Durable Object namespace, R2 buckets, and KV namespaces.

The type safety for these bindings is provided by the auto-generated `worker-configuration.d.ts`. When writing a handler, always ensure you are accessing the environment variables through the typed context.

### Accessing R2 and KV
```typescript
import { Hono } from 'hono';

const app = new Hono<{ Bindings: Env }>();

app.get('/v1/images/:key', async (c) => {
  const key = c.req.param('key');
  
  // Accessing the R2 Bucket binding
  const object = await c.env.IMAGES.get(key);
  if (!object) return c.notFound();

  // Accessing KV for metadata caching
  const cacheKey = `meta:${key}`;
  const cachedMeta = await c.env.KV_CACHE.get(cacheKey, 'json');

  const headers = new Headers();
  object.writeHttpMetadata(headers);
  headers.set('etag', object.httpEtag);

  return c.body(object.body, 200, Object.fromEntries(headers));
});
```

## The Durable Object SQLite Pattern

Fufuni utilizes a single Durable Object (DO) instance per merchant to act as a stateful SQLite database. This ensures ACID compliance for shop operations like inventory management and order processing within the Cloudflare edge.

### Why a Single DO Instance?
We use `idFromName('main')` or a fixed ID to ensure all requests for a specific merchant deployment hit the same physical Durable Object. This allows the SQLite database stored in `ctx.storage.sql` to remain consistent across all concurrent requests.

### Calling the Merchant DO
To interact with the database, you obtain a stub and use the RPC (Remote Procedure Call) mechanism. The framework convention uses `query()` for read operations and `run()` for mutations.

```typescript
// src/services/merchant.ts
import { Context } from 'hono';

export async function getProduct(c: Context<{ Bindings: Env }>, id: string) {
  // 1. Get the DO Namespace
  const ns = c.env.MERCHANT;
  
  // 2. Get the specific stub (Fufuni typically uses a singleton 'main' instance)
  const doId = ns.idFromName('merchant_singleton');
  const stub = ns.get(doId);

  // 3. Perform RPC call
  // Note: stub.query and stub.run are defined in your MerchantDO class
  const product = await stub.query('SELECT * FROM products WHERE id = ?', id);
  
  return product;
}
```

## KV Cache Architecture

To minimize latency and reduce DO CPU usage, Fufuni employs an aggressive KV-based caching layer. This is managed primarily via middleware located in `apps/merchant/src/middleware/kv-cache.ts`.

### Middleware Logic and TTLs
The `kvCacheMiddleware` generates a key using the pattern `cache:<full-url>`. It only caches `GET` requests and bypasses caching for admin operations (Authorization headers containing `sk_` or generic Bearer tokens).

| Category | Env Variable | Default |
| :--- | :--- | :--- |
| Search Results | `KV_CACHE_SEARCH_TTL_SECONDS` | 300s |
| Product Reviews | `KV_CACHE_REVIEWS_TTL_SECONDS` | 600s |
| General Catalog | `KV_CACHE_DEFAULT_TTL_SECONDS` | 3600s |

### Manual Invalidation
When a product or category is updated, the cache must be purged. The `kvInvalidateMiddleware` handles this by listing keys with the corresponding prefix and deleting them.

```typescript
// Example of manual invalidation logic
async function purgeCatalogCache(env: Env) {
  const prefix = "cache:*/v1/products";
  let cursor: string | undefined;
  
  do {
    const list = await env.KV_CACHE.list({ prefix, cursor });
    for (const key of list.keys) {
      await env.KV_CACHE.delete(key.name);
    }
    cursor = list.cursor;
  } while (cursor);
}
```

## R2 Product Media Storage

Product images are stored in the `IMAGES` R2 bucket. In production, these are served via a custom domain specified in `IMAGES_URL`.

### Storing and Serving
When a merchant uploads an image, the backend performs a `put` operation. The frontend then constructs the URL using the public R2 domain or the Worker proxy.

```typescript
app.post('/v1/admin/upload', async (c) => {
  const body = await c.req.parseBody();
  const file = body['file'] as File;
  const key = `${crypto.randomUUID()}-${file.name}`;

  // Store in R2
  await c.env.IMAGES.put(key, file, {
    httpMetadata: { contentType: file.type }
  });

  return c.json({ 
    url: `${c.env.IMAGES_URL}/${key}`,
    key 
  });
});
```

## Secret Management

Fufuni distinguishes between "Variables" (non-sensitive) and "Secrets" (encrypted). 

### The Secrets Pipeline
1.  **Local Development:** Variables are placed in the root `.env`. The command `npm run dev:env` copies these to `apps/merchant/.dev.vars` for Wrangler.
2.  **CI/CD:** Every key in `.env` must have a corresponding **GitHub Secret**. 
3.  **Deployment:** The Python script `generate-wrangler-jsonc.py` reads `.env` and generates a `secrets.json` file. The CI then runs `wrangler secret bulk < secrets.json`.

### Mailgun Integration
Transactional emails require specific secrets. If `MAILGUN_API_KEY` is missing, the framework silently skips email delivery to prevent runtime crashes.

```bash
# Required Mailgun Secrets
MAILGUN_API_KEY=key-xxxxxxxxxxxx
MAILGUN_DOMAIN=mg.yourdomain.com
MAILGUN_BASE_URL=https://api.mailgun.net # Use https://api.eu.mailgun.net for EU
MAILGUN_USER=support@yourdomain.com
```

## Workflow for Adding a New Binding

To add a new resource (e.g., a new KV namespace for session data), follow these three steps:

### 1. Update wrangler.jsonc
Add the binding to the base configuration file.
```jsonc
// apps/merchant/wrangler.jsonc
{
  "kv_namespaces": [
    { "binding": "KV_CACHE", "id": "..." },
    { "binding": "SESSION_STORE", "id": "..." } // New binding
  ]
}
```

### 2. Update Type Definitions
Run `npx wrangler types` to update `worker-configuration.d.ts`, or update the `Env` interface manually.
```typescript
interface Env {
  KV_CACHE: KVNamespace;
  SESSION_STORE: KVNamespace; // Added manually if not using auto-gen
  // ... other bindings
}
```

### 3. CI/CD Update
Add the ID to `.github/workflows/create-env-artifact.yaml` to ensure it is available in production.
```yaml
- name: Create .env file
  run: |
    echo "SESSION_STORE_ID=${{ secrets.SESSION_STORE_ID }}" >> .env
```

## CI/CD and Frontend Environmental Injection

Frontend variables in Fufuni are **not** prefixed with `VITE_`. Instead, they are injected into the build via the `define` block in `vite.config.ts`. This allows us to share a single `.env` file across the entire monorepo.

### Exposing a Variable to the Browser
To make a variable available in React, add it to `apps/client/vite.config.ts`.

```typescript
// apps/client/vite.config.ts
import { defineConfig, loadEnv } from 'vite';

export default defineConfig(({ mode }) => {
  const env = loadEnv(mode, process.cwd(), '');

  return {
    define: {
      'import.meta.env.API_BASE_URL': JSON.stringify(env.API_BASE_URL),
      'import.meta.env.STORE_NAME': JSON.stringify(env.STORE_NAME),
    }
  };
});
```

### Permission Mapping
The `import.meta.env.PERMISSIONS` array is dynamically generated in the Vite config by scanning for any key ending in `_PERMISSION`. This allows the UI to automatically adapt to new scopes without manual updates.

```typescript
// Logic inside vite.config.ts
const scopesArray = Object.keys(env)
  .filter(key => key.endsWith('_PERMISSION'))
  .map(key => env[key]);

// Injected as:
// 'import.meta.env.PERMISSIONS': JSON.stringify(scopesArray)
```

### Encrypted Artifacts
The `create-env-artifact.yaml` workflow packages the `.env`, `wrangler.jsonc`, and `secrets.json` into an encrypted `.tar.gz` using OpenSSL and the `CRYPTOKEN`. This artifact is then shared between the `build` and `deploy` jobs, ensuring that environment configuration remains consistent and secure across the pipeline.
