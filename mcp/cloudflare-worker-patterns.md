## Accessing Bindings in Route Handlers

Fufuni uses Hono as the primary web framework within Cloudflare Workers. All Cloudflare bindings (Durable Objects, KV, R2, environment variables) are accessible through the Hono context `c.env`. In our TypeScript setup, `c.env` is strictly typed based on the `Env` interface generated by Wrangler.

When writing a route, you use `c.env` to interact with the infrastructure components defined in `wrangler.jsonc`.

```typescript
// apps/merchant/src/routes/images.ts
import { Hono } from 'hono';

const app = new Hono<{ Bindings: Env }>();

app.get('/:key', async (c) => {
  const key = c.req.param('key');
  
  // 1. Access R2 Bucket
  const object = await c.env.IMAGES.get(key);
  if (!object) return c.notFound();

  // 2. Access KV for metadata
  const metadata = await c.env.KV_CACHE.get(`img-meta:${key}`, 'json');

  // 3. Access Environment Variable
  const baseUrl = c.env.IMAGES_URL;

  const headers = new Headers();
  object.writeHttpMetadata(headers);
  headers.set('etag', object.httpEtag);
  headers.set('X-Meta', JSON.stringify(metadata));

  return c.body(object.body, 200, Object.fromEntries(headers));
});

export default app;
```

## The Singleton Durable Object Pattern

Fufuni centralizes state in a **Durable Object (DO)** using the built-in SQLite storage. We typically use a single DO instance per merchant to ensure strong consistency and atomicity for all e-commerce operations.

### Getting the Stub
Because we want one instance for the entire worker, we use `idFromName` with a constant string. This ensures that every request, regardless of the colo it hits, is routed to the same stateful instance.

### Query vs Run
We follow a pattern where `query` is used for read-only SQL operations and `run` is used for mutations. The DO handles the SQLite lifecycle.

```typescript
// apps/merchant/src/lib/merchant-proxy.ts
export async function getMerchantDO(env: Env) {
  // Always use the same ID to ensure a single stateful instance
  const id = env.MERCHANT.idFromName('fufuni-merchant-singleton');
  return env.MERCHANT.get(id);
}

// Example usage in a Hono route
app.get('/products', async (c) => {
  const stub = await getMerchantDO(c.env);
  
  // Calling a method on the DO stub (RPC)
  // Inside the DO, this executes: this.ctx.storage.sql.exec("SELECT * FROM products")
  const products = await stub.getProducts(); 
  
  return c.json(products);
});
```

## KV Cache Architecture

To minimize latency and costs associated with Durable Object "wake-ups," we use a `kvCacheMiddleware`. This layer sits in front of the DO for all public GET requests.

### TTL Configuration
Caching behavior is controlled via specific environment variables (and GitHub Secrets):
- `KV_CACHE_SEARCH_TTL_SECONDS`: Defaults to 300s.
- `KV_CACHE_REVIEWS_TTL_SECONDS`: Defaults to 600s.
- `KV_CACHE_DEFAULT_TTL_SECONDS`: Defaults to 3600s for general catalog data.

### Bypass Rules
The cache is automatically bypassed if:
1. The method is not `GET`.
2. An `Authorization` header is present (unless it's a public `pk_*` key).
3. The request is an internal admin operation.

### Manual Invalidation
When the database state changes (e.g., a product is updated), the `kvInvalidateMiddleware` purges the cache. It uses a prefix-based approach to clear relevant categories and products.

```typescript
// apps/merchant/src/middleware/kv-cache.ts
// Manual invalidation example inside a route handler
app.post('/v1/products', async (c) => {
  const stub = await getMerchantDO(c.env);
  const result = await stub.createProduct(await c.req.json());

  // Invalidate by prefix
  const prefix = "cache:*/v1/products";
  const { keys } = await c.env.KV_CACHE.list({ prefix });
  for (const key of keys) {
    await c.env.KV_CACHE.delete(key.name);
  }

  return c.json(result, 201);
});
```

## R2 Image Storage

Product images and static assets are stored in the `IMAGES` R2 bucket. In production, these are typically served via a custom domain or the `IMAGES_URL` binding.

```typescript
// apps/merchant/src/lib/storage.ts
export async function uploadProductImage(env: Env, file: File, productId: string) {
  const key = `products/${productId}/${crypto.randomUUID()}-${file.name}`;
  
  await env.IMAGES.put(key, file.stream(), {
    httpMetadata: { contentType: file.type }
  });

  return `${env.IMAGES_URL}/${key}`;
}
```

## Secrets and Environment Variables

Fufuni distinguishes between "Vars" (public/non-sensitive) and "Secrets" (sensitive).

### Secret Management
Secrets must never be committed to Git. In the Fufuni framework:
- **Local:** Managed in `.dev.vars` (sourced by `wrangler dev`).
- **CI/CD:** Managed as GitHub Secrets.
- **Production:** Managed via `wrangler secret bulk`.

### Mailgun Configuration
Mailgun is the default transactional email provider. If `MAILGUN_API_KEY` is missing, the framework silently skips email sending to prevent crashes in dev environments. Required variables:
- `MAILGUN_API_KEY`: Private API key.
- `MAILGUN_DOMAIN`: The verified domain (e.g., `mg.example.com`).
- `MAILGUN_BASE_URL`: Usually `https://api.mailgun.net`.
- `MAILGUN_USER`: The "From" email address.

## Adding a New Binding

To add a new infrastructure component (like a new KV namespace or R2 bucket), follow these steps:

1.  **Update `wrangler.jsonc`**: Add the binding definition.
2.  **Generate Types**: Run `npx wrangler types` to update `worker-configuration.d.ts`.
3.  **Update CI/CD**: If the binding requires an ID or secret, add the corresponding GitHub Secret and update `.github/workflows/create-env-artifact.yaml`.

```jsonc
// apps/merchant/wrangler.jsonc
{
  "kv_namespaces": [
    { "binding": "KV_CACHE", "id": "..." },
    { "binding": "NEW_DATA_STORE", "id": "..." } // Added new binding
  ]
}
```

## CI/CD and Frontend Variable Injection

The deployment pipeline is strictly automated via GitHub Actions.

### Environment Mapping
Every `.env` variable has a 1:1 equivalent GitHub Secret. The workflow `create-env-artifact.yaml` builds an encrypted `.tar.gz` containing `.env` and `wrangler.jsonc`. This ensures the exact configuration used in testing is deployed to production.

### Exposing Vars to the Frontend
Frontend variables do **not** use the `VITE_` prefix. Instead, they are injected during the build process via the `define` block in `vite.config.ts`.

```typescript
// apps/client/vite.config.ts
import { defineConfig, loadEnv } from 'vite';

export default defineConfig(({ mode }) => {
  const env = loadEnv(mode, process.cwd(), '');
  return {
    define: {
      'import.meta.env.API_BASE_URL': JSON.stringify(env.API_BASE_URL),
      'import.meta.env.STORE_NAME': JSON.stringify(env.STORE_NAME),
      // Injected permissions array based on .env keys
      'import.meta.env.PERMISSIONS': JSON.stringify(
        Object.keys(env).filter(k => k.endsWith('_PERMISSION'))
      ),
    }
  };
});
```

To expose a new variable to the browser, you must add it to the `define` object in the Vite config.

## Database Migrations

Since Durable Objects use SQLite, schema changes require migrations. Migrations are defined in `wrangler.jsonc` and applied by the Cloudflare runtime.

```jsonc
// apps/merchant/wrangler.jsonc
"migrations": [
  {
    "tag": "v1",
    "new_sqlite_classes": ["MerchantDO"]
  },
  {
    "tag": "v2",
    "new_sqlite_tables": ["products", "categories"]
  }
]
```

To run migrations locally during development:
```bash
npx wrangler deployments migrations apply --local
```
