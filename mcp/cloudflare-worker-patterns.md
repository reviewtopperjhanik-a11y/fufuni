## Cloudflare Worker Patterns

### 1. Accessing Bindings in Route Handlers
Bindings are accessed through the `env` object in the route handler. Here are some examples:

```typescript
export default {
  async fetch(request: Request, env: Env, ctx: ExecutionContext): Promise<Response> {
    // Accessing Durable Object binding
    const merchantDO = env.MERCHANT;
    
    // Accessing R2 binding
    const images = env.IMAGES;
    
    // Accessing KV binding
    const kvCache = env.KV_CACHE;
    
    // Use the bindings as needed
    // ...
  }
}
```

### 2. Durable Object Pattern
We use a single instance of a Durable Object (DO) for our Merchant DO. Here's how to get the stub and call methods on it:

```typescript
// Get the stub
const merchantDO = env.MERCHANT;

// Call query() method
await merchantDO.query(request);
```

The `query()` method is a standard method on Durable Objects that allows read-only access. For more complex operations, use the `run()` method:

```typescript
// Call run() method
await merchantDO.run(request);
```

### 3. KV Cache
The KV cache works by serving GET responses from KV before hitting the Durable Object. The cache key is constructed as `cache:<full-url>`, including query parameters.

To invalidate cache manually, use the `kvInvalidateMiddleware`:

```typescript
// Invalidate cache for a specific key
await kvInvalidateMiddleware(request, env, ctx);
```

The `kvCacheMiddleware` bypasses the cache for non-GET methods and for Authorization headers other than `Bearer pk_*`.

### 4. R2
Product images are stored and served using R2. Here's how to store and serve an image:

```typescript
// Store an image
const image = await request.arrayBuffer();
await env.IMAGES.put(`image-${Date.now()}.jpg`, image);

// Serve an image
const image = await env.IMAGES.get(`image-${id}.jpg`);
return new Response(image, {
  headers: {
    'Content-Type': 'image/jpeg',
  },
});
```

### 5. Secrets
Secrets must be stored in Wrangler secrets (not in the `.env` file). For Mailgun, the required secrets are:

*   `MAILGUN_API_KEY`
*   `MAILGUN_DOMAIN`
*   `MAILGUN_BASE_URL` (default: `https://api.mailgun.net`)
*   `MAILGUN_USER` (sender address)

Email sending is silently skipped if `MAILGUN_API_KEY` is absent.

### 6. Adding a New Binding
To add a new binding:

1.  Update `wrangler.jsonc`:

    ```json
{
  "bindings": [
    {
      "name": "NEW_BINDING",
      "type": "r2_bucket"
    }
  ]
}
```
2.  Update `worker-configuration.d.ts`:

    ```typescript
interface Env {
  NEW_BINDING: R2Bucket;
}
```
3.  Update the `Env` type:

    ```typescript
type Env = {
  // ... existing types
  NEW_BINDING: R2Bucket;
}
```

### 7. CI/CD
Environment variables map to GitHub secrets with the same name. When adding a new environment variable:

*   Add it to `.github/workflows/create-env-artifact.yaml` (the CI encrypted artifact builder) so CI can pass it to the Worker build.

To expose a new variable to the frontend via `vite.config.ts` define block:

*   Add it to the define block in `apps/client/vite.config.ts`:

```typescript
define: {
  __VITE_ENV__: JSON.stringify({
    // ... existing variables
    NEW_VARIABLE: process.env.NEW_VARIABLE,
  }),
}
```

Frontend env vars are not prefixed with `VITE_`. They are injected via the `vite.config.ts` define block as `import.meta.env.VARIABLE_NAME`.

The `import.meta.env.PERMISSIONS` string[] is derived at build time from all `*_PERMISSION` .env keys (scopesArray in `vite.config.ts`). This drives navbar permission filtering without hardcoding permission strings.

Here is a GitHub Actions YAML file snippet illustrating mapping of .env variables to GitHub Secrets
```yml
steps:
  - name: Decrypt and create env artifact
    uses: actions/checkout@v3
    env:
      NEW_VARIABLE: ${{ secrets.NEW_VARIABLE }}
      # ... existing secrets
    run: |
      # ... create-env-artifact.yaml script
```
