## Introduction to Cloudflare Worker Patterns
The Fufuni e-commerce framework utilizes Cloudflare Workers for its backend, providing a serverless architecture with the benefits of edge computing. To leverage this architecture effectively, several patterns are employed to manage bindings, durable objects, KV cache, R2 storage, secrets, and CI/CD pipelines.

## Accessing Bindings in Route Handlers
In a Cloudflare Worker route handler, bindings such as `MERCHANT`, `IMAGES`, and `KV_CACHE` can be accessed through the `c.env` object. For example:
```typescript
export async function GET(c: Context) {
  const merchantDO = c.env.MERCHANT;
  const imagesBucket = c.env.IMAGES;
  const kvCache = c.env.KV_CACHE;
  // Use the bindings as needed in your route handler logic
}
```

## The Durable Object Pattern
The Durable Object pattern is used to manage stateful data in Cloudflare Workers. A single instance of the Durable Object is used across all requests, allowing for efficient and consistent data management. To get the stub for the Durable Object, you can use the following code:
```typescript
const merchantDO = c.env.MERCHANT;
const stub = await merchantDO.get('your-id');
```
You can then use the `stub` to call methods on the Durable Object, such as `query()` and `run()`:
```typescript
const result = await stub.query('your-method');
```
Note that the `your-id` and `your-method` placeholders should be replaced with the actual ID and method names for your Durable Object.

## KV Cache
The KV cache is used to store and retrieve data in a key-value store. The `kvCacheMiddleware` serves GET responses from the KV cache before hitting the Durable Object, reducing the load on the DO and improving performance. The cache key is constructed as `cache:<full-url>` including query parameters.

To invalidate the cache manually, you can use the `kvInvalidateMiddleware`, which purges all cache keys with a prefix matching the URL path.

## R2
Product images are stored and served from R2, a Cloudflare object storage service. The images are stored in a bucket bound to the Worker, and can be accessed using the `IMAGES` binding.

## Secrets
Secrets are stored in Wrangler secrets or in the `.env` file. When adding a new binding, it is essential to update both the Wrangler secrets and the `.env` file. The required Mailgun secrets include `MAILGUN_API_KEY`, `MAILGUN_DOMAIN`, `MAILGUN_BASE_URL`, and `MAILGUN_USER`.

## Adding a New Binding
To add a new binding, follow these steps:

1. Update `wrangler.jsonc` to include the new binding.
2. Update `worker-configuration.d.ts` to include the new binding in the `Env` type.
3. Update the `Env` type in your TypeScript code to include the new binding.
4. Add the new binding to the `.env` file and update the corresponding Wrangler secret.

## CI/CD
The CI/CD pipeline uses GitHub secrets to map env vars to the Worker build. The `create-env-artifact.yaml` workflow generates an encrypted `.env` + `wrangler.jsonc` artifact consumed by deploy jobs. To expose a new variable to the frontend, add it to the `define` block in `vite.config.ts`.

Example:
```typescript
import { defineConfig } from 'vite';
import { scopesArray } from './scopes';

export default defineConfig({
  // ...
  define: {
    'import.meta.env.PERMISSIONS': JSON.stringify(scopesArray),
  },
});
```
This will make the `PERMISSIONS` variable available to the frontend as `import.meta.env.PERMISSIONS`.
