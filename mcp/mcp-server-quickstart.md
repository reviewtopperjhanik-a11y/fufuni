## Remote MCP Architecture in Fufuni

The Model Context Protocol (MCP) is an open standard that enables AI models (like Claude 3.5 Sonnet) to securely access your local or remote tools and data sources. In the Fufuni ecosystem, we use a **Remote MCP Server** hosted on Cloudflare Workers to bridge the gap between our generated documentation and the AI assistants used by developers.

By exposing the static documentation located in the `mcp/` directory as tools, we allow the AI to "read the manual" on-demand. This significantly reduces hallucinations when the AI helps you write new Hono routes or HeroUI components, as it has access to the exact specifications of the Fufuni framework.

### Why Remote MCP?
1.  **Zero-Latency Distribution**: Updates to the framework documentation are deployed to the Worker, instantly updating the knowledge for all developers.
2.  **Stateless Execution**: Running on the Cloudflare Workers free tier is cost-effective and handles the SSE (Server-Sent Events) protocol natively.
3.  **Scoped Context**: Instead of dumping 50KB of text into every prompt, the AI only calls the specific tool (e.g., `get_hono_conventions`) when it needs that specific information.

## The Worker Entry Point

The Fufuni MCP server uses the Cloudflare Workers runtime. We utilize the `@modelcontextprotocol/sdk` for the protocol implementation. The entry point handles the upgrade to SSE and defines the available tools based on our documentation files.

    if (url.pathname === "/mcp") {

      return server.handleRequest(request);
    }

    return new Response("Fufuni MCP Server Running", { status: 200 });

## Dynamic Tool Registration with KV Caching

In a real Fufuni deployment, we don't hardcode the tool list. We iterate over the documentation index. Since reading from KV on every `list_tools` call is inefficient, we leverage the Worker's global scope to cache the file manifest.

```typescript
// apps/mcp-server/src/utils.ts
import { Env } from "./index";

let manifestCache: string[] | null = null;

export async function getDocManifest(env: Env): Promise<string[]> {
  if (manifestCache) return manifestCache;
  
  // List keys with the prefix 'doc:'
  const list = await env.MCP_DOCS.list({ prefix: "doc:" });
  manifestCache = list.keys.map(k => k.name.replace("doc:", ""));
  return manifestCache;
}

// apps/mcp-server/src/handler.ts
server.setRequestHandler(ListToolsRequestSchema, async () => {
  const docs = await getDocManifest(env);
  
  return {
    tools: docs.map(doc => ({
      name: `read_${doc}`,
      description: `Reads the Fufuni documentation regarding ${doc.replace("_", " ")}`,
      inputSchema: { type: "object", properties: {} }
    }))
  };
});
```

## Populating the Documentation

Before deploying, we use a build script to parse the `mcp/*.md` files and upload them to the KV namespace. This ensures the MCP server has data to serve.

```bash
# Example script to sync local docs to KV
#!/bin/bash

# Extract H1 from markdown to use as description
for file in ../../mcp/*.md; do
  filename=$(basename "$file" .md)
  content=$(cat "$file")
  
  echo "Uploading doc:$filename to KV..."
  npx wrangler kv:key put --binding MCP_DOCS "doc:$filename" "$content"
done
```

## Performance Optimization: KV Caching Strategy

To ensure the free tier limits (100k reads/day) are not exceeded during heavy development sessions, we implement a multi-tier cache.

1.  **Memory Cache**: Store the documentation content in a global variable in the Worker. Since Workers stay "warm" across requests, subsequent tool calls for the same doc will be near-instant.
2.  **Last-Modified Checks**: Use a `version` key in KV to invalidate the memory cache when docs are updated.

```typescript
const docCache = new Map<string, string>();
let lastUpdate: number = 0;

async function getDocContent(name: string, env: Env): Promise<string> {
  const cacheKey = `doc:${name}`;
  
  // 1. Check Memory
  if (docCache.has(cacheKey)) {
    return docCache.get(cacheKey)!;
  }
  
  // 2. Fetch from KV
  const content = await env.MCP_DOCS.get(cacheKey);
  if (!content) throw new Error("Documentation not found");
  
  // 3. Update Memory Cache
  docCache.set(cacheKey, content);
  return content;
}
```

### Handling Schema Validation
The AI will strictly follow the `inputSchema` defined in `ListToolsRequestSchema`. For Fufuni docs, we usually keep this empty as the tool name itself defines the file to be read, but you can extend this to search within files:

```typescript
{
  name: "search_docs",
  description: "Search for a keyword across all Fufuni documentation",
  inputSchema: {
    type: "object",
    properties: {
      query: { type: "string", description: "The term to search for (e.g. 'Durable Object')" }
    },
    required: ["query"]
  }
}
```

By following this structure, the Fufuni framework provides a live, high-speed documentation API that makes AI assistants significantly more effective at generating framework-compliant code.
