## Understanding the Fufuni MCP Server

The Model Context Protocol (MCP) server is the primary interface for AI assistants (like Claude or GPT-4) to understand the Fufuni codebase. Unlike static documentation, the MCP server allows an AI to dynamically query specific "tools" to retrieve the latest architecture rules, coding standards, and API definitions.

In Fufuni, the MCP server runs as a Cloudflare Worker in production or via `stdio` locally. It serves a compiled "Knowledge Base" which is a collection of Markdown files transformed into a single TypeScript module. This allows the AI to "read" the documentation as if it were part of its own context.

```typescript
// apps/mcp/src/index.ts - Simplified tool definition
import { Server } from "@modelcontextprotocol/sdk/server/index.js";
import { knowledge } from "./knowledge.js";

const server = new Server({
  name: "fufuni-docs",
  version: "1.0.0",
}, {
  capabilities: {
    tools: {},
  },
});

server.setRequestHandler(ListToolsRequestSchema, async () => ({
  tools: [
    {
      name: "get_knowledge_topic",
      description: "Retrieve specific Fufuni documentation by topic name",
      inputSchema: {
        type: "object",
        properties: {
          topic: { type: "string", enum: Object.keys(knowledge) }
        }
      }
    }
  ]
}));
```

## Directory Layout and Architecture

The knowledge system is isolated within the `apps/mcp/` directory. It uses a multi-stage pipeline: source code is ingested, processed by an LLM to generate structured Markdown, and finally bundled into the runtime server.

### Knowledge Structure
- **`apps/mcp/knowledge/topics/`**: This is where contributors spend 90% of their time. Every `.ts` file here represents one documentation topic (e.g., `routing.ts`, `database.ts`).
- **`apps/mcp/knowledge/base.ts`**: Contains the shared `Topic` interface and common system prompts.
- **`apps/mcp/knowledge/generate.ts`**: The engine that reads topics, fetches source code, calls an external LLM, and writes `.md` files to the repository root.
- **`apps/mcp/scripts/gen-knowledge.ts`**: A utility that gathers all generated `.md` files from `<repo-root>/mcp/` and converts them into the `apps/mcp/src/knowledge.ts` TypeScript module.
- **`mcp/` (Repo Root)**: The destination for generated Markdown files. These should be committed to the repository.

## The Topic Interface

Every documentation topic is defined as a TypeScript object. This object tells the generator which source files to read and how to instruct the AI to summarize them.

### Field Definitions
- `name`: String, must match the filename (without extension).
- `description`: A single sentence explaining what this topic covers.
- `sources`: An array of file paths relative to the repository root.
- `systemPrompt`: Instructions for the LLM generating the documentation. Use `BASE_SYSTEM` from `base.ts`.
- `manualFacts`: A string of "Verified Facts" that the LLM must treat as absolute truth, overriding any inferred logic.
- `buildPrompt`: A function that receives the concatenated content of all `sources` and returns the final prompt for the LLM.
- `maxSourceChars`: (Optional) Limit to prevent context window overflow.

```typescript
// Example interface usage in apps/mcp/knowledge/base.ts
export interface Topic {
  name: string;
  description: string;
  sources: string[];
  systemPrompt: string;
  manualFacts: string;
  buildPrompt: (sourcesContent: string) => string;
  maxSourceChars?: number;
}
```

## Adding a New Topic

To add knowledge, you must create a new topic file. **Never edit `knowledge.ts` directly**, as it is overwritten during the build process.

### Step-by-Step Template
Create a file at `apps/mcp/knowledge/topics/my-feature.ts`:

```typescript
/*

 */
import { Topic, BASE_SYSTEM, appendFacts } from "../base.js";

const facts = `
- MyFeature always uses the 'X' pattern.
- Developers must never call the internal 'Y' method directly.
`;

const topic: Topic = {
  name: "my-feature",
  description: "Documentation for the MyFeature implementation and its SQLite integration.",
  sources: [
    "apps/api/src/features/my-feature/schema.ts",
    "apps/api/src/features/my-feature/router.ts",
  ],
  systemPrompt: BASE_SYSTEM,
  manualFacts: facts,
  buildPrompt: (content: string) => {
    return appendFacts(facts, `
Analyze the following source code for 'MyFeature'. 
Generate a comprehensive documentation guide in Markdown format.
Focus on the Zod schemas and Hono route definitions.

SOURCE CODE:
${content}
    `);
  },
};

export default topic;
```

## The Generation Pipeline

Generating the knowledge base is a two-step process. First, the topic logic is executed to create Markdown files via an LLM. Second, those Markdown files are compiled into code.

### 1. `mcp:generate` and `mcp:generate:force`
The `generate.ts` script iterates through all topics in `apps/mcp/knowledge/topics/` alphabetically.
- **`npm run mcp:generate`**: Performs a dry-run or uses cached versions if available. It checks if source files have changed before calling the LLM API.
- **`npm run mcp:generate:force`**: Ignores caches and forces the LLM to regenerate Markdown for every single topic. Use this when you have updated the `BASE_SYSTEM` prompt.

### 2. `mcp:auto`
This is the standard command for contributors. It performs the generation and immediately follows it with the publication step.

```bash
# Required environment variables
export AI_API_KEY="your-key"
export AI_API_URL="https://api.openai.com/v1" # or compatible
export AI_MODEL="gpt-4o"

# Run the full pipeline
npm run mcp:auto
```

### 3. Publishing to Runtime
The script `apps/mcp/scripts/gen-knowledge.ts` takes all `.md` files found in the `<repo-root>/mcp/` folder and generates `apps/mcp/src/knowledge.ts`. This file exports a constant object where keys are topic names and values are the Markdown strings.

```typescript
// Example of the auto-generated apps/mcp/src/knowledge.ts
// DO NOT EDIT THIS FILE DIRECTLY
export const knowledge: Record<string, string> = {
  "my-feature": "### My Feature\n\nThis is the documentation generated by the LLM...",
  "database": "### Database\n\nFufuni uses SQLite via Durable Objects..."
};
```

## Local Testing with Claude Desktop

Before deploying the MCP server to Cloudflare, you should test it locally using the `stdio` transport. This allows your local Claude Desktop app to talk directly to your Fufuni knowledge base.

### Running the Server
The Fufuni framework provides a dedicated entry point for local execution:

```bash
# From the repository root
npx tsx apps/mcp/src/stdio.ts
```

### Configuring Claude Desktop
On macOS, edit `~/Library/Application Support/Claude/claude_desktop_config.json`. On Windows, edit `%APPDATA%\Claude\claude_desktop_config.json`.

```json
{
  "mcpServers": {
    "fufuni-local": {
      "command": "npx",
      "args": [
        "-y",
        "tsx",
        "/absolute/path/to/fufuni/apps/mcp/src/stdio.ts"
      ],
      "env": {
        "NODE_ENV": "development"
      }
    }
  }
}
```

After restarting Claude Desktop, you will see a hammer icon. You can ask Claude: *"Search the Fufuni knowledge base for the database topic"* to verify it is reading your generated Markdown.

## Critical Rules for Contributors

### The "No Manual Edit" Rule
**Never modify `apps/mcp/src/knowledge.ts` by hand.**
If you find an error in the documentation provided by the AI:
1. Identify the relevant topic file in `apps/mcp/knowledge/topics/`.
2. Add a correction to the `manualFacts` string.
3. Run `npm run mcp:auto`.
4. The LLM will use your `manualFacts` as the source of truth to correct its summary in the next generation cycle.

### Context Management
The `maxSourceChars` field is vital. If a topic includes large files (like entire UI component libraries), the LLM might truncate or fail. If you hit token limits, split the topic into smaller sub-topics (e.g., `ui-components-base.ts` and `ui-components-complex.ts`).

### Copyright Compliance
Every single topic file must start with the following header exactly as shown:
```typescript
/*
 * Copyright (c) 2026 Ronan LE MEILLAT - SCTG Development / License: AGPL-3.0-or-later
 */
```
The generator scripts check for this header; missing headers may cause CI/CD failures during the build process.
