## Store Initialization Status

The first step in any Fufuni deployment is determining whether the merchant instance has been initialized. This is handled by the `GET /v1/setup/status` endpoint. This endpoint is public and does not require authentication, as its primary purpose is to tell the frontend whether to redirect the user to the Setup Wizard or the Login page.

The backend determines "initialized" status by checking for the existence of an admin user or specific configuration keys in the Durable Object SQLite database.

```typescript
import { OpenAPIHono, createRoute, z } from '@hono/zod-openapi';
import { getDb } from '../db';
import type { HonoEnv } from '../types';

const setupApp = new OpenAPIHono<HonoEnv>();

const SetupStatusResponse = z.object({
  initialized: z.boolean().openapi({ description: 'True if the store has already been initialized' }),
}).openapi('SetupStatusResponse');

const getStatus = createRoute({
  method: 'get',
  path: '/status',
  tags: ['Setup'],
  summary: 'Check initialization status',
  responses: {
    200: { content: { 'application/json': { schema: SetupStatusResponse } }, description: 'Status retrieved' },
  },
});

setupApp.openapi(getStatus, async (c) => {
  const db = getDb(c.var.db);
  // Check if any admin API key or admin user exists
  const existing = await db.query<{ id: string }>(
    `SELECT id FROM api_keys WHERE role = 'admin' LIMIT 1`
  );
  
  return c.json({ initialized: existing.length > 0 }, 200);
});
```

The frontend uses this response in a top-level route guard. If `initialized` is `false`, the user is force-redirected to `/setup`.

## First-Run Initialization (POST /v1/setup/init)

The `POST /v1/setup/init` endpoint is the "God" method of the initialization process. It is responsible for creating the initial admin user, defining the store's core identity (name, currency), and setting up the default geographical region.

### Idempotency and the 409 Guard
To prevent accidental re-initialization or takeover of an existing store, this endpoint implements a strict guard. If an admin already exists in the database, the backend must return a `403 Forbidden` or `409 Conflict`.

```typescript
const InitBody = z.object({
  adminEmail: z.string().email(),
  storeName: z.string().min(1),
  defaultCurrency: z.string().length(3),
  defaultCountryCode: z.string().length(2),
}).openapi('InitBody');

const initStore = createRoute({
  method: 'post',
  path: '/init',
  tags: ['Setup'],
  request: {
    body: { content: { 'application/json': { schema: InitBody } } },
  },
  responses: {
    200: { content: { 'application/json': { schema: z.object({ ok: z.literal(true) }) } }, description: 'Store initialized' },
    409: { content: { 'application/json': { schema: z.object({ error: z.string() }) } }, description: 'Store already initialized' },
  },
});

setupApp.openapi(initStore, async (c) => {
  const { adminEmail, storeName, defaultCurrency, defaultCountryCode } = c.req.valid('json');
  const db = getDb(c.var.db);

  // Guard: Check if setup was already performed
  const check = await db.query('SELECT key FROM config WHERE key = "store_name"');
  if (check.length > 0) {
    return c.json({ error: 'Store is already initialized' }, 409);
  }

  // Transactional setup logic
  await db.run('BEGIN TRANSACTION');
  try {
    await db.run(`INSERT INTO config (key, value) VALUES ('store_name', ?)`, [storeName]);
    await db.run(`INSERT INTO currencies (code, symbol, is_default) VALUES (?, ?, 1)`, [defaultCurrency, '$']);
    await db.run(`INSERT INTO countries (code, name) VALUES (?, ?)`, [defaultCountryCode, 'Default Country']);
    
    // Auth0 Management logic would be triggered here
    // ...
    
    await db.run('COMMIT');
    return c.json({ ok: true }, 200);
  } catch (e) {
    await db.run('ROLLBACK');
    throw e;
  }
});
```

## Auth0 Management API Interaction

Fufuni leverages Auth0 for identity management. During the setup process, the framework interacts with the Auth0 Management API if the environment variable `AUTH0_MANAGEMENT_CLIENT_ID` is provided.

1.  **Admin Invitation**: The backend calls Auth0 to create a user with the provided `adminEmail`. It then triggers a "Change Password" or "Invitation" email so the merchant can set their credentials securely.
2.  **Tenant Configuration**: If the Auth0 tenant is "clean," Fufuni can automatically deploy required Actions, Roles (e.g., `admin:store`, `admin:database`), and Clients. This is typically handled by an internal `auth0:deploy` helper triggered during the `/init` call.

```typescript
async function inviteAdminToAuth0(email: string, env: HonoEnv['Bindings']) {
  if (!env.AUTH0_MANAGEMENT_DOMAIN || !env.AUTH0_MANAGEMENT_CLIENT_ID) {
    console.warn('Auth0 Management credentials missing; skipping invite');
    return;
  }

  // 1. Get Management Token
  const tokenRes = await fetch(`https://${env.AUTH0_MANAGEMENT_DOMAIN}/oauth/token`, {
    method: 'POST',
    headers: { 'content-type': 'application/json' },
    body: JSON.stringify({
      client_id: env.AUTH0_MANAGEMENT_CLIENT_ID,
      client_secret: env.AUTH0_MANAGEMENT_CLIENT_SECRET,
      audience: `https://${env.AUTH0_MANAGEMENT_DOMAIN}/api/v2/`,
      grant_type: 'client_credentials',
    }),
  });

  const { access_token } = await tokenRes.json();

  // 2. Create User and Assign Role
  await fetch(`https://${env.AUTH0_MANAGEMENT_DOMAIN}/api/v2/users`, {
    method: 'POST',
    headers: { 
      Authorization: `Bearer ${access_token}`,
      'Content-Type': 'application/json'
    },
    body: JSON.stringify({
      email,
      connection: 'Username-Password-Authentication',
      password: crypto.randomUUID(), // Temp password
      verify_email: true,
    }),
  });
}
```

## Frontend Setup Wizard Flow

The frontend wizard, located in `apps/client/src/pages/setup/`, is a multi-step React 19 component using HeroUI v3. It breaks the complex initialization into three manageable steps for the merchant.

### Step 1: Store Basics
The merchant provides the `Store Name`, `Default Currency` (e.g., USD, EUR), and `Base Country`. These values are stored in the local component state.

### Step 2: Admin Identity
The merchant enters their primary email address. This is the email that will receive the Auth0 invitation and gain full administrative access to the Merchant Dashboard.

### Step 3: Deployment & Verification
The UI displays a summary of the configuration. Upon clicking "Initialize", the frontend sends the `POST /v1/setup/init` request. While the request is pending, the UI shows a "Provisioning your store..." spinner. 

```tsx
// Example Step 3 Submission in React 19
const handleInitialize = async (formData: SetupData) => {
  setIsLoading(true);
  try {
    const response = await api.post('/v1/setup/init', formData);
    if (response.ok) {
      // Success: move to "Welcome" screen or redirect to login
      setStep('complete');
    }
  } catch (err) {
    toast.error(err.message || 'Initialization failed');
  } finally {
    setIsLoading(false);
  }
};
```

## Post-Setup Store Management

Once the store is initialized, the `/setup/init` endpoint is locked. Any subsequent changes to the store's identity or configuration must be performed through the specific Merchant API routes which require an `admin:store` or `admin:database` scope.

Store metadata such as logos, support emails, and social links are managed via the `Store Info` endpoints:

*   **GET /v1/store-info**: Publicly accessible (for the customer storefront).
*   **PUT /v1/store-info**: Admin-only (protected by `authMiddleware` and `adminOnly`).

## Database Maintenance & Migrations

The setup process also includes utilities for managing the underlying SQLite schema. These are typically used by developers or during automated CI/CD flows rather than by the merchant directly.

### Migration Management
The Fufuni framework tracks applied schema changes in a `migrations` table. The `adminSetup` sub-router provides endpoints to inspect and trigger these.

*   `GET /migrations/list`: Returns a list of all migrations and their execution timestamps.
*   `POST /migrations/run`: Forces the database to check for pending SQL files and apply them. In the DO environment, this is often a no-op that simply triggers the internal logic in `getDb`.

### Database Reset
For development environments, the `POST /v1/setup/reset` endpoint allows wiping the entire store state. It uses `PRAGMA foreign_keys = OFF` to bypass referential integrity constraints during the mass deletion of data across all core tables (Products, Orders, Inventory, etc.).

```typescript
// snippet from setup.ts
adminApp.openapi(resetDatabase, async (c) => {
  const db = getDb(c.var.db);
  await db.run('PRAGMA foreign_keys = OFF');
  
  const tables = ['products', 'variants', 'orders', 'customers', 'api_keys', 'config'];
  for (const table of tables) {
    await db.run(`DELETE FROM ${table}`);
  }

  await db.run('PRAGMA foreign_keys = ON');
  return c.json({ ok: true }, 200);
});
```

## Stripe Integration Setup

Configuration of payment providers occurs immediately after the core store setup. The `POST /v1/setup/stripe` endpoint validates a Stripe Secret Key by attempting to fetch the account balance before persisting the key to the encrypted `config` table.

```typescript
adminApp.openapi(setupStripe, async (c) => {
  const { stripe_secret_key, stripe_webhook_secret } = c.req.valid('json');

  // Validate key against Stripe API
  const res = await fetch('https://api.stripe.com/v1/balance', {
    headers: { Authorization: `Bearer ${stripe_secret_key}` },
  });

  if (!res.ok) {
    throw ApiError.invalidRequest('Invalid Stripe secret key');
  }

  const db = getDb(c.var.db);
  const configValue = JSON.stringify({
    secret_key: stripe_secret_key,
    webhook_secret: stripe_webhook_secret || null,
  });

  // Atomic upsert into the config table
  await db.run(
    `INSERT INTO config (key, value, updated_at) VALUES ('stripe', ?, ?)
     ON CONFLICT(key) DO UPDATE SET value = ?, updated_at = ?`,
    [configValue, now(), configValue, now()]
  );

  return c.json({ ok: true }, 200);
});
```
