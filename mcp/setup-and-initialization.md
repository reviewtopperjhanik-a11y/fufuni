## Initial Status Check

Before the Fufuni dashboard becomes operational, the frontend must determine if the backend has been initialized. This is handled by a dedicated status endpoint. The `GET /v1/setup/status` route is public and serves as the entry point for the setup wizard logic.

The backend determines "initialized" status primarily by checking for the existence of an administrative user or initial API keys. If this returns `false`, the React frontend automatically redirects the user to the `/setup` route.

### Backend Implementation of Status Check

```typescript
import { OpenAPIHono, createRoute, z } from '@hono/zod-openapi';
import { type HonoEnv } from '../types';
import { getDb } from '../db';

const SetupStatusResponse = z.object({
  initialized: z.boolean().openapi({ example: true }),
}).openapi('SetupStatusResponse');

const getStatus = createRoute({
  method: 'get',
  path: '/status',
  tags: ['Setup'],
  summary: 'Check initialization status',
  responses: {
    200: {
      content: { 'application/json': { schema: SetupStatusResponse } },
      description: 'The initialization status of the store',
    },
  },
});

const setupApp = new OpenAPIHono<HonoEnv>();

setupApp.openapi(getStatus, async (c) => {
  const db = getDb(c.var.db);
  // Check if an admin key or admin user exists
  const existingKeys = await db.query(`SELECT id FROM api_keys WHERE role = 'admin' LIMIT 1`);
  const initialized = existingKeys.length > 0;

  return c.json({ initialized }, 200);
});

export { setupApp };
```

## First-Run Initialization

The `POST /v1/setup/init` endpoint is the core of the first-run experience. According to the verified framework facts, this endpoint is responsible for creating the initial admin user, the primary store configuration, and the default region/currency settings.

### Guarding Against Re-initialization
The initialization process is strictly idempotent. It includes a guard clause that checks if an administrator already exists. If the database is already configured, any subsequent calls to `/init` must return a `409 Conflict` error to prevent unauthorized hijacking of the store configuration.

### Implementation Example: Setup Logic

```typescript

import { z } from '@hono/zod-openapi';

const InitBody = z.object({
  adminEmail: z.string().email(),
  storeName: z.string().min(1),
  defaultCurrency: z.string().length(3),
  defaultCountryCode: z.string().length(2),
}).openapi('InitBody');

// Inside the Hono handler:
const handleInit = async (c) => {
  const { adminEmail, storeName, defaultCurrency, defaultCountryCode } = c.req.valid('json');
  const db = getDb(c.var.db);

  // 1. Guard check
  const adminExists = await db.query(`SELECT id FROM api_keys WHERE role = 'admin' LIMIT 1`);
  if (adminExists.length > 0) {
    throw ApiError.conflict('Store is already initialized.');
  }

  // 2. Initialize Store Config
  const storeId = crypto.randomUUID();
  await db.run(
    `INSERT INTO config (key, value, updated_at) VALUES ('store_info', ?, ?)`,
    [JSON.stringify({ name: storeName, id: storeId }), now()]
  );

  // 3. Setup Default Region/Currency
  await db.run(
    `INSERT INTO currencies (code, name, symbol) VALUES (?, ?, ?)`,
    [defaultCurrency, defaultCurrency, '$']
  );
```

## Auth0 Management API Integration

Fufuni leverages the Auth0 Management API during setup to handle administrative identity without storing sensitive passwords locally. 

When `POST /v1/setup/init` is called, the framework performs two critical tasks:
1.  **Auth0 Tenant Configuration**: If the `AUTH0_MANAGEMENT_CLIENT_ID` environment variable is present and the tenant is unconfigured, the framework runs an internal equivalent of `auth0:deploy` to set up connections and roles.
2.  **Admin Invitation**: It sends an invitation email to the provided `adminEmail`. This user is granted the `admin:store` and `admin:database` roles within the Auth0 tenant.

### Management API Service Example

```typescript
async function inviteAdmin(email: string, env: HonoEnv['Bindings']) {
  const managementToken = await getAuth0ManagementToken(env);
  
  const response = await fetch(`https://${env.AUTH0_DOMAIN}/api/v2/users`, {
    method: 'POST',
    headers: {
      Authorization: `Bearer ${managementToken}`,
      'Content-Type': 'application/json',
    },
    body: JSON.stringify({
      email,
      connection: 'Username-Password-Authentication',
      verify_email: true,
      app_metadata: { roles: ['admin'] },
    }),
  });

  if (!response.ok) {
    const error = await response.json();
    throw new Error(`Auth0 User Creation Failed: ${JSON.stringify(error)}`);
  }
}
```

## Setup Wizard Frontend Flow

The frontend setup wizard (located in `apps/client/src/pages/setup/`) is a multi-step React 19 component using HeroUI v3 components. It guides the user through the initial configuration in three distinct phases.

### Step 1: Store Foundation
The user provides basic branding information:
-   **Store Name**: The public-facing name of the shop.
-   **Default Currency**: Base currency for all pricing (e.g., USD, EUR).
-   **Default Country**: Used to initialize the first shipping region.

### Step 2: Administrative Access
The user inputs the email address for the primary administrator. The frontend sends this to the `/v1/setup/init` endpoint. Upon success, the backend triggers the Auth0 invitation.

### Step 3: Tenant Verification
The wizard displays a confirmation screen. The user is instructed to check their email for the Auth0 invitation and complete the signup process. Once the user logs back in, the frontend verifies the JWT claims to ensure the setup was successful.

## Post-Setup Management

After the initial setup is complete, the `/v1/setup/init` endpoint is locked. Further modifications to the store's identity and configuration must be performed through specialized administrative endpoints.

### Store Info Management
The `GET/PUT /v1/store-info` endpoints allow administrators to update metadata that wasn't part of the core initialization, such as logos, physical addresses, support emails, and social media links. This data is stored as a JSON object in the `config` table under the `store_info` key.

### Stripe Integration
Connecting Stripe is a secondary setup task, handled by `POST /v1/setup/stripe`. This validates the provided secret key against the Stripe API before saving it.

## Database and Migration Maintenance

For development and recovery purposes, Fufuni provides administrative routes to reset the state or manually trigger migrations. These routes require the `admin:database` role, which is typically only granted via a specific JWT claim and not available to standard API keys.

### Resetting the Environment
The `/v1/setup/reset` endpoint wipes all primary data tables. This is used when a developer needs to re-run the initialization wizard from scratch.

### Migration Control
The framework tracks applied schema changes in a `migrations` table.

| Endpoint | Description |
| :--- | :--- |
| `GET /v1/setup/migrations/list` | Returns all applied migrations and their timestamps. |
| `POST /v1/setup/migrations/run` | Triggers the SQLite migration helper to apply pending `.sql` files. |
| `POST /v1/setup/migrations/clean` | Clears the migration history table (use with caution). |

### Migration Query Example

```sql
-- Example of checking for pending migrations in the backend
-- This is often triggered by a simple SELECT 1 on the DB object
SELECT name FROM migrations WHERE name = '0001_initial_schema.sql';
```

When `db.query('SELECT 1')` is called on the initialization helper, the Durable Object checks the filesystem for any `.sql` files not present in the `migrations` table and executes them in sequence.
