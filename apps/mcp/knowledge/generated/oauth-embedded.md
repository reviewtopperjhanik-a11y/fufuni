## Purpose of the Embedded OAuth2 Server

While Fufuni uses Auth0 as the primary identity provider for customer authentication (OpenID Connect), it includes a built-in OAuth2 server to handle **Machine-to-Machine (M2M)** communication and third-party integrations. This allows external services, AI agents, or administrative tools to interact with the Merchant API without requiring a browser-based login flow.

The embedded server is designed for high performance on Cloudflare Workers, utilizing SQLite (via Durable Objects) for client storage and HMAC SHA-256 (HS256) for stateless token verification. It specifically targets the `client_credentials` grant type to facilitate secure merchant-level access.

```typescript
// Example: Distinguishing between Auth0 and Internal OAuth
// Auth0: Customer Identity (Social login, email/pass)
// Embedded OAuth2: Programmatic access (API keys, Integrations)

import { Hono } from 'hono';
import { oauthMiddleware } from '../middleware/oauth';
import { customerAuthMiddleware } from '../middleware/auth';

const app = new Hono();

// This route accepts EITHER a customer session OR an M2M integration token
app.get('/v1/orders', customerAuthMiddleware, oauthMiddleware, (c) => {
  const isMachine = !!c.get('oauth_payload');
  return c.json({ data: [], source: isMachine ? 'api_integration' : 'customer_portal' });
});
```

## Required Configuration: OAUTH_JWT_SECRET

The OAuth2 server requires a dedicated secret key for signing Access Tokens. This secret must be configured in your Cloudflare environment. Without this secret, the server will fail to issue or verify tokens.

To set the secret in production, use the Wrangler CLI:

```bash
# Add the secret to your Cloudflare Worker environment
npx wrangler secret put OAUTH_JWT_SECRET

# Example for local development in .dev.vars
OAUTH_JWT_SECRET="a-very-long-and-random-string-at-least-32-chars"
```

### JWT Signing Algorithm
Fufuni uses **HS256** (HMAC with SHA-256). While Auth0 usually uses RS256 (Asymmetric), HS256 is preferred for the embedded server because it is significantly faster to verify in a serverless environment and reduces the overhead of fetching public keys (JWKS).

## Client Registration and Management

OAuth clients are stored in the `oauth_clients` table. Managing these clients is restricted to admin-level access. When a client is created, the system generates a `client_id` and a `client_secret`. 

**Security Note:** The `client_secret` is hashed using `bcrypt` (or the framework's internal `hashKey` utility) before storage. It is returned in plaintext **only once** during the creation response.

### Admin Endpoints for Client Management

| Method | Endpoint | Description |
| :--- | :--- | :--- |
| `GET` | `/v1/oauth/clients` | List all registered M2M clients |
| `POST` | `/v1/oauth/clients` | Register a new client (Returns plaintext secret) |
| `DELETE` | `/v1/oauth/clients/:id` | Revoke a client and all its permissions |

```typescript
// Implementation snippet for creating a client
import { uuid, now } from '../types';
import { hashKey } from '../middleware/auth';

async function createOAuthClient(db: Database, name: string, scopes: string[]) {
  const clientId = uuid();
  const plaintextSecret = generateRandomString(32); // Helper to generate entropy
  const secretHash = await hashKey(plaintextSecret);

  await db.run(
    `INSERT INTO oauth_clients (id, client_id, secret_hash, name, granted_scopes, created_at)
     VALUES (?, ?, ?, ?, ?, ?)`,
    [uuid(), clientId, secretHash, name, JSON.stringify(scopes), now()]
  );

  return {
    client_id: clientId,
    client_secret: plaintextSecret, // RETURNED ONLY ONCE
    name,
    scopes
  };
}
```

## Token Request (Client Credentials Grant)

Third-party integrations exchange their `client_id` and `client_secret` for a JWT access token via the `/v1/oauth/token` endpoint. 

### Request Format
The endpoint expects a `POST` request with a JSON body.

```bash
curl -X POST https://api.fufuni.store/v1/oauth/token \
  -H "Content-Type: application/json" \
  -d '{
    "grant_type": "client_credentials",
    "client_id": "client_789...",
    "client_secret": "sec_456...",
    "scope": "read:products write:orders"
  }'
```

### Response Format
Upon successful verification, the server returns a Bearer token.

```json
{
  "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "scope": "read:products write:orders"
}
```

## Token Structure and Claims

The issued Access Tokens are standard JWTs. They contain claims that identify the client and define the boundaries of their access.

### Standard Claims
- `iss` (Issuer): The origin URL of your merchant API.
- `sub` (Subject): The `client_id` of the integration.
- `exp` (Expiration): Unix timestamp (default is `now + 3600s`).
- `iat` (Issued At): Unix timestamp of creation.
- `scope`: A space-delimited string of granted permissions.

```typescript
// Example of the payload generated by the server
interface OAuthJWTPayload {
  iss: string;
  sub: string; // client_id
  scope: string;
  iat: number;
  exp: number;
}

// Logic for generating the token
import { sign } from 'hono/jwt';

async function generateToken(client: any, requestedScopes: string, secret: string) {
  const payload: OAuthJWTPayload = {
    iss: 'fufuni-merchant-api',
    sub: client.client_id,
    scope: requestedScopes,
    iat: Math.floor(Date.now() / 1000),
    exp: Math.floor(Date.now() / 1000) + 3600,
  };
  
  return await sign(payload, secret);
}
```

## Scope System and Permission Validation

The Fufuni scope system follows a hierarchical "subset" validation model. When a client requests tokens, the `requested_scopes` must be a subset of the `granted_scopes` assigned to that client record in the database.

### Available Scopes
The framework supports the following granular scopes for API access:

- `read:products`: View product catalogs and inventory.
- `write:products`: Create or update product details.
- `read:orders`: Access order history and status.
- `write:orders`: Update order fulfillment status.
- `read:customers`: View customer profiles (excluding sensitive payment data).

### Scope Validation Logic
```typescript
function validateScopes(requested: string, assigned: string[]): boolean {
  const requestedList = requested.split(' ').filter(Boolean);
  return requestedList.every(s => assigned.includes(s));
}

// Usage in /token endpoint
if (!validateScopes(body.scope, JSON.parse(client.granted_scopes))) {
  throw ApiError.invalidRequest('Requested scopes exceed client permissions');
}
```

## Token Verification via oauthMiddleware

To protect a route with OAuth2, you must apply the `oauthMiddleware`. This middleware extracts the Bearer token from the `Authorization` header, verifies the HS256 signature using `OAUTH_JWT_SECRET`, and checks if the required scope is present for the specific endpoint.

### Middleware Implementation
The middleware attaches the decoded payload to the Hono context, allowing downstream handlers to know which client is making the request.

```typescript
import { verify } from 'hono/jwt';
import { HonoEnv } from '../types';

export const oauthMiddleware = async (c: any, next: () => Promise<void>) => {
  const authHeader = c.req.header('Authorization');
  if (!authHeader?.startsWith('Bearer ')) {
    return await next(); // Pass through to potentially allow Auth0 middleware
  }

  const token = authHeader.split(' ')[1];
  try {
    const payload = await verify(token, c.env.OAUTH_JWT_SECRET);
    c.set('oauth_payload', payload);
    await next();
  } catch (e) {
    return c.json({ error: 'invalid_token' }, 401);
  }
};
```

### Route-Level Scope Protection
You can further restrict routes by checking the `scope` claim within the handler:

```typescript
app.post('/v1/products', oauthMiddleware, async (c) => {
  const payload = c.get('oauth_payload');
  
  if (!payload || !payload.scope.includes('write:products')) {
    return c.json({ error: 'insufficient_scope' }, 403);
  }

  // Proceed with product creation...
  return c.json({ success: true });
});
```

### Comparison Summary: Auth0 vs. Embedded OAuth2

| Feature | Auth0 (Standard) | Embedded OAuth2 (This Ref) |
| :--- | :--- | :--- |
| **Primary User** | Shoppers (Customers) | API Integrations / AI Agents |
| **Flow Type** | Authorization Code + PKCE | Client Credentials |
| **Storage** | External (Auth0 Cloud) | Internal (Durable Object SQLite) |
| **Algorithm** | RS256 (Asymmetric) | HS256 (Symmetric) |
| **Secrets** | Client ID / Domain | `OAUTH_JWT_SECRET` |
| **UI** | Hosted Login Pages | Headless / JSON API |
