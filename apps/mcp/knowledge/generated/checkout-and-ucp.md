## Universal Commerce Protocol (UCP)

The Universal Commerce Protocol in Fufuni serves as a generic, platform-agnostic bridge between the frontend and the backend commerce logic. Unlike the final checkout process, UCP is stateless regarding payment; it is designed for cart validation, price resolution across multiple currencies, and tax estimation. 

You should call the UCP endpoint whenever the cart state changes (item addition, quantity updates, or discount code entry). This ensures the frontend displays a "Source of Truth" regarding totals before the user enters the payment funnel.

### UCP Endpoint and Payload

The UCP implementation resides under `POST /v1/ucp`. It accepts a list of line items and returns an enriched envelope containing resolved prices, taxes, and grand totals.

```typescript
// Example of a UCP request from the frontend or an external agent
const validateCart = async (items: { id: string; quantity: number }[], currency: string) => {
  const response = await fetch('https://api.fufuni.com/v1/ucp', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({
      line_items: items.map(i => ({ item: { id: i.id }, quantity: i.quantity })),
      currency: currency,
    }),
  });

  if (!response.ok) {
    const error = await response.json();
    throw new Error(error.message);
  }

  return await response.json();
};
```

## Stripe Checkout Flow

The `POST /v1/checkout` endpoint is the terminal step of the purchasing process. Unlike UCP, this endpoint is strictly integrated with Stripe and is protected by the `customerAuthMiddleware`. It requires a valid Auth0 JWT to associate the resulting order with a specific customer identity.

### Execution Steps
1.  **Authentication**: Validates the Auth0 token and extracts the `customerId`.
2.  **Inventory Locking**: Performs a synchronous check against the Durable Object (SQLite).
3.  **Order Creation**: A record is inserted into the `orders` table with a `pending` status.
4.  **Stripe Initialization**: Depending on the cart configuration, it initializes either a `PaymentIntent` (for direct elements) or a `CheckoutSession` (for redirected 3DS flows).
5.  **Response**: Returns the necessary identifiers for the frontend to complete the transaction.

### Implementation Example

## Inventory Validation and Synchronization

Fufuni handles inventory with high consistency by executing checks within the Durable Object's SQLite transaction. This prevents race conditions where two customers might attempt to purchase the last item simultaneously.

### The 409 Conflict Error
If the requested quantity for any SKU in the cart exceeds the `available` count (`on_hand - reserved`), the endpoint immediately aborts. No Stripe session is created, and no order record is persisted.

```typescript
// Logic typically found in lib/inventory.ts or the DO handler
async function reserveInventory(db: Database, sku: string, qty: number) {
  const result = await db.run(
    `UPDATE inventory 
     SET reserved = reserved + ? 
     WHERE sku = ? AND (on_hand - reserved) >= ?`,
    [qty, sku, qty]
  );

  if (result.changes === 0) {
    // This triggers the 409 Conflict response in the route handler
    throw ApiError.conflict(`Insufficient inventory for SKU: ${sku}`);
  }
}
```

## Tax Computation inside Checkout

Tax calculation in Fufuni is dynamic and depends on the `region_id` associated with the cart or the customer's shipping address. The system supports both tax-inclusive (TTC) and tax-exclusive (HT) pricing models.

### Integration with Stripe
When generating the Stripe payload, the system maps internal `tax_rates` to Stripe's line items.
- If the region is **Tax Inclusive**: The unit price sent to Stripe is adjusted downward to account for the tax already included, while the tax itself is added as a separate line item or identified via `tax_code` to ensure Stripe's calculations match the Fufuni internal totals exactly.
- If the region is **Tax Exclusive**: The tax amount is calculated and added as a separate `unit_amount` line item named after the tax (e.g., "VAT 20%").

```typescript
// Calculation fragment
const { taxes, itemRates } = await calculateCartTaxes(db, cartId, countryCode);

// Logic to balance rounding errors for Stripe
const totalTTC = subtotal + shipping + taxes.reduce((a, b) => a + b.amount_cents, 0);
// Any difference between (Sum of Lines) and (Order Total) is injected into the final tax line
```

## Stripe Integration: Intent vs Session

Fufuni utilizes two primary Stripe flows to handle different frontend requirements:

| Flow Type | Use Case | Return Values |
| :--- | :--- | :--- |
| **PaymentIntent** | Used for "Headless" checkouts where the credit card fields are hosted directly on the Fufuni React frontend (Stripe Elements). | `clientSecret` |
| **Checkout Session** | Used for redirected checkouts or when 3D Secure / Local Payment Methods (iDEAL, Klarna) require a Stripe-hosted UI. | `sessionId`, `checkout_url` |

Fufuni does **not** use the official Stripe Node.js SDK, as it is too heavy for Cloudflare Workers' startup time and often relies on Node-specific globals. Instead, Fufuni uses a custom `stripe.ts` utility that performs `fetch()` calls directly against the Stripe REST API.

## Stripe Webhook Events

The webhook handler at `POST /v1/webhooks/stripe` is the final arbiter of order state. It transitions orders from `pending` to their terminal or actionable statuses.

### Handled Events and Side Effects
- `payment_intent.succeeded`:
    - Updates order status to `paid`.
    - Converts `reserved` inventory to a permanent deduction (decrements `on_hand`).
    - Triggers confirmation emails.
- `payment_intent.payment_failed`:
    - Updates order status to `failed`.
    - Releases `reserved` inventory back to `available`.
- `checkout.session.completed`:
    - Handles the fulfillment of sessions used for 3DS or external redirects.
    - Synchronizes the `stripe_checkout_session_id` with the internal `orderId`.

```typescript
// Webhook event routing
switch (event.type) {
  case 'payment_intent.succeeded':
    await db.run(
      "UPDATE orders SET status = 'paid', updated_at = ? WHERE stripe_payment_intent_id = ?",
      [now(), event.data.object.id]
    );
    // Finalize inventory: subtract reserved from on_hand
    break;
  case 'payment_intent.payment_failed':
    await db.run(
      "UPDATE orders SET status = 'failed' WHERE stripe_payment_intent_id = ?",
      [event.data.object.id]
    );
    break;
}
```

## Required Wrangler Secrets

For the Stripe integration to function within the Cloudflare Workers environment, you must configure specific environment variables. Note that these should be added via `wrangler secret put` and not stored in a plain `.dev.vars` or `.env` file in production.

### Essential Secrets

1.  `STRIPE_SECRET_KEY`: Your restricted or standard secret key from the Stripe Dashboard.
2.  `STRIPE_WEBHOOK_SECRET`: The signing secret (starts with `whsec_`) used to verify that incoming webhook requests actually originate from Stripe.

```bash
# Setting secrets for the merchant application
wrangler secret put STRIPE_SECRET_KEY --env production
wrangler secret put STRIPE_WEBHOOK_SECRET --env production
```

### Accessing Secrets in Code
In the Hono environment, these secrets are available via `c.env`:

