## The Triple-Entry Schema Pattern

Fufuni uses a "Triple-Entry" system for database schema management. Because Fufuni runs on Cloudflare Durable Objects with SQLite, we must handle two scenarios: the creation of a brand-new Durable Object instance (which needs the full schema immediately) and the upgrade of existing instances (which need incremental migrations).

Every database change must be implemented in three places:
1.  **The `SCHEMA` constant in `do.ts`**: Contains the full, up-to-date DDL. New Durable Objects use this to build their entire database at once.
2.  **A Migration Block in `ensureInitialized()`**: A conditional block in the `do.ts` file that applies changes to existing instances and records the migration as "applied" in the `migrations` table.
3.  **A Migration SQL File**: A standalone `.sql` file in `apps/merchant/migrations/` used for documentation and forward-compatibility with external tooling (like D1 or local SQLite CLI).

## Step-by-Step Migration Guide

### 1. Create the SQL Migration File
Navigate to `apps/merchant/migrations/` and identify the next sequence number. If the last file was `034-add-email-settings.sql`, your new file will be `035-add-tags.sql`.

```sql
-- apps/merchant/migrations/035-add-tags.sql
-- Migration 035: Product Tags support
-- This allows categorizing products with arbitrary string tags for filtering.

PRAGMA foreign_keys = ON;

CREATE TABLE IF NOT EXISTS product_tags (
  id         TEXT PRIMARY KEY,
  product_id TEXT NOT NULL REFERENCES products(id) ON DELETE CASCADE,
  tag_name   TEXT NOT NULL,
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  UNIQUE(product_id, tag_name)
);

CREATE INDEX IF NOT EXISTS idx_product_tags_name ON product_tags(tag_name);

-- Add a denormalized tag column to products for faster preview
ALTER TABLE products ADD COLUMN tags_csv TEXT;
```

### 2. Register the Migration in `do.ts`
The `ensureInitialized()` method is called before any SQL operation to ensure the local SQLite database is up to date. Durable Object SQL operations are **synchronous**. You must check if the migration has already been applied by querying the `migrations` table.

```typescript
// Inside apps/merchant/src/do.ts -> MerchantDO class

private ensureInitialized() {
  if (this.initialized) return;

  // 1. Initial Schema Setup (for new DOs)
  this.sql.exec(SCHEMA);

  // 2. Incremental Migrations (for existing DOs)
  
  // Example Migration 035 logic
  const migration035 = this.sql.exec(
    "SELECT name FROM migrations WHERE name = '035-add-tags'"
  ).one();

  if (!migration035) {
    console.log("Applying migration 035-add-tags...");
    // We use a transaction-like block via multiple exec calls or a multi-line string
    this.sql.exec(`
      CREATE TABLE IF NOT EXISTS product_tags (
        id         TEXT PRIMARY KEY,
        product_id TEXT NOT NULL REFERENCES products(id) ON DELETE CASCADE,
        tag_name   TEXT NOT NULL,
        created_at TEXT NOT NULL DEFAULT (datetime('now')),
        UNIQUE(product_id, tag_name)
      );
      CREATE INDEX IF NOT EXISTS idx_product_tags_name ON product_tags(tag_name);
    `);
    
    // Check if column exists before adding (to ensure idempotency)
    try {
      this.sql.exec("ALTER TABLE products ADD COLUMN tags_csv TEXT;");
    } catch (e) {
      // Ignore "duplicate column name" errors if the SCHEMA constant already ran
      console.warn("Column tags_csv might already exist, skipping ALTER TABLE");
    }

    // Record that migration is applied
    this.sql.exec("INSERT INTO migrations (name) VALUES ('035-add-tags')");
  }

  this.initialized = true;
}
```

## Data Type Conventions

Fufuni follows strict SQLite type mappings to ensure consistency across the framework and the frontend:

| Logical Type | SQLite Type | Notes |
| :--- | :--- | :--- |
| **UUIDs / IDs** | `TEXT` | Store as strings (e.g., `prod_123`). |
| **Dates / Times** | `TEXT` | Use ISO-8601 strings. Default: `(datetime('now'))`. |
| **Booleans** | `INTEGER` | Use `0` for false, `1` for true. |
| **Currency / Cents** | `INTEGER` | Never use FLOAT for money. Store as cents (e.g., 1000 = $10.00). |
| **Decimals / Rates** | `REAL` | Used for tax percentages or star ratings (e.g., 4.5). |
| **JSON Objects** | `TEXT` | Store as stringified JSON (e.g., `metadata`, `taxes_json`). |

### Example: Using Booleans and Cents
```sql
CREATE TABLE IF NOT EXISTS promotions (
  id TEXT PRIMARY KEY,
  is_active INTEGER NOT NULL DEFAULT 0, -- Boolean
  discount_cents INTEGER NOT NULL,      -- Money
  minimum_spend_cents INTEGER DEFAULT 0 -- Money
);
```

## Migration Idempotency and Safety

In a distributed environment like Cloudflare Workers, code can restart or fail at any time. Your migrations **must** be idempotent.

### Use `IF NOT EXISTS`
Always use the `IF NOT EXISTS` clause for `CREATE TABLE` and `CREATE INDEX`. This prevents the migration from crashing if the table was partially created in a previous failed attempt.

### Handling `ALTER TABLE`
SQLite does not support `IF NOT EXISTS` for `ADD COLUMN`. If a migration fails halfway through, a subsequent run might try to add the same column again.

The safest pattern is to wrap `ALTER TABLE` in a `try/catch` block within the migration logic or query the `pragma_table_info` to check for column existence.

```typescript
// Safe column addition pattern
const tableInfo = this.sql.exec("PRAGMA table_info(products)").toArray();
const columnExists = tableInfo.some(col => col.name === 'new_feature_enabled');

if (!columnExists) {
  this.sql.exec("ALTER TABLE products ADD COLUMN new_feature_enabled INTEGER DEFAULT 0");
}
```

### The `migrations` Table
The framework maintains a `migrations` table automatically. Every block in `ensureInitialized()` must check this table before executing. The name used in the `INSERT` statement must match the filename stem (the part before `.sql`) exactly.

## Pitfalls to Avoid

### 1. Asynchronous Confusion
Do **not** use `await` or `db.run()` inside `ensureInitialized()`. The `this.sql` interface provided by Durable Objects is synchronous. Using asynchronous patterns here will cause race conditions where queries are executed before the schema is ready.

### 2. Changing Past Migrations
Never edit a migration file (e.g., `027-categories.sql`) once it has been merged and deployed. If you forgot a column in the "categories" table, create a new migration `036-add-meta-to-categories.sql`. Durable Objects that have already applied `027` will never see your changes if you edit the old file.

### 3. Naming Conflicts
Ensure the name in `INSERT INTO migrations (name) VALUES ('...')` matches the file name exactly. If they differ, developers using automated tools to sync local databases with Durable Objects will experience schema drift.

### 4. Missing the SCHEMA Constant
If you add a migration but forget to update the `SCHEMA` constant, new stores will be created with an outdated schema. They will then immediately run the migration logic, which works, but is inefficient and can lead to bugs if the migration logic assumes certain table states that only exist in older versions.

### 5. Foreign Key Constraints
SQLite enforces foreign keys only if `PRAGMA foreign_keys = ON;` is executed. While the framework handles this, always ensure your migration files include this PRAGMA at the top if they are meant to be run manually against a D1 instance or local file.

```sql
-- Proper header for migration files
PRAGMA foreign_keys = ON;
-- Your SQL follows...
```
