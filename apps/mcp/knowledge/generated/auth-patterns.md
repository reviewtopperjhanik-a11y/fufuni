## Supported Token Formats

The Fufuni framework provides a polymorphic authentication layer through `authMiddleware`. It distinguishes between browser-based users, automated scripts using API keys, and third-party integrations using OAuth.

| Token Type | Identification Logic | Storage / Verification |
| :--- | :--- | :--- |
| **Auth0 JWT** | 3-part dot-separated string (header.payload.signature) | Verified against Auth0 JWKS using `AUTH0_DOMAIN`. |
| **Admin API Key** | Starts with `sk_` prefix | Hashed and compared against the `api_keys` table. |
| **OAuth Token** | 64-character lowercase hexadecimal string | Hashed and compared against the `oauth_tokens` table. |

### Implementation: Key Hashing and Generation
API keys are never stored in plain text. The system uses SHA-256 via the Web Crypto API for verification.

```typescript
import { hashKey, generateApiKey } from './middleware/auth';

// Generating a new secret key for a merchant
const rawKey = generateApiKey('sk'); 
// Output: sk_3f2a... (48 hex chars)

// Verification logic used inside middleware
const tokenFromHeader = "sk_...";
const hashedToken = await hashKey(tokenFromHeader);

// Database query example
// SELECT role FROM api_keys WHERE key_hash = ?
```

## Backend RBAC Guards and AuthRoles

The `AuthRole` determines what a requester is allowed to do. When an Auth0 JWT is processed, permissions (claims) are mapped to internal roles.

### Role Mapping Table

| AuthRole | Required Permission (Auth0) | Default Permission String | Typical Use Case |
| :--- | :--- | :--- | :--- |
| `admin` | `ADMIN_STORE_PERMISSION` | `admin:store` | Managing products, orders, and settings. |
| `authadmin` | `ADMIN_AUTH0_PERMISSION` | `auth0:admin:api` | Managing user permissions and fetching M2M tokens. |
| `databaseadmin` | `DATABASE_PERMISSION` | `admin:database` | Raw SQL execution or database maintenance. |
| `aiadmin` | `AI_PERMISSION` | `ai:api` | Configuring LLM providers and translation settings. |
| `mail` | `MAIL_PERMISSION` | `mail:api` | Accessing transactional email logs and templates. |
| `customer` | None (valid JWT only) | N/A | Accessing personal profile and order history. |
| `oauth` | N/A | N/A | External integrations via `oauth_tokens` table. |

### Guard Usage in Hono Routes

Guards are applied as middleware before the final route handler. Multiple guards can be chained.

```typescript
import { Hono } from 'hono';
import { authMiddleware, adminOnly, aiAccessOnly } from '../middleware/auth';
import type { HonoEnv } from '../types';

const app = new Hono<HonoEnv>();

// 1. Apply base auth to verify the token exists and is valid
app.use('/v1/admin/*', authMiddleware);

// 2. Protect specific sub-resources with RBAC guards
app.get('/v1/admin/products', adminOnly, async (c) => {
  return c.json({ products: [] });
});

app.post('/v1/admin/ai/translate', adminOnly, aiAccessOnly, async (c) => {
  const { text } = await c.req.json();
  // Handler logic...
  return c.json({ translated: "..." });
});
```

## SuperAdmin and Management API Tokens

The `superAdminOnly` guard (checking for the `authadmin` role) is primarily used to protect sensitive infrastructure routes. A key example is the Management API proxy, which handles Auth0 Machine-to-Machine (M2M) tokens.

Fufuni caches these tokens to avoid exceeding Auth0's rate limits for M2M token generation.

### Guarding the Management Token Proxy
```typescript
import { Hono } from 'hono';
import { authMiddleware, superAdminOnly } from '../middleware/auth';
import { ApiError } from '../types';

const auth0Api = new Hono<HonoEnv>();

// Only users with 'auth0:admin:api' permission can reach this
auth0Api.get('/token', authMiddleware, superAdminOnly, async (c) => {

    "SELECT token FROM internal_cache WHERE key = 'auth0_m2m' AND expires_at > ?",
    [new Date().toISOString()]
  );
  
  if (cachedToken.length === 0) {
    // Logic to refresh token from Auth0 via Client Credentials flow
  }

  return c.json({ access_token: cachedToken[0].token });
});
```

## Customer Authentication

The `customerAuthMiddleware` is designed for public storefront APIs where users are logged in but do not have administrative privileges. It explicitly rejects API keys (`sk_`, `pk_`) to ensure only browser-initiated JWT sessions are accepted.

### Scoped Customer Access
```typescript
import { Hono } from 'hono';
import { customerAuthMiddleware } from '../middleware/customer-auth';
import { getDb } from '../db';

const me = new Hono<HonoEnv>();

// Protect all routes in this router
me.use('*', customerAuthMiddleware);

me.get('/profile', async (c) => {
  const auth = c.get('auth');
  const db = getDb(c.var.db);

  // Extract Auth0 'sub' (subject) to find the local customer record
  const customer = await db.query(
    "SELECT * FROM customers WHERE auth0_sub = ? LIMIT 1",
    [auth.sub]
  );

  return c.json(customer[0] || { email: auth.email, sub: auth.sub });
});
```

## OAuth Scope Validation

When using hexadecimal OAuth tokens (role `oauth`), permissions are checked via "scopes" rather than Auth0 permissions. The `requireScope` factory creates dynamic middleware for these checks.

### Protecting OAuth Endpoints
```typescript
import { Hono } from 'hono';
import { authMiddleware, requireScope } from '../middleware/auth';

const externalApi = new Hono<HonoEnv>();

externalApi.get(
  '/inventory',
  authMiddleware, 
  requireScope('inventory:read', 'products:read'), 
  async (c) => {
    const auth = c.get('auth');
    // For OAuth tokens, oauthScopes is populated from the database
    console.log('Authorized scopes:', auth.oauthScopes);
    return c.json({ stock: 100 });
  }
);
```

## Frontend Security Patterns

Fufuni uses React 19 and `@auth0/auth0-react`. Security is handled through high-level components and hooks that react to the user's authentication state and permission set.

### Guarding Routes and UI Elements

| Component / Hook | Purpose |
| :--- | :--- |
| `AuthenticationGuard` | Replaces a page component. Redirects to Auth0 login if the user is not authenticated. |
| `AuthenticationGuardWithPermission` | Conditional wrapper. Only renders `children` if the user has a specific Auth0 permission. |
| `useAuth()` | Provides `isAuthenticated`, `user`, and `loginWithRedirect`. Use for basic login state. |
| `useSecuredApi()` | Provides `hasPermission(perm)`. Use for logic-based permission checks inside components. |

### Example: Component-Level Permissions
```tsx
import { AuthenticationGuardWithPermission } from "@/components/auth/AuthenticationGuardWithPermission";
import { useSecuredApi } from "@/hooks/useSecuredApi";
import { Button } from "@heroui/react";

export const ProductSettings = () => {
  const { hasPermission } = useSecuredApi();

  return (
    <div>
      <h3>General Settings</h3>
      
      {/* Conditional UI based on permission */}
      <AuthenticationGuardWithPermission 
        permission="admin:store" 
        fallback={<p>You do not have permission to delete products.</p>}
      >
        <Button color="danger">Delete Product</Button>
      </AuthenticationGuardWithPermission>

      {/* Logic-based permission check */}
      {hasPermission("admin:database") && (
        <section className="mt-4 p-4 border-red-500 border">
          <h4>Advanced Database Actions</h4>
        </section>
      )}
    </div>
  );
};
```

## User and Permission Management

While Auth0 is the source of truth, Fufuni provides an administrative interface to manage users without leaving the storefront application. The `UsersAndPermissionsPage` leverages the cached Management API tokens to perform CRUD operations on Auth0 users.

### The UsersAndPermissionsPage Logic
This page (located at `/admin/users-and-permissions`) allows administrators to:
1. List all users in the Auth0 tenant.
2. View specific roles and permissions assigned to a user.
3. Add or remove the `admin:store`, `ai:api`, or other permissions defined in the framework.

```tsx
// Inside UsersAndPermissionsPage (Simplified Logic)
import { useAuth0Management } from "@/hooks/useAuth0Management";

export const PermissionToggle = ({ userId, permission }: { userId: string, permission: string }) => {
  const { assignPermission, removePermission, userPermissions } = useAuth0Management(userId);
  
  const isGranted = userPermissions.some(p => p.permission_name === permission);

  const handleToggle = async () => {
    if (isGranted) {
      await removePermission(permission);
    } else {
      await assignPermission(permission);
    }
  };

  return (
    <Switch isSelected={isGranted} onValueChange={handleToggle}>
      {permission}
    </Switch>
  );
};
```

## Summary of Identity Flows

1.  **Browser Login**: User hits `LoginButton` -> Redirects to Auth0 -> Returns to app with JWT -> `authMiddleware` validates JWT -> `c.var.auth` populated with roles based on permissions.
2.  **API Client**: Client sends `Authorization: Bearer sk_...` -> `authMiddleware` hashes key -> Database lookup in `api_keys` -> `c.var.auth` populated with the role stored in DB.
3.  **Third-Party Integration**: Client sends `Authorization: Bearer <64_hex_chars>` -> `authMiddleware` hashes key -> Database lookup in `oauth_tokens` -> `c.var.auth` populated with `role: 'oauth'` and scopes from DB.
