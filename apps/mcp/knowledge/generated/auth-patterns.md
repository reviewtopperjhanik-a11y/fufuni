## Supported Token Types

The Fufuni framework provides a unified authentication entry point via `authMiddleware`. It distinguishes between three distinct token formats to support browser-based administrators, automated scripts, and third-party integrations.

| Token Type | Identification | Storage/Verification | Use Case |
| :--- | :--- | :--- | :--- |
| **Auth0 JWT** | Three-part dot-separated string | Verified against Auth0 JWKS (Tenant) | Browser-based Admin Dashboard users. |
| **Admin API Key** | Starts with `sk_` | SHA-256 hash lookup in `api_keys` table | Backend-to-backend automation, CLI tools. |
| **OAuth Token** | 64-char hex string | SHA-256 hash lookup in `oauth_tokens` table | Scoped third-party application access. |

```typescript
// Example of how authMiddleware identifies a JWT vs an API key
const token = authHeader.slice(7);

if (token.split('.').length === 3 && !token.startsWith('sk_')) {
  // Logic: Treat as Auth0 JWT
  const payload = await verifyAuth0Jwt(token, domain, audience);
  // ... map permissions to roles
} else if (token.startsWith('sk_')) {
  // Logic: Treat as Internal Admin API Key
  const keyHash = await hashKey(token);
  const result = await db.query('SELECT role FROM api_keys WHERE key_hash = ?', [keyHash]);
}
```

## Authentication Roles (AuthRole)

Role-Based Access Control (RBAC) in Fufuni is derived primarily from Auth0 permissions when using JWTs, or assigned statically in the database for API keys. The `AuthRole` type defines the possible security contexts:

- `public`: Unauthenticated request or using a public key (`pk_`).
- `admin`: Default admin role. Requires the `admin:store` permission (configurable via `ADMIN_STORE_PERMISSION`).
- `authadmin`: Superadmin role. Requires `auth0:admin:api` permission. Grants access to Management API token generation.
- `databaseadmin`: Requires `admin:database`. Allows direct SQLite query execution.
- `aiadmin`: Requires `ai:api`. Allows modification of AI translation parameters.
- `mail`: Requires `mail:api`. Allows access to transactional email logs and triggers.
- `customer`: Verified Auth0 user without administrative permissions. Used for `/v1/me/*` routes.
- `oauth`: Scoped access for third-party tokens.

### Role Assignment Mapping

```typescript
// Mapping logic within authMiddleware for Auth0 JWTs
const perms = payload.permissions as string[];
const roles: AuthRole[] = [];

if (perms.includes('admin:store')) roles.push('admin');
if (perms.includes('auth0:admin:api')) roles.push('authadmin');
if (perms.includes('admin:database')) roles.push('databaseadmin');

c.set('auth', {
  role: roles.length === 1 ? roles[0] : roles,
  // ...
});
```

## Backend RBAC Guards

Guards are Hono middleware functions that intercept requests after `authMiddleware` has populated the context. They ensure the authenticated entity possesses the required role.

| Guard | Required Role | Typical Use Case |
| :--- | :--- | :--- |
| `adminOnly` | `admin` | Managing products, categories, and orders. |
| `superAdminOnly` | `authadmin` | Accessing Auth0 Management tokens, managing users. |
| `databaseAdminOnly` | `databaseadmin` | Debugging with raw SQL via the `/v1/db/query` endpoint. |
| `aiAccessOnly` | `aiadmin` | Configuring Groq/OpenAI models and system prompts. |
| `mailAccessOnly` | `mail` | Viewing Mailgun logs or re-sending order confirmations. |
| `validJwtAuthOnly` | Any JWT | Verifying a user is logged in via Auth0, regardless of perms. |

### Implementation Example: Protecting Admin Routes

```typescript
import { Hono } from 'hono';
import { authMiddleware, adminOnly, superAdminOnly } from './middleware/auth';
import { type HonoEnv } from './types';

const app = new Hono<HonoEnv>();

// 1. Apply base authentication
app.use('/v1/admin/*', authMiddleware);

// 2. Restrict to general admins
app.get('/v1/admin/products', adminOnly, async (c) => {
  return c.json({ products: [] });
});

// 3. Restrict to super admins (Auth0 management)
app.get('/v1/__auth0/token', superAdminOnly, async (c) => {
  // This endpoint returns a cached Management API token
  // to prevent hitting Auth0 M2M quotas.
  const token = await getManagementToken(c.env);
  return c.json({ access_token: token });
});
```

## Customer Authentication

For customer-facing routes (e.g., viewing personal order history or updating a profile), Fufuni uses `customerAuthMiddleware`. Unlike `authMiddleware`, it **rejects** API keys and **does not** require specific administrative permissions.

It extracts the following claims from the Auth0 JWT:
- `sub`: The Auth0 user ID (e.g., `auth0|12345`).
- `email`: The user's primary email.
- `user_metadata`: Custom fields stored in Auth0.

```typescript
// apps/merchant/src/routes/me.ts
import { customerAuthMiddleware } from '../middleware/customer-auth';

const me = new Hono<HonoEnv>();

me.use('*', customerAuthMiddleware);

me.get('/', async (c) => {
  const auth = c.get('auth');
  const db = getDb(c.var.db);
  
  // Resolve local customer record using Auth0 'sub'
  const customer = await db.query(
    'SELECT * FROM customers WHERE auth0_sub = ? LIMIT 1',
    [auth.sub]
  );
  
  return c.json(customer[0]);
});
```

## Frontend Security Guards

The React frontend utilizes the `useAuth` and `useSecuredApi` hooks to handle conditional UI and route protection.

### 1. Page-Level Protection
The `AuthenticationGuard` component wraps a route's main component. If the user is not logged in, they are automatically redirected to the Auth0 login page.

```typescript
// apps/frontend/src/routes.tsx
import { AuthenticationGuard } from './components/auth/AuthenticationGuard';
import { ProductsPage } from './pages/ProductsPage';

const routes = [
  {
    path: '/admin/products',
    element: <AuthenticationGuard component={ProductsPage} />,
  },
];
```

### 2. Permission-Based UI (RBAC)
To hide specific parts of the UI (like a "Delete" button) based on permissions, use `AuthenticationGuardWithPermission`.

```tsx
import { AuthenticationGuardWithPermission } from './components/auth/AuthenticationGuardWithPermission';

export function ProductTable({ product }) {
  return (
    <div>
      <ViewButton id={product.id} />
      
      <AuthenticationGuardWithPermission 
        permission="admin:store" 
        fallback={<p>You cannot edit products</p>}
      >
        <EditButton id={product.id} />
      </AuthenticationGuardWithPermission>
    </div>
  );
}
```

### 3. Verification Hooks
- `useAuth()`: Provides `isAuthenticated` (boolean) and `user` object. Use for synchronous state checks.
- `useSecuredApi()`: Provides `hasPermission(perm: string)`. This is an **asynchronous** check that inspects the actual Access Token claims.

```typescript
const { hasPermission } = useSecuredApi();
const [canQuery, setCanQuery] = useState(false);

useEffect(() => {
  async function check() {
    const allowed = await hasPermission('admin:database');
    setCanQuery(allowed);
  }
  check();
}, []);
```

## Administrative Identity Management

Fufuni allows administrators to manage users and their permissions directly within the storefront UI via the `UsersAndPermissionsPage` (`/admin/users-and-permissions`).

This page interfaces with the backend `/v1/__auth0/*` routes. Because it uses the `superAdminOnly` guard, it can request the Management API token to:
1. List all users in the Auth0 tenant.
2. Assign or remove permissions (e.g., adding `ai:api` to a specific user).
3. Block/unblock users.

This ensures that daily administrative tasks do not require access to the Auth0 Dashboard, centralizing the merchant experience.

### Provisioning the Identity Provider
To set up the necessary Auth0 structure, the framework includes a provisioning script that creates the API, the application, and the standard permission set.


This script automates:

- Registration of standard permissions (`admin:store`, `ai:api`, etc.).
- Setup of Auth0 Actions to inject permissions into the Access Token.
