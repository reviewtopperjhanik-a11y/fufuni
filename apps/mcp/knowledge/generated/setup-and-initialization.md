## Checking Initialization Status

The Fufuni backend provides a specific endpoint to determine if the store has already been configured. This is primarily used by the frontend router to decide whether to redirect the user to the Setup Wizard or the Dashboard.

The logic for `GET /v1/setup/status` checks for the existence of an administrator record in the SQLite database (Durable Object). If at least one admin exists, the store is considered `initialized`.

```typescript
import { OpenAPIHono, createRoute, z } from '@hono/zod-openapi';
import { getDb } from '../db';
import type { HonoEnv } from '../types';

const statusRoute = createRoute({
  method: 'get',
  path: '/v1/setup/status',
  tags: ['Setup'],
  summary: 'Check if store is initialized',
  responses: {
    200: {
      content: {
        'application/json': {
          schema: z.object({
            initialized: z.boolean(),
          }),
        },
      },
      description: 'Initialization status',
    },
  },
});

const app = new OpenAPIHono<HonoEnv>();

app.openapi(statusRoute, async (c) => {
  const db = getDb(c.var.db);
  
  // Check for existing admin user
  const admin = await db.query('SELECT id FROM users WHERE role = "admin" LIMIT 1');
  const initialized = admin.length > 0;

  return c.json({ initialized }, 200);
});
```

The frontend React application uses a high-level guard component or a loader in the router to check this status. If `initialized` is `false`, the user is force-redirected to `/setup`.

## The First-Run Initialization Endpoint

The `POST /v1/setup/init` endpoint is the gateway to creating a new Fufuni instance. It performs several critical operations in a single transaction: creating the initial admin user, setting up basic store information, and defining the default region and currency.

### Idempotency and Guards
This endpoint implements a strict 409 Conflict guard. If the database already contains an administrator, the request is rejected immediately. This prevents malicious or accidental re-initialization of an existing store.

```typescript
import { createRoute, z } from '@hono/zod-openapi';
import { ApiError, now } from '../types';
import { getDb } from '../db';

const SetupInitBody = z.object({
  adminEmail: z.string().email(),
  storeName: z.string().min(1),
  defaultCurrency: z.string().length(3),
  defaultCountryCode: z.string().length(2),
}).openapi('SetupInitBody');

const initRoute = createRoute({
  method: 'post',
  path: '/v1/setup/init',
  tags: ['Setup'],
  request: {
    body: { content: { 'application/json': { schema: SetupInitBody } } },
  },
  responses: {
    200: { content: { 'application/json': { schema: z.object({ ok: z.literal(true) }) } }, description: 'Success' },
    409: { content: { 'application/json': { schema: z.object({ error: z.string() }) } }, description: 'Already initialized' },
  },
});

// Implementation logic inside the handler:
// 1. SELECT id FROM users WHERE role = 'admin'
// 2. If exists -> throw ApiError.conflict('Store already initialized');
// 3. INSERT INTO store_info (name) VALUES (storeName)
// 4. INSERT INTO regions (name, currency_code) VALUES ('Default', defaultCurrency)
// 5. Trigger Auth0 Management API invite for adminEmail
```

### Required Fields
The payload must contain the `adminEmail` (which will receive the Auth0 invitation), the `storeName`, and localization defaults (`defaultCurrency` like 'USD', `defaultCountryCode` like 'US').

## Auth0 Management API Integration

During the setup phase, Fufuni interacts with the Auth0 Management API. If the environment variable `AUTH0_MANAGEMENT_CLIENT_ID` is present and the tenant hasn't been configured, the system can automatically trigger `auth0:deploy`.

### Admin User Invitation
When `POST /v1/setup/init` is called, the framework does not just create a local user record. It communicates with Auth0 to ensure the identity provider is ready.

```typescript
async function inviteAdminToAuth0(email: string, env: HonoEnv['Bindings']) {
  const managementToken = await getAuth0ManagementToken(env);
  
  const response = await fetch(`https://${env.AUTH0_DOMAIN}/api/v2/users`, {
    method: 'POST',
    headers: {
      Authorization: `Bearer ${managementToken}`,
      'Content-Type': 'application/json',
    },
    body: JSON.stringify({
      email,
      connection: 'Username-Password-Authentication',
      password: generateSecureTemporaryPassword(), // Or use Auth0's invitation flow
      verify_email: true,
      user_metadata: { role: 'admin' },
    }),
  });

  if (!response.ok) {
    throw new Error('Failed to create admin in Auth0');
  }
}
```

This ensures that once the setup wizard finishes, the administrator can immediately log in via the Auth0 Universal Login page using the email provided during setup.

## Post-Setup Store Management

Once the store is initialized via `/v1/setup/init`, that endpoint is locked. Any further modifications to the store's identity must be performed through the `store-info` endpoints. This separation ensures that the critical bootstrap logic (which creates the first admin) is never re-run, while day-to-day administrative tasks like updating the logo or social links are handled by standard CRUD operations.

```typescript
const updateStoreInfo = createRoute({
  method: 'put',
  path: '/v1/store-info',
  security: [{ bearerAuth: ["admin:store"] }],
  request: {
    body: {
      content: {
        'application/json': {
          schema: z.object({
            name: z.string().optional(),
            logo_url: z.string().url().optional(),
            support_email: z.string().email().optional(),
            social_links: z.record(z.string()).optional(),
          }),
        },
      },
    },
  },
  responses: {
    200: { content: { 'application/json': { schema: z.object({ ok: z.literal(true) }) } }, description: 'Updated' },
  },
});
```

The database stores these details in a `config` table or a specific `store_info` table, and they are fetched by the frontend to render the merchant header and footer.

## Setup Wizard Frontend Flow

The frontend setup wizard (located in `apps/client/src/pages/setup/`) is a multi-step React 19 component using HeroUI v3 components. It guides the user through the initial configuration in three distinct stages.

### Step 1: Store Basics
The user enters the store name and selects the primary currency. This stage populates the local state that will eventually be sent to the `/init` endpoint.

```tsx
import { Input, Select, SelectItem } from "@heroui/react";

export const Step1StoreBasics = ({ data, updateData }) => {
  return (
    <div className="flex flex-col gap-4">
      <Input 
        label="Store Name" 
        value={data.storeName} 
        onChange={(e) => updateData({ storeName: e.target.value })} 
      />
      <Select 
        label="Primary Currency"
        selectedKeys={[data.defaultCurrency]}
        onSelectionChange={(keys) => updateData({ defaultCurrency: Array.from(keys)[0] })}
      >
        <SelectItem key="USD">USD - US Dollar</SelectItem>
        <SelectItem key="EUR">EUR - Euro</SelectItem>
      </Select>
    </div>
  );
};
```

### Step 2: Admin Account
The user provides the administrator's email address. The UI explains that an invitation will be sent via Auth0. This email will become the "Super Admin" of the platform.

### Step 3: Auth0 Tenant Verification
The final step displays the Auth0 configuration status. If the framework detects that the Auth0 tenant is not yet fully configured (e.g., missing specific rules or roles), it provides a "Verify & Deploy" button. Clicking this triggers the backend to run the Auth0 deployment script, ensuring the merchant's tenant is ready for e-commerce traffic.

## Handling Re-initialization Attempts

If a developer or automated script attempts to call `POST /v1/setup/init` on an already active store, Fufuni returns a `409 Conflict`. This is a hard guard in the backend handler.

```typescript
// Backend logic snippet
const adminExists = await db.prepare('SELECT 1 FROM users WHERE role = "admin"').first();

if (adminExists) {
  return c.json({
    error: 'CONFLICT',
    message: 'This Fufuni instance has already been initialized. To reset, use the /v1/setup/reset endpoint with database-admin privileges.'
  }, 409);
}
```

The frontend catches this error and redirects the user to the login page, as a 409 implies the setup is no longer required and the application is ready for use. For local development or emergency recovery, the `adminSetup` router (provided in the source code) includes a `/reset` route that requires a specific JWT with the `admin:database` scope to wipe all tables, allowing the setup wizard to be run again.

### Database Reset (Development Only)
The `/reset` endpoint is highly destructive and should only be used in non-production environments. It disables foreign key checks and iterates through every table in the SQLite schema to delete all data.

```sql
-- The logic used by the /reset endpoint internally
PRAGMA foreign_keys = OFF;
DELETE FROM products;
DELETE FROM orders;
DELETE FROM users;
-- ... deletes every table ...
PRAGMA foreign_keys = ON;
```

After calling `/reset`, the `GET /v1/setup/status` endpoint will once again return `initialized: false`, enabling the setup wizard for the next visit.
