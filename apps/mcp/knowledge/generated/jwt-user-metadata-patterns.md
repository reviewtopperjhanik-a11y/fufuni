## The useTokenUserData Hook

The `useTokenUserData` hook is the primary interface for React components to access and synchronize data stored within the Auth0 JWT. In Fufuni, we treat the JWT's `user_metadata` as a lightweight, client-side state persistence layer. This hook handles the extraction of claims from the `access_token` and ensures that all components using the same data key stay in sync when mutations occur.

### Returned Claims and Types

When the hook parses an Auth0 token, it returns a strongly-typed object containing:
- `sub`: The unique Auth0 user identifier.
- `email`: User's email address.
- `name`: Full name.
- `picture`: Profile image URL.
- `permissions`: An array of strings representing Auth0 permissions.
- `roles`: An array of strings representing assigned roles.
- `user_metadata`: Arbitrary JSON object for client-side preferences (wishlists, UI settings).

### Usage Example: Managing a Wishlist

The hook requires a `parseFromToken` function to extract the specific subset of metadata you need and an `eventName` to facilitate cross-component synchronization via `CustomEvent`.

```typescript
import { useTokenUserData } from "@/hooks/use-token-user-data";
import { jwtDecode } from "jwt-decode";

interface UserClaims {
  user_metadata?: {
    wishlist?: string[];
  };
}

/**
 * Custom hook for wishlist management using JWT metadata
 */
export function useWishlist() {
  const eventName = "fufuni:wishlist-sync";

  const { data, isLoading, setData } = useTokenUserData<string[]>(
    (token) => {
      if (!token) return [];
      try {
        const decoded = jwtDecode<UserClaims>(token);
        return decoded.user_metadata?.wishlist || [];
      } catch {
        return [];
      }
    },
    eventName
  );

  const toggleWishlist = (productId: string) => {
    const newData = data.includes(productId)
      ? data.filter((id) => id !== productId)
      : [...data, productId];
    
    // Update local state
    setData(newData);
    
    // Trigger sync for other components using this hook
    window.dispatchEvent(new CustomEvent(eventName, { detail: newData }));

    // Note: A background API call to update Auth0 user_metadata should follow here
  };

  return { wishlist: data, isLoading, toggleWishlist };
}
```

## Auth0 user_metadata Patterns

In Fufuni, `user_metadata` is an arbitrary JSON blob stored in Auth0. While it is easy to read, updating it requires a backend proxy to the Auth0 Management API to ensure security and prevent users from escalating their own privileges.

### Normalizing Store Keys

Because Fufuni is multi-tenant, we often store metadata specific to a single store (e.g., a "saved cart" for one shop but not another). Auth0 prohibits dots (`.`), colons (`:`), and slashes (`/`) in field names. We use normalization helpers to convert URLs into valid keys.

```typescript
import { normalizeStoreUrl, getStoreMetadata } from "@/lib/store-metadata";

const rawMetadata = {
  "https___shop_fufuni_com": {
    theme: "dark",
    recent_searches: ["shoes", "hats"]
  },
  global_preference: "newsletter_on"
};

const storeUrl = "https://shop.fufuni.com/";
const key = normalizeStoreUrl(storeUrl); // Result: "https___shop_fufuni_com"

const specificMetadata = getStoreMetadata(rawMetadata, storeUrl);
console.log(specificMetadata.theme); // "dark"
```

### When to use user_metadata
- **Wishlists:** Low-stakes product IDs.
- **UI Preferences:** Dark mode, language choice, layout density.
- **Feature Onboarding:** Boolean flags indicating if a user has seen a tutorial.
- **Drafts:** Temporary states that should survive a page refresh across devices.

## Store Metadata (Server vs Client)

It is critical to distinguish between **User Metadata** (per-user in Auth0) and **Store Metadata** (per-store in SQLite). Store Metadata handles global configuration for the shop, such as Stripe API keys, branding colors, or shipping rules.

### Server-Side Implementation (Merchant App)

On the backend, store metadata is persisted in the `store_metadata` table. Access is managed via a `metadata_key`.

```typescript
import { Hono } from "hono";
import { getMetadata, setMetadata } from "@/lib/store-metadata";
import { db } from "@/db";

const app = new Hono();

// GET /v1/store-metadata/shipping_config
app.get("/v1/store-metadata/:key", async (c) => {
  const key = c.req.param("key");
  const data = await getMetadata(db, key);
  
  if (!data) return c.json({ error: "Not found" }, 404);
  return c.json(data);
});

// PUT /v1/store-metadata/shipping_config
app.put("/v1/store-metadata/:key", async (c) => {
  const key = c.req.param("key");
  const body = await c.req.json();
  
  await setMetadata(db, key, body);
  return c.json({ success: true });
});
```

### Client-Side Store Helpers

The frontend utilizes helpers to interact with these configurations. Unlike `user_metadata`, these values are usually fetched via standard `fetch` or `react-query` calls and stored in the application's global config state.

```typescript
import { getStoreMetadata, setStoreMetadata } from "@/lib/store-metadata";

// Example of updating a store-level configuration via the admin panel
async function updateLogoUrl(newUrl: string) {
  const currentConfig = await fetch("/api/v1/store-metadata/branding").then(res => res.json());
  
  const updatedConfig = {
    ...currentConfig,
    logo_url: newUrl
  };

  await fetch("/api/v1/store-metadata/branding", {
    method: "PUT",
    body: JSON.stringify(updatedConfig)
  });
}
```

## Permissions and JWT Claims

Fufuni utilizes Auth0 Post-Login Actions to inject custom claims into the JWT. This allows the backend to verify authorization without making external API calls to Auth0 on every request.

### Claim Injection Logic

A custom namespace (e.g., `https://fufuni.com/`) is prefixed to claims to avoid collisions. The permissions array is specifically extracted from the user's Auth0 roles and assigned scopes.

```typescript
// Conceptual example of the Auth0 Action logic
exports.onExecutePostLogin = async (event, api) => {
  const namespace = 'https://fufuni.com/';
  if (event.authorization) {
    api.idToken.setCustomClaim(`${namespace}permissions`, event.authorization.permissions);
    api.accessToken.setCustomClaim(`${namespace}permissions`, event.authorization.permissions);
  }
};
```

### Checking Permissions in React

Use the `useTokenUserData` hook to retrieve the permissions array for conditional rendering.

```typescript
import { useTokenUserData } from "@/hooks/use-token-user-data";

export function AdminPanel() {
  const { data: claims } = useTokenUserData((token) => {
    // Logic to extract permissions from JWT
    return parsePermissions(token);
  }, "auth:sync");

  const canEditProducts = claims.permissions.includes("write:products");

  if (!canEditProducts) {
    return <div>Access Denied</div>;
  }

  return <button>Edit Product Catalog</button>;
}
```

## Security and Visibility

JWTs are **encoded, not encrypted**. This means any data placed in `user_metadata` or standard claims is visible to anyone who possesses the token string (including the end user via tools like `jwt.io`).

### What NOT to store in user_metadata
1. **Secret Keys:** Never store API secrets, private keys, or passwords.
2. **PII (Sensitive):** Avoid storing social security numbers, health data, or bank details.
3. **Internal Flags:** Do not store internal-only flags like `is_internal_tester` if you don't want the user to know they are being tracked as such.
4. **Large Blobs:** JWTs are sent in HTTP headers. If the `user_metadata` grows too large, requests may fail due to "Header Too Large" errors (typically > 8KB).

### Data Segregation Strategy

| Data Type | Storage Location | Visibility |
| :--- | :--- | :--- |
| User Preferences | Auth0 `user_metadata` | Public (Decodable) |
| User Permissions | JWT Claims (Roles) | Public (Decodable) |
| Global Store Config | SQLite `store_metadata` | Merchant Admin Only |
| Sensitive Customer Data | SQLite `customers` table | Backend Only |
| Payment Credentials | Encrypted Vault / Stripe | Never in Fufuni DB |

By following this pattern, Fufuni ensures that the client remains responsive (using JWT-cached data) while keeping sensitive logic and configuration securely handled on the server side.
