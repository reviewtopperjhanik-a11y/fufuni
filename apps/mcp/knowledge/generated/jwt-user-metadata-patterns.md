## The `useTokenUserData` Hook

The `useTokenUserData` hook is the primary mechanism for React components to access and synchronize data stored within the Auth0 JWT. In Fufuni, we use the `user_metadata` field of the Auth0 ID/Access token to store non-sensitive customer preferences like wishlists, recently viewed items, or saved shopping carts.

### Return Type and Claims

The hook returns a stateful object containing the parsed data and loading indicators. When parsing the token, Fufuni expects the following standard and custom claims:

- `sub`: The unique Auth0 user identifier.
- `email`: The user's email address.
- `name` / `picture`: Basic profile information.
- `permissions`: An array of strings representing RBAC permissions (e.g., `['read:products', 'write:orders']`).
- `roles`: An array of strings representing Auth0 roles.
- `user_metadata`: An arbitrary JSON object containing the store-specific data.

### Implementation Example: Wishlist Sync

The following example demonstrates how to build a `useWishlist` hook using `useTokenUserData`. It includes the necessary logic to parse the token and dispatch a `CustomEvent` to keep all wishlist icons in sync across the UI.

```typescript
import { useTokenUserData } from "@/hooks/use-token-user-data";
import { jwtDecode } from "jwt-decode";
import { getStoreMetadata } from "@/lib/store-metadata";

const WISHLIST_SYNC_EVENT = "fufuni:wishlist-sync";
const STORE_URL = import.meta.env.VITE_STORE_URL;

interface UserTokenPayload {
  user_metadata?: Record<string, any>;
  [key: string]: any;
}

export function useWishlist() {
  const { data: wishlist, isLoading, setData } = useTokenUserData<string[]>(
    (token) => {
      if (!token) return [];
      try {
        const decoded = jwtDecode<UserTokenPayload>(token);
        // Extract store-specific metadata (handles URL normalization internally)
        const storeMeta = getStoreMetadata(decoded.user_metadata, STORE_URL);
        return storeMeta?.wishlist || [];
      } catch (e) {
        return [];
      }
    },
    WISHLIST_SYNC_EVENT
  );

  const toggleWishlist = async (productId: string) => {
    const nextWishlist = wishlist.includes(productId)
      ? wishlist.filter((id) => id !== productId)
      : [...wishlist, productId];

    // 1. Update local state for the current component
    setData(nextWishlist);

    // 2. Dispatch event to sync other components
    window.dispatchEvent(
      new CustomEvent(WISHLIST_SYNC_EVENT, { detail: nextWishlist })
    );

    // 3. Persist to Auth0 via your backend API
    await fetch("/api/v1/customer/metadata", {
      method: "PATCH",
      body: JSON.stringify({ wishlist: nextWishlist }),
    });
  };

  return { wishlist, toggleWishlist, isLoading };
}
```

## Auth0 user_metadata Patterns

Auth0 `user_metadata` is a key-value store intended for user preferences that do not impact core security logic (which should go in `app_metadata`). In Fufuni, we treat `user_metadata` as a client-side cache of the user's interaction state.

### Key Normalization

Auth0 has strict requirements for metadata keys: they cannot contain dots (`.`), colons (`:`), or slashes (`/`). Since Fufuni is multi-tenant and often keys data by the store's base URL, we must normalize these URLs into safe keys.

```typescript
/**
 * apps/client/src/lib/store-metadata.ts
 * Transforms "https://store.fufuni.com/" into "https___store_fufuni_com"
 */
export const normalizeStoreUrl = (storeUrl?: string): string | undefined => {
  if (!storeUrl) return undefined;
  return storeUrl
    .replace(/\/$/, "") 
    .replace(/[:.\/]/g, "_");
};

// Usage when reading from a decoded JWT
const userMetadata = decodedToken.user_metadata;
const storeKey = normalizeStoreUrl("https://my-shop.com");
const myStoreData = userMetadata[storeKey] || {};
```

### Read/Write Flow

1.  **Read**: The data is read directly from the JWT on the client side using `useTokenUserData`. This avoids an extra API call on every page load.
2.  **Write**: To update metadata, the client sends a `PATCH` request to the Fufuni backend. The backend uses the Auth0 Management API to update the user's profile.
3.  **Refresh**: After a successful write, the backend typically triggers a silent token refresh or the client relies on the `CustomEvent` sync until the next login.

## Store Metadata vs. User Metadata

It is critical to distinguish between **User Metadata** (Auth0) and **Store Metadata** (SQLite).

-   **User Metadata**: Specific to a single user (e.g., "User A's wishlist").
-   **Store Metadata**: Global configuration for the entire storefront (e.g., "Store's primary brand color", "Tax calculation settings").

### Server-Side Store Metadata (Merchant API)

In the backend, store metadata is stored in a dedicated SQLite table within the Store's Durable Object.

```typescript
// apps/merchant/src/lib/store-metadata.ts
import { DurableObjectSQL } from "@/types/sql";

export async function getMetadata(db: DurableObjectSQL, key: string) {
  const result = await db.prepare(
    "SELECT value FROM store_metadata WHERE metadata_key = ?"
  ).bind(key).first();
  
  return result ? JSON.parse(result.value as string) : null;
}

// Usage in a Hono route
app.get("/v1/store-metadata/:key", async (c) => {
  const key = c.req.param("key");
  const db = c.get("db");
  const value = await getMetadata(db, key);
  return c.json({ [key]: value });
});
```

### Client-Side Store Metadata Usage

The frontend uses store metadata to drive UI configuration.

```typescript
// apps/client/src/lib/store-metadata.ts
export const setStoreMetadata = async (key: string, value: any) => {
  const response = await fetch(`/api/v1/store-metadata/${key}`, {
    method: "PUT",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ value }),
  });
  return response.ok;
};
```

## Permissions and Roles in JWT

Permissions in Fufuni are managed via Auth0 RBAC and injected into the JWT using an **Auth0 Post-Login Action**. This allows the backend and frontend to verify capabilities without querying Auth0 on every request.

### Injected Claims structure

The JWT payload will contain an array of permissions. This is typically namespaced to avoid collisions:

```json
{
  "sub": "auth0|123",
  "https://fufuni.com/permissions": [
    "admin:all",
    "products:read",
    "products:write"
  ],
  "permissions": [
    "admin:all",
    "products:read"
  ]
}
```

### Checking Permissions in React

Use the `useAuth` hook or `useTokenUserData` to guard UI elements.

```typescript
import { useAuth } from "@/authentication";

export function AdminPanel() {
  const { user } = useAuth();
  
  // Namespace is defined in your environment config
  const namespace = "https://fufuni.com/";
  const permissions = user?.[`${namespace}permissions`] || [];
  
  const canEdit = permissions.includes("products:write");

  if (!canEdit) return <p>Access Denied</p>;

  return (
    <div>
      <button>Edit Product</button>
    </div>
  );
}
```

## Security Best Practices

When working with JWTs and metadata, follow these strict rules to prevent security vulnerabilities:

### 1. The JWT is Public
The JWT is encoded, not encrypted. Anyone with the token can decode it (e.g., via `jwt.io`).
- **NEVER** store passwords, private keys, or sensitive PII in `user_metadata`.
- **NEVER** store internal database IDs that could lead to IDOR (Insecure Direct Object Reference) if exposed.

### 2. Validation
Always validate the structure of the data returned from the JWT using Zod before using it in your logic.

```typescript
import { z } from "zod";

const WishlistSchema = z.array(z.string().uuid());

// Inside useTokenUserData parse function
const rawWishlist = storeMeta?.wishlist;
const validatedWishlist = WishlistSchema.safeParse(rawWishlist).success 
  ? rawWishlist 
  : [];
```

### 3. Server-Side Verification
While the frontend uses the JWT claims to hide/show UI elements, the backend **must** always verify the JWT signature and check permissions against the actual token payload provided in the `Authorization` header. Do not trust "permission" flags sent in the request body.

### 4. Size Limitations
Auth0 limits the size of `user_metadata` (usually around 8KB). 
- **DO** store small lists of IDs (wishlists).
- **DO NOT** store large objects, binary data, or historical logs. Use the Store's Durable Object SQLite for large datasets.

### 5. Metadata Mutability
`user_metadata` can be updated by the user if your backend provides an endpoint for it. Ensure that the endpoint only allows updates to specific "safe" keys (like `wishlist` or `theme`) and rejects updates to "privileged" keys.

```typescript
// Server-side guard example
app.patch("/v1/customer/metadata", async (c) => {
  const body = await c.req.json();
  const allowedKeys = ["wishlist", "language", "currency"];
  
  const filteredUpdates = Object.keys(body)
    .filter(key => allowedKeys.includes(key))
    .reduce((obj, key) => {
      obj[key] = body[key];
      return obj;
    }, {} as Record<string, any>);

  // Proceed to update Auth0 with filteredUpdates only
});
```
