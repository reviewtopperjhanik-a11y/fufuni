## Data Model and Schema

Fufuni manages inventory at the intersection of product variants and warehouses. This allows for complex fulfillment scenarios such as regional stock management and shipping from the nearest facility.

### SQLite Schema Definitions

The core logic relies on two primary tables: `warehouses` for location metadata and `inventory` for the actual quantities.

```sql
-- Represents a physical storage location
CREATE TABLE warehouses (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  address TEXT,
  is_default BOOLEAN DEFAULT 0,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);

-- Tracks quantity per variant per warehouse
CREATE TABLE inventory (
  variant_id TEXT NOT NULL,
  warehouse_id TEXT NOT NULL,
  on_hand INTEGER NOT NULL DEFAULT 0,   -- Physical stock in the building
  reserved INTEGER NOT NULL DEFAULT 0,  -- Stock held for pending checkouts
  updated_at INTEGER NOT NULL,
  PRIMARY KEY (variant_id, warehouse_id),
  FOREIGN KEY (variant_id) REFERENCES variants(id),
  FOREIGN KEY (warehouse_id) REFERENCES warehouses(id)
);
```

## Transaction Safety in Durable Objects

Inventory mutations in Fufuni are inherently sensitive to race conditions (e.g., two customers buying the last item simultaneously). Because the Fufuni backend runs inside **Cloudflare Durable Objects**, every request for a specific merchant is processed by a single-threaded instance of that DO.

All SQL operations are executed against a local SQLite database within the DO. By wrapping inventory logic in standard SQL transactions or relying on the DO's sequential execution, we guarantee that `available = on_hand - reserved` remains accurate.

```typescript
// Example of a transactional adjustment within a Hono route
const result = await db.transaction(async (tx) => {
  const stock = await tx.query('SELECT on_hand FROM inventory WHERE variant_id = ?', [vId]);
  if (stock[0].on_hand < qty) throw new Error('Insufficient stock');
  
  await tx.run('UPDATE inventory SET on_hand = on_hand - ? WHERE variant_id = ?', [qty, vId]);
});
```

## Core Inventory Helpers (lib/inventory.ts)

The framework provides four standardized utility functions to interact with the inventory system. These should be used instead of raw SQL queries whenever possible to ensure consistency.

### 1. getStockLevel(db, variantId)
Calculates the total available stock across all warehouses.

```typescript
export async function getStockLevel(db: Database, variantId: string): Promise<number> {
  const rows = await db.query<{ on_hand: number; reserved: number }>(
    `SELECT SUM(on_hand) as total_on_hand, SUM(reserved) as total_reserved 
     FROM inventory WHERE variant_id = ?`,
    [variantId]
  );
  
  if (!rows || rows.length === 0) return 0;
  return rows[0].total_on_hand - rows[0].total_reserved;
}
```

### 2. reserveStock(db, variantId, qty)
Increments the `reserved` column. This is called during the checkout validation phase before payment is attempted. It ensures the item is "held" for the customer.

```typescript
export async function reserveStock(db: Database, variantId: string, qty: number): Promise<void> {
  const timestamp = Date.now();
  // Attempt to reserve from the warehouse with the most stock
  const result = await db.run(
    `UPDATE inventory 
     SET reserved = reserved + ?, updated_at = ?
     WHERE variant_id = ? 
     AND (on_hand - reserved) >= ?
     LIMIT 1`,
    [qty, timestamp, variantId, qty]
  );

  if (result.changes === 0) {
    throw new Error(`Insufficient inventory for variant: ${variantId}`);
  }
}
```

### 3. releaseStock(db, variantId, qty)
Decrements the `reserved` column without changing `on_hand`. Called when a checkout expires or is canceled by the user.

```typescript
export async function releaseStock(db: Database, variantId: string, qty: number): Promise<void> {
  await db.run(
    `UPDATE inventory 
     SET reserved = MAX(reserved - ?, 0), updated_at = ?
     WHERE variant_id = ?`,
    [qty, Date.now(), variantId]
  );
}
```

### 4. deductStock(db, variantId, qty)
The final step. Decrements both `on_hand` and `reserved` once a payment is confirmed (typically via Stripe Webhook).

```typescript
export async function deductStock(db: Database, variantId: string, qty: number): Promise<void> {
  await db.run(
    `UPDATE inventory 
     SET on_hand = MAX(on_hand - ?, 0), 
         reserved = MAX(reserved - ?, 0),
         updated_at = ?
     WHERE variant_id = ?`,
    [qty, qty, Date.now(), variantId]
  );
}
```

## Checkout Lifecycle Integration

The inventory system follows a strict state machine during the order process to prevent overselling while maintaining a smooth user experience.

1.  **Validation (Cart/Checkout Start):**
    *   System calls `getStockLevel`.
    *   If available, system calls `reserveStock`.
    *   The `reserved` count prevents other users from claiming the same units.
2.  **Payment Phase:**
    *   The user is redirected to Stripe.
    *   Inventory remains in `reserved` state.
3.  **Completion (Webhook):**
    *   On `checkout.session.completed`, the system calls `deductStock`.
    *   Stock physically leaves the "on-hand" count.
4.  **Failure/Expiry (Webhook/Cleanup):**
    *   On `checkout.session.expired` or manual cancellation, the system calls `releaseStock`.
    *   Units return to the "available" pool.

## Admin Inventory Endpoints

Administrators manage stock levels through the `/v1/inventory` and `/v1/warehouses` route groups.

### Listing Stock Levels
Retrieve the status of all variants. This route supports filtering by `variantId`.

```typescript
// GET /v1/inventory/:variantId
const getVariantStock = createRoute({
  method: 'get',
  path: '/{variantId}',

adminApp.openapi(getVariantStock, async (c) => {
  const { variantId } = c.req.valid('param');
  const db = getDb(c.var.db);
  
  const items = await db.query(
    `SELECT i.*, w.name as warehouse_name 
     FROM inventory i 
     JOIN warehouses w ON i.warehouse_id = w.id 
     WHERE i.variant_id = ?`,

  );
  
  return c.json({ items }, 200);
});
```

### Manual Adjustments
The `adjust` endpoint allows increasing or decreasing physical `on_hand` stock. Use a negative `delta` to reduce stock (e.g., for damaged goods).

```typescript
// POST /v1/inventory/adjust
// Body: { variantId: "v_123", warehouseId: "wh_main", delta: 50 }
adminApp.openapi(adjustStockRoute, async (c) => {
  const { variantId, warehouseId, delta } = c.req.valid('json');
  const db = getDb(c.var.db);

  await db.run(
    `INSERT INTO inventory (variant_id, warehouse_id, on_hand, updated_at)
     VALUES (?, ?, ?, ?)
     ON CONFLICT(variant_id, warehouse_id) DO UPDATE SET
     on_hand = on_hand + excluded.on_hand,
     updated_at = excluded.updated_at`,
    [variantId, warehouseId, delta, Date.now()]
  );

  return c.json({ success: true }, 200);
});
```

## Low-Stock Webhooks

Fufuni includes a monitoring system that triggers events when inventory levels become critical. This is typically fired inside the `deductStock` logic or after an admin adjustment.

### Trigger Conditions
A `low_stock` event is dispatched if:
1.  A sale is committed (`deductStock`).
2.  The resulting `available` stock (`on_hand - reserved`) is less than or equal to the `low_stock_threshold` (default is 10).

### Event Payload
Webhooks are sent as POST requests to configured endpoints:

```json
{
  "event": "inventory.low_stock",
  "created_at": 1700000000,
  "data": {
    "variant_id": "var_998877",
    "sku": "TSHIRT-BLUE-L",
    "current_available": 4,
    "threshold": 10,
    "warehouse_breakdown": [
      { "warehouse_id": "wh_north", "available": 4 },
      { "warehouse_id": "wh_south", "available": 0 }
    ]
  }
}
```

## Multi-Warehouse Logic

Fufuni treats the "default warehouse" as the primary source of truth for new products. When a new product or variant is created, the system automatically initializes an inventory record for the warehouse marked `is_default: 1`.

### Default Warehouse Strategy
*   **Aggregated Display:** The storefront usually displays the SUM of all available quantities across all warehouses.
*   **Fulfillment Priority:** When `reserveStock` is called, the framework selects the warehouse with the highest available quantity to ensure balanced depletion.
*   **Regional Constraints:** If a merchant uses `regions`, the API can filter the `inventory` query by `warehouse_id`s associated with a specific region.

### Warehouse CRUD
Administering warehouses is done via standard REST operations.

```typescript
// POST /v1/warehouses
// Body: { name: "Berlin Hub", address: "Hauptstr 1", is_default: false }
adminApp.openapi(createWarehouseRoute, async (c) => {
  const db = getDb(c.var.db);
  const body = c.req.valid('json');
  const id = `wh_${crypto.randomUUID()}`;

  // If this is set to default, unset others
  if (body.is_default) {
    await db.run('UPDATE warehouses SET is_default = 0');
  }

  await db.run(
    'INSERT INTO warehouses (id, name, address, is_default, created_at, updated_at) VALUES (?, ?, ?, ?, ?, ?)',
    [id, body.name, body.address, body.is_default ? 1 : 0, Date.now(), Date.now()]
  );

  return c.json({ id, ...body }, 201);
});
```
