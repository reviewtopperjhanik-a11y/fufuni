Fufuni is an AI-native, 100% free-tier commerce framework designed to run entirely on the Cloudflare edge. By leveraging Cloudflare Workers for compute and Durable Objects with embedded SQLite for state, Fufuni eliminates traditional database latency and connection pooling issues. The framework is built for developers who want a production-ready, multi-tenant capable store with zero monthly overhead, featuring deep integration with Auth0 for identity, Stripe for payments, and the Universal Commerce Protocol (UCP) for AI shopping agents.

Fufuni utilizes a modern, type-safe stack optimized for edge performance and developer experience.

## 📁 Monorepo Structure

The project is a Turborepo-managed monorepo. It uses a single `.env` file at the root which is injected into various workspaces during development via `npm run dev:env`.

### Core Workspaces

- **`apps/client`**: The React 19 storefront and admin dashboard.
  - `src/pages/admin/`: Back-office management interfaces.
  - `src/config/site.ts`: The source of truth for the sidebar and RBAC visibility.
  - `src/lib/store-api.ts`: Auto-generated or hand-tuned typed API client.
- **`apps/merchant`**: The backend "brain" (Cloudflare Worker).

  - `src/do.ts`: The `MerchantDO` Durable Object class containing the SQLite schema and logic.
  - `migrations/`: Numbered `.sql` files for database versioning.
- **`apps/mcp`**: A remote Model Context Protocol server that allows AI assistants (like Claude or Cursor) to read the project's documentation and codebase structure.

## 🔄 Request Lifecycle

Every request to the Fufuni backend follows a specific path to ensure data consistency and high performance. Because Fufuni uses Durable Objects, all data for a single store instance is processed in a single JavaScript isolate.

1.  **Client Initiation**: The React SPA (or an AI agent) sends an HTTP request to the Cloudflare Worker URL.
2.  **Worker Entry (`index.ts`)**:
    - **CORS Middleware**: Handles cross-origin headers.
    - **DO Binding**: The Worker identifies the target Durable Object (usually the 'default' instance) and attaches a stub to the context.
    - **KV Cache Layer**: For `GET` requests to products or categories, the `kvCacheMiddleware` checks Cloudflare KV. If a hit occurs, it returns immediately, bypassing the Durable Object.
3.  **Authentication Middleware**: Validates either a `pk_` (Public Key), `sk_` (Secret Key), or an Auth0 JWT.
4.  **Durable Object Dispatch**: If the request isn't cached, Hono routes the request to the `MerchantDO`.
5.  **SQLite Execution**: Inside `MerchantDO`, the logic executes a SQL query against the local `c.storage.sql` instance.
6.  **Response & Invalidation**: If the request was a mutation (`POST`/`PATCH`/`DELETE`), the `kvInvalidateMiddleware` purges relevant keys from KV before the response is returned to the client.

### Code Example: Backend Route Flow
This example shows how a typical admin route is defined and secured in `apps/merchant/src/routes/catalog.ts`:

```typescript
import { OpenAPIHono, createRoute, z } from '@hono/zod-openapi';
import { authMiddleware } from '../middleware/auth';
import { type Env, type Variables } from '../types';

const adminCatalog = new OpenAPIHono<{ Bindings: Env; Variables: Variables }>();

// 1. Define the OpenAPI contract
const getProductRoute = createRoute({
  method: 'get',
  path: '/{id}',
  request: {
    params: z.object({ id: z.string().uuid() }),
  },
  responses: {
    200: { description: 'Product details' },
    404: { description: 'Product not found' },
  },
  security: [{ bearerAuth: [] }],
});

// 2. Apply Auth0 RBAC Middleware
adminCatalog.use('*', authMiddleware(['admin:store']));

// 3. Implement the logic that talks to the DO
adminCatalog.openapi(getProductRoute, async (c) => {
  const { id } = c.req.valid('param');
  const db = c.get('db');
  
  // All business logic executes inside the DO via the stub
  const product = await db.getProduct(id);
  
  if (!product) {
    return c.json({ error: 'Not Found' }, 404);
  }
  
  return c.json(product, 200);
});

export { adminCatalog };
```

## 📏 Key Conventions

To maintain consistency across the framework, contributors must follow these patterns:

### 1. Database Migrations
Fufuni uses a "Triple-Entry" migration system. When modifying the database schema, you must update:
1.  The `SCHEMA` constant in `apps/merchant/src/do.ts` (for fresh installs).
2.  The `ensureInitialized()` method in `apps/merchant/src/do.ts` (to handle runtime checks).
3.  A new `.sql` file in `apps/merchant/migrations/` (for existing deployments).

### 2. Authentication & Keys
- **Public Keys (`pk_...`)**: Used by the storefront for non-sensitive operations (viewing products, adding to cart).
- **Admin Keys (`sk_...`)**: Kept for legacy compatibility and internal scripts.
- **Auth0 JWTs**: The primary method for Admin Dashboard security. Permissions are verified via `scope` or `permissions` claims in the token.

### 3. Internationalization (i18n)
Product and category content (titles, descriptions) are stored as JSON strings in the database to support multilingual content without extra tables.
```json
{
  "en-US": "Classic T-Shirt",
  "fr-FR": "T-Shirt Classique",
  "he-IL": "טי-שירט קלאסי"
}
```

### 4. Error Handling
All API errors should use the `ApiError` class, which ensures the frontend receives a standardized JSON object with a code and a human-readable message.

```typescript
// Inside a route handler
if (stock < requestedQty) {
  throw new ApiError('insufficient_stock', 'Not enough items in warehouse', 400);
}
```

### 5. Frontend Visibility
Sidebar items in the admin panel are gated by permissions defined in `apps/client/src/config/site.ts`. Adding a new admin page requires adding an entry here with the required permission string (e.g., `admin:store`).

```typescript
// apps/client/src/config/site.ts
export const siteConfig = (permissions: string[]) => ({
  navItems: [
    {
      label: "Inventory",
      href: "/admin/inventory",
      isVisible: permissions.includes("admin:store"),
    }
  ]
});
```

## 🚀 Deployment Workflows

Fufuni is built for CI/CD via GitHub Actions.

### Cloudflare Worker Deployment
The `deploy-cloudflare-worker.yaml` workflow triggers on pushes to `main`. It:
1.  Installs dependencies.
2.  Runs the `build:env` script to generate necessary artifacts.
3.  Uses `wrangler deploy` to push the `merchant` workspace.
4.  Automatically provisions the Durable Object, R2 bucket, and KV namespaces based on `wrangler.jsonc`.

### Frontend Deployment
The `pages.yaml` workflow builds the Vite application and deploys the `dist/` folder to GitHub Pages. It uses the `STORE_URL` environment variable to configure the base path and absolute links.

### Demo Resilience
The `reset-demo.yaml` workflow is a scheduled task that wipes the SQLite database of the live demo instance and runs the `seed.ts` script, ensuring a clean state for prospective users every 24 hours.

## 🤖 Universal Commerce Protocol (UCP)
Fufuni implements the [UCP specification](https://ucp.dev), making it one of the first "agent-ready" commerce engines. 

- **Discovery**: Agents can query `/.well-known/ucp` to understand the store's capabilities.
- **Catalog**: Optimized endpoints at `/ucp/v1/products` provide clean JSON for LLM consumption.
- **Checkout**: AI agents can initiate checkout sessions directly via POST requests, receiving a Stripe URL in response that they can present to the human user for final payment.

### Code Example: UCP Discovery
The UCP router in `apps/merchant/src/routes/ucp.ts` exposes the store identity to AI agents:

```typescript
ucp.get('/.well-known/ucp', (c) => {
  return c.json({
    ucp_version: '1.0.0',
    capabilities: [
      'dev.ucp.shopping.catalog',
      'dev.ucp.shopping.browse',
      'dev.ucp.shopping.checkout',
      'dev.ucp.shopping.order'
    ],
    store_meta: {
      name: c.env.STORE_NAME,
      url: c.env.STORE_URL
    }
  });
});
```
