## Outbound Webhooks Overview

Fufuni uses an outbound webhook system to notify external services (like ERPs, custom shipping trackers, or marketing tools) when specific events occur within the store. Unlike **Inbound Webhooks** (such as the Stripe integration in `webhooks.ts`), which receive data from external providers, **Outbound Webhooks** dispatch events from the Fufuni Worker to URLs registered by the store administrator.

### Inbound vs. Outbound Webhooks

It is critical to distinguish between these two flows in the Fufuni codebase:

| Feature | Inbound Webhooks | Outbound Webhooks |
| :--- | :--- | :--- |
| **Direction** | External $\rightarrow$ Fufuni | Fufuni $\rightarrow$ External |
| **Example** | Stripe Payment Success | Order Created, Low Inventory |
| **Code Location** | `apps/merchant/src/routes/webhooks.ts` | `apps/merchant/src/routes/webhooks-outbound.ts` |
| **Authentication** | Provider-specific (e.g., Stripe Signatures) | `X-Fufuni-Signature` (HMAC-SHA256) |

## Supported Event Names

Fufuni supports granular event subscriptions. You can subscribe to specific events, use wildcards for categories, or subscribe to all events using `*`.

| Event Name | Trigger Point |
| :--- | :--- |
| `order.created` | Dispatched immediately after a successful checkout and order record creation. |
| `order.updated` | Dispatched when an admin updates the order status or metadata. |
| `order.shipped` | Dispatched specifically when an order's status transitions to "shipped". |
| `order.refunded` | Dispatched when a payment refund is processed via the admin dashboard. |
| `inventory.low` | Dispatched when a product's available quantity drops to or below the threshold (default: 5). |
| `order.*` | Catch-all for any event starting with `order.`. |
| `*` | Catch-all for every event supported by the framework. |

## Delivery Mechanics and Retries

Fufuni ensures reliable delivery using Cloudflare Workers' `ctx.waitUntil()` to avoid blocking the main request thread. 

### Retry Schedule
If a delivery fails (network error or non-2xx response), the system enters a retry loop. Fufuni follows an exponential back-off strategy for up to **3 total attempts**:
1.  **Initial Attempt**: Immediately upon event trigger.
2.  **Retry 1**: 2 seconds after failure.
3.  **Retry 2**: 4 seconds after failure.
4.  **Final Fail**: If the 3rd attempt fails, the delivery is marked as `failed`.

### Database Schema
Deliveries are tracked in the `webhook_deliveries` table. This is essential for auditing and manual resending.

```sql
CREATE TABLE webhook_deliveries (
  id TEXT PRIMARY KEY,
  webhook_id TEXT NOT NULL,
  event_type TEXT NOT NULL,
  payload TEXT NOT NULL,         -- JSON serialized WebhookPayload
  status TEXT NOT NULL,          -- 'pending', 'success', 'failed'
  attempts INTEGER DEFAULT 0,
  response_code INTEGER,
  response_body TEXT,
  created_at TEXT NOT NULL,
  last_attempt_at TEXT
);
```

## HMAC-SHA256 Signature Verification

To prevent Man-in-the-Middle attacks and unauthorized payloads, every outbound webhook request includes a cryptographic signature.

### Headers Sent
| Header | Description |
| :--- | :--- |
| `X-Fufuni-Signature` | The HMAC-SHA256 hex signature of the JSON body. |
| `X-Fufuni-Timestamp` | Unix timestamp when the delivery was initiated. |
| `X-Fufuni-Delivery-Id` | Unique ID of the delivery attempt. |

### Consumer Verification (Node.js/TypeScript)
The consumer should compute the HMAC of the raw request body using the `secret` (prefixed with `whsec_`) provided during registration.

```typescript
import { createHmac, timingSafeEqual } from 'node:crypto';

function verifyFufuniSignature(
  rawBody: string, 
  signature: string, 
  secret: string
): boolean {
  const hmac = createHmac('sha256', secret);
  const computedSignature = hmac.update(rawBody).digest('hex');
  
  // Use timingSafeEqual to prevent timing attacks
  return timingSafeEqual(
    Buffer.from(signature),
    Buffer.from(computedSignature)
  );
}

```

## Manual Resend and Secret Rotation

### Manual Retry
If a delivery failed due to a temporary outage on the consumer's side, administrators can trigger a manual retry. This resets the attempt counter and initiates a new asynchronous delivery attempt.

**Endpoint:** `POST /v1/webhooks/{id}/deliveries/{deliveryId}/retry`

```typescript
// Route implementation snippet from webhooks-outbound.ts
adminApp.openapi(retryDeliveryRoute, async (c) => {
  const { id, deliveryId } = c.req.valid('param');
  const db = getDb(c.var.db);

  // Mark as pending to allow the background task to pick it up
  await db.run(
    `UPDATE webhook_deliveries SET status = 'pending', attempts = 0 WHERE id = ?`, 
    [deliveryId]
  );

  // Trigger background delivery
  c.executionCtx.waitUntil(retryDelivery(c.var.db, webhook, delivery));

  return c.json({ status: 'pending', message: 'Delivery retry triggered' });
});
```

### Secret Rotation
If a secret is leaked, it must be rotated immediately. Rotating the secret invalidates the old one and returns a new `whsec_` prefixed string. Existing deliveries in the retry queue will use the new secret for subsequent attempts.

**Endpoint:** `POST /v1/webhooks/{id}/rotate-secret`

```typescript
// Example: Using rotation via API
const rotate = await fetch(`/v1/webhooks/${webhookId}/rotate-secret`, {
  method: 'POST',
  headers: { 'Authorization': `Bearer ${token}` }
});
const { secret } = await rotate.json();
console.log(`Update your receiver with the new secret: ${secret}`);
```

## Handling Large Payloads

Webhook payloads contain the primary data associated with the event (e.g., the full `Order` object for `order.created`). If a response body from the receiver is exceptionally large, Fufuni truncates the `response_body` stored in the database to the first **1000 characters** to preserve SQLite performance and storage limits within the Durable Object.

### Inventory Notifications

The `inventory.low` event is special because it is triggered within the inventory update logic rather than a direct status change.

  stub: DOStub,
