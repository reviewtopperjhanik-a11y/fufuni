## The ApiError Class Structure

The Fufuni framework centralizes error handling through the `ApiError` class. This class extends the native JavaScript `Error` but adds HTTP-specific metadata: `statusCode`, a machine-readable `code`, and an optional `details` object for providing context (like validation errors or affected resource IDs).

In the backend, when an `ApiError` is thrown, the global Hono error handler catches it and serializes it into a standardized JSON envelope. This ensures that the frontend always receives a predictable response format.

### Error Response Envelope

Every error returned by the Fufuni API follows this structure:

```typescript
{
  "error": {
    "code": "string",       // Machine-readable slug (e.g., 'not_found')
    "message": "string",    // Human-readable description
    "details": {}           // Optional object containing contextual data
  }
}
```

### Class Definition Reference

The class is defined in `apps/merchant/src/types.ts`. It utilizes static methods to simplify the creation of common HTTP errors.

```typescript
import { ApiError } from '@/types';

// Manual instantiation

```

## Backend: Throwing ApiErrors in Hono

Fufuni uses Hono with Zod-OpenAPI. Errors should be thrown directly within the route handlers. The framework's middleware handles the conversion from the `ApiError` instance to the JSON response and the appropriate HTTP status code.

### Basic Usage Example

In this example, we fetch a product by ID. If the product is missing, we throw a `404 Not Found`.

```typescript
import { Hono } from 'hono';
import { ApiError, type HonoEnv } from '@/types';
import { getDb } from '@/db';

const app = new Hono<HonoEnv>();

app.get('/products/:id', async (c) => {
  const id = c.req.param('id');
  const db = getDb(c);

  const [product] = await db.query(
    'SELECT * FROM products WHERE id = ?',
    [id]
  );

  if (!product) {
    // This is caught by the global error handler
    throw ApiError.notFound(`Product with ID ${id} was not found.`);
  }

  return c.json(product);
});

export default app;
```

### Handling Business Logic Conflicts

For e-commerce specific logic, such as inventory management, use the specialized static methods to provide better debugging info to the frontend.

```typescript
import { ApiError } from '@/types';

/**
 * Validates if a cart can be converted to an order.
 */
async function validateInventory(db: any, items: { sku: string; qty: number }[]) {
  for (const item of items) {
    const [stock] = await db.query(
      'SELECT stock_quantity FROM inventory WHERE sku = ?',
      [item.sku]
    );

    if (!stock || stock.stock_quantity < item.qty) {
      // Specialized error for inventory issues
      throw ApiError.insufficientInventory(item.sku);
    }
  }
}
```

## Frontend: Handling API Errors

Fufuni frontends use the `useSecuredApi()` hook to interact with the merchant backend. This hook handles authentication headers automatically. When a request returns a non-2xx status code, the underlying fetcher typically throws an error containing the JSON payload.

### Error Handling in React 19

When calling the API inside a `useEffect` or an event handler (like a form submission), you must use a `try/catch` block to intercept `ApiError` responses.

```tsx
import React, { useState } from 'react';
import { Button, Input, Alert } from '@heroui/react';
import { useSecuredApi } from '@/hooks/useSecuredApi';

export const ProductEditor = ({ productId }: { productId: string }) => {
  const api = useSecuredApi();
  const [loading, setLoading] = useState(false);
  const [errorMsg, setErrorMsg] = useState<string | null>(null);

  const handleUpdate = async (formData: FormData) => {
    setLoading(true);
    setErrorMsg(null);

    try {
      const response = await api.put(`/api/products/${productId}`, {
        name: formData.get('name'),
      });
      
      if (!response.ok) {
        // Parse the standard ApiError JSON body
        const errorData = await response.json();
        throw new Error(errorData.error?.message || 'Update failed');
      }
      
      console.log('Product updated successfully');
    } catch (err: any) {
      // Set the message from the backend ApiError
      setErrorMsg(err.message || 'An unexpected error occurred');
    } finally {
      setLoading(false);
    }
  };

  return (
    <div className="flex flex-col gap-4">
      {errorMsg && (
        <Alert color="danger" title="Error">
          {errorMsg}
        </Alert>
      )}
      
      <form action={handleUpdate} className="space-y-4">
        <Input name="name" label="Product Name" placeholder="Enter name" />
        <Button type="submit" color="primary" isLoading={loading}>
          Save Changes
        </Button>
      </form>
    </div>
  );
};
```

### Mapping Error Codes to UI Components

In advanced scenarios, you might want to perform specific UI actions based on the error `code` rather than just displaying the `message`.

```tsx
try {
  await api.post('/api/checkout', cartData);
} catch (err: any) {
  const errorJson = await err.response?.json();
  const code = errorJson?.error?.code;

  switch (code) {
    case 'insufficient_inventory':
      const sku = errorJson.error.details?.sku;
      toast.error(`Sorry, item ${sku} just went out of stock!`);
      break;
    case 'unauthorized':
      window.location.href = '/login';
      break;
    default:
      toast.error(errorJson?.error?.message || 'Server error');
  }
}
```

## Global Error Handler Logic (Conceptual)

While developers usually only interact with `throw ApiError`, it is helpful to understand how the backend processes it. The Fufuni backend uses a `onError` handler in the Hono application:

```typescript
// Conceptual implementation in apps/merchant/src/index.ts
app.onError((err, c) => {
  if (err instanceof ApiError) {
    return c.json(
      {
        error: {
          code: err.code,
          message: err.message,
          details: err.details,
        },
      },
      { status: err.statusCode as any }
    );
  }

  // Fallback for native errors
  console.error('Unhandled System Error:', err);
  return c.json(
    {
      error: {
        code: 'internal_server_error',
        message: 'A system error occurred.',
      },
    },
    { status: 500 }
  );
});
```

By adhering to this pattern, you ensure that even if a database connection fails or an unexpected exception occurs, the client always receives a structured response instead of a generic HTML error page from the Cloudflare edge.
