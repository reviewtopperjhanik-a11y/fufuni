## Core Binding Access in Hono

Fufuni leverages [Hono](https://hono.dev/) with the `zod-openapi` middleware to provide a type-safe API. In the Worker environment, all Cloudflare bindings (Durable Objects, R2, KV, and Environment Variables) are accessed through the Hono context `c.env`.

Every handler receives the `Env` type, which is automatically generated and maintained in `apps/merchant/worker-configuration.d.ts`.

```typescript
import { createRoute, z } from '@hono/zod-openapi';
import { AppRoute } from '../types';

// Accessing different bindings within a route handler
export const getStorageInfo = createRoute({
  method: 'get',
  path: '/v1/system/storage',
  responses: {
    200: {
      description: 'Returns metadata about bindings',
      content: { 'application/json': { schema: z.object({ hasKV: z.boolean(), hasR2: z.boolean() }) } }
    }
  }
});

const handler: AppRoute<typeof getStorageInfo> = async (c) => {
  // 1. KV Access
  const kvValue = await c.env.KV_CACHE.get('some-key');
  
  // 2. R2 Access
  const image = await c.env.IMAGES.get('products/id_123.webp');
  
  // 3. Durable Object Binding
  const doNamespace = c.env.MERCHANT;

  return c.json({
    hasKV: !!c.env.KV_CACHE,
    hasR2: !!c.env.IMAGES
  }, 200);
};
```

## Durable Object Persistence Pattern

Fufuni uses a **Single Durable Object Instance** pattern. Unlike traditional horizontally scaled workers, Fufuni routes all merchant-specific logic to a single DO named `MerchantDO`. This ensures strict serializability for SQLite transactions and prevents race conditions in inventory management.

### Accessing the DO Stub
To interact with the DO, you must obtain a "stub" using a consistent ID. We use `idFromName("merchant")` to ensure every request targeting this worker hits the same SQLite database instance.

```typescript
// apps/merchant/src/lib/do-client.ts
import { Context } from 'hono';

/**
 * Utility to get the singleton MerchantDO stub
 */
export function getMerchantDO(c: Context) {
  const id = c.env.MERCHANT.idFromName('merchant');
  return c.env.MERCHANT.get(id);
}

// Example usage in a route
const updateProduct = async (c: Context) => {
  const stub = getMerchantDO(c);
  const body = await c.req.json();

  // 'run' is used for mutations (INSERT/UPDATE/DELETE)
  await stub.run('UPDATE products SET price = ? WHERE id = ?', [body.price, body.id]);
  
  // 'query' is used for SELECTs
  const product = await stub.query('SELECT * FROM products WHERE id = ?', [body.id]);
  
  return c.json(product);
};
```

## KV Caching and Invalidation

Fufuni implements an aggressive caching layer via `KV_CACHE` to minimize DO wake-ups and SQLite CPU usage for read-heavy operations like product catalogs.

### Middleware Implementation
The `kvCacheMiddleware` automatically intercepts GET requests. It uses a cache key format of `cache:<full-url>`.

- **Search Results:** Cached for `KV_CACHE_SEARCH_TTL_SECONDS` (Default: 300s).
- **Reviews:** Cached for `KV_CACHE_REVIEWS_TTL_SECONDS` (Default: 600s).
- **Other GETs:** Cached for `KV_CACHE_DEFAULT_TTL_SECONDS` (Default: 3600s).

**Bypass Logic:** The cache is bypassed if an `Authorization` header is present with an Admin JWT or a Secret Key (`sk_`). Public `pk_` keys still trigger the cache.

### Manual Cache Invalidation
When a product or category is modified, the `kvInvalidateMiddleware` purges relevant keys using a prefix-based scan.

```typescript
// Example of manual invalidation logic within the framework
async function invalidateCatalogCache(env: Env) {
  const prefixes = ['cache:*/v1/products', 'cache:*/v1/categories'];
  
  for (const prefix of prefixes) {
    let cursor: string | undefined;
    do {
      const list = await env.KV_CACHE.list({ prefix, cursor });
      for (const key of list.keys) {
        await env.KV_CACHE.delete(key.name);
      }
      cursor = list.cursor;
    } while (cursor);
  }
}
```

## R2 Image Management

Product images are stored in the `IMAGES` R2 bucket. The URL used to serve these images is configured via the `IMAGES_URL` environment variable.

### Serving Images
Images are typically served through a public bucket URL or a Worker-proxy route.

```typescript
// apps/merchant/src/routes/images.ts
export const uploadImage = async (c: Context) => {
  const formData = await c.req.parseBody();
  const file = formData['file'] as File;
  const key = `products/${crypto.randomUUID()}.webp`;

  await c.env.IMAGES.put(key, await file.arrayBuffer(), {
    httpMetadata: { contentType: 'image/webp' }
  });

  return c.json({ url: `${c.env.IMAGES_URL}/${key}` });
};
```

## Environment Variables and Secrets

Fufuni distinguishes between standard variables and sensitive secrets.

### Backend Secrets
The following must be set as secrets in Cloudflare (via `wrangler secret put` or the `secrets.json` bulk upload in CI):
- **Mailgun:** `MAILGUN_API_KEY`, `MAILGUN_DOMAIN`, `MAILGUN_USER`. If `MAILGUN_API_KEY` is missing, the system silently skips sending emails.
- **Stripe:** `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`.
- **Auth0:** `AUTH0_CLIENT_SECRET`, `AUTH0_MANAGEMENT_API_CLIENT_SECRET`.

### Adding a New Binding
1.  **Update `wrangler.jsonc`:** Add the binding under the appropriate array (e.g., `kv_namespaces`).
2.  **Update Types:** Run `npx wrangler types` to update `worker-configuration.d.ts`.
3.  **Global Env:** Ensure the `Env` interface in your source code reflects these changes for local development.

## CI/CD and Secret Pipeline

The Fufuni deployment pipeline ensures that local `.env` variables are synchronized with GitHub Secrets and eventually Cloudflare Workers.

### 1. The `.env` to GitHub Mapping
Every variable in your local `.env` file must have a 1:1 matching GitHub Secret in the repository.

### 2. `create-env-artifact.yaml`
This workflow is the "Source of Truth" for CI. It rebuilds a `.env` file from GitHub Secrets. If you add a new variable to the project, **you must add an echo line to this file**, or it will be missing in production.

```yaml
# .github/workflows/create-env-artifact.yaml
- name: Create .env file
  run: |
    echo "NEW_SETTING=${{ secrets.NEW_SETTING }}" >> .env
    # ... existing variables ...
```

### 3. Secret Injection
The `generate-wrangler-jsonc.py` script consumes the `.env` file and creates:
- A `wrangler.jsonc` with `secrets.required` populated.
- A `secrets.json` file used by `wrangler secret bulk`.

## Frontend Integration (Vite)

Frontend environment variables are not prefixed with `VITE_`. Instead, they are injected at build time via the `define` block in `apps/client/vite.config.ts`.

### Exposing a New Var to the Browser
To make a variable available in the React app:

```typescript
// apps/client/vite.config.ts
export default defineConfig(({ mode }) => {
  const env = loadEnv(mode, process.cwd(), '');
  return {
    define: {
      'import.meta.env.MY_NEW_SETTING': JSON.stringify(env.MY_NEW_SETTING),
    }
  };
});
```

### Permissions Logic
Fufuni uses a special `import.meta.env.PERMISSIONS` array. This is derived at build time by filtering all `.env` keys ending in `_PERMISSION`.

```typescript
// In vite.config.ts logic
const scopesArray = Object.keys(env)
  .filter((key) => key.endsWith('_PERMISSION'))
  .map((key) => env[key]);

// In React Components
const userPermissions = useAuth().permissions;
const hasAccess = import.meta.env.PERMISSIONS.every(p => userPermissions.includes(p));
```

## Development Commands

### Local Development
The recommended command for development is `npm run dev:env` from the monorepo root. This:
1.  Copies the root `.env` to `apps/merchant/.dev.vars`.
2.  Starts the Merchant Worker on `localhost:8787`.
3.  Starts the Client Vite app on `localhost:5173`.

### Stripe Webhooks
Since webhooks require a public endpoint or a local tunnel, run the following in a separate terminal:
```bash
# Requires Stripe CLI
npm run stripe:listen
```
This forwards Stripe events to your local Worker, reading the secret key directly from `.env`.
