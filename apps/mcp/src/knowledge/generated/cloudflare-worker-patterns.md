## Accessing Bindings in Route Handlers

```typescript

import { Hono } from 'hono'
import { z } from 'zod'
import { zValidator } from '@hono/zod-validator'

const products = new Hono()

// Accessing bindings in a route handler
products.get('/', async (c) => {
  // Durable Object namespace binding
  const merchantStub = c.env.MERCHANT.get(c.env.MERCHANT.idFromName('main'))

  // R2 bucket binding
  const imagesBucket = c.env.IMAGES

  // KV namespace binding
  const cache = c.env.KV_CACHE

  // Use the bindings...
  return c.json({ message: 'Accessed all bindings successfully' })
})
```

## Durable Object Pattern

Fufuni uses a single Durable Object instance pattern for all stateful operations. This approach:

1. **Single Instance**: Only one `MerchantDO` instance is created (named "main") to handle all merchant data
2. **Consistent State**: Ensures all requests interact with the same data store
3. **Simplified Architecture**: Avoids complex coordination between multiple DO instances

To use the Durable Object:

```typescript
// Getting the stub (reference) to the DO
const merchantStub = c.env.MERCHANT.get(
  c.env.MERCHANT.idFromName('main')
)

// Calling query() for read operations
const response = await merchantStub.fetch(
  new Request('https://example.com', {
    method: 'GET',
    headers: { 'X-Query': 'getProducts' }
  })
)

// Calling run() for write operations
const writeResponse = await merchantStub.fetch(
  new Request('https://example.com', {
    method: 'POST',
    headers: { 'X-Command': 'createProduct' },
    body: JSON.stringify(productData)
  })
)
```

## KV Cache Middleware

Fufuni implements a sophisticated KV caching layer that automatically caches GET responses. Key features:

1. **Automatic Caching**: GET responses are cached with keys based on the full URL (including query params)
2. **Selective Bypass**: Cache is bypassed for:
   - Non-GET requests
   - Requests with admin JWTs (Authorization: Bearer pk_*)
   - SK keys (Authorization: Bearer sk_*)

```typescript
// apps/merchant/src/middleware/kv-cache.ts
export const kvCacheMiddleware = (cache: KVNamespace) => {
  return async (c: Context, next: Next) => {
    // Bypass cache for non-GET requests
    if (c.req.method !== 'GET') return await next()

    // Bypass for admin tokens
    const auth = c.req.header('Authorization')
    if (auth?.startsWith('Bearer pk_') || auth?.startsWith('Bearer sk_')) {
      return await next()
    }

    const cacheKey = `cache:${c.req.url}`
    const cached = await cache.get(cacheKey)

    if (cached) {
      return new Response(cached, {
        headers: { 'X-Cache': 'HIT' }
      })
    }

    const response = await next()
    await cache.put(cacheKey, response.body)
    return response
  }
}
```

Cache TTL is configurable via these environment variables:
```bash
KV_CACHE_SEARCH_TTL_SECONDS=300     # 5 minutes for search results
KV_CACHE_REVIEWS_TTL_SECONDS=600    # 10 minutes for reviews
KV_CACHE_DEFAULT_TTL_SECONDS=3600   # 1 hour for other routes
```

## R2 Storage for Product Images

Product images are stored in Cloudflare R2 and served directly from the edge:

```typescript
// apps/merchant/src/routes/v1/products.ts
products.post('/:id/image', zValidator('form', productImageSchema), async (c) => {
  const { id } = c.req.param()
  const formData = await c.req.formData()
  const imageFile = formData.get('image') as File

  // Store in R2
  await c.env.IMAGES.put(`products/${id}/${imageFile.name}`, await imageFile.arrayBuffer())

  // Generate signed URL for access
  const imageUrl = `${c.env.IMAGES_URL}/products/${id}/${imageFile.name}`

  return c.json({ imageUrl })
})
```

Images are served via direct R2 URLs configured through the `IMAGES_URL` environment variable.

## Secrets Management

Fufuni follows these principles for secrets management:

1. **Wrangler Secrets vs .env**:
   - All sensitive values go in `.env` during development
   - In production, these become Wrangler secrets via `wrangler secret` commands

2. **Mailgun Configuration**: Required secrets for email functionality:
   ```bash
   MAILGUN_API_KEY=your_api_key
   MAILGUN_DOMAIN=your_domain.com
   MAILGUN_BASE_URL=https://api.mailgun.net
   MAILGUN_USER=no-reply@your-domain.com
   ```

3. **GitHub Secrets**: Every `.env` variable must have a corresponding GitHub secret with the same name.

## Adding New Bindings

To add a new binding (like a new R2 bucket or KV namespace):

1. **Update wrangler.jsonc**:
   ```json
   {
     "r2_buckets": [
       {
         "binding": "NEW_BUCKET",
         "bucket_name": "new-bucket"
       }
     ]
   }
   ```

2. **Update worker-configuration.d.ts**:
   ```typescript
   interface Env {
     NEW_BUCKET: R2Bucket
   }
   ```

3. **Add to Env type** (if using a custom type):
   ```typescript
   // apps/merchant/src/types.ts
   export interface Env extends Cloudflare.Env {
     NEW_BUCKET: R2Bucket
   }
   ```

## CI/CD Flow

The deployment process works as follows:

1. **Environment Artifact**: `create-env-artifact.yaml` generates an encrypted tarball containing:
   - `.env` file with all secrets
   - Generated `wrangler.jsonc`
   - `secrets.json` for bulk Wrangler secret upload

2. **Deployment Workflow**: `deploy-cloudflare-worker.yaml`:
   - Decrypts the artifact
   - Runs `wrangler secret bulk` with `secrets.json`
   - Deploys the worker

3. **Frontend Variables**: To expose variables to the frontend:
   ```javascript
   // apps/client/vite.config.ts
   define: {
     'import.meta.env.STORE_URL': JSON.stringify(process.env.STORE_URL),
     'import.meta.env.PERMISSIONS': JSON.stringify(scopesArray)
   }
   ```

4. **Development Command**:
   ```bash
   npm run dev:env -- --base=/testing
   ```
   This starts both worker and frontend with proper environment variables.
