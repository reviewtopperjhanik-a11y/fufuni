## Outbound Webhooks Overview

Fufuni provides an outbound webhook system to notify external services about events occurring within the merchant store. Unlike inbound webhooks (like those received from Stripe), outbound webhooks are dispatched by the Fufuni Durable Object to URLs you register. This system ensures high availability through asynchronous delivery, persistent logging in SQLite, and an exponential back-off retry mechanism.

### Event Types and Triggers

Webhooks are triggered at specific points in the order and inventory lifecycle. Subscribers can listen for specific events or use wildcards (e.g., `order.*` or `*`).

| Event Name | Trigger Point |
| :--- | :--- |
| `order.created` | Dispatched immediately after a successful checkout and order record creation. |
| `order.updated` | Dispatched when an order status is manually updated by an admin. |
| `order.shipped` | Dispatched when an order's fulfillment status changes to shipped. |
| `order.refunded` | Dispatched when a payment refund is processed. |
| `inventory.low` | Dispatched when a product variant's available stock drops below the threshold (default: 5). |

## Delivery Mechanics and Retries

The Fufuni framework uses a "Fan-out" pattern. When an event occurs, the system queries all active webhooks, filters for subscribers, and creates a record in the `webhook_deliveries` table before attempting delivery.

### Retry Schedule

If an endpoint returns a status code outside the 2xx range (excluding 4xx errors other than 429), Fufuni initiates a retry loop.
- **Max Attempts:** 3
- **Back-off Logic:** Exponential back-off using $2^{attempt} \times 1000$ms.
- **Verified Fact Schedule:** Per system configuration, the standard retry delays are **1s, 4s, and 16s**.

```typescript
// Delivery loop logic in apps/merchant/src/lib/webhooks.ts
for (let attempt = 1; attempt <= MAX_ATTEMPTS; attempt++) {
  try {
    const response = await fetch(url, {
      method: 'POST',
      headers: { 'X-Fufuni-Signature': signature, /* ... */ },
      body: JSON.stringify(payload),
    });

    if (response.ok) {
      await db.run(`UPDATE webhook_deliveries SET status = 'success' WHERE id = ?`, [deliveryId]);
      return;
    }
  } catch (err) {
    // Wait before next attempt
    if (attempt < MAX_ATTEMPTS) {
      await new Promise((r) => setTimeout(r, Math.pow(2, attempt) * 1000));
    }
  }
}
```

## Security: Signature Verification

To ensure that a webhook request actually came from your Fufuni instance, you **must** verify the HMAC-SHA256 signature provided in the headers.

### Signature Headers

- `X-Fufuni-Signature`: The hex-encoded HMAC-SHA256 signature.
- `X-Fufuni-Timestamp`: The Unix timestamp when the signature was generated (to prevent replay attacks).
- `X-Fufuni-Delivery-Id`: A unique ID for the specific delivery attempt.

### Node.js Verification Example

The following example demonstrates how a consumer service (using Express or Hono) should verify the payload using the `whsec_` secret obtained during registration.

```typescript
import crypto from 'node:crypto';

function verifyFufuniSignature(
  payload: string, 
  signature: string, 
  secret: string
): boolean {
  // 1. Recompute the HMAC-SHA256
  const hmac = crypto.createHmac('sha256', secret);
  const digest = hmac.update(payload).digest('hex');

  // 2. Constant-time comparison to prevent timing attacks
  try {
    return crypto.timingSafeEqual(
      Buffer.from(digest, 'hex'),
      Buffer.from(signature, 'hex')
    );
  } catch {
    return false;
  }
}
```

## Delivery Logs and Monitoring

Every delivery attempt is stored in the SQLite database within the Durable Object. This allows admins to audit failures and debug integration issues.

### Querying Delivery History

The `webhook_deliveries` table tracks the full lifecycle of a message. You can query this via the Admin API: `GET /v1/webhooks/{id}/deliveries/{deliveryId}`.

```sql
-- Internal schema for delivery tracking
SELECT 
    id, 
    event_type, 
    status, -- 'pending', 'success', 'failed'
    attempts, 
    response_code, 
    response_body, 
    created_at 
FROM webhook_deliveries 
WHERE webhook_id = ? 
ORDER BY created_at DESC 
LIMIT 50;
```

### Manual Resend

If a delivery fails permanently after 3 attempts, or if your external system was down for an extended period, you can trigger a manual retry through the UI or API. This resets the attempt counter and pushes the delivery back into the `pending` state for immediate processing.

```typescript
// Triggering a manual retry via API
adminApp.openapi(retryDeliveryRoute, async (c) => {
  const { id, deliveryId } = c.req.valid('param');
  const db = getDb(c.var.db);

  const [webhook] = await db.query<any>(`SELECT * FROM webhooks WHERE id = ?`, [id]);
  const [delivery] = await db.query<any>(
    `SELECT * FROM webhook_deliveries WHERE id = ? AND webhook_id = ?`,
    [deliveryId, id]
  );

  // Re-run the delivery logic asynchronously
  c.executionCtx.waitUntil(retryDelivery(c.var.db, webhook, delivery));

  return c.json({ status: 'pending', message: 'Delivery retry triggered' }, 200);
});
```

## Inbound vs. Outbound Webhooks

It is critical to distinguish between the two types of webhooks in the Fufuni framework:

### Inbound Webhooks (Stripe/Providers)
- **Source:** External (Stripe, PayPal, etc.).
- **Path:** `/v1/webhooks/stripe`.
- **Logic:** Defined in `apps/merchant/src/routes/webhooks.ts`.
- **Purpose:** To inform Fufuni that a payment succeeded so Fufuni can create an order.
- **Security:** Uses `stripe.webhooks.constructEvent` with the `STRIPE_WEBHOOK_SECRET`.

### Outbound Webhooks (Fufuni Events)
- **Source:** Internal (Fufuni Merchant App).
- **Path:** Registered URLs (User-defined).
- **Logic:** Defined in `apps/merchant/src/routes/webhooks-outbound.ts` and `lib/webhooks.ts`.
- **Purpose:** To inform external systems (ERP, CRM, Analytics) that a Fufuni event occurred.
- **Security:** Uses `X-Fufuni-Signature` with the `whsec_` secret.
