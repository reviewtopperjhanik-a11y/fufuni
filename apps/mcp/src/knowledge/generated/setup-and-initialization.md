## Initial Setup Status

The Fufuni framework uses a "first-run" detection mechanism to determine if the store needs configuration. The frontend setup wizard relies on the `GET /v1/setup/status` endpoint to check if an administrative user has already been created. This endpoint is public and does not require authentication, as its primary purpose is to block the setup flow once the store is live.

```typescript
import { createRoute, z } from '@hono/zod-openapi';

const SetupStatusResponse = z.object({
  initialized: z.boolean().openapi({
    description: 'Returns true if an admin user already exists in the system',
    example: false,
  }),
}).openapi('SetupStatusResponse');

export const getSetupStatus = createRoute({
  method: 'get',
  path: '/v1/setup/status',
  tags: ['Setup'],
  summary: 'Check initialization status',
  responses: {
    200: {
      content: { 'application/json': { schema: SetupStatusResponse } },
      description: 'Setup status retrieved',
    },
  },
});
```

In the frontend, if `initialized` returns `false`, the user is automatically redirected to the `/setup` route to begin the onboarding process. Once initialized, this endpoint remains active but returns `true`, causing the setup wizard to become inaccessible to prevent accidental re-configuration.

## Primary Store Initialization

The core of the onboarding process is the `POST /v1/setup/init` endpoint. This is a high-privilege operation that can only be executed once. It performs several critical tasks: creating the initial admin user, setting up the store profile, and establishing the default financial settings (currency and country).

### Request Payload and Idempotency

The endpoint enforces strict idempotency. If an admin user or store configuration already exists, the backend returns a `409 Conflict` error to prevent overwriting the existing state.

```typescript
const SetupInitBody = z.object({
  adminEmail: z.string().email().openapi({ example: 'admin@fufuni.io' }),
  storeName: z.string().min(1).openapi({ example: 'Fufuni Official Store' }),
  defaultCurrency: z.string().length(3).openapi({ example: 'USD' }),
  defaultCountryCode: z.string().length(2).openapi({ example: 'US' }),
}).openapi('SetupInitBody');

export const postSetupInit = createRoute({
  method: 'post',
  path: '/v1/setup/init',
  tags: ['Setup'],
  request: {
    body: { content: { 'application/json': { schema: SetupInitBody } } },
  },
  responses: {
    200: { content: { 'application/json': { schema: z.object({ ok: z.boolean() }) } }, description: 'Setup successful' },
    409: { content: { 'application/json': { schema: z.object({ error: z.string() }) } }, description: 'Already initialized' },
  },
});
```

During this call, the system:
1.  **Validates** the absence of an existing admin.
2.  **Creates** the `regions` and `currencies` records based on the provided default country and currency.
3.  **Inserts** the initial store metadata into the `config` table.
4.  **Triggers** the Auth0 Management API to invite the specified `adminEmail`.

## Setup Wizard Frontend Flow

The frontend wizard (located in `apps/client/src/pages/setup/`) is a step-by-step UI built with HeroUI v3 that guides the merchant through three distinct phases.

### Step 1: Store & Currency Identity
The user provides the `storeName`, `defaultCurrency`, and `defaultCountryCode`. This determines the primary locale of the commerce instance.

### Step 2: Administrative Access
The user enters the `adminEmail`. This email is used to create the first identity in the Auth0 tenant and assign the `admin:store` or `admin:database` scopes.

### Step 3: Tenant Verification
The system verifies the Auth0 tenant configuration. If `AUTH0_MANAGEMENT_CLIENT_ID` and related secrets are present, the system automatically runs the equivalent of `auth0:deploy` to configure the tenant's rules, roles, and branding to match the Fufuni requirements.

```typescript
// Example of the frontend submitting the wizard data
async function handleSetupSubmit(data: SetupFormData) {
  const response = await fetch('/v1/setup/init', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(data),
  });

  if (response.status === 409) {
    toast.error('Store already initialized. Please log in.');
    return;
  }

  if (response.ok) {
    navigate('/setup/complete');
  }
}
```

## API Key and Security Initialization

Before the store logic is even accessible, the low-level infrastructure requires API keys for system-to-system communication. The `adminSetup` router provides an `/init` path (separate from the merchant setup) specifically for seeding `api_keys`.

```typescript
const InitKeysBody = z.object({
  keys: z.array(z.object({
    id: z.string().uuid(),
    key_hash: z.string(),
    key_prefix: z.string(),
    role: z.enum(['public', 'admin']),
  })),
}).openapi('InitKeysBody');

// This endpoint is used by CLI tools or deployment scripts
// to inject the primary admin keys into the SQLite database.
adminApp.openapi(initKeys, async (c) => {
  const { keys } = c.req.valid('json');
  const db = getDb(c.var.db);

  const existing = await db.query(`SELECT id FROM api_keys LIMIT 1`);
  if (existing.length > 0) {
    throw ApiError.conflict('API keys already exist.');
  }

  for (const key of keys) {
    await db.run(
      `INSERT INTO api_keys (id, key_hash, key_prefix, role, created_at) 
       VALUES (?, ?, ?, ?, ?)`,
      [key.id, key.key_hash, key.key_prefix, key.role, now()]
    );
  }
  return c.json({ ok: true }, 200);
});
```

## Auth0 Management API Integration

Fufuni relies on the Auth0 Management API for user provisioning during the setup phase. When `POST /v1/setup/init` is called, the backend uses the configured `AUTH0_DOMAIN` and `AUTH0_MANAGEMENT_CLIENT_SECRET` to interact with the Auth0 instance.

1.  **User Creation**: It checks if the user exists in Auth0. If not, it creates the user record.
2.  **Invitation**: It triggers a password reset or verification email to act as an "invite."
3.  **Role Assignment**: It assigns the `admin` role to ensure the user has the necessary JWT scopes (`admin:store`, `admin:database`) to manage the backend.

If the Auth0 tenant has not been configured yet (missing Fufuni-specific rules or connections), and the management credentials are provided, the framework performs a self-deployment to ensure the tenant state matches the required schema.

## Database Migrations and Maintenance

The setup process also involves ensuring the SQLite schema in the Durable Object is up-to-date. The `adminSetup` router exposes endpoints to list and run migrations.

```typescript
const listMigrations = createRoute({
  method: 'get',
  path: '/migrations/list',
  tags: ['Setup'],
  security: [{ bearerAuth: ["admin:database"] }],
  responses: {
    200: { 
      content: { 'application/json': { schema: MigrationListResponse } },
      description: 'List of applied SQL migrations' 
    },
  },
});

adminApp.openapi(listMigrations, async (c) => {
  const db = getDb(c.var.db);
  const items = await db.query<{ name: string; applied_at: string }>(
    `SELECT name, applied_at FROM migrations ORDER BY applied_at ASC`
  );
  return c.json({ items }, 200);
});
```

To run pending migrations, the frontend or a CLI tool calls `POST /migrations/run`. In Fufuni, this is often implemented as a side effect of a standard query (like `SELECT 1`) because the `getDb()` utility handles schema verification and migration execution lazily when the database connection is initialized.

## Post-Setup Management

Once the initial setup is complete, standard store information (logo, support email, social links) is no longer managed via the setup endpoints. Developers must use the dedicated `/v1/store-info` routes.

```typescript
const UpdateStoreInfoBody = z.object({
  name: z.string().optional(),
  logo_url: z.string().url().optional(),
  support_email: z.string().email().optional(),
  social_links: z.record(z.string()).optional(),
}).openapi('UpdateStoreInfoBody');

// Example PUT handler for store information
// This requires a valid Admin JWT (admin:store scope)
adminApp.openapi(updateStoreInfo, async (c) => {
  const data = c.req.valid('json');
  const db = getDb(c.var.db);
  
  const configValue = JSON.stringify(data);
  await db.run(
    `INSERT INTO config (key, value, updated_at) VALUES ('store_info', ?, ?)
     ON CONFLICT(key) DO UPDATE SET value = ?, updated_at = ?`,
    [configValue, now(), configValue, now()]
  );

  return c.json({ ok: true });
});
```

## Database Reset and Recovery

In development or staging environments, it may be necessary to wipe the system and restart the setup wizard. The `POST /v1/setup/reset` endpoint handles this by disabling foreign key constraints and purging all tables in the correct order.

```sql
-- The logic used by the reset handler
PRAGMA foreign_keys = OFF;
DELETE FROM product_reviews;
DELETE FROM orders;
DELETE FROM products;
DELETE FROM regions;
DELETE FROM config;
DELETE FROM api_keys;
-- ... all other tables ...
PRAGMA foreign_keys = ON;
```

This operation requires the `admin:database` scope and is typically restricted to JWT-based authentication only, preventing API keys from accidentally triggering a total data loss. Once the reset is complete, `GET /v1/setup/status` will return `initialized: false`, allowing the wizard to run again.
