## The ApiError Class Specification

The Fufuni framework uses a centralized `ApiError` class to standardize how the backend communicates failures to the frontend. Instead of returning raw `Response` objects manually, developers should throw an instance of `ApiError`. This ensures that the HTTP status code, the machine-readable error code, and the human-readable message are always consistent.

### Helper Methods Reference

The following static methods are available on the `ApiError` class to handle common REST scenarios:

| Method | HTTP Status | Error Code | Typical Use Case |
| :--- | :--- | :--- | :--- |
| `badRequest(msg, details?)` | 400 | `bad_request` | Generic client-side errors or malformed payloads. |
| `invalidRequest(msg, details?)` | 400 | `invalid_request` | Schema validation failures (e.g., Zod issues). |
| `unauthorized(msg?)` | 401 | `unauthorized` | Missing or expired credentials/tokens. |
| `forbidden(msg?)` | 403 | `forbidden` | Authenticated but lacks required permissions (RBAC). |
| `notFound(msg?)` | 404 | `not_found` | Resource (Product, Order, etc.) does not exist in SQLite. |
| `conflict(msg)` | 409 | `conflict` | Unique constraint violations (e.g., duplicate email). |
| `insufficientInventory(sku)` | 409 | `insufficient_inventory` | Attempting to purchase more items than available in stock. |
| `internalServerError(msg?)`| 500 | `internal_server_error` | Unexpected server crashes or logic failures. |
| `stripeError(msg)` | 502 | `stripe_error` | Failures communicating with the Stripe Gateway. |

### The Error Response Shape

When an `ApiError` is thrown, the Hono global error handler (located in the app initialization) catches it and serializes it into a standard JSON envelope. This structure is what the frontend expects.

```typescript
// Standard JSON Error Envelope
{
  "error": {
    "code": "not_found",
    "message": "The requested product was not found in this store.",
    "details": {
      "id": "prod_123"
    }
  }
}
```

## Backend Implementation Examples

The backend uses these helpers inside Hono route handlers. Because they are instances of `Error`, throwing them immediately halts execution and triggers the error response lifecycle.

### Resource Verification and 404s

In this example, we attempt to retrieve a product. If the SQLite query returns an empty array, we throw a `notFound` error.

```typescript
import { Hono } from 'hono';
import { ApiError, type HonoEnv } from '@/types';

const app = new Hono<HonoEnv>();

app.get('/products/:id', async (c) => {
  const { id } = c.req.param();
  const db = c.get('db');

  const products = await db.query(
    'SELECT * FROM products WHERE id = ?',
    [id]
  );

  if (products.length === 0) {
    // Standardizing the 404 response
    throw ApiError.notFound(`Product with ID ${id} not found`);
  }

  return c.json(products[0]);
});
```

### Authorization and RBAC (403/401)

The framework automatically handles initial JWT validation, but specific route logic might require manual permission checks using `c.var.auth`.

```typescript
app.delete('/settings', async (c) => {
  const auth = c.get('auth');

  // Check if the user has specific admin privileges
  if (!auth.permissions?.includes('admin:settings')) {
    throw ApiError.forbidden('You do not have permission to delete store settings');
  }

  // Implementation logic...
  return c.json({ success: true });
});
```

### Inventory Management and Conflict (409)

The `insufficientInventory` helper is specialized for e-commerce logic. It automatically includes the `sku` in the `details` block.

```typescript
app.post('/checkout', async (c) => {
  const { sku, quantity } = await c.req.json();
  const db = c.get('db');

  const [inventory] = await db.query<{ stock: number }>(
    'SELECT stock FROM inventory WHERE sku = ?',
    [sku]
  );

  if (!inventory || inventory.stock < quantity) {
    // This specifically triggers code: 'insufficient_inventory'
    throw ApiError.insufficientInventory(sku);
  }

  // Continue checkout...
});
```

### Data Validation and Metadata (400)

When using `invalidRequest`, you can pass an object containing field-level errors to help the frontend highlight specific inputs.

```typescript
app.patch('/profile', async (c) => {
  const body = await c.req.json();

  if (!body.email || !body.email.includes('@')) {
    throw ApiError.invalidRequest('Invalid profile data', {
      email: 'A valid email address is required',
      received: body.email
    });
  }

  // Save profile...
});
```

## Creating Custom Errors

If the standard static helpers do not cover your use case, you can instantiate `ApiError` directly. This is useful for domain-specific status codes or custom machine-readable codes.

```typescript
app.post('/gift-cards/redeem', async (c) => {
  const { code } = await c.req.json();
  
  const [card] = await c.get('db').query(
    'SELECT * FROM gift_cards WHERE code = ?',
    [code]
  );

  if (card.is_expired) {
    // Custom error code 'expired_card' with a 410 Gone status
    throw new ApiError(
      'expired_card',
      410,
      'This gift card expired on ' + card.expiry_date,
      { expiredAt: card.expiry_date }
    );
  }
});
```

## Frontend: Handling Errors with useSecuredApi

In the Fufuni frontend (React 19), communication with the backend is typically managed through the `useSecuredApi` hook. This hook handles Auth0 token injection and response parsing.

When the backend throws an `ApiError`, the promise returned by the API call will reject. You should catch these rejections and handle them using the structured properties.

### Integration with HeroUI Toasts

The standard way to inform the user is using `addToast` from HeroUI v3.

```typescript
import React from 'react';
import { useSecuredApi } from '@/hooks/useSecuredApi';
import { addToast, Button } from '@heroui/react';

export const ProductDeleter = ({ productId }: { productId: string }) => {
  const api = useSecuredApi();
  const [isLoading, setIsLoading] = React.useState(false);

  const handleDelete = async () => {
    setIsLoading(true);
    try {
      await api.delete(`/products/${productId}`);
      addToast({
        title: "Success",
        description: "Product removed.",
        color: "success"
      });
    } catch (err: any) {
      // Accessing the standardized error shape
      const errorData = err.data?.error;
      
      const message = errorData?.message || "An unexpected error occurred";
      const code = errorData?.code || "unknown_error";

      addToast({
        title: `Error: ${code}`,
        description: message,
        color: "danger"
      });

      if (code === 'insufficient_inventory') {
        console.error("SKU out of stock:", errorData.details.sku);
      }
    } finally {
      setIsLoading(false);
    }
  };

  return (
    <Button 
      color="danger" 
      isLoading={isLoading} 
      onPress={handleDelete}
    >
      Delete Product
    </Button>
  );
};
```

### Global Error Transformation

Inside `useSecuredApi`, the response interceptor ensures that the error body is attached to the rejected promise. It is critical to check for `err.data.error` to access the Fufuni-specific `ApiError` fields.

```typescript
// Logic simplified from the useSecuredApi implementation
const response = await fetch(url, options);
if (!response.ok) {
  const errorJson = await response.json().catch(() => ({}));
  const customError = new Error(errorJson.error?.message || 'API Error');
  // Attach the standard payload to the error object
  (customError as any).data = errorJson;
  (customError as any).status = response.status;
  throw customError;
}
```

### Form Field Validation Handling

When handling `invalidRequest` (400), you can map the `details` object directly to UI components like `HeroUI Input`.

```typescript
const [fieldErrors, setFieldErrors] = React.useState<Record<string, string>>({});

const onSubmit = async (data: FormData) => {
  try {
    await api.post('/resource', data);
  } catch (err: any) {
    if (err.data?.error?.code === 'invalid_request') {
      // Map details (field names) to local state
      setFieldErrors(err.data.error.details || {});
    }
  }
};

// In render:
<Input 
  label="Email"
  isInvalid={!!fieldErrors.email}
  errorMessage={fieldErrors.email}
  // ...
/>
```

## Best Practices

1.  **Never return raw strings**: Always use `ApiError` helpers so the frontend receives a predictable JSON structure.
2.  **Use `details` for dynamic data**: If an error involves a specific ID, SKU, or date, put it in the `details` object rather than just concatenating it into the `message` string. This allows the frontend to potentially localize or format the data differently.
3.  **Specific Codes over Status Codes**: Status codes (like 409) tell the browser how to behave, but Error Codes (like `insufficient_inventory`) tell the application logic how to behave. Always provide a specific code.
4.  **Security**: Avoid putting sensitive system information (like raw SQL query strings or stack traces) into the `message` or `details` of an `ApiError` that might be sent to a public client. Use `internalServerError` for generic "something went wrong" messages while logging the real error to the Worker console.
