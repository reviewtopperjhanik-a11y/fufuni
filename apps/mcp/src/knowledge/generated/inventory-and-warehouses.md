## Data Model and Schema

Fufuni uses a multi-layered inventory system that tracks stock at both an aggregated level (legacy support) and a granular per-warehouse level. While the API typically interacts via the SKU (Stock Keeping Unit), the underlying database relates stock to variants and specific physical locations.

### Database Tables

The core of the inventory system resides in two primary tables: `inventory` and `warehouse_inventory`.

```sql
-- Represents physical locations where stock is stored
CREATE TABLE warehouses (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  address TEXT,
  is_default INTEGER DEFAULT 0, -- 1 if this is the default warehouse for new products
  priority INTEGER DEFAULT 100, -- Lower number = higher priority for fulfillment
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);

-- Granular tracking per variant per warehouse
CREATE TABLE warehouse_inventory (
  id TEXT PRIMARY KEY,
  sku TEXT NOT NULL,
  warehouse_id TEXT NOT NULL,
  on_hand INTEGER DEFAULT 0,    -- Physical units in the building
  reserved INTEGER DEFAULT 0,   -- Units committed to unpaid orders/carts
  updated_at INTEGER NOT NULL,
  FOREIGN KEY (warehouse_id) REFERENCES warehouses(id)
);

-- Aggregated table for legacy lookups and fast dashboarding
CREATE TABLE inventory (
  sku TEXT PRIMARY KEY,
  on_hand INTEGER DEFAULT 0,
  reserved INTEGER DEFAULT 0,
  updated_at INTEGER NOT NULL
);
```

## Transaction Safety in Durable Objects

Inventory mutations are inherently sensitive to race conditions. Fufuni mitigates this by running all stock-related logic within **Durable Objects**. 

Since a Durable Object (DO) provides single-threaded execution for its specific state, requests are processed sequentially. This ensures that two simultaneous "Reserve" requests for the last remaining item cannot both succeed. Every stock adjustment is performed as an atomic operation against the local SQLite database within the DO.

```typescript
// Example of a transactional mutation within a DO request handler
async function handleStockAdjustment(db: Database, sku: string, delta: number) {
  // SQLite transaction ensures both log and level are updated together
  await db.run('BEGIN TRANSACTION');
  try {
    const result = await db.run(
      `UPDATE inventory 
       SET on_hand = on_hand + ?, updated_at = ? 
       WHERE sku = ? AND (on_hand + ?) >= 0`,
      [delta, Date.now(), sku, delta]
    );

    if (result.changes === 0) {
      throw new Error("Insufficient stock for reduction");
    }

    await db.run(
      `INSERT INTO inventory_logs (id, sku, delta, timestamp) VALUES (?, ?, ?, ?)`,
      [crypto.randomUUID(), sku, delta, Date.now()]
    );
    await db.run('COMMIT');
  } catch (e) {
    await db.run('ROLLBACK');
    throw e;
  }
}
```

## lib/inventory.ts Helper Functions

The framework provides four standard utility functions to manage stock levels. These should always be used instead of raw SQL updates to ensure the legacy `inventory` table and the `warehouse_inventory` tables remain in sync.

### 1. getStockLevel(db, variantId)
Calculates the total available units for a variant across all warehouses.
**Available = on_hand - reserved**.

```typescript
export async function getStockLevel(db: Database, sku: string): Promise<number> {
  const row = await db.queryFirst<{ available: number }>(
    `SELECT SUM(on_hand - reserved) as available 
     FROM warehouse_inventory 
     WHERE sku = ?`,
    [sku]
  );
  return row?.available ?? 0;
}
```

### 2. reserveStock(db, variantId, qty)
Called when a user adds an item to their cart or begins the checkout process. It moves units from "Available" to "Reserved".

```typescript
export async function reserveStock(db: Database, sku: string, qty: number): Promise<void> {
  // Logic: Finds warehouse with highest stock and increments 'reserved'
  const result = await db.run(
    `UPDATE warehouse_inventory 
     SET reserved = reserved + ?, updated_at = ?
     WHERE sku = ? AND (on_hand - reserved) >= ?
     ORDER BY (on_hand - reserved) DESC LIMIT 1`,
    [qty, Date.now(), sku, qty]
  );
  
  if (result.changes === 0) throw ApiError.insufficientInventory(sku);
}
```

### 3. releaseStock(db, variantId, qty)
Called when a checkout fails, a cart expires, or an order is cancelled. It decrements the `reserved` count, making the units available for other customers again.

### 4. deductStock(db, variantId, qty)
Called after a successful payment (e.g., Stripe Webhook). It permanently decrements both `on_hand` and `reserved` counts. This is the final step in the inventory lifecycle.

## Checkout Lifecycle

The inventory state transitions through several phases during a customer's journey:

1.  **Selection**: Customer views product. The UI calls `getStockLevel` to show availability.
2.  **Reservation**: Customer proceeds to checkout. The system calls `reserveStock`. The items are now "held" and cannot be sold to others.
3.  **Outcome A (Success)**: Payment is confirmed. The system calls `deductStock`. Physical `on_hand` inventory is reduced.
4.  **Outcome B (Failure/Cancel)**: Payment fails or the session times out. The system calls `releaseStock`. The `reserved` count is cleared.

| Event | `on_hand` | `reserved` | `available` |
| :--- | :--- | :--- | :--- |
| Initial State | 10 | 0 | 10 |
| **reserveStock(2)** | 10 | 2 | 8 |
| **deductStock(2)** (Success) | 8 | 0 | 8 |
| *OR* **releaseStock(2)** (Failure) | 10 | 0 | 10 |

## Admin Endpoints

Administrators manage stock levels through the `merchant` API. These routes require `admin:store` or `legacy sk_` scopes.

### List Inventory
`GET /v1/inventory` lists aggregated levels.
`GET /v1/inventory/:variantId` returns a breakdown per warehouse.

```bash
# Get stock for a specific SKU
curl -X GET "https://api.fufuni.com/v1/inventory/TSHIRT-BLUE-L" \
     -H "Authorization: Bearer $ADMIN_TOKEN"
```

### Adjust Stock
`POST /v1/inventory/adjust` is used for manual corrections, restocks, or shrinkage logs. The `delta` can be positive or negative.

```typescript
// Admin Route: Adjusting stock for a specific warehouse
adminApp.openapi(adjustInventoryRoute, async (c) => {
  const { variantId, warehouseId, delta } = c.req.valid('json');
  const db = getDb(c.var.db);

  await db.run(
    `UPDATE warehouse_inventory 
     SET on_hand = on_hand + ?, updated_at = ? 
     WHERE sku = ? AND warehouse_id = ?`,
    [delta, Date.now(), variantId, warehouseId]
  );
  
  return c.json({ success: true }, 200);
});
```

### Warehouse CRUD
Warehouses are managed via `POST /v1/warehouses`. 
- New products automatically create `warehouse_inventory` entries for the warehouse marked `is_default: 1`.
- Deleting a warehouse is only permitted if all `on_hand` values for that location are zero.

## Low-Stock Webhooks

The framework monitors inventory levels during every `deductStock` operation. If the remaining `available` quantity falls below a defined threshold, a webhook event is triggered.

### Trigger Condition
- **Threshold**: Defaults to 10 units (configurable in store settings).
- **Timing**: Checked immediately after `deductStock` or `adjustInventory`.

### Webhook Payload
The event `inventory.low_stock` is dispatched to registered endpoints.

```json
{
  "event": "inventory.low_stock",
  "created_at": 1700000000,
  "data": {
    "sku": "TSHIRT-BLUE-L",
    "available_quantity": 4,
    "threshold": 10,
    "warehouse_id": "wh_primary",
    "product_id": "prod_12345"
  }
}
```

## Multi-Warehouse Logic

Fufuni supports complex fulfillment scenarios through warehouse priorities and regional grouping.

### Stock Aggregation
When the frontend asks for product availability, the backend aggregates all rows for that SKU in the `warehouse_inventory` table. This allows a merchant to sell stock located in London and New York as a single pool of items.

### Fulfillment Priority
When `reserveStock` is called without a specific `warehouse_id`, Fufuni uses an "Available First" strategy:
1.  Query all warehouses containing the SKU.
2.  Sort by `(on_hand - reserved) DESC`.
3.  Allocate the reservation to the warehouse with the most current slack.
4.  If multiple warehouses have equal stock, the one with the lowest `priority` value (integer) is chosen.

### Default Warehouse
The `is_default` flag on the `warehouses` table identifies the primary intake location. When a new product variant is created via the dashboard, the system automatically initializes an inventory record for this warehouse with `on_hand: 0`.

```typescript
// Initializing a new SKU in the default warehouse
const defaultWh = await db.queryFirst('SELECT id FROM warehouses WHERE is_default = 1');
if (defaultWh) {
  await db.run(
    'INSERT INTO warehouse_inventory (id, sku, warehouse_id, on_hand, reserved, updated_at) VALUES (?, ?, ?, 0, 0, ?)',
    [crypto.randomUUID(), newSku, defaultWh.id, Date.now()]
  );
}
```
