## Order Lifecycle & Status Machine

The Fufuni framework manages orders through a strictly defined state machine. Every order progresses from an initial intent to a final delivered or terminal state (cancelled/refunded). Status changes are not merely database updates; they trigger side effects including transactional emails via Mailgun and webhook dispatches to external integrations.

### Status Transition Diagram

```text
[ pending ] ────────────────┐
     │                      │
(Payment Success)           (Manual/System Timeout)
     │                      │
     v                      v
[   paid  ] ──────────> [ cancelled ] (Restores Inventory)
     │
(Start Fulfillment)
     │
     v
[ processing ] ───────> [ refunded ] (Stripe Refund + DB Entry)
     │
(Add Tracking)
     │
     v
[  shipped  ] ────────> [ partially_refunded ]
     │
(Delivery Confirmed)
     │
     v
[ delivered ]
```

### Valid Transitions and Side Effects

| Status | Meaning | Side Effect |
| :--- | :--- | :--- |
| `pending` | Order created, awaiting Stripe payment. | None. |
| `paid` | Payment confirmed by Stripe webhook. | Customer confirmation email sent. |
| `processing` | Admin has acknowledged the order. | `order.updated` webhook. |
| `shipped` | Carrier tracking info added. | Shipping email sent; `shipped_at` timestamp set. |
| `delivered` | Final delivery confirmed. | Delivery confirmation email. |
| `cancelled` | Order voided before fulfillment. | **Inventory restored** to origin warehouse. |
| `refunded` | Full payment returned via Stripe. | Refund email sent; status updated to `refunded`. |

All administrative order endpoints require the `admin:store` permission or a legacy Secret Key (`sk_`).

## Updating Order Status

Administrators update orders via the `PATCH /v1/orders/{orderId}` endpoint. This endpoint is reactive: if you update the status to `shipped`, the system automatically captures the current time into `shipped_at` and triggers the shipping notification email.

### Example: Marking an Order as Shipped

```typescript
// apps/merchant/src/routes/orders.ts (Simplified Logic)
adminApp.openapi(updateOrder, async (c) => {
  const { orderId } = c.req.valid('param');
  const { status, tracking_number, tracking_url } = c.req.valid('json');
  const db = getDb(c.var.db);

  const updates: string[] = [];
  const params: unknown[] = [];

  if (status === 'shipped') {
    updates.push('status = ?, shipped_at = ?');
    params.push('shipped_at', now());
    
    // Trigger transactional email via worker's execution context
    c.executionCtx.waitUntil(
      sendOrderStatusEmail(c.env, c.var.db, orderId, 'shipped')
    );
  }

  params.push(orderId);
  await db.run(`UPDATE orders SET ${updates.join(', ')} WHERE id = ?`, params);
  
  return c.json({ success: true });
});
```

## Refund Flow & Stripe Integration

Fufuni supports both full and partial refunds. When a refund is initiated, the framework communicates with Stripe's API first. Only if Stripe confirms the transaction does Fufuni record the refund in the local SQLite `refunds` table and update the order status.

### Processing a Partial Refund

```typescript
// Example of a POST request to /v1/orders/{id}/refund
// Body: { "amount_cents": 5000, "reason": "requested_by_customer" }

adminApp.openapi(refundOrder, async (c) => {
  const { orderId } = c.req.valid('param');
  const { amount_cents, reason } = c.req.valid('json');
  const db = getDb(c.var.db);
  
  // 1. Fetch order for Stripe Payment Intent ID
  const [order] = await db.query<any>(`SELECT * FROM orders WHERE id = ?`, [orderId]);
  
  // 2. Execute Stripe Refund
  const stripe = new Stripe(c.get('auth').stripeSecretKey!);
  const stripeRefund = await stripe.refunds.create({
    payment_intent: order.stripe_payment_intent_id,
    amount: amount_cents, // if null, Stripe does full refund
    reason: reason as Stripe.RefundCreateParams.Reason,
  });

  // 3. Log to audit trail
  await db.run(
    `INSERT INTO refunds (id, order_id, stripe_refund_id, amount_cents, status, created_at)
     VALUES (?, ?, ?, ?, ?, ?)`,
    [uuid(), orderId, stripeRefund.id, stripeRefund.amount, 'succeeded', now()]
  );

  // 4. Update order status based on remaining balance
  const newStatus = (amount_cents >= order.total_cents) ? 'refunded' : 'partially_refunded';
  await db.run(`UPDATE orders SET status = ? WHERE id = ?`, [newStatus, orderId]);

  return c.json({ status: newStatus, refund_id: stripeRefund.id });
});
```

## Order Cancellation & Inventory Restoration

Cancelling an order is a critical operation because it must reverse the inventory deductions made during the checkout process. Fufuni iterates through all `order_items` and increments the `on_hand` count in the `warehouse_inventory` table (or the global `inventory` table if warehouses are not utilized).

### Inventory Recovery Logic

```sql
-- This operation is typically wrapped in a transaction or sequential run block
-- Step 1: Update order status
UPDATE orders SET status = 'cancelled', updated_at = '2025-01-01T10:00:00Z' WHERE id = 'ORD_123';

-- Step 2: Loop through items and restore (Pseudo-code logic handled by the Worker)
-- For each item in order_items:
UPDATE warehouse_inventory 
SET on_hand = on_hand + ?, 
    updated_at = ? 
WHERE sku = ? AND warehouse_id = ?;
```

```typescript
// Implementation in Hono route
const items = await db.query<any>(`SELECT sku, qty, warehouse_id FROM order_items WHERE order_id = ?`, [orderId]);

for (const item of items) {
  if (item.warehouse_id) {
    await db.run(
      `UPDATE warehouse_inventory SET on_hand = on_hand + ? WHERE sku = ? AND warehouse_id = ?`,
      [item.qty, item.sku, item.warehouse_id]
    );
  } else {
    await db.run(
      `UPDATE inventory SET on_hand = on_hand + ? WHERE sku = ?`,
      [item.qty, item.sku]
    );
  }
}
```

## CSV Export for Accounting

The main order list endpoint doubles as a reporting tool. By appending `export=csv`, the backend bypasses JSON serialization and returns a standard CSV file. This is filtered by `from` and `to` ISO timestamps to generate monthly or quarterly reports.

### Requesting an Export

```bash
# Export all orders for March 2026
curl -X GET "https://api.fufuni.com/v1/orders?export=csv&from=2026-03-01T00:00:00Z&to=2026-03-31T23:59:59Z" \
     -H "Authorization: Bearer YOUR_ADMIN_TOKEN" \
     --output march_orders.csv
```

The CSV includes columns for:
- `number` (The human-readable ORD-XXXX-XXXX)
- `customer_email`
- `total_cents` & `currency`
- `tax_cents`
- `status`
- `created_at`

## Order Item Immutability

One of the most important architectural decisions in Fufuni is the **capture-at-purchase** pattern for order items. When an order is created, the system copies the current price, tax rate, and product title into the `order_items` table. 

**Why this is necessary:**
1. **Price Changes:** If a product was $10 when the customer bought it, but the price is raised to $15 later, the order history must still reflect $10.
2. **Product Deletion:** If a variant is deleted from the `variants` table, the order must remain intact for tax and audit purposes.
3. **Multi-Currency:** The `currency` and `unit_price_cents` are locked to the currency used at the moment of checkout.

### Order Item Schema (SQL)

```sql
CREATE TABLE order_items (
  id TEXT PRIMARY KEY,
  order_id TEXT NOT NULL,
  sku TEXT NOT NULL,
  title TEXT NOT NULL, -- Captured at purchase
  qty INTEGER NOT NULL,
  unit_price_cents INTEGER NOT NULL, -- Captured at purchase
  tax_rate REAL DEFAULT 0, -- Captured at purchase
  tax_amount_cents INTEGER DEFAULT 0, -- Captured at purchase
  warehouse_id TEXT, -- ID of the warehouse that fulfilled this item
  FOREIGN KEY (order_id) REFERENCES orders(id)
);
```
