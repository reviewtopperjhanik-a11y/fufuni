## How to Add a Database Migration

### When to use a migration (vs editing the SCHEMA constant directly)

Use a migration when:
- Adding new tables or columns to an existing database
- Modifying existing schema in a way that must be applied to deployed instances
- You need forward-compatibility with the migration system

Edit the `SCHEMA` constant directly only when:
- Creating the initial schema for a new database
- Making changes that don't affect existing data (rare)

## Exact Steps

### 1. Create the SQL file

1. Create a new file in `apps/merchant/migrations/` with the pattern `NNN-description.sql` where:
   - `NNN` is the next 3-digit number (current highest is 034)
   - `description` is kebab-case (e.g., `035-add-tags.sql`)

2. Add `PRAGMA foreign_keys = ON;` at the top
3. Use `IF NOT EXISTS` for all `CREATE TABLE` and `CREATE INDEX` statements
4. Include comments explaining the purpose

**Example:**
```sql
-- Migration 035: Product tags
-- Hierarchical tag system for product categorization.

PRAGMA foreign_keys = ON;

CREATE TABLE IF NOT EXISTS tags (
  id          TEXT PRIMARY KEY,
  name        TEXT NOT NULL,
  slug        TEXT NOT NULL UNIQUE,
  parent_id   TEXT REFERENCES tags(id) ON DELETE SET NULL,
  position    INTEGER NOT NULL DEFAULT 0,
  status      TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active', 'inactive')),
  created_at  TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at  TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE IF NOT EXISTS product_tags (
  product_id  TEXT NOT NULL REFERENCES products(id) ON DELETE CASCADE,
  tag_id      TEXT NOT NULL REFERENCES tags(id) ON DELETE CASCADE,
  PRIMARY KEY (product_id, tag_id)
);

CREATE INDEX IF NOT EXISTS idx_product_tags_tag ON product_tags(tag_id);
CREATE INDEX IF NOT EXISTS idx_tags_slug ON tags(slug) WHERE status = 'active';
```

## Common Pitfalls

1. **Missing `IF NOT EXISTS`**: Always include it for `CREATE TABLE` and `CREATE INDEX` statements
2. **Idempotency**: Migrations must run multiple times without error
3. **Column types**: Use:
   - `TEXT` for UUIDs and ISO dates
   - `INTEGER` for booleans (0/1) and cents
   - `REAL` for percentages and ratings
4. **Name mismatch**: The migration `name` must exactly match the SQL file stem (e.g., `035-add-tags` for `035-add-tags.sql`)
5. **Foreign key constraints**: Include `PRAGMA foreign_keys = ON;` at the top of migration files
6. **Index naming**: Follow the pattern `idx_[table]_[column]` for consistency

Remember: Never modify existing migrations after deployment. Always create new migrations for changes.
