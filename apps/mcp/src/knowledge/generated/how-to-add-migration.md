## When to Use a Migration

Use a migration **whenever you modify the database schema**:
- Adding/removing tables, columns, or indexes
- Altering column types or constraints
- Adding seed data (e.g., default themes)

**Do NOT edit the `SCHEMA` constant directly** unless you are also creating a migration. The `SCHEMA` constant is a **source of truth for new Durable Objects**, while migrations handle **upgrades for existing instances**.

## Common Pitfalls

### 1. **Idempotency Violations**
- **Problem**: Running the same migration twice fails (e.g., `CREATE TABLE` without `IF NOT EXISTS`).
- **Fix**: Always use `IF NOT EXISTS` for tables/indexes and `INSERT OR IGNORE` for seed data.

### 2. **Mismatched Migration Names**
- **Problem**: The `name` in `ensureInitialized()` does not match the SQL file stem (e.g., `"035-tags"` vs `035-add-tags.sql`).
- **Fix**: Use the exact file stem (e.g., `"035-add-tags"`).

### 3. **Incorrect Column Types**
- **Problem**: Using `BOOLEAN` (not supported in SQLite) or `VARCHAR` (use `TEXT` instead).
- **Fix**: Stick to these types:
  - **UUIDs/ISO dates**: `TEXT`
  - **Booleans**: `INTEGER` (0/1)
  - **Cents/quantities**: `INTEGER`
  - **Percentages/ratings**: `REAL`

### 4. **Missing Foreign Key Support**
- **Problem**: Forgetting `PRAGMA foreign_keys = ON` in the SQL file.
- **Fix**: Add it at the top of every migration file.

### 5. **Non-Atomic Schema Changes**
- **Problem**: Splitting a logical change (e.g., adding a column + its index) across multiple migrations.
- **Fix**: Group related changes into a single migration.

### 6. **Editing Deployed Migrations**
- **Problem**: Modifying an existing migration file after deployment.
- **Fix**: Always create a **new migration** (e.g., `036-fix-tags.sql`).
