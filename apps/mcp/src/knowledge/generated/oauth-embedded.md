## Purpose of the Embedded OAuth2 Server

While Fufuni uses Auth0 as the primary identity provider for customer and merchant web sessions, the framework includes a built-in OAuth2 server to handle **Machine-to-Machine (M2M)** authentication and third-party integrations. This allows external services, AI agents, or specialized mobile apps to interact with the Merchant API without requiring a browser-based Auth0 flow.

The embedded server is designed for high performance within Cloudflare Workers, leveraging SQLite (Durable Objects) for client storage and HS256 JWTs for stateless verification. It strictly follows the OAuth 2.0 specification for `client_credentials` and `authorization_code` grants, though for backend-to-backend communication, the `client_credentials` flow is the standard entry point.

### Router Configuration Example

The OAuth server is typically mounted at `/v1/oauth` within the merchant application.

```typescript
import { Hono } from 'hono';
import { oauth } from './routes/oauth';
import { oauthMiddleware } from './middleware/auth';

const app = new Hono<{ Bindings: Bindings }>();

// OAuth2 Endpoints (Token issuance, Discovery)
app.route('/v1/oauth', oauth);

// Example of a protected route accepting OAuth tokens
app.get('/v1/products', oauthMiddleware, async (c) => {
  const scopes = c.get('jwtPayload').scopes;
  // logic...
  return c.json({ items: [] });
});
```

## Client Registration and Management

OAuth clients represent the external applications authorized to access the API. Registration is performed via admin-only endpoints. When a client is created, the system generates a `client_id` and a `client_secret`. 

**Critical Security Rule:** The `client_secret` is stored using a bcrypt hash in the `oauth_clients` table. It is returned in plaintext **only once** during the creation response. If lost, the secret must be rotated by deleting and recreating the client or using a specific reset endpoint.

### Creating an OAuth Client

The following example demonstrates how the internal admin API creates a new integration client with specific scopes.

```typescript
// Admin endpoint: POST /v1/oauth/clients
oauth.post('/clients', async (c) => {
  const db = getDb(c.var.db);
  const { name, scopes } = await c.req.json<{ name: string, scopes: string[] }>();
  
  const clientId = `client_${uuid().substring(0, 8)}`;
  const rawSecret = generateSecret(); // 32-char hex string
  const hashedSecret = await bcrypt.hash(rawSecret, 10);
  
  await db.run(
    `INSERT INTO oauth_clients (id, client_id, client_secret_hash, name, granted_scopes, created_at)
     VALUES (?, ?, ?, ?, ?, ?)`,
    [uuid(), clientId, hashedSecret, name, JSON.stringify(scopes), now()]
  );

  // Secret is returned ONLY here
  return c.json({
    client_id: clientId,
    client_secret: rawSecret,
    name,
    scopes
  }, 201);
});
```

## The client_credentials Grant Flow

External services use their credentials to exchange for a short-lived Access Token. The request must use `application/x-www-form-urlencoded` or `application/json`.

### Token Request Example (curl)

To request a token, the client sends its ID and Secret.

```bash
curl -X POST https://api.fufuni.store/v1/oauth/token \
  -H "Content-Type: application/json" \
  -d '{
    "grant_type": "client_credentials",
    "client_id": "client_abc123",
    "client_secret": "super-secret-hex-value",
    "scope": "read:products write:orders"
  }'
```

### Server-Side Implementation

The server validates the secret and ensures the requested scopes are a subset of the scopes originally granted to that client.

```typescript
async function handleClientCredentials(c: Context, body: any) {
  const { client_id, client_secret, scope } = body;
  const db = getDb(c.var.db);

  const [client] = await db.query<any>(
    "SELECT * FROM oauth_clients WHERE client_id = ?", 
    [client_id]
  );

  if (!client || !(await bcrypt.compare(client_secret, client.client_secret_hash))) {
    throw ApiError.unauthorized('Invalid credentials');
  }

  const grantedScopes = JSON.parse(client.granted_scopes);
  const requestedScopes = scope ? scope.split(' ') : grantedScopes;
  
  // Ensure requested scopes don't exceed granted permissions
  const finalScopes = requestedScopes.filter((s: string) => grantedScopes.includes(s));

  const token = await signJWT(
    {
      sub: client_id,
      scopes: finalScopes,
      iss: 'fufuni-internal',
    },
    c.env.OAUTH_JWT_SECRET
  );

  return c.json({
    access_token: token,
    token_type: 'Bearer',
    expires_in: 3600,
    scope: finalScopes.join(' ')
  });
}
```

## Token Structure and Signing

Fufuni uses **HS256** (HMAC with SHA-256) for signing OAuth tokens. This is faster than RS256 for internal verification and simplifies secret management via Wrangler secrets.

### Required Wrangler Secret
Every Fufuni environment must have the following secret set:
```bash
npx wrangler secret put OAUTH_JWT_SECRET
```

### JWT Claims (Payload)
The standard payload for an issued token includes:
- `sub`: The `client_id` of the integration.
- `scopes`: An array of strings representing authorized actions.
- `iat`: Issued at timestamp.
- `exp`: Expiration timestamp (default is `now() + 3600`).
- `iss`: The issuer identifier (usually the store domain or a static string like `fufuni-internal`).

```typescript
// Token verification logic in middleware
import { verify } from 'hono/jwt';

export const oauthMiddleware = async (c: Context, next: Next) => {
  const authHeader = c.req.header('Authorization');
  if (!authHeader?.startsWith('Bearer ')) return next();

  const token = authHeader.split(' ')[1];
  try {
    const payload = await verify(token, c.env.OAUTH_JWT_SECRET);
    c.set('jwtPayload', payload);
    c.set('isOAuth', true);
  } catch (e) {
    // Fallback or error based on route requirements
  }
  await next();
};
```

## Scope Authorization System

Scopes define the granularity of access allowed for a machine token. Unlike Auth0 user permissions which are mapped to roles, OAuth scopes are directly tied to the token itself.

### Available Scopes

| Scope | Description |
| :--- | :--- |
| `read:products` | List and view product details, variants, and stock. |
| `write:products` | Create, update, or delete products and inventory. |
| `read:orders` | View order history and status. |
| `write:orders` | Update order status or create manual orders. |
| `read:customers` | Access customer profiles and metadata. |
| `ucp:scopes:*` | Specialized scopes for Unified Commerce Platform compliance. |

### Enforcing Scopes in Handlers

Fufuni provides a utility to check if the current request's token possesses the required scope.

```typescript
import { ApiError } from '../types';

export function requireScope(required: string) {
  return async (c: Context, next: Next) => {
    const payload = c.get('jwtPayload');
    const scopes = (payload?.scopes as string[]) || [];
    
    if (!scopes.includes(required)) {
      throw ApiError.forbidden(`Missing required scope: ${required}`);
    }
    await next();
  };
}

// Usage in a router
const productRouter = new Hono<HonoEnv>();
productRouter.post('/', requireScope('write:products'), async (c) => {
  // Logic only executes if the OAuth token has write:products
});
```

## Token Revocation

Fufuni implements a revocation endpoint that allows clients to invalidate tokens before they naturally expire. Because the tokens are stateless JWTs, revocation works by deleting the record from the `oauth_tokens` table if a "refresh token" or "access token hash" tracking system is active. 

In the simplified machine-to-machine flow, revocation often targets the `client_id` itself (effectively banning the client) or uses a short TTL to minimize the window of risk for compromised tokens.

```typescript
oauth.post('/revoke', async (c) => {
  const { token } = await c.req.parseBody<{ token: string }>();
  const db = getDb(c.var.db);
  const tokenHash = await hashKey(token);
  
  // We remove the token from our audit/tracking table
  // Note: The JWT remains valid until 'exp' unless checked against a blacklist
  await db.run(
    "DELETE FROM oauth_tokens WHERE access_token_hash = ?",
    [tokenHash]
  );
  
  return c.json({ revoked: true });
});
```

### Integration with Customer Auth

Fufuni routes are often configured to accept multiple authentication methods. The `oauthMiddleware` and the `customerAuthMiddleware` (Auth0) can both populate the context. The business logic can then determine if the actor is a `Customer` or an `App`.

```typescript
app.get('/v1/me/orders', async (c) => {
  const isOAuth = c.get('isOAuth');
  
  if (isOAuth) {
    // Logic for an AI Agent checking orders for a client
    const clientId = c.get('jwtPayload').sub;
    return c.json(await getOrdersByClient(clientId));
  } else {
    // Logic for a logged-in human user via Auth0
    const user = c.get('user');
    return c.json(await getOrdersByCustomer(user.id));
  }
});
```
